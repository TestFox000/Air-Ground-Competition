## 3. ★ 新增保证：两半场同轮成对发出（t13 现场口径提醒）

**要求（队长 t16 追加）**：车侧 `bridge_info_wait_s = 2.0 s` 只覆盖「两半场情报**相隔 ≤2 s** 到达」；
超隔的那个半场只进遥测、**路线已冻结**。所以 supervisor 必须保证每轮 lower/upper 成对发出且间隔 ≤2 s。

**旧实现的问题**：两个半场是**两个独立槽**，各自按 `bridge_period_s` 节流。若两半场是分两次
从感知层进来的（相隔 Δ），它们的重发相位就错开 Δ：某一轮只发 lower、0.7 s 后才补 upper
（旧单测 `test_lower_and_upper_are_independent_slots` 正是这么断言的）。Δ 一大就逼近甚至超出 2 s 窗口。

**改法（`tick()`，共 3 行）**：

```python
fresh_bridge = [s for s, r in self.records.items()
                if r.etype == "bridge_passable" and r.age(now) <= self.cfg.info_ttl_s]
bridge_round_due = any(now >= self._next_intel.get(s, 0.0) for s in fresh_bridge)
...
if now < due and not (bridge_round_due and rec.etype == "bridge_passable"):
    continue
```

⇒ **任一新鲜桥洞半场到点，就把所有新鲜桥洞半场一起发**。附带好处：成对发出时两槽的
`_next_intel` 用同一个 `now` 推进，**相位自动对齐**，此后每轮都成对。
代价：每轮多发 1 条 ≤160 B 报文（相对 1 Hz 心跳 + 6 条/2 s 的桥洞重发可忽略）。
过期半场不受影响（仍走 `intel_stale`，**不会被"成对"复活**）。

## 4. 真机实测（★ 车侧接收时刻为准）

方法：无人机 `run` 发桥洞情报，小车侧只读消费者（`/tmp` 探针）逐条记录 `t_recv` 与 `half`，
统计相邻两条桥洞报文的间隔。`lower→upper` = 同一轮内成对间隔；`upper→lower` = 跨轮间隔。

| 相位 | 注入方式 | 车侧 lower→upper | 车侧相邻两条**最大**间隔 |
|---|---|---|---|
| P1 | `run --bridge lower=K10 --bridge upper=K5`（同时注入） | 中位 **0.016 s** / 最大 **0.023 s**（n=11） | **1.13 s** |
| P2 | `--cmd-file` 一次写入两行 | 中位 **0.016 s** / 最大 **0.022 s**（n=9） | **1.12 s** |
| **P3** | **两半场相隔 5 s 分两次注入**（模拟感知层分开报出） | 中位 **0.017 s** / 最大 **0.027 s**（n=10） | **1.13 s** |

三种场景都**远小于 2 s 窗口**。机侧 `intel_emit` 的 `ts` 交叉验证：同轮 lower/upper 相差 0.000–0.001 s
（同一 tick 内产生）。

**P3 车侧时间线（原文，证明"晚到的半场把先到的一起带出来"）**：

```
t=  0.000s  half=lower block=K10      ← 只有 lower 被注入（upper 还未知）
t=  0.226s  half=lower block=K10
t=  0.715s  half=lower block=K10
t=  2.179s  half=lower block=K10      ← 每 2 s 一轮，只有 lower
...（4 轮，共 12 条 lower）
t=  5.242s  half=lower block=K10      ← upper 注入的那一刻
t=  5.269s  half=upper block=K5       ← ★ 与 lower 相隔 0.027 s（老实现这里还是单发 upper）
t=  5.494s  half=upper block=K5
```

## 6. 边界与遗留（如实交代）

1. **成对保证已实测覆盖"两半场分两次到达"**，但**感知层一次样本同时给出两半场**仍是最省事的做法
   （少一次往返；`protocol.recommended_cadence()` 已注明）。
2. 「2 s 窗口」的**车侧消费语义**（先到的那半场是入库还是被丢弃、路线冻结后晚到的对能否触发换洞）
   属 t6/车侧，本任务只保证**线上成对**，未起车栈验证（车栈保持冷态）。
3. 实测窗口是**同一 AP（testfox）**下的；换 AP / 换交换机不改变"成对"结论（那是发送侧时序），
   但会改变端到端时延，建议赛前重跑一次 §4 的三相位（脚本一条命令）。
4. 未改任何行为逻辑的部分：`info_stale_s=30`、`car_state_period_s=0.7`、`heartbeat_offline_s=3`
   本来与车侧一致，未动。
5. `dz_send_waypoint.py` 的 `bridge` 子命令仍按"给一个 half 发一条"工作；成对保证在 supervisor
   侧实现（现场正式跑用 supervisor）。
