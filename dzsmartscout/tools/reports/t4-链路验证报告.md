### 2.2 ★ 域号结论（对任务书上"历史坑"的修正）

任务书写的坑是「车 `.bashrc` 曾 export `ROS_DOMAIN_ID=118` 而无人机为 0」。**今天实测：这个坑仍在，但方向要改一个字——两端默认域号都是 0，118 只活在两个 env 文件里。**

| 起法 | 无人机 | 小车 | 后果 |
|---|---|---|---|
| 交互式终端 / VNC 桌面 | **0**（`.bashrc` 压根没写域号） | **118**（`.bashrc:126`） | **两端不一致 → 静默互不可见** |
| `ssh host 'cmd'` / systemd / cron | **0** | **0**（`.bashrc` 第 6–9 行有非交互守卫 `*) return;;`，第 126 行根本执行不到） | 两端都为 0，也**不是** 118 |
| 显式 `. env 文件`（或跑 `dzlink_supervisor.py`，它 import 阶段自己读 `dzlink.env`） | **118** | 118（`start_all.sh:123` source `$WS/dzros.env`） | ✅ 一致，这是唯一可用组合 |

* 小车 `/home/duzhong/.bashrc` 实测关键行：
  ```bash
  6:  case $- in
  7:      *i*) ;;
  8:        *) return;;      ← 非交互 shell 到这里就 return，下面的域号声明被跳过
  9:  esac
  ...
  126: export ROS_DOMAIN_ID=118
  ```
* 小车 `start_all.sh:123`：`if [ -f "$WS/dzros.env" ]; then . "$WS/dzros.env"; fi`，**并且** `:161` 会在域号偏离标准值时打横幅告警 —— 这条自检是这套车唯一的兜底，值得保留。
* **对 t3/t4 的实际含义**：`dzlink_supervisor.py` 走 `bootstrap_domain()`，**不依赖外部环境变量**，机侧天然稳；车侧完全依赖 `start_all.sh` 这一条 `source`。**任何绕过 `start_all.sh` 的起栈方式（手工 `ros2 run`、systemd、ssh 一行命令）都会把车丢回域 0**，且零报错。给 t6/现场的口径：**域号只认 `~/dzrobot/dzros.env` 与 `~/dzlink_tools/dzlink.env` 两个文件；起节点前必须 source。**

### 2.3 DDS 发现端口结论

FastDDS 的端口规则是 `7400 + 250×域号`（participant 发现组播），单播端口 `7410 + 250×域号 (+2×participantId)`。**真机实测吻合**：

| 主机 | 域 118 的 UDP 绑定（实测 `ss -lunp`） | 域 0 的绑定（同机对照） |
|---|---|---|
| 无人机 | `0.0.0.0:36900`（`7400+250×118` ✓）、`36910/36911`（ros2 daemon）、`36912/36913`（探针节点） | `0.0.0.0:7400`、`7412`、`7413` |
| 小车 | `0.0.0.0:36900`（✓）、`36910/36911`、`36914/36915` | `0.0.0.0:7400`、`7412`、`7413` |

⇒ **在 7400 上嗅探永远看不到域 118 的对端**；现场用 `tcpdump udp port 7400` 判断"链路不通"是会误判的，要按 `7400+250×域号` 算端口。

**组播转发能力（定量，双向各测两次）**：

| 方向 | 第 1 次（20 包 @2.5Hz） | 第 2 次（30 包 @2.5Hz） | 结果 |
|---|---|---|---|
| 机 → 车 `225.0.0.1:49150` | 10/20 收到 | 11/30 收到 | **丢包 50%** |
| 车 → 机 `225.0.0.1:49150` | 9/20 收到 | 11/30 收到 | **丢包 55%~63%** |

原始 UDP 组播实测丢包 **50%~63%**（WiFi 组播按最低速率发、不重传的典型表现；小车侧 `iw` 信号 -57 dBm，非弱信号）。

**但这不影响 DDS 发现**：SPDP 是周期性重复宣告（FastDDS 启动时还有 initial announcements 突发），丢几个包不影响最终发现。实测 8 格矩阵的订阅端首次 `count_publishers>=1` 全部落在 **3.33–4.32 s**（订阅端进程启动起算；发布端进程在 3.5 s 才被拉起、自身还需约 1 s 启动），即**发现几乎与发布端端点出现同步完成**——本任务**未做严格的发现时延测量**，只作定性结论；逐格时间线见 [`qos_matrix_cells/`](t4-evidence/qos_matrix_cells/) 里各 cell JSON 的 `peer_count_timeline`。

**风险与建议**：AP 一旦换成"禁组播/客户端隔离"更严的，发现会直接停摆（症状：ping/SSH 全通、ROS 互不可见、零报错）。仓库里已有 [`tools/link/fastdds-unicast-wifi.xml`](../link/fastdds-unicast-wifi.xml) 单播兜底，**赛前应在赛场 AP 上再跑一次本文 §9 的 S1/S2**，通过即可放心用默认组播。

## 4. ③ ★ QoS 反向组合变异测试

历史团队的教训是「RELIABLE/BEST_EFFORT 不匹配 = 静默失败且不报错」。本节把它变成一张可复核的真机矩阵。

**方法**：自研探针 [`t4_qos_probe.py`](../link/probe/t4_qos_probe.py)，在 `std_msgs/String` 上以指定 QoS 发 40 条 / 收，同时记录「实收条数」与「DDS 图上看到的对端端点数」；两个方向各跑 4 格，共 8 格，逐格有独立 JSON（[`qos_matrix_cells/`](t4-evidence/qos_matrix_cells/)、汇总 [`qos_matrix.json`](t4-evidence/qos_matrix.json)）。

### 4.1 8 格矩阵（真机实测）

| 方向 | 发布端 QoS | 订阅端 QoS | 发出 | **收到** | 发布端看到的订阅者数 | 订阅端看到的发布者数 | 判定 |
|---|---|---|---|---|---|---|---|
| 机→车 | RELIABLE | RELIABLE | 40 | **39** | 1 | 1 | ✅ 兼容 |
| 机→车 | RELIABLE | BEST_EFFORT | 40 | **39** | 1 | 1 | ✅ 兼容（降级到 BE） |
| 机→车 | BEST_EFFORT | RELIABLE | 40 | **0** | **1** | **1** | ❌ **不兼容：静默收不到** |
| 机→车 | BEST_EFFORT | BEST_EFFORT | 40 | **40** | 1 | 1 | ✅ 兼容 |
| 车→机 | RELIABLE | RELIABLE | 40 | **40** | 1 | 1 | ✅ 兼容 |
| 车→机 | RELIABLE | BEST_EFFORT | 40 | **39** | 1 | 1 | ✅ 兼容 |
| 车→机 | BEST_EFFORT | RELIABLE | 40 | **0** | **1** | **1** | ❌ **不兼容：静默收不到** |
| 车→机 | BEST_EFFORT | BEST_EFFORT | 40 | **39** | 1 | 1 | ✅ 兼容 |

**完全符合 DDS 兼容性规范**（offered RELIABLE 可服务 requested BEST_EFFORT，反之不成立），双向对称。

### 4.2 两个反直觉的关键点（现场最容易误判的地方）

1. **"匹配数=1" 不等于"能收到"。** 两个不兼容格里，发布端与订阅端**都**看到对端端点各 1 个（`count_subscribers`/`count_publishers` 是**发现层**计数，不反映 QoS 匹配），但实收 **0 条**。⇒ 现场**不能**用 `ros2 topic info` 的 count 或"发出去没报错"判断链路通；必须看**实收**。
2. **失败其实会打一行 WARN，但只在订阅端日志里**。小车侧用 RELIABLE 订阅 BEST_EFFORT 发布者时，rclpy 打了：
   ```
   [WARN] [t4_car_consumer]: New publisher discovered on topic '/dzlink/drone_to_car',
   offering incompatible QoS. No messages will be received from it.
   Last incompatible policy: RELIABILITY
   ```
   证据 [`s4_car_neg_consumer.txt`](t4-evidence/s4_car_neg_consumer.txt)。**精准表述**：QoS 不兼容不是"完全没有日志"，而是"**没有任何话题级/工具级报错，只有订阅端进程自己一行 WARN**"——现场把节点输出重定向到文件后就基本看不见了。而车侧契约里 `/dzlink/drone_to_car` 就是 BEST_EFFORT（见下），**一旦有人把订阅端改成 RELIABLE，就是这条路径**。

### 4.3 契约档位在真机上的实测（不是读源码的推断）

用 [`t4_qos_info.py`](../link/probe/t4_qos_info.py) 抓**对端端点携带的 QoSProfile 原文**：

| 话题 | 车侧源码契约（部署版 `~/dzrobot`，逐行核实） | 真机抓到的对端 QoS | 证据 |
|---|---|---|---|
| `/nav/waypoint` | `contract.py:73` `QOS_EVENT` = `KEEP_LAST(10)/RELIABLE/VOLATILE`，direction `"sub"` | 机侧 supervisor 发布（RELIABLE），车侧探针收到 3/3 条 | [`s5_car_route_consumer.txt`](t4-evidence/s5_car_route_consumer.txt) |
| `/dzlink/drone_to_car` | `contract.py:94` `QOS_LINK` = `KEEP_LAST(10)/BEST_EFFORT/VOLATILE`，`"sub"` | 车端看到机侧 publisher = **BEST_EFFORT / VOLATILE** | [`s2_car_sees_drone_publisher_qos.json`](t4-evidence/s2_car_sees_drone_publisher_qos.json) |
| `/dzlink/car_to_drone` | `contract.py:96` `QOS_LINK` = BEST_EFFORT，`"pub"` | 机端看到车侧 publisher = **BEST_EFFORT / VOLATILE** | [`s6_drone_sees_car_publisher_qos.json`](t4-evidence/s6_drone_sees_car_publisher_qos.json) |

`QOS_LINK` 的源码注释原文：`QOS_LINK = QosSpec(depth=10, reliability="best_effort")     # 无人机链路允许丢旧帧`（`contract.py:41`）。

**⇒ t3 的 supervisor 把三条话题的 QoS 写死为 `RELIABLE / BEST_EFFORT / BEST_EFFORT` 是正确且必要的**，与部署版车侧逐字一致。

### 4.4 一个必须知道的副作用：VOLATILE 无补发，首包会丢

矩阵里 8 格中有 7 格是 39/40 或 40/40 —— 少的那一条**恒为第 0 条**（订阅端样本从 `#1` 开始，见各 cell JSON 的 `samples`）。原因：`Durability = VOLATILE`（车侧契约如此），发布端在匹配完成前发出的第一条不会补给后加入的订阅者。

**现场口径**：**任何情报都必须重复发**。t3 的 supervisor 已经这么做（每条 `x3` 遍 + bridge 每 2 s 重发），这个设计是对的，不要为了"省流量"去掉。

### D3 🟠 车侧桥洞状态**只有一个槽位**，`bridge_of("lower")` 会被 `upper` 永久顶掉

车侧部署版源码（逐行核实）：

```python
# ~/dzrobot/src/dzbrain/dzbrain/core/state.py:104-121
class DroneState:
    bridge_half: str | None = None      # "lower" | "upper"
    bridge_block: str | None = None     # 例 "K9"
    def bridge_of(self, half, *, now, stale_s) -> str | None:
        if self.bridge_half != half or self.bridge_block is None:
            return None                 # ← 半场对不上就 None
        if now - self.bridge_ts > stale_s:
            return None
        return self.bridge_block

# ~/dzrobot/src/dzbrain/dzbrain/tasks/drone.py:283
self.bridge_half, self.bridge_block = half, block     # ← 覆盖式赋值，单槽
```

## 10. 局限与未验证项（如实交代）

1. **没有与真实 dzbrain 端到端跑过**（车栈按任务要求保持冷态）。车侧行为的证据来自 ① **部署版源码逐行核实**（`~/dzrobot/src/dzbrain/...`，与本地 `dzrobot_v2` 副本可能不同，本报告一律以车上那份为准），② **按该源码逐字复刻的 `/tmp` 探针**。**"dzbrain 本人能做到"仍需起栈后补一次 L3 验证。**
2. **D3 的后果**（`bridge_of("lower")` 恒 None）是从源码推出的**静态结论**，没有起栈实测（起栈就违反本任务的冷态约束）。建议 t6 完成后专门验一条：只发 lower → 车侧遥测是否显示 lower。
3. `/nav/waypoint` 的**消费者是车侧旧核还是 dzbrain**未在本任务核实（车栈冷态无法看 `ros2 topic info` 的订阅者）；只用探针证明了**线上报文与 QoS 档位可行**。
4. 组播丢包数字是**原始 UDP** 的观测，不等于 DDS 发现的实际成功率；本报告给出的是"发现成功 + 数据 39~40/40"的间接证据，未做丢包→发现时延的定量建模。
5. 我只在**一个 AP（`testfox`）**上测过；换 AP 必须重跑 §9 的 S1/S2/R1（任务书也要求"发现端口结论"以实测为准）。
6. 双写者实验里第二个写者是我方探针（`t4_qos_pub`），**没有**真的去跑车上的 `send_waypoint.py`（避免在车上留下任何长效副作用）。
