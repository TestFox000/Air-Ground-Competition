## 1. 格级定位精度（可核对的预算）

**标定链（官方图纸，全自动）**：外框内边 → `frame_inner=[7,10,647,512]`；灰格线最小二乘精修 →
`sx=45.5857 px`、`sy=45.5073 px`；四角点解析拟合残差 **0.000 px**；`self_check=True`（154 格全覆盖）。

| 误差来源 | 量级（px） | 折算到场地（1 px ≈ **7.69 mm**，0.35 m / 45.51 px） |
|---|---|---|
| 角点解析拟合残差 | < 0.01 | **< 0.1 mm** |
| 格线最小二乘（亚像素） | ~0.2 | ~1.5 mm |
| 色块质心（面积加权） | ~0.3 | ~2.3 mm |
| **合计（保守）** | ~0.5 | **≈ 4 mm** |

**格分配余量（最关键的一条）**：格心到边界 = 半格 = 22.8 px ≈ **17.5 cm**。
⇒ 上表的毫米级误差要放大 **~4000 倍**才可能串格；工程上真正的风险不是"算不准"，
而是**整张图裁切/视角变化导致标定失效**（那是"该重标"而不是"精度不够"）。

**端到端自检（不是自证）**：官方图 20 个满格色块的 **in-cell 覆盖 0.80~0.91**，
而它们的 **4-邻格覆盖 0.000**（t39 证据）⇒ 色块不跨界、格心不偏；
本卡 `field_map_check` 再把四类点位与真源逐条对齐（0 差异）。

## 2. 置信度阈值建议

`perception.field_map.confidence_thresholds()` 给出建议值（可直接 `accept={...}` 覆盖）：

| 类 | 官方图实测区间 | 建议阈值 | 理由 |
|---|---|---|---|
| `mine`（12 cm 圆片） | 0.80~0.84 | **0.55** | 圆片面积小、受格线切割影响大 ⇒ 留足余量 |
| `obstacle`（30 cm 桶） | 0.66~0.69 | **0.60** | 实测下沿 0.66；0.60 只吃掉 9%，却挡掉"半个格子"的误检 |
| `target`（靶区色块） | 0.66~0.67 | **0.55** | 跨格板会切掉一部分面积 |
| `bridge`（桥顶通行格） | 0.74~0.75 | **0.55** | 与 `bridge_arrow` 的方向置信度互补使用 |
| `car` / `arrow` / `label_box` | —（合成/实拍） | 0.45 / 0.45 / 0.50 | 车顶板小（0.22×0.10 m）；箭头要的是方向不是面积 |

**用法与纪律**
1. **默认阈值下"空结果"是可信结论**（没有就是没有）；被刷掉的会进 `rejected`（带理由），不会静默丢。
2. 想更保守：`build_field_map(..., accept={"mine": 0.7})`；**不要**低于 0.5 —— t2 的拒收样本集中在 0.30 以下
   （黄标注框、格线碎片），0.5 以下会开始收进噪声。
3. **置信度是"颜色覆盖率"折算的相对量，不是概率**：不要拿它做贝叶斯融合；跨图比较只在同一调色板内有效。
4. 任何"跳过不确定格"的上层策略，都应读 `perception.cell_confidence`（本卡新增，逐格）而不是只看类别列表。

## 3. 蓝面朝向：判得了吗？（含移动靶 0.12 m/s 的量化）

### 3.1 结论：**无人机俯视判不了，车端云台才是正确传感器**

靶的蓝/红面是**竖直面**，无人机是**俯视**——看到的是靶的**顶面**。
真图实测（官方图 + 旧图纸两张）：`estimate_blue_face()` 都返回 `unknown`，
证据里写明 `蓝/红面像素都太少（俯视看不到竖直面）`，**蓝 0.0000 / 红 0.0000**。
这是**正确行为**：看不出来就说看不出来，绝不猜。

### 3.2 移动靶 0.12 m/s 的帧率/拖影影响（量化）

| 量 | 值 | 说明 |
|---|---|---|
| 帧间位移 | `0.12 m/s ÷ 30 fps` = **4.0 mm/帧** | 与视角无关 |
| 换算到像素 | 2 mm/px ⇒ **2.0 px/帧**；7.7 mm/px（图纸尺度）⇒ 0.52 px/帧 | `field_map.motion_budget()` |
| 对"颜色可分性"的影响 | **可忽略** | 靶面在画面里 ≥20 px 宽时，2 px 拖影只让边缘糊 10%，色相中心不变 |
| 对"朝向判定"的影响 | **不是瓶颈** | 判定靠"哪一面在视野里"，与运动无关 |
| 需要的观察窗口 | ≥ 0.5 s（≥15 帧）取多数票 | 单帧误判可由时序投票消掉 |

**⇒ 拖影不是问题，视角才是问题。** 若真要用机载相机判朝向，需要**斜视**（俯角明显小于 90°）
或绕行侧望，并且蓝/红面各需一小块可见面积（建议 ≥ 15×15 px）。

### 3.3 已实现的判据 + 我实测踩到的假阳性（重要）

`estimate_blue_face()` 判据：`蓝占比 ≥ 0.02` 且 `蓝 ≥ 2×红` ⇒ `toward_us`（反之 `away`，都不够 ⇒ `unknown`）。

**踩坑**：场地**外框是深蓝的**（官方图 `(48,80,144)` ⇒ H≈220°、S≈0.67、V≈0.57）——**正好落在"蓝面"色带里**！
旧图纸的靶格 B11/C11 紧贴外框，我最初的 ROI 外扩 15% ⇒ 吃到外框 ⇒ 误报 `toward_us`（蓝占比 0.1056）。
**两条守卫已落地**：① ROI **默认不外扩**（`margin_frac=0`）；② 蓝/红块**质心必须落在 ROI 中央 80%**，
贴边的"蓝条"（=外框）一律不算。回归测试：`test_blue_face_guard_rejects_arena_frame_color`。

### 3.4 给车侧的建议（不在本卡改动范围）

1. **朝向判定留在车端云台**（已在用 `cls==1` 门控）——那是对的传感器；
2. 若要把"朝向"作为**先验**下发给车侧：用**时序多数票**（≥15 帧一致）再发布，单帧不许发；
3. 蓝/红色相阈值**必须现场标定**（`BLUE_FACE_HSV`/`RED_FACE_HSV` 现在是占位默认值），
   标定方法同 `docs/感知可行性_摄像头评估.md` 的标定流程。

## 5. 能力边界与风险（一览）

| 做什么 | 能不能 | 依赖条件 / 风险 |
|---|---|---|
| 图纸/截图 → 雷/障/靶/桥逐格出图 | ✅ 0 差异 | 需**规则图纸**（有外框+格线）才能自动标定；实拍照片要手点或外部标定 |
| 实拍航拍帧 → 同上 | ⚠️ 待相机 | t2 退化实验：≥32 px/m 可跑；**模糊 ≥3 px 丢雷/箭头/车，≥4 px 丢桶，≥8 px 丢靶**；噪声 σ≤20/255 可，σ≥30 让桶退化 |
| 车位姿（格 + yaw） | ✅ | 车顶板 ≥ 0.22×0.10 m 且与场地色差明显；丢帧时**宁可不报** |
| 桥顶箭头方向 | ✅ −96°（真值 −90°，误差 6°） | 点抖动 σ ≥ 箭头长度 10% 时**方向可能翻转**（置信度仍 >0.9）⇒ 默认输出"位置"而非"方向" |
| 蓝面朝向 | ❌ 俯视 | 见 §3 |
| 起终点**语义** | ⚠️ 半自动 | 标注框能定位；框内印字未 OCR（需要时用 4 个框的**相对排布**做语义消歧是个已知可行的下一步） |
| 单帧确定性 | ✅ | 全管线无随机（85 项测试全绿，含 12 张合成图 + 2 张真图回归） |
