## 0. 最重要的发现（先看这三条）

### 🔴 发现一：定位链路整体是死的，`/localization` 从来没有被发布过

`FAST_LIO_LOCALIZATION_ROS2` 启动 4 个节点，其中 **3 个在 import 阶段就崩溃**：

```
$ ros2 launch fast_lio_localization velodyne_localization.launch.py
[INFO] [fastlio_mapping-1]:       process started with pid [7669]     ← 活
[INFO] [global_localization.py-2]:process started with pid [7671]
[INFO] [transform_fusion.py-3]:   process started with pid [7673]
[INFO] [global_map_publisher.py-4]:process started with pid [7675]
[ERROR][global_map_publisher.py-4]: process has died [exit code 1]    ← 1.4 s 后死
[ERROR][global_localization.py-2]:  process has died [exit code 1]    ← 死
[ERROR][transform_fusion.py-3]:     process has died [exit code 1]    ← 死
```
（铁证：`~/.ros/log/2026-09-26-15-50-55-215402-ubuntu-7668/launch.log`）

**根因**（已逐条 import 实测）：

| 缺失的模块 | 谁需要它 | 实测结果 |
|---|---|---|
| `open3d` | `global_map_publisher.py:4`、`global_localization.py:7` | `ModuleNotFoundError`（dpkg 无包、dist-packages 无目录、`~/.local` 无） |
| `tf_transformations` | `global_localization.py:11`、`publish_initial_pose.py:5`、`transform_fusion.py:13` | `ModuleNotFoundError`；**兜底路径也失效**：`from tf2_ros import transformations` → `ImportError` |

**为什么这条最重要**：

- `1.txt` 运行手册第 ② 步起的定位链路，**产出是不存在的**。
- `transform_fusion.py` 正是 `/localization` 的发布者 —— 它死了，`/localization` 就不存在。
- `1.txt` 第 ④ 步 `px4_odom_convert`（默认 `mode=localization`）订阅 `/localization` —— **收不到任何输入，就一条都不会往 PX4 发**。
- 结论：**这台机器上，PX4 从来没有通过这条路径拿到过外部视觉**。所有依赖"位置环"的 Offboard 动作（悬停、Goto、路径跟随）在真实飞行中都失去了位置反馈来源。

> **今天的可用替代**：`fastlio_mapping`（C++ 节点）是活的，它自己发布 `/Odometry`（`laserMapping.cpp:1109,1148`，约 50 Hz）。把 `px4_odom_convert` 改成 `mode:=odom` 就能立刻打通外部视觉 —— 代价是没有地图修正、没有重定位。详见 §9 建议 ①。

### 🔴 发现二：飞控侧参数完全不在机载电脑上

全盘搜索 `EKF2_EV|EKF2_GPS|COM_OBL|EKF2_HGT_MODE|MAV_1_CONFIG`：**零命中**；`~/.ros` 里也没有参数记录。

`EKF2_EV_CTRL`（融合哪几路外部视觉）、`EKF2_EV_DELAY`、`EKF2_EV_POS_X/Y/Z`（雷达杆臂）、`EKF2_HGT_MODE`、`COM_DISARM_LAND`、`COM_OBL_RC_ACT`、`COM_OF_LOSS_T`、`MPC_XY_VEL_MAX`…… 这些决定"能不能飞、飞丢时怎么办"，**一个字节都不在这台电脑上**。飞控板当前也没接（无 `/dev/ttyACM*`，`lsusb` 里没有任何飞控设备）。

### 🔴 发现三：`px4_path` 有一处"录了新路径却飞旧路径"的契约断裂

`px4_path/config/params.yaml:25` 跟随读 `recorded_path_2.txt`，`:119` 录制写 `recorded_path.txt`，而 `README.md:103-106` 明确要求两者相等；再加上 `overwrite_existing: false` 会让每次录制自动改名 `_1/_2/_3…`。**录制完新路径，跟随节点读到的仍是旧文件** —— 而且路径只在节点构造时读一次，按 `4` 并不会重新加载。

## 1. 系统全景与代码清单

### 1.1 "飞控代码"在这里指什么

机载电脑上**没有 PX4 固件**。飞控板（Pixhawk 类）通过 USB 串口接 `MicroXRCEAgent`（uXRCE-DDS），把 PX4 的 uORB 话题映射成 ROS 2 的 `/fmu/in/*` 与 `/fmu/out/*`。机载电脑上跑的是 PX4 的"外脑"：**定位 + 坐标桥 + Offboard 控制 + 路径规划**，共 5 个进程。

## 2. 启动时序（以 `~/dzpx4/1.txt` 为准）

```bash
① ros2 launch livox_ros_driver2 msg_MID360_launch.py          # 雷达: CustomMsg 10Hz + Imu 200Hz
② ros2 launch fast_lio_localization velodyne_localization.launch.py   # ⚠ 见发现一，实际只有 fastlio_mapping 活着
③ MicroXRCEAgent serial --dev /dev/ttyACM0 -b 921600          # PX4 ↔ ROS2 桥（需飞控已连接）
④ ros2 launch px4_odom_convert px4_odom_convert.launch.py      # ⚠ 默认订阅 /localization（不存在）
⑤ ros2 launch px4_imu_bridge sensor_combined_to_imu.launch.py  # PX4 的 IMU → ROS
⑥ ros2 launch px4_control px4_control.launch.py                # Offboard 控制节点
⑦ ros2 run px4_control px4_teleop_node --params-file .../params.yaml   # 键盘（必须在真实 TTY）
⑧ ros2 launch px4_path px4_path.launch.py                      # 录制或跟随（由 YAML 决定）
```

**顺序上的硬约束**（从代码推出，非猜测）：

- ③ 必须早于 ④⑤⑥：没有 `MicroXRCEAgent` 就没有 `/fmu/*`，`px4_control_node` 永远卡在"心跳不足/不在 Offboard"的拒绝分支。
- ② 必须早于 ④：`px4_odom_convert` 收满 20 帧定位才开始发（`px4_odom_convert.cpp:68-91`）。
- ⑥ 必须早于按 `0` 至少 `heartbeat_before_offboard` 个周期（20 Hz 下 1 s），否则 `handle_offboard()` 直接拒绝（`px4_control_node.cpp:336-342`）。
- ⑧ 的 `record_mode` 在 **YAML 里**、不是 launch 参数，且**不支持飞行中切换**（`px4_path.launch.py:11-38` 在启动时读 YAML 决定实例化哪个可执行文件）。

## 4. 逐包详解

### 4.1 `px4_control` —— Offboard 控制入口（839 行，质量最高的一段代码）

| 可执行 | 源码 | 职责 |
|---|---|---|
| `px4_control_node` | `src/px4_control_node.cpp`（662 行） | 状态机 + Offboard 心跳 + 设定值 + Goto 门控 |
| `px4_teleop_node` | `src/px4_teleop_node.cpp`（177 行） | 读终端键盘 → 只发 `/px4_control/command` |

**接口表**

| 方向 | 话题 | 类型 | QoS |
|---|---|---|---|
| sub | `/fmu/out/vehicle_local_position` | `px4_msgs/VehicleLocalPosition` | best_effort, depth 5 |
| sub | `/fmu/out/vehicle_status` | `px4_msgs/VehicleStatus` | best_effort, depth 5 |
| sub | `/px4_control/command` | `px4_control/ControlCommand` | 默认 reliable, depth 10 |
| sub | `/px4_control/goto` | `px4_control/GotoTarget` | 默认 reliable, depth 10 |
| pub | `/fmu/in/offboard_control_mode` | `px4_msgs/OffboardControlMode` | 默认 |
| pub | `/fmu/in/trajectory_setpoint` | `px4_msgs/TrajectorySetpoint` | 默认 |
| pub | `/fmu/in/vehicle_command` | `px4_msgs/VehicleCommand` | 默认 |
| pub | `/px4_control/goto_enabled` | `std_msgs/Bool` | **reliable + transient_local（锁存）** |

**状态机**（`px4_control_node.hpp:21-28`）

```text
DISARMED ──按0(Offboard)+按1(ARM)──► ARMING ──PX4报 ARMED──► TAKEOFF
   ▲                                                          │ |z-目标z|<arrive_tol
   │                                                          ▼
   │◄── 离开 Offboard(RC接管/failsafe) ───────────────────── HOVER
   │                                                       │  ▲
   │                                            按3 LAND   │  │ 按5 / GotoTarget(active=false)
   │                                                       ▼  │
   └──────── PX4 报 arming_state=STANDBY ─────────── LANDING ──┘
                                                          │
                                                          ▼
                                                       LANDED
```

**三个刻意的设计细节（都是踩过坑才会写出来的）**

1. **起飞前把目标死贴当前位姿**：`on_local_position()` 在 `DISARMED/LANDED` 下 `target_ = current_`（`:193-197`），注释："whenever Offboard becomes active the drone will hold, not jump"。
2. **未用分量填 NaN 而不是 0**：`:505-543`，注释："PX4 v1.14+ expects unused setpoint components filled with NaN. A zero in velocity/acceleration/jerk is treated as a feed-forward, which fights the position controller and causes overshoot / bounce on takeoff"。
3. **落地完成只认 PX4 的解锁状态**：`:214-228`，且明确放在"离开 Offboard"处理**之前**，因为 PX4 可能同时退出 Offboard 并上锁。

**Goto 门控（人机权限交接）** —— 全系统最微妙的一段：

- `goto_enabled` 默认 `false`；只有 `state==HOVER && local_pos_valid` 时按 `4` 才能打开（`:468-474`）。
- 打开后 `WASDQE`/`L/R` 全被忽略（`:437-440, 454-457`）—— 防止人机抢方向盘。
- `active=true` 必须 11 个字段全部有限，否则**关 Goto 并悬停**（`:300-311`）。
- 按 `5` 或收到 `active=false`：关 Goto、清前馈、把当前位置固化为悬停点（`:152-171`）。注意 `active=false` **不检查许可状态，无条件生效**（`:288-291`）。
- 1 s 没收到新目标自动关 Goto（`:579-586`）。

### 4.2 `px4_odom_convert` —— 定位进 PX4 的最后一公里（287 行）

三种模式（launch 默认 `localization`，正是**没有输入**的那个）：

| 模式 | 输入 | 状态 |
|---|---|---|
| `odom` | `/Odometry` | ✅ 输入存在（`fastlio_mapping` 在发） |
| `localization` ← **手册用的** | `/localization` | ❌ 输入不存在（见发现一） |
| `tf` | TF `map → lidar`，50 Hz 轮询 | ❌ `map→camera_init→body`，没有 `lidar` 帧 |

输出 `/fmu/in/vehicle_visual_odometry`（`SensorDataQoS`），**只填位置和姿态**，速度/角速度/速度方差全 `NaN`，`velocity_frame = UNKNOWN`（`:118-119, 165-195`）。收满 20 帧才开闸（`:68-91`）。

### 4.3 `px4_imu_bridge` —— 把 PX4 的 IMU 借给 ROS（148 行）

- `/fmu/out/sensor_combined` → `/fmu/out/imu_data`（`sensor_msgs/Imu`），`SensorDataQoS`，200 Hz。
- FRD→FLU：x 不变，y/z 取反（`:42-60`）；用 `orientation_covariance[0] = -1` 正确标记"不提供姿态"（`:118`）。
- 自带转换耗时统计（每 1 s 打印 latest/avg/max，`:62-93`）。
- ⚠️ **时间戳问题见 R08**。

### 4.4 `px4_path` —— 录制与跟随（~2100 行）

> 逐文件解析见 **`notes/px4_path.md`（603 行，13 章）**。以下是主干。

**编译真相**：7 个 `.cpp` **全部参与编译**，没有未编译的死源码。

| 产物 | 编译的源文件 |
|---|---|
| `path_record_node` | `path_record_node.cpp` + `path_record_process.cpp` |
| `path_follow_node` | `path_follow.cpp` + `path_follow_waypoint_node.cpp` + `path_follow_trajectory_node.cpp` |
| `px4_path_core`（静态库） | `motion_trajectory.cpp` + `path_loader.cpp`，仅被 `path_follow_node` 链接 |

**话题**：`path_record_node` 订 `/localization`（❗同样受发现一影响）、发 `/path_record/visualization`（RViz 用，无定时器）；`path_follow_node` 订 `/fmu/out/vehicle_local_position` 与 `/px4_control/goto_enabled`（锁存），发 `/px4_control/goto`（20 Hz）。两侧 QoS 与 `px4_control` **严格配对** ✅。

**状态机**：

```text
录制：构造即开录 → 关键点抽取 → 【Ctrl-C 析构时】补末点+平滑+压缩 → .tmp + rename 原子落盘
跟随：INIT → LOADED（路径已读 + 定位有效）→ 按 '4' 才可能 PURSUING
      按 '5' → PAUSED（冻结进度）；再按 '4' 原地续跑
      末段到点 → HOLD（持续重发终点）
      内部致命错误 → 发 active=false → px4_control 关许可悬停 → 退回 LOADED
      ※ 路径只在构造函数读一次，没有重载入口
```

**算法（`motion_trajectory.cpp`，527 行）**：累积弦长参数化的**自然三次样条**（x/y/z + 解缠 yaw，C² 连续）→ 均匀弧长采样算曲率限速 `v ≤ √(a_lat/κ)` → 前向/后向两遍加速度可达性约束 → 夹紧三次 `s(t)`（首末速度强制 0）→ 按实测 v/a/jerk/向心四项比例整体拉伸时间（×1.001 安全系数）。**jerk 只用于校验，不发给 PX4**（PX4 的 `TrajectorySetpoint.jerk` 被 `px4_control` 固定填 NaN）。

**关键性质：跟随没有本地位姿闭环**。它只输出 (p, v, a, yaw, yawspeed) 参考 + 一个**标量**参考时钟缩放（误差 ≥ `tracking_pause_error_m` 冻结、之间线性降速），位置环完全由 PX4 承担；**没有任何横向纠偏项**。重定时用 `a·k² + v·k̇` 的二次不等式把加速度夹回限值内 —— 这是整个包技术含量最高、也最正确的一段。

### 4.5 定位：`FAST_LIO_LOCALIZATION_ROS2`

> 详见 **`notes/fastlio.md`（300 行）**。核心事实：

- **实际生效的配置是 `mid360_test.yaml`**（`velodyne_localization.launch.py:33` 默认值），手册选择正确：`lidar_type:1` 走 `CustomMsg` 分支，匹配 MID-360 的 `/livox/lidar`；`extrinsic_T:[-0.011,-0.02329,0.04412]` 与 MID-360 内置 IMU 的出厂标定吻合。
  ⚠️ 只有 `mid360_test.yaml` 含重定位三段配置；换成 `mid360.yaml` 会让 `map_file_path` 落回上游作者的 `/home/myungw00/...highway2.pcd`（**不存在**），重定位链路静默死亡。

## 5. 坐标系：最容易出错的地方（已做数值验证）

### 5.1 PX4 与 ROS 的约定

| 概念 | PX4 | ROS |
|---|---|---|
| 世界系 | NED（北-东-地） | ENU（东-北-天） |
| 机体系 | FRD（前-右-下） | FLU（前-左-上，即 base_link） |
| 四元数 | 机体系 → NED | 机体系 → ENU |

`px4_ros_com/frame_transforms.h`：`NED_ENU_Q = quaternion_from_euler(π, 0, π/2)`（`:173`）、`AIRCRAFT_BASELINK_Q = quaternion_from_euler(π, 0, 0)`（`:180`）。实现是**单侧乘**而非共轭（`frame_transforms.cpp:157-198`）：

```cpp
case ENU_TO_NED:           out = NED_ENU_Q * q;              // 世界系左乘
case AIRCRAFT_TO_BASELINK: out = q * AIRCRAFT_BASELINK_Q;    // 机体系右乘
enu_to_ned_local_frame(v)  → 反射实现 = (v.y, v.x, -v.z)
```

### 5.2 `px4_odom_convert` 的合成链路

```cpp
R_enu_slam_ = diag(-1, -1, 1);  t_enu_slam_ = (0,0,0);   // px4_odom_convert.cpp:20-28，写死
p_slam = (x, y, z - z_offset_m);
p_enu  = R_enu_slam * p_slam;
p_ned  = enu_to_ned_local_frame(p_enu);            // = (p_enu.y, p_enu.x, -p_enu.z)
R_enu_body = R_enu_slam * R_slam_body;
q_px4 = ros_to_px4_orientation(q_enu);
```

### 5.3 数值验证结论（`verify_frames.py`，2000 组随机位姿）

| 检查项 | 结果 |
|---|---|
| 反射实现 vs 四元数实现是否同一个旋转 | **一致**（矩阵逐元素相同，det 均为 +1） |
| 位置链路自洽性 | **是**，最大误差 `1.07e-14` |
| 姿态链路自洽性 | **是**，最大误差 `1.25e-15` |
| 位置与姿态是否用**同一个**旋转 | **是** |

**`R_total = R_NED_ENU · diag(-1,-1,1)` 的实际含义：**

| SLAM 轴 | 映射到 NED | 说明 |
|---|---|---|
| `+x_slam` | `(0, -1, 0)` | 西 |
| `+y_slam` | `(-1, 0, 0)` | 南 |
| `+z_slam` | `(0, 0, -1)` | 向上 ✅ |

**关键推论**：`diag(-1,-1,1)` 是**绕垂直轴的纯偏航旋转**，且位置与姿态共用同一个变换。因此：

- 这个常数取什么值**只影响"哪边算北"，不影响控制自洽性** —— `px4_control` 的目标、`px4_path` 的路径、PX4 的反馈都在同一个变换后的 NED 系里。
- **前提是该矩阵必须保持"绕垂直轴的纯旋转"**。若有人往里面塞横滚/俯仰分量，位置系与姿态系就会分家：

| `R_enu_slam` 混入的横滚 | 每 1 m 水平位移被错算成的高度变化 |
|---:|---:|
| 0.5° | 0.87 cm |
| 1.0° | 1.75 cm |
| 2.0° | 3.49 cm |
| 5.0° | 8.72 cm |

即 1° 失配在 20 m 航线上污染约 35 cm 高度通道，且是**与水平位置成比例的系统误差**，EKF2 无法自行辨识掉。

**还有一个前提没被任何代码校验**：SLAM 世界系的 z 轴必须竖直向上。而 FAST-LIO **并不把世界系对齐到重力**——`IMU_Processing.hpp:198` 把重力估成一个**状态向量**，`:200` 那行把初始姿态设为单位阵的代码是**注释掉的**（且即使启用也是单位阵）。也就是说：**世界系 = 开机瞬间的 IMU 姿态**。开机时飞机不水平，整条链路的"上"就不是真的上，EV 姿态会与 IMU 的重力方向打架。见 R07。

### 5.4 `px4_path` 的 loader 与 `px4_odom_convert` 是否一致？—— **逐项核对，完全一致** ✅

| 项 | `px4_odom_convert` | `px4_path/path_loader.cpp` | 判定 |
|---|---|---|---|
| SLAM→ENU 位置 | `diag(-1,-1,1)`, `t=0` | `(-x,-y,z)`（`:30-32`） | 一致 |
| ENU→NED 位置 | `enu_to_ned_local_frame` | `(y,x,-z)`（`:34`） | 一致 |
| yaw 提取式 | `atan2(2(q0q3+q1q2), 1-2(q2²+q3²))` | 同一式子（`:119-120`） | 逐字一致 |
| ENU→NED yaw | `NED_ENU_Q * q`（左乘） | `π/2 − yaw_enu`（`:122`） | 一致（左乘参考系变换对纯偏航即此式） |
| FLU↔FRD | `q * AIRCRAFT_BASELINK_Q`（右乘 180° 滚转） | 只取 yaw，不涉及 | 右乘纯 roll 不改 yaw → 一致 |

且 loader 的 yaw 换算对**任意姿态精确**（不是小角度近似）。`path_loader` 与 `px4_odom_convert` 读的是同一份 `R_enu_slam` 概念 —— **这是这份代码里做得最严谨的一处 **。

**唯一耦合条件**：`z_offset_m` 必须保持 `0.0`。loader 里没有对应的 z 偏移项，一旦有人给 `z_offset_m` 填非零值，**整条路径的高度会整体差该偏移量**（见 R11）。

### 重点条目展开

#### 🔴 R01 定位链路整体不可用

- **现象**：`global_map_publisher.py`、`global_localization.py`、`transform_fusion.py` 三个节点启动后 1.4 s 内全部 `exit code 1`。
- **触发**：任何人执行手册第 ② 步。
- **后果**：`/localization` 不存在 → `px4_odom_convert`（默认 `mode=localization`）无输入 → **PX4 从未拿到外部视觉**。所有依赖位置环的 Offboard 动作失去反馈来源。
- **为什么一直没被发现**：`transform_fusion.py:54` 在无全局修正时用 `eye(4)`，即"就算重定位没成功也照常输出看起来正常的位姿"；而这里更彻底 —— 节点直接死了，但 `fastlio_mapping` 还在正常打日志、RViz 照常显示点云地图，**现场观感与"一切正常"几乎没有区别**。
- **修法**（按代价排序）：
  1. **立刻可用**：`px4_odom_convert` 改用 `mode:=odom`（订阅 `fastlio_mapping` 正在发的 `/Odometry`）。代价：无地图修正、无重定位。
  2. `pip3 install open3d tf-transformations`（Open3D 自 0.14 起官方提供 Linux aarch64 预编译 wheel，见 [Open3D ARM 支持文档](https://www.open3d.org/docs/latest/arm.html)），或 `sudo apt install ros-humble-tf-transformations`。装完再验一次三个节点能否起来。
  3. 给 launch 加"节点存活检查"：任一 python 节点死了就 `Shutdown`，不要让"半死"状态静默通过。

#### 🟠 R04 `px4_path` 一起来就自动飞

- **现象**：`/px4_control/goto_enabled` 是 `transient_local` 锁存订阅；跟随节点一旦同时满足"许可真 + 定位有效 + LOADED"就在回调里**自动** `start_trajectory()` 并发目标（`path_follow_trajectory_node.cpp:447 → 393-403`）。
- **触发**：飞机已在 HOVER 且按过 `4`，此时任何原因重启 `px4_path`（重载路径、崩溃重启）。
- **后果**：操作者以为只是"起了个跟随节点"，飞机立刻自主飞行；且连接段（当前位置 → 路径首点）**只按 `max_step_dist=1.5 m` 打点，总长无上限** —— 起点离首点 200 m 就老老实实飞 200 m，沿途无围栏。
- **修法**：加显式"开始跟随"输入（默认 `autostart: false`）；给连接段设总长硬上限（如 3 m）；启动时把首点与当前位姿的距离打日志。

#### 🟠 R05 误差纠正不受限速约束

- **现象**：参考时钟冻结时（误差 ≥ `tracking_pause_error_m`，当前 1.5 m），发布的是"1.5 m 外的一个位置目标 + 速度/加速度前馈全 0"。
- **后果**：`px4_control` 把它当纯位置目标交给 PX4 位置环，飞机以 **PX4 自己的 `MPC_XY_VEL_MAX`**（而不是 `max_speed_mps: 0.8`）飞过去 —— "动力学受限轨迹"的限速在误差纠正阶段**完全失效**。而 `max_tracking_error_m: 5.0` 的中止门也救不了：参考冻结后飞机只会越来越近，误差不会再涨，**这个门几乎永不触发**。
- **修法**：(a) 把机上 `MPC_XY_VEL_MAX` 降到与 `max_speed_mps` 同量级（0.5~1.0 m/s）作为硬兜底 —— 最省事也最可靠；(b) 把发布位置夹在参考点前方 `k·error` 处；(c) 把 `max_tracking_error_m` 降到 1.6~2.0 m 让它真正可达。

#### 🟠 R06 幽灵参数 + 恒定的复位与质量

- **证据**：`px4_odom_convert.launch.py:18-19` 传了 `max_position_jump_m`、`max_attitude_jump_rad`；节点只声明了 7 个参数（`px4_odom_convert.cpp:12-18`）；对已编译二进制 `strings` 搜索命中数 **0**；全源码树 grep 除 launch 外无任何引用。
- **后果**：一个写在启动文件里、**从未实现**的定位跳变门限。加上 `reset_counter` 恒 0（`:197`）、`quality` 恒 100（`:199`）、`covariance` 全零（FAST-LIO 侧也全零），EKF2 对"SLAM 跳变/重定位/重启"完全无感知。
- **修法**：实现它（比较上一帧 NED 位置/姿态增量，超限丢帧并递增 `reset_counter`），或**先删掉 launch 里这两行**以免误导下一个人。

#### 🟠 R07 世界系对齐与地图来源

- `IMU_Processing.hpp:200` 把初始姿态对齐那行注释掉了（即使启用也是单位阵）→ **世界系 = 开机瞬间的 IMU 姿态，不是重力对齐系**。FAST-LIO 把重力当状态向量估计，所以飞机水平时"看起来" z 是向上的；开机时飞机倾斜，整条链路的"上"就是错。而 `EKF2` 假设 EV 位置/姿态在本地 NED 系下 —— 与 IMU 重力不一致会让 EKF2 打架。
- `src/maps/` 里 3 张 PCD 的 mtime 与整个源码树同为 **9-24 15:09**（一次性拷入），说明**不是本团队现场建的图**；而 `publish_initial_pose.py` 在 135 个历史 run 里**一次都没出现过** → 从未做过重定位，地图从未被验证过。
- **修法**：上机做静态校验 —— 飞机水平静止时，比对 `/localization` 的姿态与 PX4 的 `vehicle_attitude`（roll/pitch 应一致，yaw 允许差一个常数），不一致就不许解锁。把 `R_enu_slam` 改成 ROS 参数，并写一份"开机必须水平"的操作规程。

#### 🟠 R08 IMU 桥的时间戳

- `sensor_combined_to_imu.cpp:104-109`：`header.stamp.sec = msg->timestamp / 1e6`，而 `SensorCombined.timestamp` 是 **PX4 自开机起的微秒数**。发布出来的是"1970-01-01 00:00:0X"。
- 后果：任何按 ROS 时间做同步/超时/TF 插值的消费方都会出错。FAST-LIO 主要取 `linear_acceleration`/`angular_velocity`，目前不敏感；但这条 IMU 一旦被拿去做 TF 或 `message_filters` 同步就会踩。
- 修法：改成 `this->now()`，或建立 boot→ROS 偏移；至少写进 README。
