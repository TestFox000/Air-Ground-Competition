## 0. 一页速览（只读这一页也能干活）

### 0.1 这套系统是什么

**不是**"无人机自己会规划并飞"。它是一个 **"人先飞一遍录轨迹 → 机器照着飞"** 的 **回放式路径跟随系统**：

```
人手动飞（遥操） → FAST-LIO 记录轨迹 → 存成 txt → 之后飞机自动沿该轨迹回放
```

外加一条**向小车发航点**的链路。**没有**自主避障、**没有**自主建图决策、**没有**视觉识别。

### 0.2 一句话状态

| 面 | 状态 |
|---|---|
| **感知+定位** | ✅ 通到 `/fmu/in/vehicle_visual_odometry` **42.4 Hz**（2026-10-06 实测） |
| **飞控链路** | ❌ **PX4 飞控板从未接过**（无 `/dev/ttyACM*`），2026-10-08 复核仍未插 |
| **路径跟随** | ⚠️ 代码完整、参数齐，但**从未在真机飞过**（没有飞控板就没法飞） |

### 0.3 最重要的三个坑（先记住，别再踩）

1. **`ros2 launch px4_odom_convert px4_odom_convert.launch.py` 会静默不发数据** —— 默认 `mode=localization` 订阅一个**从不存在的话题**。**必须加 `mode:=odom`**（§6.3）。
2. **`px4_path` 有"录了新路径却飞旧路径"的契约断裂** —— 跟随读 `recorded_path_2.txt`、录制写 `recorded_path.txt`。补丁 02 已修，未应用。
3. **跨机 ROS 靠 `ROS_DOMAIN_ID=118` 对齐** —— 全车唯一真相源是 `dzros.env` / `dzlink.env`。域号不一致时 **ping 通、SSH 通、网页台通，ROS 就是互相看不见且零报错**。

### 1.2 飞控链路为什么"不是坏软件"

机载电脑**没有 PX4 固件**。PX4 跑在单独的飞控板上，通过 USB 串口 + `MicroXRCEAgent`（uXRCE-DDS）把 PX4 的 uORB 话题映射成 ROS 2 的 `/fmu/in/*` 与 `/fmu/out/*`。

**飞控板不插 ⇒ 没有 `/fmu/*` ⇒ 所有 Offboard 控制无法进行。** 2026-06 至 10-08 期间从未插过。

## 2. 系统架构与端到端数据流

### 2.1 完整链路

```
                     ┌────────── 感知层 ──────────┐
  Livox MID-360 ──eno1 以太网──► livox_ros_driver2
                                     │
          ┌──────────────────────────┴────────────────────────┐
   /livox/lidar (CustomMsg 10Hz)              /livox/imu (Imu 200Hz)
          │                                                │
          ▼                                                │
  fast_lio_localization ─┬─ fastlio_mapping ✅ 活 ─► /Odometry ~44Hz
                         ├─ global_map_publisher.py ❌ 崩
                         ├─ global_localization.py  ❌ 崩 ─► /map_to_odom
                         └─ transform_fusion.py    ❌ 崩 ─► /localization ❌不存在
          │                （三者都缺 open3d / tf_transformations）
          │
          ├─────────► dzlink_pc2_bridge ──/livox/points──► 小车（另一条线）
          │
                     ┌────────── 桥接层 ──────────┐
                     │ px4_odom_convert          │ px4_imu_bridge
                     │  in: /Odometry (odom 模式) │ in: /fmu/out/sensor_combined
                     │  out: /fmu/in/vehicle_     │ out: /fmu/out/imu_data
                     │       visual_odometry 42Hz │      (Imu 200Hz)
                     └────────────┬────────────────┘
                                  ▼
                     ┌────────── 控制层 ──────────┐
  px4_teleop_node ──/px4_control/command──┐     │
                                           ▼     │
  px4_path ──/px4_control/goto──► px4_control_node
      ▲                                  │  └─ /fmu/out/*（自身状态）
      └────/px4_control/goto_enabled────┘  ← 锁存，唯一人机许可闸门
                     │
        /fmu/in/offboard_control_mode  (20Hz 心跳)
        /fmu/in/trajectory_setpoint    (20Hz 位置+前馈)

                     ▼
        MicroXRCEAgent（串口 /dev/ttyACM0 @921600）
                     ▼
             PX4 飞控板 ❌ 未连接
```

### 5.3 坐标转换（最容易出错的地方）

录制文件保存 **FAST-LIO SLAM 原始坐标**，加载时才转 PX4 NED（`path_loader.cpp:30-34`）：

```text
SLAM ──(绕 Z 转 180°)──► ENU ──(x↔y, z 取反)──► NED
      slam_to_enu()          enu_to_ned()
      {−x, −y, z}            {y, x, −z}
```

- `px4_odom_convert.cpp:20-23` 用同一套 `R_enu_slam_`（`diag(−1,−1,1)`），`:25-28` 的 `t_enu_slam_` 恒为零向量
- `px4_odom_convert.cpp:148-149` 的姿态转换走 `px4_ros_com::frame_transforms::ros_to_px4_orientation(q_enu)`（四元数级）；`path_loader` 是先归一化再取 yaw（标量级）—— **两者等价，已数值验证**
- 航向：`yaw_slam` → `+π` → `π/2 − yaw_enu`
- **已用 `verify_frames.py`（2000 组随机位姿）验证 `px4_odom_convert` 与 `path_loader` 逐项一致** ✅
- ⚠️ 但 `map` 帧**不是 ENU**：FAST-LIO 初始化只对齐重力、**不对齐偏航**（`IMU_Processing.hpp:200`）
- ⚠️ `path_loader.cpp:89` 的 `z_min_enu/z_max_enu` 检查只是**软警告**（打印后继续），不拒绝加载

### 5.5 `ego-planner` —— **未接入，备选**

grep 全树 `GotoTarget` / `/px4_control/goto` → **0 命中**。

它的 `traj_server.cpp:245` 发的是 `quadrotor_msgs/PositionCommand`（话题 `/position_cmd`），消费方是自带的 `uav_simulator/fake_drone`（仿真四旋翼模型）—— **与真飞控链完全不通**。

### 7.7 两条通道的协议细节（写代码前必读）

**A 通道 `/nav/waypoint`（RELIABLE，纯文本路线）**

```
N10 M10 L10 L9 K9 J9 J10 I10 H10 G10* F10 F11 E11 N5
```

| 记号 | 含义 |
|---|---|
| `N10` / `L9` | 棋盘式坐标（列字母 + 行号），直接用**裁判场地格号** |
| `*` 后缀 | 该点为**停车打靶**点（如 `G10*`） |
| `R:` 前缀 | 该点为**倒车**点 |

**B 通道 `/dzlink/drone_to_car`（BEST_EFFORT，JSON）**

| `type` | 载荷 | 语义 |
|---|---|---|
| `heartbeat` | `seq` | 存活心跳，**3 s 不刷新即判离线** |
| `bridge_passable` | `lower` / `upper` / `confidence` | 桥洞 **K10**(下半场) / **K5**(上半场) 哪个可通行（本图真值；旧图曾是 K9/K4） |
| `target_zone` | `blocks` | 敌我/打击区位置 |
| `field_verify` | `mines` / `obstacles` | 地雷与障碍物 |

| 规则 | 值 |
|---|---|
| 车回 `ack` | 话题 `/dzlink/car_to_drone`，带 `seq` |
| 情报有效期 | **30 s**（超时报废，需重发） |
| 车等情报最长时间 | **2 s**（`mission.bridge_info_wait_s`，2026-10-11 起 20→2；只管「两半场相隔 ≤2 s 到达」，超时用默认 K10/K5） |

⚠️ **QoS 方向性**：本项目无人机发 → 车收，两者都是 RELIABLE（`/nav/waypoint`）或都是 BEST_EFFORT（JSON）时才能通。
**车发 → 机收**时，车侧 `/dzlink/car_to_drone` 是 BEST_EFFORT，而 `ros2 topic echo` 默认 RELIABLE ⇒ **echo 收不到就误判"车没在发"**，必须显式 `best_effort` QoS。

### 7.8 小车侧"停车点偏 10 cm"的结论（无人机不受影响，但两车协同时会叠加）

用户实测：从格中心走完后**终点比预期中心偏后约 10 cm**。已定位根因，**不是里程计尺度误差累积**：

| 项 | 值 | 性质 |
|---|---|---|
| 根因 | 到达判据里**写死的前导量** `0.10 + π·0.073/4 ≈ 0.157 m` | 固定偏移，恒定 |
| 实测尺度误差 | 3.4 m 行程上约 **−1.0%** | 累积误差 |
| "每走一格减一点"能否解决？ | ❌ **不能，而且会更糟** —— −1.0% 逐格累加到 1.34 m，远超 10 cm | 结论：**暂不实施** |
| 正确方向 | 把 `0.10` 这个常数**参数化**（如 `arrival_lead_m`），现场实测标定 | 已提出，**用户未答复** |

> 结论对无人机的意义：**无人机侧没有同类问题**（`px4_path` 用 `switch_tol`/`terminal_tol` 判到位，不是里程计推算），两车的偏差要分别处理。
