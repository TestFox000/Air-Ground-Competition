## 3. 协作教训清单（坑 → 当时损失 → 防法）

> 每条给三段：**坑**（发生了什么）/ **损失**（代价，可量化处给数字）/ **防法**（下队怎么堵）。

### L-01 折返点白名单硬编码，换图即全线无解
- **坑**：`TS_TURNED_MINES=("D8",)` 只含旧图的雷。换第五张图后 A4 是口袋雷（西出界、南 A5 是障碍），正交移动集下不可能直线穿心，但白名单没有它。
- **损失**：v3·t29 整卡 **failed**。车端 `plan_route_from_config` 恒 `PlannerError` → 静默回退旧 62 点路线 → `config_selfcheck` **12 error**、`route_check` **5 项失败**、**不可发车**。24 组参数矩阵全部无解。定位耗时：约 1.5 小时（卡创建 12:30 → 更新 12:38 后转下一卡修）。
- **防法**：任何"把某场地要素写进代码常量"的键（雷/障碍/靶/桥洞/折返点），换图验收卡必须包含一条：**逐个要素对白名单做一次存在性对拍**。v3·t31 的修法就是把它变成常量 + 相位常量的**联合矩阵**（24 组）来取证，而不是试一两次。

### L-02 相位常量与白名单耦合，改一个必须重跑矩阵
- **坑**：`TS_PHASE_CELL="C6"` 与 `TS_TURNED_MINES` 是耦合的。只把 A4 加进白名单（C6+A4）能出解，但那条 58 token 路线在 C9 撞障碍 **603 拍@0.15 / 453 拍@0.35**。
- **损失**：差点"修好了却更危险"——`route_check` 对那条路线报 **0 error**，只有真值足迹链仿真才暴露碰撞。若直接上车就是撞。
- **防法**：常量改动后**必须跑全参数矩阵再选值**，且选择理由写进 acceptance（v3·t31 写明"选 A6 理由＝A6/B6 数值同价，C6 在 C9 撞"）。

### L-03 判据用折线口径 ⇒ 乐观 ⇒ 假绿
- **坑**：`route_check` 用折线算车体净空，同一处它算 0.350 m；真值足迹链（FootprintObs）算出 0.0191 m，10 拍后车体∩柱面。
- **损失**：603 拍碰撞若未发现＝直接撞桩。v3·t29 用它定位、v3·t31 才用真值口径验收。
- **防法**：**门禁工具与验收工具必须不同源**。折线口径只能当快速筛子，放行判据一律走真值足迹 + 双档仿真。

### L-04 值去重吞掉状态边沿 ⇒ 硬件停在错误姿态
- **坑**：云台命令按"值变了才发"去重。TRACK→锁止那拍 `want(0)` 与缓存值相同 ⇒ **漏发** ⇒ 云台保持最后一个目标方向。这不是 bug 的表象，是去重策略与"电平保持"语义冲突。
- **损失**：v3·t24 原实现被用户追加验收 A2 打回返工；修法是新增**锁止边沿** `lock_edge` 强制发一次 0。若未发现，实车会在离开射击点后云台继续指着旧目标。
- **防法**：任何"去重/节流"的发布逻辑，验收卡必须显式要求断言**状态序列全序**（如 `[0,2,0,2,0]`），而不只是"最终值正确"。

### L-05 两个写者同抢一个话题 ⇒ 互相覆写
- **坑**：`mission`（巡迹时 `scan_mode=continuous` → 发 `scan_request=2`）与 `aim`（锁止 → 发 0）同写 `/nav/scan_request`。run11 实测顺序：aim 发 0 → mission 发 2 → 云台起转。云台巡迹全程在转。
- **损失**：用户明确要杜绝的现象；且因为 aim 侧有去重、不会再补发 0，**一旦覆写就再也纠不回来**。
- **防法**：**单写者模式**——锁止模式下 mission 完全不发该话题（连 FINISH 的 0 也不发，由 aim 接管）。验收靠 harness 级全序断言（v3·t24 A1/A2）。

### L-06 安全锁存的启动竞态：首拍次序决定生死
- **坑**：Safety 首拍（t≈+0.7 s）时 Localization 还没跑第一拍 ⇒ `_task_age` 因 `last_tick_at==0` 返回 **inf** ⇒ `heart_age > pose_timeout_s*2` 恒真 ⇒ 首拍即 `pose_stalled` 锁存 SAFE_STOP。本该救它的"启动宽限 3.0 s"判据是"**桥**从未有过帧"，而桥由**另一个进程**喂数据。
- **损失**：车一动不动；**同代码同 config（62 点/0.35）两趟结果相反**，会随机复现。v2·t27 才定位（15:15 卡死 vs 15:30 正常），定性为"启动竞态 × 确定性放大缺陷"。
- **防法**：① 首拍前所有 `_task_age` 类判据必须处理"从未 tick"（返回 inf 等价于最坏）；② 宽限判据必须覆盖**所有外部数据源**而非只护一个桥；③ 实车问题定位第一件事是找**同代码同 config 的对照趟**——有对照才 8 分钟定位，没有对照就永远悬着。

### L-07 测试自身的 import 顺序造假绿
- **坑**：`test_shutdown.py` 自己 `sys.path.insert(0, src/dzbrain)`，**赢过** `PYTHONPATH`。只把变异体放进 `PYTHONPATH` 时，导入到的仍是真源 ⇒ 变异体"全绿"。
- **损失**：**v3·t9 的 5 个变异体"测试能拦住"的结论全部不成立**——一轮验证工作作废。v3·t14 发现并修复，还加了"覆盖没生效就直接报红"的自证断言。
- **防法**：真变异测试必须用 `DZ_PKG_ROOT` 之类**能覆盖 `sys.path[0]`** 的机制，并在测试里**断言被导入模块的 `__file__` 指向副本**。否则变异测试本身是假绿。

### L-08 僵尸态测试挂死整个门禁
- **坑**：`_live_loop` 在测试进程内直接跑，收不了口（修前 **5 分钟不结束**，只能外部 kill）。
- **损失**：一次门禁跑批被单套测试拖死。
- **防法**：每个可能挂死的用例**包一层子进程 + `subprocess.run(timeout=...)`**，子进程内再加 `join(timeout=4s)` 以便回报 why/alive/logs。修后 M4 变异 8.59 s 可读 FAIL 收口。

### L-09 任务卡判据本身不成立 ⇒ 实现者被迫 fail
- **坑**：多张卡的 acceptance 写的是一个**事实性错误的前提**。例：v2·t15 假设"结构自检把 K11 贴边数成 2 次"——实测计数逻辑正确，被数成 2 次的是上半场 `J1→K1` 在 K1 附近来回穿梭；v2·t6 假设"存在合法的无隔板侧向 90° 路线"——穷尽论证证明本图该形态**结构性不存在**（3 颗雷在第 7 行 + D..N 段唯一出入口是南邻行）。
- **损失**：能力其实已实现且默认零影响，但因判据不可满足只能报 failed。v2 的 4 张 failed 里有 3 张是这种性质。
- **防法**：**派卡人写物理/几何类判据前必须先做穷尽论证**（v2·t6 自己写了 5 条纯几何判据证明不可行）。派卡卡里应允许"判据不成立"作为**一等交付**：实现者有权报 failed 并给出反证，然后由队长改判据重派，而不是逼实现者改代码去迎合错误前提。

### L-10 卡内配置被换掉 ⇒ 判据不可满足（判据与状态耦合）
- **坑**：v2·t17 的 ②④ 两条判据，在同一卡执行期间 `config/` 被别的卡换掉 ⇒ 判据自动失效。
- **损失**：核心缺陷已修好并验证，仍只能报 failed。
- **防法**：判据里凡涉及可被他人改动的状态（config、map、依赖版本），acceptance 必须写"**若该状态在本卡期间变化，本卡作废重派**"；或用 acceptance 的 sha256 钉把状态钉死。

### L-11 `edit_plan` 被旧 assignee 残留永久卡死 ⇒ 取消重建链
- **坑**：car-auto-plan 队里 t1 遗留的 assignee（`verifier`）残留引用，使后续 `edit_plan` 全部被系统级校验**永久拒绝**。连撞三次：t14→t17、t15→t16、t17→t19。
- **损失**：**3 张卡被取消重建**（4 个 cancelled 中的 3 个纯粹是工具卡死，与内容无关）；依赖链被迫重排。
- **防法**：无法改依赖时**取消重建，并把"内容与 assignee 不变、仅依赖变化"写进取消理由**——这是可审计的做法。但更根本的：**任务卡完成/取消时必须清空 assignee 残留**；队长侧每轮结束检查一次有没有孤儿 assignee。

### L-12 上游指令变更 ⇒ 旧卡契约被覆盖 ⇒ 双写冲突风险
- **坑**：用户新指令升级了压雷口径与速度，t10 的原契约（车体盖雷心、速度不动）已被覆盖。
- **损失**：若不取消，两卡并行会双写同一批文件。
- **防法**：t10 主动取消并写明"被 t12 取代、原契约已被覆盖、取消以避免双写冲突"——**主动作废并保留理由，是比静默改判据好的做法**。队长侧应在用户指令变更时**先扫一遍在办卡**，作废被覆盖的。

### L-13 判据是"任务书说全绿" ⇒ 复核发现多出 2 红
- **坑**：v2·t25 任务书写"其余全绿"，复核实测 **28 套 24 绿 / 4 红**，多出 `test_motion_limit 16/17` 与 `test_deploy 85/86`，且两红同源于另一卡 15:3x 的改动。
- **损失**：若复核不复跑就判 pass，会把 2 条新增红放行。
- **防法**：复核卡**必须自己重跑**，明写"不复用实现者日志"（v5·t6 acceptance 就写了"自己重跑 sim 缺省态与 bench 开启态，不复用实现者日志"）。

### L-14 并发编辑 ⇒ 全量回归偶发红 ⇒ 归因成本高
- **坑**：t7 并发写 `planner.py` 时，另一卡的全量回归出现 `test_planner ⑫.8` 一条红。
- **损失**：归因花了额外一轮（stash 对照 + 单跑 3×110 项）才确认"非我引入且已自愈"。
- **防法**：见 L-17 的隔离态门禁法 + L-18 的基线对照法。**并发编辑同一文件在本项目是常态**（多队同时改 `planner.py`/`robot.yaml`/`robot.yaml` 的 planner 段），因此这两法必须**制度化**，不是可选项。

### L-15 隔离态门禁：临时 stash 队友改动，但必须完整恢复
- **坑**："写域干净 OK（写域外改动数 = 0）"这条判据在**完整态**下永远不成立（队友有 22 个未提交改动）。v3 的做法是临时 stash 掉写域外改动再跑原命令原语义。
- **损失**：stash 操作本身有风险——若中途出错会破坏队友的工作区。
- **防法**：v3 的完整流程可直接抄：**① 快照写域外文件列表 + in-scope 文件 SHA256 → ② stash push（带清晰 message）→ ③ 跑原命令原语义 → ④ stash pop → ⑤ 校验写域外 diff 数量恢复、in-scope SHA256 逐位相同、`git stash list` 为空、抽验队友标记内容完好**。五步缺一不可。

### L-16 换图/换 config 后回归大面积变红 ⇒ 必须做基线对照
- **坑**：换第五张图后 29 套里 **11 套非零退出**（autoplan 103/138、bridge_gate 38/47、calib 99/101、core 49/50、drone 65/66、motion_limit 16/17、physics 98/103、planner -1/-1、route 160/161、sim 107/113、sim_guard 103/109）。
- **损失**：分不清"我改坏的"和"换图导致的期望值变化"⇒ 容易瞎改测试掩盖真缺陷。
- **防法**：**基线对照脚本**——临时回滚 `robot.yaml`→HEAD、`map.yaml`→旧图备份，跑完立即恢复并逐位哈希校验，然后逐条列出新增红（套名/断言号/旧期望/新图实际值）。v3·t29 两次实验都"恢复成功"。**"不得自行改测试"要写进 acceptance**。

### L-17 写域纪律有效但被并发破坏时的判据写法
- **坑**：`写域干净 OK` 这类判据在多人并发下形同虚设（v3 有 22 个写域外改动待确认来源）。
- **损失**：无（此条是正面经验）。v3 的处理是**逐文件核对 mtime 早于本卡编辑时刻**来证明那些改动是队友产物。
- **防法**：in-scope 声明要精确到**文件路径**（不是目录）；验收时用 `mtime < 本卡首次落盘时刻` + `git status` 双证据区分归属。

### L-18 工具层面的静默失败：写域外遗留
- **坑**：t13 严格守住了写域，但仍发现 `tools/plan_route.py` 的 `--config` 帮助文本仍把"起点朝向"算作配置项——写域外的遗留不一致。
- **损失**：小（文档不一致），但会让后来人按错的前提操作。
- **防法**：写域外的发现**只报不改**并显式列在报告里（t13 原文："写域外遗留 1 条：…（已上报）"）。这条纪律应保留——它保证了 in-scope 契约不被静默破坏。

### L-19 契约 verify 命令原文写错 ⇒ 验证者必须自行纠正
- **坑**：v3·t31 的 verify ① 原文不可执行：`hasattr(dzbrain.route.planner,'plan_route_from_config')` → **False**（该函数在 `dzbrain.tasks.mission`），且 `cfg` 必填。
- **损失**：无实质损失，但若照抄会卡住。
- **防法**：验证者发现契约命令不可执行时，**用等价可执行形式验证 + 在报告里写明契约原文的两处错误 + 建议修文档**，而不是跳过该项或假装跑过。

### L-20 模型路由不支持 reasoning effort ⇒ 卡片直接死掉
- **坑**：camview-ann-team·t8 报 `provider "our-free-model" model "z-ai/glm-5.3-flash" does not support reasoning effort "high"`（`UNSUPPORTED_REASONING_EFFORT`），任务 failed。
- **损失**：1 张卡报废（该队唯一 failed）。
- **防法**：**建队时逐个成员校验 (provider, model, effort) 三元组**，不要照抄上一队的配置——v5 的描述里就写着"全员改用【不含 deepseek】的免费模型路由"，而 v4/v5 的成员 effort 设定各不相同（`max`/`high`/`balanced`/`on`）。

### L-21 整队零产出（v4/v5）
- **坑**：car-auto-plan-v4 与 v5 各建队、建 6~7 张目标极清晰的高质量卡，**但一张都没被认领**（v4 存续 16 分钟、v5 存续 35 分钟即归档）。
- **损失**：v3 的 7 张未竟卡（config 恢复提速档、上场门禁、拐角四件套、独立复核、仿真出图、快照重写、备份预案）**全部原样留在 pending**，无人推进。而这些事项到 v5 归档时仍是待办。
- **防法**：**卡片质量不等于产出**。派卡后应确认"卡片已被认领"再认为建队成功；对"上一队有 N 张 pending 就直接重建队"的模式要警惕——**重复建队不解决认领问题**（v4→v5 就是同一个目标的第二次重建，仍 0 认领）。

### L-22 观察员类成员被用户指令取消 ⇒ 成员/卡需同步作废
- **坑**：v3·t27（靶面观察）被用户指令取消，理由改为"每次射击自动截图、完赛直接看图"，`target-observer` 成员被移除。
- **损失**：无（及时取消）。
- **防法**：用户改方案时，同步作废**相关成员 + 相关卡片**，不要让成员空转或让卡挂着。v3 的处理（"已移除"）是干净的。

### L-23 已提交内容与实物不符（正向经验：逐文件核对）
- **坑**：v3·t6 的对账——任务卡自述改 4 个文件，实际 3 个已在 HEAD（工作区无 diff），唯一未提交的是 `test_autoplan.py`（tempfile 卫生修复）。
- **损失**：无（此条是正面经验）。
- **防法**：复核卡**逐文件核对 in-scope 声明 vs 实物 diff**（car-auto-plan·t6 的 verifier 就是这么做的）。配合 SHA256。

### L-24 取消的重构样本仍有 100% 完成率的正例
- **坑**：（无坑，此条为对照）
- **损失**：无。
- **防法**：v1-to-v2-architect 的组织形态值得抄：**7 个成员（2 分析 + 5 builder），7 张卡全 completed，判据统一为 `rel_tol=1e-12` 逐位对拍，`builder-test` 收尾时交 916 条新边界断言。**它之所以全绿，靠的是"**单一硬判据（逐位一致）+ 明确的不改清单（不改行为、不换话题名、不改启动脚本）+ 每个 builder 自带对拍测试**"。air-ground-v1 若做重写类工作，应复制这个形态而不是 6 职能 DAG。

## 4. 对现役 air-ground-v1 的 5 条具体建议

> 每条给：**依据**（哪条教训/结论）→ **建议动作**（可执行）→ **为什么现在值得做**（本阶段特征）。
> ★ 标出的 5 条对应队长点名的"任务卡粒度、写盘范围、回归口径"等方向。

### ★ 建议 1｜把"双通道契约"做成可变异验证，而不是只做一次联调
- **依据**：L-07（测试自身造假绿）、C-04（真变异矩阵经 `DZ_PKG_ROOT`）、C-10（失败必须暴露成可诊断错误）、L-03（近似口径乐观假绿）。
- **建议动作**：为 `/nav/waypoint`（RELIABLE）与 `/dzlink/drone_to_car`（BEST_EFFORT）各写一个变异体——**故意把 QoS 改错、把车侧订阅摘掉、把 `seq` 回执吞掉、把 topic 名打错一字**——确认无人机侧测试会红。特别注意 QoS 反向组合（车 RELIABLE / 机 BEST_EFFORT）**完全收不到且不报错**，这是跨机 ROS 2 最经典的静默失败，必须有一条测试专门钉它。变异体运行时用 `DZ_PKG_ROOT` 式覆盖并在测试里断言 `__file__` 指向副本。
- **为什么现在**：本阶段核心就是双通道通信，而 DDS 上"看起来通了"与"真的通"是两回事。历史上 v3 花了 t9→t14 两张卡才发现自己的变异测试本身是假绿。

### ★ 建议 2｜任务卡粒度按"一个可验证断言"拆；写盘范围精确到文件；派卡前先做穷尽论证
- **依据**：L-09（判据前提不成立⇒实现者被迫 fail）、L-10（判据与状态耦合）、L-01/L-02（常量耦合，改一个炸全线）、L-18（写域外遗留）、L-11/L-12（双写与覆盖）。
- **建议动作**：① `inScope/outOfScope` **精确到文件路径**（不是目录），并加一句"写域外发现只报不改"；② acceptance 末尾加一条"**卡内若某可变量被他人改动，本卡作废重派**"；③ 涉及耦合常量/阈值（感知置信度、topic 名、QoS 档、闸门参数）的改动**必须附组合矩阵或 N 组参数扫描取证**，不是试一两次就下结论；④ 队长派卡前先做**穷尽论证**确认判据可满足，并明确允许"判据不成立"作为一等交付（实现者报 failed + 给反证，而非改代码迎合错误前提）。
- **为什么现在**：感知侧（网格/雷障/靶/箭头）天然有多组互相耦合的阈值与开关，正是 L-01/L-02 那种形状；且本阶段多成员并发写同一批接口定义，早立写盘范围比事后返工便宜。

### ★ 建议 3｜"静默失败"是本阶段头号风险：真值口径 + 隔离态门禁 + 基线对照要制度化
- **依据**：L-03、L-05（双写者覆写不可逆）、L-06（首拍次序竞态）、L-14（并发编辑偶发红）、L-15（隔离态门禁五步）、L-16（基线对照）、L-17（mtime + git status 归属判定）、C-09（门禁不过走确定性回退）。
- **建议动作**：① 任何"打印 `已发送/已收到/已发布`"的代码路径，必须配一条**消费者真收到了**的独立证据（回执 / 计数器 / 端到端计数差 / 双机 `topic info -v` 订阅数）；② 同一话题**只允许一个写者**，写者归属写进代码头注释；③ 首拍/启动类判据必须处理"从未 tick"（返回 inf 等价最坏）与**全部外部数据源**的宽限；④ 多人并发时启用五步隔离态门禁（快照 → stash → 跑原命令原语义 → pop → in-scope SHA256 逐位相同 + `stash list` 为空 + 抽验队友标记完好）；⑤ 换图/换 config 类改动后跑基线对照（临时回滚→跑→逐位哈希恢复→逐条列新增红），且 acceptance 明写"**不得自行改测试**"。
- **为什么现在**："不发车、只做感知/通信/仿真"意味着**大量失败会伪装成成功**（车没动、话题没通、消费者没订阅、云台保持旧姿态，全都静默）。历史 7 队里至少 6 张 failed 的根因是静默或假绿，不是能力不足。

### ★ 建议 4｜回归口径第一天就立 known-red 台账，判据只登记不改
- **依据**：C-05（known-red 只增不改、转绿标"已收口"不删行、"0 新增红"按台账逐条同名同数核对）、C-07（默认行为不变用 sha256 钉）、L-13（任务书说全绿但实际多出 2 红）。
- **建议动作**：本队**第一天**就建 known-red 表（文件、断言号、失败原因、归类 A/B/C）；验收卡统一写"**除台账 N 条外 0 新增红**"；判据**不得为绿灯而修改**——要改必须写明理由并在报告单列；每张动公共代码的卡都用"改前=改后 sha256 前 16 位 + 关键指标逐位相同"证明零影响；新键必须登记 Config/SCHEMA 且 `default` 为关闭/中性，缺键时行为与旧版逐位一致（C-08）。
- **为什么现在**：本阶段要在"不发车"前提下积累可信度，回归基线就是可信度地基。历史证明地基晚立一天，之后每次"新增红"都要花一整轮归因（L-14/L-16：29 套里 11 套变红）。

### ★ 建议 5｜避免重复建队；**认领率**是建队成功的唯一硬指标
- **依据**：L-21（v4/v5 两队 0 认领、v3 的 7 张卡原样烂在 pending）、L-11（取消重建链 3 次）、L-20（模型 effort 不支持致卡死）、L-22（成员/卡需随指令同步作废）。
- **建议动作**：① 派卡后**主动确认卡片已被认领**，把"认领数/总数"当建队成功指标——v4 目标极清晰仍 16 分钟 0 认领、v5 同样 35 分钟 0 认领，v3 的 7 张未竟卡因此烂到今天；② 建队时**逐成员校验 (provider, model, effort) 三元组**可执行，不照抄上一队（camview·t8 即死于 `UNSUPPORTED_REASONING_EFFORT`）；③ 用户改方案时同步作废相关成员与卡；④ 卡片完成/取消时确认无 assignee 残留（v3 队 3 次取消重建的直接原因）；⑤ 目标过大时**收窄本轮范围**，本阶段只做感知/通信/协议/车侧执行/仿真台架，不发车——这一点已在队目标里，执行时不要在卡里偷偷扩大。
- **为什么现在**：本阶段任务多，最可能的失败模式就是"建队、写信漂亮的卡、没人领、原样挂着"——历史上已完整发生过两轮，而这些卡的内容（恢复提速档、上场门禁、拐角四件套、独立复核、上下文快照、备份预案）到今天仍是待办。

## 5. 一句话总结

7 个历史团队共 **123 张任务卡 / 65 个成员槽位**，沉淀出 **31 条可复用结论**与 **24 条协作教训**。核心元教训只有一句：**这个项目绝大多数失败不是"不会做"，而是"静默失败"与"假绿"**——任务卡判据前提不成立、耦合常量炸全线、近似口径乐观、双写者覆写不可逆、测试自身 import 造假绿、首拍次序竞态锁存、整队零产出。

**"少建队、建了就盯认领"、"判据与证据同批产出"、"默认行为不变要能用 sha256 自证"**——这三句是 air-ground-v1 在"不发车"这个低风险窗口里最该先落地的纪律。
