## 一、总体架构对比

```
出厂（官方 dzpx4）：
Livox MID360 → FAST-LIO2 → px4_odom_convert(纯坐标转换) → PX4 EKF2
                              无防护、无对齐、SLAM z 直通、无运维工具

我们的新体系：
Livox MID360 → FAST-LIO2 → px4_odom_convert 增强版 v2 → PX4 EKF2
                              四层韧性防护 + 防双实例 + z 换源
       + 一键部署/回滚 + autostart 编排 + Agent 看门狗
       + 一键体检 + 出厂症状诊断 + 飞行黑匣子/会话日志
```

改动主线：**咽喉件 px4_odom_convert 三代演进**（原版 → v1 → v2），
其余是围绕它的部署、自启、观测、体检工具链。

## 二、核心件 px4_odom_convert：三代演进

### 2.0 官方原版行为（当前机上"出厂代码"即此状态）

- 只做 ENU→NED 坐标转换与四元数转换，直通发布 `/fmu/in/vehicle_visual_odometry`
- SLAM 跳变原样进 EKF（实测跟丢重捕跳 37~62m 会瞬间打崩 EKF）
- z 轴用 SLAM z（两个场地实测漂移 5.56m / 8.9m）
- 无 SLAM↔EKF 坐标系对齐管理（依赖固定旋转矩阵）
- 无部署工具、无防重复启动、无运行告警

### 2.1 v1（2026-10-16，两天四轮实飞实测落地）

| # | 改动 | 内容 | 实测依据 |
|---|------|------|----------|
| 1 | auto-align | SLAM 位姿直通 + EV reset_counter 一次性重锚（0→1），EKF 帧与 SLAM 地图帧重合；另一模式 align_yaw_to_ekf 可将 SLAM yaw 对齐 EKF 磁航向后冻结 | SLAM 与 EKF 局部 NED 帧不一致，历史方案在三个对齐策略间反复（见 2.2 备注） |
| 2 | jump guard | 单步位移 >0.5m（或 yaw >0.8rad）先 hold：重发上一有效位姿 + 位置/姿态方差放大至 100（EKF 视角=静止且不可信）；地面待命连续 8 帧（43Hz 下约 0.2s）仍大才判"真实大位移"接受 | FAST-LIO 被搬运/剧烈晃动跟丢重捕，/localization 单步跳 37~62m、z 漂 5m，直通策略令解锁坐标漂走 |
| 3 | armed 门控 | 解锁状态永不接受大位移（0.2s 内移动数米物理不可能 = 100% 跟丢），hold 到底保 EKF；仅地面待命允许"被搬运"式重锚 | 飞行中 SLAM 跟丢时防止 EKF 被撕扯 |
| 4 | z 轴换源 | 高度用 EKF 反馈 z（气压计主导）替换 SLAM z，EV z 与 EKF z 零残差 = 关闭 EV-z 融合，高度完全由气压计闭环 | 两个场地 SLAM z 分别漂 5.56m / 8.9m，而气压计悬停高度始终正常 |

> 备注：v1 之前日志中出现过三个 auto-align 版本迭代（SLAM 对齐 EKF 帧 →
> 仅对齐 yaw → SLAM 直通+bump 重锚），最终收敛为上表方案。

### 2.2 v2（2026-10-17，日志回溯修复）

背景：10-16~10-17 飞行日志实锤两处 v1 放大器——①SLAM 持续疯跳（ICP 摇摆，
单帧 26~585m）时"连续 8 帧即接受"把疯跳当真实位移放行；②每次接受都 bump
reset_counter，EKF xy_reset 每秒 +1（累计 3764 次、uint8 255 饱和循环，
持续约 14 小时无人察觉）。v2 在 v1 之上叠加三级防护与防双实例：

| # | 改动 | 内容 | 实测依据 |
|---|------|------|----------|
| 5 | L1 insane 熔断 | 单帧位移 >2m（43Hz 等效 86m/s，物理上限约 40 倍）或 yaw >1.6rad 判 SLAM 数据无效：输出锁定在最后放行位姿、绝不 bump；恢复需 SLAM 相邻帧稳定 86 帧（≈2s，用不受 hold 影响的原始相邻帧流判定）。原位恢复直接接管直通；新位置恢复需 disarmed+非风暴+节流允许才一次 bump 平滑重锚（86 帧稳定确认远强于常规 8 帧）；armed/风暴/节流窗口内保持熔断，条件满足瞬间自动重锚 | /localization 单帧跳 26~585m（ICP fitness 0~0.9 摇摆，10-17 上午 100% 失败全 0）；旧版 8 帧全放行且每次 bump |
| 6 | L2 bump 节流 | bump reset_counter 最小间隔 10s；窗口内判定基准与输出均不动，后续帧持续 hold/confirm 循环复查（每 0.2s 一次），窗口过后才真正 bump+放行。设计要点：窗口内不可前移判定基准，否则窗口结束后位置会经正常放行分支无 bump 突变 | v1 每秒多次 bump 直接造成 reset 风暴 |
| 7 | L3 EKF reset 风暴熔断 | 60s 滑动窗内 EKF reset >5 次即置 storm：冻结一切 accept/bump、ERROR 告警、hold 输出保 EKF；窗口滑过自动解除并恢复正常防护。检测挂在 vehicle_local_position 回调（xy/heading reset counter 变化即计入） | reset 风暴持续 14h 只打 WARN 无动作 |
| 8 | 防双实例 | 两级：①启动拒绝——构造时 count_publishers(VIO 话题)>0 直接 FATAL+抛异常退出（main 捕获干净退出），后启动实例自动自杀；②运行期监测——10s 定时器查 VIO 与 SLAM 话题发布者数，>1 打 ERROR（DUPLICATE INSTANCE / DUAL SLAM SOURCE，后者可发现上游双 FAST-LIO），不自动退出（armed 下跳变由 L1 兜底，自动退出会造成飞行中 VIO 断链，更危险） | 双栈并行实锤：手动栈+autostart 栈并行时双 FAST-LIO 同发 /localization 406 秒（21:39:53~21:46:38）、双 odom 同发 VIO 93 秒，EKF 被两路测量撕扯出 reset 风暴 |

**验证方式**（本地无 ROS2 环境）：
- `tests/test_jump_guard_v2.py`：与 C++ 决策逻辑逐行等价的 Python 状态机，
  6 场景回放断言——正常悬停直通零 bump / 疯跳锁定零 bump / 平滑搬运直通+
  重定位恰好 1 次 bump / armed 疯跳 hold 到底 / EKF 风暴冻结与自动解除 /
  节流全程 hold 窗口过后才放行
- 真机编译验证随 patch_deploy.py 部署步骤自动进行（删产物强制重编，rc≠0 即停）

**v2 可调参数**（launch 免改默认可用）：
`slam_insane_m=2.0`、`slam_recover_n=86`、`slam_recover_m=0.1`、
`slam_recover_yaw_rad=0.1`、`bump_min_interval_s=10.0`、
`ekf_storm_window_s=60.0`、`ekf_storm_max_resets=5`

## 三、部署与运维工具链（原版完全没有）

| 工具 | 位置 | 功能 |
|------|------|------|
| patch_deploy.py | tools/ | 一键部署：机上备份（.bak_patch_时刻）→ 推送 cpp/hpp → 删产物强制重编（绕过 colcon 增量构建坑）→ 重启节点 → 验证 v2 横幅与 delta 流 → **部署后体检**（VIO/SLAM Publisher count=1、EKF xy_reset_counter 静置 10s 增长≤2、新实例横幅必须为 Resilience layer v2）。`--no-restart` 只编不启；`--rollback` 回滚最近备份。密码走 AG_ORIN_PASS 环境变量 |
| check_stack_health.py | tools/ | 一键体检（约 30s）：节点进程数（livox/fastlio/odom/agent 各应 1）→ 话题发布者数（/localization、VIO 各应 1）→ EKF reset 10s 增长 → 最近 5 分钟 DUPLICATE/INSANE/STORM 告警扫描；`--kill-dup` 自动杀同类较新实例（保留 PID 最小即最早启动者）。**起飞前标准流程：体检 → 43Hz 自检 → 悬停验证** |
| factory_flight_diag.py | tools/ | 出厂/换码后症状诊断（只读）：vehicle_status 解锁拒绝原因（pre_flight_checks_pass/failure_flags）、EKF z 有效性两帧漂移、VIO 是否在发布及 NaN 检查、气压计读数、进程清单；自动判读"EV 污染假设"vs"参数重置假设"并给对应修复 |
| remote_run.py | tools/ | SSH/SFTP 原语，断链自动重试（paramiko），全部工具复用 |

独立部署包：`guard_v2_deploy_20261017.zip`（onboard/dzpx4_patch + tools 三件 +
测试），目录结构满足 patch_deploy 相对路径依赖，解压即用。

## 四、开机自启与看门狗

- **autostart_agup.sh**（crontab `@reboot` 挂载）：tmux 按依赖顺序编排
  livox → fastlio → agent → wdog → odom → imu → control → path → teleop，
  每窗口独立日志落 `~/drone_logs/node_*.log`
- 版本演进：v1（全栈+相机检测）→ v2（全栈）→ **v3（flight-link only：
  只起 agent/wdog，定位栈改手动启动）**——注意当前机上即 v3，重启后定位栈
  不会自启，需手动跑 start_drone.sh / start_fastlio.sh 或恢复 v2 模式
- **Agent 看门狗**：监控串口存在、Agent 存活、遥测静默秒数、重启计数；
  Agent 死自动拉起。2026-10-17 诊断实锤其 61s 重启循环工作正常
  （飞控 uXRCE 客户端卡死时 Agent 反复被拉起但等不到连接）

**已知链路规则**（Lessons 沉淀，违反即复现故障）：
1. 起飞前 30s 自检：`ros2 topic hz /fmu/in/vehicle_visual_odometry` 确认约 43Hz，无输出禁止起飞
2. 飞控断电重上电后 uXRCE 客户端可能卡死，**Orin 侧重启 Agent 无效，必须飞控断电 5 秒重上电**（若卡死在飞控侧）
3. MicroXRCEAgent 不会自动重建会话，飞控重上电后需重启 Agent 进程

## 八、当前状态与恢复指引（截至本文撰写）

机上现状：**出厂版 px4_odom_convert**（无 z 换源/无防护）+ autostart v3
（定位栈不自启）+ 飞控 uXRCE 待断电复位。对应症状：
- 高度模式失控 ← 出厂版无 z 换源，SLAM z 污染 EKF（若 EV 融合参数仍开启）
- 键盘无法解锁 ← uXRCE 链路断（命令到不了飞控）
- 自稳勉强可用 ← 遥控器直连飞控不经过 Orin；"勉强"为出厂参数与机体不匹配

**恢复步骤**（部署包 guard_v2_deploy_20261017.zip）：
1. 飞控断电 5 秒重上电（复位 uXRCE 客户端），等 ttyACM0 枚举
2. 重启 MicroXRCEAgent（wdog 会自动拉起亦可），验证 vehicle_status 有数据流
3. `python tools/check_stack_health.py --host <IP> --kill-dup` 体检清双实例
4. `python tools/patch_deploy.py --host <IP> --user duzhong` 部署 v2（自动备份+体检收尾）
5. 手动启动定位栈（autostart v3 模式下）或恢复 v2 全栈自启
6. 悬停验证判据：0.5m 悬停 10s，位移 <0.3m、零突跳、高度纹丝不动

回滚：`python tools/patch_deploy.py --host <IP> --rollback`（机上 .bak_patch_* 备份）。
