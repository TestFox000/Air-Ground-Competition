# 空地协同插件整合方案（讨论稿 v1）

> 撰写：lead　｜　日期：2026-10-17　｜　状态：**待讨论，未动一行代码**
> 本文所有数字均为本轮实测，不是估计。凡未验证的，文中明确标注「未验证」。

---

## 0. 一句话结论

**两个插件应该合并成一个包、一个侧栏图标、一套路由、一份 noVNC、一套共享代码；「车」与「机」降级为同一插件内的两个「节点」。** 真正做到「空地协同」的不是把两个面板并排，而是合并后才存在的 5 件事（见 §5）。

三位成员独立审计后，有三条结论比初稿更明确：

1. **合并底座必须是「车侧」**，不是机侧——车侧 `index.js` 是超集（32 路由 vs 20），`src/` 多 3 个模块，机侧的真增量只有 4 项（温度、飞控电池、`batteryView` 三态、connector loopback 改写）。
2. **合并本身只会丢车侧功能**（若以机侧为底，12 条 `/sim*` 与 3 个 Host 模块全丢）。**机侧没有任何一项「车侧没有且车侧也想要」的核心能力。**
3. **发现 3 个现存真 bug**（假绿 / 假红 / 假归因），都是「注释写对了、实现没跟上」——合并是修它们的最佳时机，因为改一处修两边。

**但有 7 个分叉必须先由你拍板**（见 §6），其中 ② ⑥ 会影响现场怎么用。

### 1.6 三个「把 A 说成 B」的现存 bug（合并时必须一并修）

这三个都是成员审计时挖出来的**真 bug**，不是设计口味问题。lead 已逐条独立复核。

**① 假绿：面板打开后的头两分钟可能显示上一次运行留下的绿点**

`GET /status` 返回的是**缓存**探针，不触发探测：
```js
// dzrobot_v2/dsh-plugin-dzrobot-ssh/index.js:156-160
const snapshot = status.get()
return send(200, { …, probe: snapshot.probe, … })
```
而 client 挂载时直接把它当现状画（`client.js:2101-2114` → `:2175` 的 `<dot data-state={state.probe?.state}>`）。
唯一的活探针是 **120 s 一次**的 `POST /probe`（`client.js:2822-2830`）。

> 讽刺的是两侧代码注释早就写对了纪律：`client.js:2818-2819`「a stale green dot is the one thing worse than none」。
> **纪律写对了，只是没覆盖到「挂载时读缓存」这第二个读点。**

**② 假红：无人机飞控板插着、DDS 静默 → 显示「无飞控」**

机侧 `metrics.js` 精心设计了三态（`batteryFc=present` + `batteryNote=dds_silent|no_ros`），注释原文写着 *"never 无飞控 about a plugged-in board"*（`metrics.js:33-34`）。
**但 UI 一处都不读**——lead 实测计数：

```
dzdrone-ssh/client.js  : batteryNote=0  dds_silent=0  no_ros=0  batteryFc=0
dzdrone-ssh/float.html : batteryNote=0  dds_silent=0  no_ros=0  batteryFc=0
```

于是 `batteryView()` 走到最后一个分支就返回 `{ state: 'nofc' }`：
```js
// dzsmartscout/dsh-plugin-dzdrone-ssh/client.js:1658-1668
function batteryView(reading, error, now) {
  …
  const battery = reading.battery
  if (battery != null && Number.isFinite(battery.percent) …) return { state:'live', … }
  return { state: 'nofc' }        // ← 飞控在 + DDS 静默 也掉进这里
}
```

**③ 假归因：数值越界被说成「ROS 栈未运行」**

`normalizeBattery()` 越界时 `return null`（`metrics.js:251-257`），但 `batteryNote` 仍是 `null`，UI 统一归因为 `no_stack`（ROS 栈没起）。**数值本身有问题，被说成了栈没起。**

> 这三条的共同点：**代码里注释写对了纪律，实现没跟上**。合并是修掉它们的最佳时机——因为改一处就修两边。

### 1.7 机侧文案漏改「车」

机侧 `src/ssh.js:204,206` 的探测文案**还写着「车」**：

```
'端口被拒绝（车已开但 sshd 没起？）'
'网络不可达（车还没连上 WiFi？）'
```

实测证据（本轮刚打）：`GET /api/dzdrone-ssh/status` 返回
```json
{"probe":{"state":"unreachable","detail":"网络不可达（车还没连上 WiFi？）"}}
```
无人机掉线时面板会告诉你「车还没连上 WiFi」。**这是机械改名漏改。**

另有两处同类漏改：`vnc-app.html` 的「这台车的 VNC 需要密码」（`:47,164`），与 JS 注释里的 `car's`（`:139,223`）。

### 1.8 一个数据脏点（合并时必须处理）

实测 `~/.dsh/dzrobot-ssh/settings.json` 与实时 `/api/dzrobot-ssh/status` 里有两个**源码里不存在、git 历史里也不存在**的键：

```json
"camHost": "", "camPort": 8080
```

根因已定位：`src/store.js:115-152` 的 `sanitize()` 是**只做类型强制、不过滤未知键**（`const next = { ...patch }` 之后只处理已知键，最后原样 `return next`）。于是任何一次 POST `/config` 带进来的多余键会被永久写盘。

**合并时的新 store 必须加白名单**，否则脏键会跟着带进新插件。

### 1.9 当前运行态（合并的验收基线）

本轮实测，两个插件在 `http://127.0.0.1:52882` 上**都活着**：

| 插件 | `/status` | `probe.state` | 说明 |
|---|---|---|---|
| dzrobot-ssh | 200 | **ready**（1773 ms） | 车此刻真连得上 |
| dzdrone-ssh | 200 | **unreachable**（3070 ms） | 机此刻不在网（`dzsmart.local` 解析不到） |

> 合并后这个能力**一个都不能少**：两个接口都 200、各自 probe 如实报。

## 2. 三个候选架构

### 方案 A · 单包双节点（推荐）

```
dsh-dzairground-ssh        ← 一个包
├── index.js               ← Host 半身，节点注册表 { car, drone }
├── client.js              ← 浏览器半身，一个图标 / 一个面板
├── src/
│   ├── nodes.js           ← ★新增：节点描述（id/role/host/metrics能力/文件捷径/工作区根）
│   ├── store.js           ← 结构化设置 { car:{...}, drone:{...} }（★加白名单）
│   ├── ssh.js             ← 一份（LOGIN_MARKER 参数化）
│   ├── metrics.js         ← 一份（能力驱动，见 §4.2）
│   ├── files.js  vnc.js  ws.js  trust.js  reload.js   ← 一份
│   ├── simbench.js  stressbench.js  dronesim.js        ← 一份（原车侧）
├── novnc/                 ← 一份（583,780 B，原样）
└── sim.html  float.html  vnc-app.html  vnc-connect.html
```

- **路由**：`/api/dzairground-ssh/status`（双节点一次拿全）＋ `/car/*`、`/drone/*`（单节点）＋ `/sim/*`（不变）
- **侧栏**：1 个图标 `dzairground-ops`
- **代价**：要动 client.js 的结构（一次性），要写数据迁移
- **收益**：重复归零；改一个 bug 只改一处；双节点状态一次拿全

### 方案 B · 共享内核 + 两个薄封装

抽一个内部包 `dsh-ssh-core`，两个插件各剩薄壳。
- 优点：改动局部，两个插件可独立升级
- 缺点：**不满足「合并为一个插件」**；仍然 3 个包、2 个图标、2 条数据目录；协同功能仍要跨包拼

### 方案 C · 伞形插件（新插件依赖旧两个插件）

新插件只管面板 + 协同层，底层仍调两个旧插件。
- 优点：代码不动
- 缺点：3 个包；进程内跨插件调用没有正式契约（只能走 HTTP 回环），反而更脆；旧插件的数据目录还在

### 推荐：方案 A

理由只有一条：**你要的是「一个空地协同插件」。B 和 C 都是「两个插件 + 一层胶水」，胶水迟早腐坏。**

### 3.4 浮窗（shell.overlay）

✅ **已定稿：一张卡多格**（附录 C.1 ③）——一张浮窗卡内含车电量格 + 机温度格 + 机飞控电量格，各格独立曲线、独立 `data-level` 染色：

```
┌─ 空地状态 ───────────────────── 开机 2:31:07 ─┐
│  小车电量        无人机温度      飞控电量        │
│  78%             61.2°C          —（无飞控）     │
│  [曲线]          [曲线]          [曲线]          │
└────────────────────────────────────────────────┘
```

理由：两块卡会在角落互相遮挡；一卡多格比页签更符合「一眼看全」，且飞控电量格能直接承载 ② 选定的**三态**（无飞控 / 飞控无数据 / 有数据）——三态文案就落在这一格里，不需要另开位置。

### 3.5 数据迁移

| 从 | 到 |
|---|---|
| `~/.dsh/dzrobot-ssh/settings.json` | `~/.dsh/dzairground-ssh/settings.json` → `{ car: {...} }` |
| `~/.dsh/dzdrone-ssh/settings.json` | 同上 → `{ drone: {...} }` |

**迁移规则（三条硬性）**：
1. **白名单**：只拷 `SETTINGS_INITIAL` 里存在的键，`camHost`/`camPort` 之类一律丢弃（§1.7）
2. **不覆盖**：目标已存在则不迁移（幂等）
3. **可回滚**：迁移前把两份旧 settings 备份成 `settings.migrated-<ts>.json`

**掉线如实表达（硬规则）**：`probe.state ∈ {ready, unreachable, needs-password, host-key, error}`，UI 只认这五种。`ready` 才亮绿；`unreachable` 必须是灰/红 + 原因原文。**禁止用上次的值假装在线**——现在 `status.json` 缓存了上次 probe，UI 必须比对 `at` 时间戳。

### 4.2 统一 metrics 契约（能力驱动 + 逐格归因）

> 本节已按成员审计结果修订。**关键更正**：原稿把 `battery` 当成可共用键，那是错的——见下方「命名冲突」一节。

**① 必须解决的命名冲突（这是合并唯一必须人工设计的接口）**

两侧都有个键叫 `battery`，但**类型不同**（lead 已独立复核源码）：

| 侧 | 键 | 类型 | 源码 |
|---|---|---|---|
| 车 | `battery` | `number \| null` | `dzrobot-ssh/src/metrics.js:237` |
| 机 | `battery` | `{percent, voltage} \| undefined` | `dzdrone-ssh/src/metrics.js:244-248` |

**如果直接 `{...car, ...drone}` 浅合并，车侧的电量数字会被静默覆盖成一个对象**，而车侧 `float.html:232` 用 `Number.isFinite(...)` 读它 —— **不报错，只默默显示 `NaN%`**。这类 bug 最难发现，必须在契约层改名，不能靠运行期没崩来判断。

**② 合并后的形状（逐格带归因）**

```jsonc
{
  "nodes": {
    "car": {
      "ok": true, "at": 1792234596505, "latencyMs": 1774,
      "gauges": {
        "batteryPercent": { "v": 78.0, "quality": "live" },
        "batteryVoltage": { "v": 11.9, "quality": "live" },
        "cpuPercent":     { "v": 31.5, "quality": "live" },
        "uptimeSec":      { "v": 9067, "quality": "live" },
        "bootEpoch":      { "v": 1792225530, "quality": "live" }
      }
    },
    "drone": {
      "ok": true, "at": 1792234597796, "latencyMs": 812,
      "gauges": {
        "temp":           { "v": 61.2, "quality": "live", "detail": "cpu-thermal · 6 测点峰值" },
        "cpuPercent":     { "v": 24.0, "quality": "live" },
        "uptimeSec":      { "v": 4821, "quality": "live" },
        "batteryPercent": { "v": null, "quality": "absent",
                            "reason": "dds_silent",
                            "detail": "飞控板在，/fmu/out/battery_status 无数据" }
      }
    }
  }
}
```

**每格都是 `{v, quality, reason?, detail?}`**，而不是裸数字。这样 UI 永远能回答「这个数为什么没有」——现在两侧只能整体说一句「无飞控」，把十种不同的现场情况压成一句错话。

**③ 统一缺席词汇表（两侧词表去重后 6 条，每条对应不同的现场动作）**

| `reason` | 含义 | 现场该做什么 | 来自 |
|---|---|---|---|
| `unreachable` | SSH 连不上 | 查网络/上电 | 车/机都有 |
| `stale` | 探针是缓存，超时未刷新 | 点「测试连通性」 | ★新增（修假绿） |
| `no_stack` | ROS 栈没起，话题没发布 | 跑 `start_all.sh` | 原车侧 |
| `no_battery_topic` | ROS 在，但电池话题没数据 | 查底盘节点 | ★新增（修假归因） |
| `dds_silent` | 飞控板在，但 `/fmu/*` 话题无数据 | 查 uXRCE-DDS agent | 原机侧 |
| `no_ros` | 有飞控设备，但没装/没 source ROS | 查 ROS 环境 | 原机侧 |
| `no_fc` | **压根没插飞控板** | 插板子 | 原机侧 `batteryFc=absent` |
| `not_supported` | 这个节点没有这个指标 | 正常，不用管 | ★新增（能力声明里没有） |

> `no_fc` 与 `dds_silent` **绝不能混用**：前者是「没有硬件」，后者是「有硬件没数据」。机侧 `metrics.js:33-34` 的注释已经明令禁止混淆，但 UI 层没执行（§1.6②）。

### 4.3 能力声明驱动 UI

面板与浮窗**不写死**「车有电量、机有温度」，而是读 `NODES[x].gauges` 决定画几个格子、画什么。
→ 后果：以后再加第三个节点（比如另一台车）不用改 UI。

> ✅ **这正是用户 ①「我不知道什么意思」选择的那一项**：本节的「读 gauges 决定画几格」= 附录 C.2 里的**方案 A 能力驱动**。
> 具体表现：车卡 3 格（电量/CPU/开机）、机卡 4 格（温度/CPU/开机/飞控电量），**谁有画谁，没有的格不画**——不会出现写着「不支持」的死格。
> 配套硬约束：`②` 三态（无飞控 / 飞控无数据 / 有数据）由 `reason` 字段承载，`no_fc` / `dds_silent` / 有值 三者一一对应，UI 直接映射文案，**不许再猜**。

### C.2 ①「metrics」到底是什么意思

**它就是浮窗上那几个数字格。** 两侧现在长得不一样，因为两台机器真的能测到的东西不一样：

| 节点 | 浮窗现有格子 | 数据来源 |
|---|---|---|
| 小车 | **电量** / CPU / 开机时长（3 格） | 电量走 ROS `/Battery_Percentage`；读不到就用电压按 12 V 满 / 10 V 空**折算** |
| 无人机 | **温度** / CPU / 开机时长 / **飞控电量**（4 格） | 温度读 `/sys/class/thermal/`；飞控电量走 PX4 `/fmu/out/battery_status` |

「合并策略」问的是：**车的浮窗要不要画一个温度格（写上「不支持」），机的浮窗要不要画一个底盘电量格？**

- **A 能力驱动（我替你定这个）**：车只画 3 格、机画 4 格。谁有就画谁的。
- B 统一两格：对称，但一半格子永远写着「不支持」——**现场看一眼多一个空格，纯噪声**。
- C 合成健康度：把 4 个数压成 1 个，**坏了一个你不知道是哪个坏**。

选 A 的实质理由：这不是审美，是**排障时你需要的定位粒度**。所以定了 A，你不需要再管它。
