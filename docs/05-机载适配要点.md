# 05 · 机载适配要点（模型上 Orin 板前必读）

机载程序 `onboard/dzuav/`（C++/TensorRT，JetPack 5 / TRT 8.5）。本轮已审阅过夜重构（Kimi Code），结论：无原则性问题。与模型相关的适配点如下。

## ① 形状契约耦合（换引擎前必改）

`onboard/dzuav/src/HbbDetector.cpp` 现在硬校验引擎输出形状 `[1,11,33600]`：

- 11 = 4（框坐标）+ **7 类**（官方 HbbDetector 引擎）
- 33600 = 1280 输入下的 anchor 数（(160² + 80² + 40²)，imgsz 不变则不变）
- **10 类的 v2 模型上板时输出是 `[1,14,33600]`——把期望值 11 改成 14**，否则构造即抛 `shape mismatch`（报错会打印实际形状，这是防护特性）
- 同理若换 `cell_classifier` 引擎，其契约为 `letter_logits [1,14]`、`row_logits [1,11]`

## ② 引擎转换

- 用仓库 `tools/orin_convert_engines.sh` 在板上转（pt → onnx → engine）；引擎与 TRT 版本绑定，**不要**把 PC 上转的 engine 直接拷过去用
- TRT 8.5 的 API 是 `enqueueV3/setTensorAddress` 一代；析构走 `destroy()`（代码已按 `NV_TENSORRT_MAJOR` 分流，勿改回 delete）

## ③ 运行韧性

- 断流重开只有**一次**，再失败进程退出（exit 4）。比赛现场建议给 dzuav 配 systemd `Restart=always` 看门狗
- UDP 广播有节流告警（每 300 次失败报一次），现场抓包排障时看 stderr

## ④ 类别语义对齐

- 机载广播的 `type` 字段语义由官方 7 类引擎定义；v2（10 类）上板后 type 值会变——**车端 `src/ag_integrate` 的类别映射表要同步改**，先查 `intel_protocol` 与 `field_matrix` 的类名→id 映射再部署
- bridge 类在 v2 已删：任务路由的"桥洞通行"逻辑若引用了 bridge 检出，应改为只信 arrow（产品决策：无箭头桥洞不可通行）

## ⑤ 互斥后处理（可选增强）

训练侧数据已按"同一物体单类别"清洗；推理侧可在 `processFrame` 加一步：IoU>0.5 的不同类框只留高置信度。能再压一部分格号→雷同框。
