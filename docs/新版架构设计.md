### 3.1 进程与线程拓扑（单进程多线程）

```
dzbrain 进程
├─ 主线程：rclpy MultiThreadedExecutor(4 线程池) —— 只跑 ROS 回调（订阅/服务），不做决策
├─ T1 LocalizationTask   20 Hz  定位与锚定：belief pose（格/米双表示）、到位吸附、漂移统计
├─ T2 TrackerTask        50 Hz  循迹：纯追踪 → pursuitAngle（唯一底盘驱动写入者）
├─ T3 MissionTask        10 Hz  任务调度：航点推进、停站事件、全局状态机、超时兜底
├─ T4 AimTask            50 Hz  云台瞄准+打击：目标观测融合、轨道运动估计、提前量、开火门控、弹药账本
├─ T5 FixTask            10 Hz  误差修正：系统比例误差估计、航向偏置、视觉反算修正
├─ T6 DroneTask           5 Hz  无人机通信：心跳、桥洞情报、靶区/雷障核对、车状态回传
├─ T7 SafetyTask         20 Hz  安全看门狗：心跳监控、越界、定位失联、急停（唯一有权强制停车者）
└─ T8 TelemetryTask       2 Hz  遥测/记录：统一状态快照、事件流、复盘数据（供网页/日志）
```

**为什么不"每任务一个进程"**：任务间共享信念位姿/路线状态/目标状态的频率极高（50 Hz 级），跨进程要序列化 + 时钟对齐；而重活（RKNN 推理、100 Hz 云台伺服、串口）本来就在独立 C++ 进程里，Python 侧线程足够。**用户要的"多线程部署每个任务点"由此满足**，同时保留将来把某个任务拆成独立进程的接口边界（任务只通过 Blackboard/事件总线通信，不直接互相调用）。

### 3.2 线程间通信（两种，别无其它）

| 机制 | 用途 | 实现 |
|---|---|---|
| **Blackboard**（共享状态 + 锁 + 快照） | 高频只读共享：位姿、路线位置、目标状态、无人机情报、安全标志 | 每键带"值+时间戳+版本号"；任务每拍取**不可变快照**，写者用 `with lock` |
| **EventBus**（单向事件队列） | 低频解耦：`ARRIVED_SHOOT_POINT` / `TARGET_FIRST_SEEN` / `HIT_CONFIRMED` / `DRONE_BRIDGE_PASSABLE` / `SAFETY_STOP` | `queue.Queue`，多消费者各自队列；事件不可变且带来源与时间戳 |

**禁止**：任务之间直接方法调用、共享可变对象、跨任务锁嵌套。跨任务依赖一律走事件。

### 3.3 任务基类契约

```python
class TaskThread(threading.Thread):
    name: str; rate_hz: float
    def setup(self) -> None: ...      # 订阅/发布/初始化，异常即启动失败（预检门禁会拦）
    def tick(self) -> None: ...       # 子类实现，单拍逻辑，必须非阻塞、必须无长 I/O
    def on_event(self, e: Event) -> None: ...
    # 框架保证：固定频率（补偿漂移）、异常隔离（单拍异常记录并继续/降级）、
    #          心跳（last_tick_at / loop_overrun_count）、优雅停止（stop() + join(timeout)）
```

## 四、纯追踪算法规范（通用好用 = 全部可配 + 可离线验证）

### 4.1 参数化（目标：几何/速度/判据全部进 `config/robot.yaml`，无硬编码）

| 类别 | 键（新增/迁移） | 默认 | 说明 |
|---|---|---|---|
| 车辆几何 | `pursuit.wheelbase_m` | 0.157 | 轴距（旧代码硬编码；现场可实测更新） |
| | `pursuit.max_steer_deg` / `max_steer_rate_deg_s` | 30 / 120 | 舵角限幅 + **新增**转向速率限幅（防一帧跳 60°） |
| 前视 | `pursuit.lookahead_min_m` / `_max_m` / `_k_v` | 0.18 / 0.45 / 1.2 | `ld = clamp(k_v·v, [min,max])`（旧为硬编码 0.15） |
| 曲率 | `pursuit.curvature_gain` | 1.0 | **1.0=教科书式 `δ=atan(2L sinα/ld)`**；设 0.5 可复现旧行为（旧代码漏了因子 2） |
| | `pursuit.lat_acc_max_mps2` | 0.35 | 曲率限速 `v_curve = sqrt(a_lat/|κ|)` |

| 转角 | `pursuit.corner_angle_deg` / `corner_slow_dist_m` / `corner_speed_mps` | 45 / 0.45 / 0.12 | 统一一处几何（消除 20°/45°/45° 三套阈值） |
| 停站 | `pursuit.stop_radius_m` / `overshoot_tol_m` | 0.17 / 0.30 | 停站触发与"开过头"补触发 |
| 安全 | `pursuit.map_safety_margin_m` | 0.60 | 越界急停（**提到最顶层**，所有分支生效） |

### 4.2 算法（每拍 50 Hz）

> ⚠️ **换公式的已知后果（必须现场整定前知会）**：旧代码的舵角分母是"车→前视点的**弦长**"，
> 新实现按标准做法用"**前视弧长预算 `ld`**"，两者差一个 `cos α`。所以即使把
> `curvature_gain` 设成 0.5（去掉因子 2），过弯仍比旧车**略硬**：
> 在 α=10°、ld=0.15、L=0.157 时，旧 10.1479° vs 新 10.3012°（**+0.153° / +1.5%**）。
> 这是"修掉漏因子 2"的同一条链路，属**有意变更**；首次实车建议先把
> `pursuit.corner_speed_mps` / `lat_acc_max_mps2` 保守一点，再按实际表现整定。
> 旧代码的退化保护 `dist < 0.01 → 直接 (0,0) 急刹` 没有移植 —— 改为
> "α=0 + `lookahead_floor_m` 兜底分母"（保住"防增益爆炸"的本意，但不再无预警急刹；
> 急刹职责归 `SafetyTask` 与停站状态机）。

1. **段定位**：`Path.project(pose)` → 当前段索引 + 沿程 s（**索引窗口 + 缓存**，替代每拍 2 次 O(N) 全扫；索引可后退以支持倒车/绕行）。
2. **前视点**：从投影点沿路径按弧长 `ld` 前进取点；接近顶点且转角 > `corner_angle` 时前视点钳到顶点（沿用旧代码已验证的"防最后一刻切角"策略，L1657–1731）。
3. **舵角**：`κ = 2 sinα / ld`；`δ = atan(κ·L)`；限幅 + 速率限幅；倒车段按 `reverse_steer_sign` 反转。
4. **速度**：`v = min(v_cruise, v_curve(κ), v_segment(speed_scale), v_stop_approach(d), v_corner, v_bridge, v_shoot_approach)`，再乘底盘量化补偿（`dzactuator` 的 `|v·23/0.33|` 截断有 −4.3% 系统误差，配置项 `chassis_speed_quant_comp`）。
5. **输出**：`pursuitAngle`（`Twist`：`linear.x`=m/s、`angular.z`=**度**舵角）+ **零 Twist = 刹车**；QoS `depth1/BEST_EFFORT` 契约不变（底盘订阅端要求）。

### 4.3 路线模型（替代 5 个平行数组）

```python
@dataclass(frozen=True)
class Waypoint:
    block: str            # "K9"
    x: float; y: float    # 米制中心
    yaw: float            # 到位后应朝向
    reverse: bool = False # R: 前缀
    shoot: bool = False   # * 后缀（射击停站）
    scan: bool = False    # :SCAN_STOP
    speed_scale: float = 1.0
    dwell_s: float = 0.0
    group: str | None = None   # SHOOT@ 候选链组号
    branch: str | None = None  # 分叉标签（无人机桥洞决策用，见 §七）
```

token 语法**保持向后兼容**（`*` / `R:` / `:SHOOT_STOP` / `:SCAN_STOP` / `SHOOT@靶标` / 末点 `,x|,y`），解析器变成**纯函数**（无 ROS 依赖，可单测）。

### 4.4 离线仿真（先做，风险最低、收益最大）

`tools/sim_pursuit.py`：几何路径 + 自行车模型 + 定位误差注入（比例误差/航向漂移/量化）+ 输出轨迹与指标（横向误差 RMS、超调、到位精度、总时长）。
用途：① 在本机把前视/增益/限幅调好再上车；② 每次改算法跑回归；③ 复现"跑偏 3.56 m"这类问题。
验收：仿真里 34 航点全程**能跑完**、无越界、横向误差 RMS ≤ 0.15 m（物理下限约 0.10 m，见 §7.1 末的几何推导）、总时长可预期。

## 五、移动轨道靶打击方案

**场景**（用户确认）：靶是**移动电子靶标**，轨道占相连两格（现场为 G11+H11，中心距 0.35 m，**行程 0.70 m**），靶在轨道上**来回走**。

**实测参数（用户给定，2026-10-07）**：

| 参数 | 值 | 推导结论 |
|---|---|---|
| 移速 | **4 cm/s**（匀速） | 单程 0.70 m ÷ 0.04 = **17.5 s**，往返 ≈35 s |
| 周期 | 无限，一直来回跑 | 无"停止回合"，不能等它停 |
| 端点停顿 | **无停顿**（瞬时折返） | ⚠️ **"折返点狙击"不可行**（端点没有停留窗口），策略必须走"带提前量的运动中开火" |
| 链路延迟 | 0.5–0.9 s（实测） | 延迟期目标位移 **2.0–3.6 cm**；在 0.35 m 距离上 ≈1 个开火框宽（14–26 px）→ **不做提前量必打偏一个框** |
| 提前量量级 | 4 cm/s × 0.35 s ≈ **1.4 cm** | 属"可精确补偿"范围，用时间戳对齐的延迟补偿即可 |

→ **默认开火策略改为 `moving_lead`**：预测落点在动态框内 + 连续 N 帧；`turnaround`（折返窗口）降级为可选项（本靶无停顿等价于不可用），保留 `sweep` 备用。速度慢是本靶的有利条件：只要**把延迟补偿做对**，命中窗口足够宽。

### 5.1 观测量与状态估计

| 层 | 内容 |
|---|---|
| 原始观测 | `offset_center` = [dx, dy, cls, 框宽, 框高, 关键点…]，30 Hz；每帧只发一个目标 |
| 距离代理 | 框宽 `w` 经 `box_w_far/near` 标定映射为距离（旧代码只用于死区宽度，**未用于提前量**） |
| 轨道坐标 | `s ∈ [0,1]`：由 bearing（dx）+ 距离 + 站台→轨道几何反算 |
| 估计器 | 1-D α-β 滤波（可升级 Kalman）：输出 `s, ṡ`；**折返检测**（`ṡ` 过零 + 端点邻近） |
| 延迟补偿 | `lead_time = 视觉流水线延迟 + 伺服滞后`（可配，默认 0.35 s；用时间戳对齐而不是拍脑袋） |

### 5.2 开火策略（可配，默认折返点优先）

| 策略 | 判据 | 适用 |
|---|---|---|
| `moving_lead`（**默认**，针对本靶） | 预测落点（含 `lead_time` 延迟补偿）在动态框内 + 连续 N 帧 | 匀速慢靶（本靶 4 cm/s） |
| `sweep` | 目标速度矢量已知 → 等目标**扫过瞄准线**的瞬间（提前量在框内） | 中速靶 |
| `turnaround` | 端点减速/折返窗口 | ⚠️ **本靶无端点停顿（瞬时折返）→ 不可用**，仅保留给"有停顿"的靶型 |

三条共同前提：**放行门真实生效**（见 §六 B1 修复）、命中即停火、单靶发数上限。

### 5.3 命中闭环（新增，省弹药）

**已落地（不再依赖"另行补齐"的中间话题）**：`dzbrain` 直接订阅车端**已经在发**的
`/HpAndHitmsg`（`std_msgs/UInt8MultiArray`，5 字节，`dzjudgment` 收帧即发 + 1 Hz 心跳），
在纯 Python 侧解析 → `AimTask` 记账：命中即停火、扣减弹药、记录证据。
好处是不动任何 C++ 硬件包、车端无需重编译（铁律：车端只读），且离线可测。

| 字节 | 含义 | 用途 |
|------|------|------|
| `[0]` | 对方血量 `targethp` | ★**命中判据：下降 N = 命中 N 次**；上升 = 新一局 → 重建基线 |
| `[1]` | 己方血量 `self_hp` | 我方挨打计数（遥测/复盘） |
| `[2]` | 被击打方位 `Bing_hit` | ⚠️ **我方被打方位**（0x01左/0x02前/0x03右/0x04后/0x10未被击打），**不是**命中确认 |
| `[3]` | 硬件累计发数 | 与云台 `/shoot_count` 交叉校验 |
| `[4]` | 剩余弹药 | 弹药对账 |

⚠️ 两个致命坑（都已在测试里钉死）：
① 旧文档把 `[6]`（即本表的 `[2]` 击打位）当命中 —— 那是**我们挨打**，照此实现会"每挨一发就停火一次"，
   而真正打中靶时毫无反应；
② 该话题带 1 Hz 心跳且**值与实帧完全相同**，必须按**状态变化**计数（HP 下降量），
   按"收到帧"计数会把命中刷成天文数字。

解析器：[src/dzbrain/dzbrain/io/referee.py](../src/dzbrain/dzbrain/io/referee.py)；
契约登记 `referee_hp`。契约里原有的 `/referee/hit`、`/referee/ammo`（`Int32`）车端**无生产者**，
保留作未来桥接兜底，且只在从未收到合法 `/HpAndHitmsg` 帧时才认（防双计）。
**全场仅 10 发**，闭环是刚需。

## 七、误差修正（FixTask）与无人机通信（DroneTask）

### 7.1 误差修正（FixTask）—— 用户选定：**只做 L2 位置修正**

| 层 | 状态 | 内容 |
|---|---|---|
| **L2 位置修正（本期实现）** | ✅ 选定 | ① 到位吸附（每到一个航点把信念位姿锚回格心）② 单段漂移统计与告警 ③ **系统性比例误差在线估计**：若每段都朝同一方向偏，说明 `ticksPerMeter` 存在系统误差 → 估计修正系数（保守步长 + 夹紧，防误收敛）④ 修正量全程可观测（报表/日志） |
| L1 航向修正 | ⏸ 预留 | IMU/编码器航向一致性 + 直行段偏置估计（接口留好，默认关） |
| L3 视觉反算修正 | ⏸ 预留 | 射击站上以已知靶位反算车位姿（接口留好，默认关） |
| L4 无人机位置修正 | ⏸ 预留 | 依赖无人机提供车的绝对位置（默认关） |

设计上 L1/L3/L4 与 L2 共用同一个"修正量汇合点"（`FixTask` 输出 `(dx, dy, dyaw, scale)` 到 Blackboard，由 `LocalizationTask` 统一应用），所以将来打开任何一层都不用改架构。

> ★★ **吸附的硬约束（仿真实测教训，必须遵守）**：吸附只有在"信念位姿本来就在格心附近"时才成立。
> 仿真里在**零误差**条件下开启吸附，`belief` 误差 RMS 从 **0.0000 m 被抬到 0.1191 m** ——
> 也就是"吸附"这个动作本身在**制造误差**（触发用真值、落点用格心，belief 被平移了最多一个吸附半径），
> 且实测会让现场图路线从"能跑完"退化成"跑不完"（822 s 撞步数上限、path_len_ratio 5.31）。
> 落地规则：
> 1. 吸附半径必须**小于**到位判定半径（`fix.anchor_max_offset_m`=0.08 < `pursuit.arrival_m`=0.12）；
> 2. 支持部分吸附（`fix.anchor_gain` < 1 更保守）；
> 3. 真实系统里"真值"不可得，判据只能用**控制收敛信号**（速度近零 + 已到点 + 直线段），
>    绝不能把"离航点近"当唯一条件。

> ★ **横向误差的物理下限（解释"为什么不能拿 0.06 m 当验收线"）**：
> `max_steer_deg=30°` + `wheelbase=0.157 m` ⇒ 最小转弯半径 `L/tan30° ≈ 0.27 m`；
> 而现场图一个 90° 弯只给 **0.35 m** 段长 ⇒ 车**必然**从顶点外侧掠过（实测最近 0.24 m）。
> 因此现场图路线的 `cross_track_rms` 实测地板是 **0.095~0.12 m**，
> 验收线定为 **≤0.15 m**（配"不越界 + 能跑完 + 末点误差 < 0.15 m"一起看），而不是追求做不到的 0.06 m。

### 7.2 无人机通信契约（待无人机侧确认）

| 项 | 约定 |
|---|---|
| 传输 | 同一 ROS2 domain 的话题（已验证 L2/L3 直连、双向 0% 丢包）；`std_msgs/String`，JSON 载荷，带 `seq/ts` 与 `type` |
| `/dzlink/drone_to_car` | `{"type":"bridge_passable","half":"lower","block":"K9","confidence":0.92,"ts":...}` / `{"type":"target_zone","blocks":["G11","H11"]}` / `{"type":"field_verify","mines":["H1",...],"obstacles":["D1",...],"diff":[...]}` / `{"type":"heartbeat"}` |
| `/dzlink/car_to_drone` | `{"type":"car_state","block":"J9","yaw_deg":87,"phase":"TRACK","plan":["N10","L10",...],"ts":...}` / `{"type":"ack","of":1234}` |
| 频率 | 心跳 1 Hz（**基础设施，不是功能**）；情报事件驱动（变更即发 + 1 Hz 重复）；车状态 1–2 Hz |
| 车侧消费 | ① **桥洞情报 → 选择穿越格**（见 §7.3）② **靶区/雷/障碍核对**：与 `map.yaml` + 视觉结果比对，不一致时告警并把差异写日志与遥测（高空视角 vs 地面识图）③ 车状态回传供无人机/地面站显示 |
| 失效兜底 | 心跳丢失 > 3 s：不阻塞任务（"宁可漏打，不可卡死"），告警 + 保持默认分支/默认地图 |

### 7.3 ★ 路线模型修正：U 形赛道 + **两处桥洞穿越格由情报决定**（用户权威澄清）

用户原话（2026-10-07）：
> 整个赛道是一个 14 列（A~N）× 11 行（1~11）的场地，在 D6~N6 和 D7~N7 之间有一个隔板，
> 在整个 K 列有一个桥，**每个格子都是一个桥洞**，在分界处有一个刚好一格宽的挡板。
> 因此小车要完成的路线其实是一个 **U 形赛道**：从 **N10 出发** → 通过 **K7~K11 任意一个格子里可能出现的一个桥洞** →
> 绕过 D6~N6 和 D7~N7 之间的隔板 → 开始**压雷、避障、打靶** → 然后穿过 **K1~K6 之间任意一个格子里可能出现的一个桥洞** → 到达 **N5 终点**。

**落地结论（对旧路线的重要修正）**：

| 结论 | 说明 |
|---|---|
| 路线不是一个固定列表 | 两次穿洞的**格号是每局随机的**（下半场 ∈ K7~K11，上半场 ∈ K1~K6），必须**参数化** |
| 旧路线把 K9/K4 写死 | 现场图识图当时恰好是 K9/K4，但**每局会变** → 写死会在别的局直接撞墙 |
| 无人机情报是硬输入 | 只有无人机能看到桥顶标识 → `DroneTask` 给出 `bridge_passable(half, block)` |
| 路线分三段生成 | **① 前缀**：起点 → 下桥洞入洞前的整备点（L{r}）② **中段**：穿洞 → 绕隔板（A/B/C 列）→ 压雷/避障/打靶 ③ **后缀**：上桥洞整备点 → 穿洞 → N5 |
| 分叉的时机与兜底 | 车出发时情报可能还没到 → 先跑前缀到整备点（顺路），到位后若情报已到则用真实格号生成中段；**超时（可配，默认 20 s）仍未收到 → 用默认格号（可配，默认下半场 K9 / 上半场 K4）并高声告警** |
| 校验增强 | `route_check` 增加：穿洞格 ∈ 候选集合、入洞前至少有 `align_straight_before` 格直线、U 形绕行必经 A/B/C 列 |
