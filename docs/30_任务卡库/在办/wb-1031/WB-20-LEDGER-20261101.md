## 为什么 dict 是错的抽象（不看这条就会做错方向）

`reg[path] = e` 的隐含假设是**"后来的登记代表当前状态"**。但本仓里这个假设是错的：
多条登记的语义不是"状态更新"，而是"**多个卡同时在改同一文件**"。

**铁证**（wb-doc 发现）：
```
config/robot.yaml → card = "AIM-LAT-20261022 + SHOOT-LINK-20261023 + CFG-A-20261031 + CFG-B-20261031 + WB-7-HANDSHAKE-20261031"
```
**有人已经在用"把多个卡名塞进一个 card 字段"手动绕开 dict 覆盖** ⇒ 使用者用字符串拼接绕过了容器语义，而门禁完全不知道。

⇒ 记入 `§12.10 L11`：**当使用者开始"绕开结构"时，先怀疑结构，不要先修使用者。**

## 为什么不是"纯 list + 任一过期就红"

现在就有 17 条会"多条并存"；若"任一过期就红"，会把"正在多卡协作"的正常状态**天天判红** ⇒ 信号被噪声淹掉。这与 `§12.10 L6` 的"稀释信号"是同一形态：**不是断言冗余，是红太多以致没人看**。

所以采用「list 并存 + **任一条有效算有主** + **过期条分 WARN/RED**」三段式，并用 `superseded_by` 区分：
- **被后来的登记盖掉**（有人忘了清）＝ 漏收口 ⇒ RED
- **被更新替代**（旧卡已收口、新卡接手）＝ 正常迭代 ⇒ WARN

`superseded_by` 还会**顺手产出一条可审计的接手链**——谁的卡接了谁，机器可查。
