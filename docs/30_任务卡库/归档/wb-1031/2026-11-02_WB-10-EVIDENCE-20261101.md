# WB-10 · 干跑工具的副作用污染（证据被当草稿纸 + 根目录泄漏）

## 读过的台账条目

- D-063（本线翻案依据）；铁律 5「证不出来 = 没完成」——**证据文件被随手覆写，等于证据链自我作废**。
- WB-9 卡面 §9：`dryrun_full_route.py:111` 用 `cwd=str(WORKSPACE)` 调机侧脚本（本卡查到的第 ② 条正是它的副作用）。

## 为什么必须修（captain 实测踩到）

本轮 captain 为复核 WB-9 的「5 处消费点支持显式 `--map`」跑了同一条命令两次（`--engine tour`、`--map <vendor 快照>`），结果**同一文件被覆写两次**：

| 时刻 | `EVIDENCE/dryrun_full_route.txt` 内容 | 问题 |
|---|---|---|
| WB-9 交付时（权威） | `引擎=tour` / 68 token / `ok=True` | 这是 WB-9 的验收证据 |
| captain 跑 `--engine tracker-safe` | `引擎=tracker-safe` / 0 token / 退码 2 | 权威证据被一次**交叉实验**替换掉 |
| captain 再跑缺省 | `tracker-safe` / 0 token | 又被替换 |
| 复跑 `--engine tour` | 恢复为 68 token | 靠运气还原，不是机制保证 |

危害不是"脏了一个文件"，而是：**任何人在这份工作区里做一次实验，都会把上一个人的验收证据悄悄换成自己那次的结果**，而且 `git status` 只显示"改了一个文件"，看不出是谁、用什么参数改的。`test_planner_sync` 与 `HASH_LEDGER.json` 都在钉这份证据的哈希，所以这属于会**制造假红/假绿**的结构性缺陷。

第 ② 条同源：`dzlink_supervisor.default_log_path()` 在 Windows 用 `os.getcwd()`，而 `dryrun_full_route.py:111` 把 cwd 设成**工作区根**，于是根目录被掉出 `dzlink_supervisor.jsonl`（本轮 captain 已两次把它移进 `_tmp_session/wb-1031/legacy/`，但**机制没修，下次跑还会掉**）。

## 处置原则

1. **干跑默认只读**：不落证据就不写盘；要落证据走显式开关（建议 `--write-evidence`），且文件名带参数指纹（引擎 + 地图 sha 前 8 位），**绝不**覆盖既有权威证据。
2. 机侧脚本的日志落地目录显式指定（传 `--log` 或环境变量），不许靠 cwd 兜底。
3. 不删任何既有 EVIDENCE 内容；历史文件原样保留，新证据另名。
4. 不许为了绿把 `test_planner_sync`/`HASH_LEDGER` 的期望改掉——本卡只改"谁有权限写这份文件"。

## 验收（独立复跑）

见 front matter `verify` 两条；外加负例：不带落证开关跑一次，`git status` 必须无变化。改动者自报不算过（铁律 7）。

## 回滚点

`_tmp_session/wb-1031/wb10/preimage/`（改前文件逐字节 + sha256）；禁止 `git checkout`。

## 经验总结

- 现象：干跑工具每次运行都**覆写** EVIDENCE，且在工作区根掉 `dzlink_supervisor.jsonl`——「我跑一次实验会顶掉别人的验收证据」。
- 机制：产物文件名不含参数信息 ⇒ 同路径必然互相覆盖；干跑本该只读却写了盘。
- 位置：干跑脚本 + `tools/link/dzlink_supervisor.py`。
- 处置：干跑默认**纯只读**（一个文件都不写）；落证走显式 `--write-evidence`，产物按 `引擎_地图sha前8` 另名 ⇒ 同参数两次可逐位比 sha256、换参数自动换名。另修 2 个同类缺陷。
- 证据：两处缺陷先实跑复现再修再双向反证；`dryrun_full_route.txt` 现无任何自动写者。
