### 2.1 我们需要对接的话题（其余不要碰）

| 方向 | 话题 | 类型 | 说明 | 来源 |
|---|---|---|---|---|
| 我方 → 车 | `/nav/waypoint` | `std_msgs/String` | **路线/复位命令**，见 §4 | `path_executor.py` 订阅 |
| 车 → 我方 | `/HpAndHitmsg` | `UInt8MultiArray` | 裁判状态 `[targethp, self_hp, hit, shots, ammo]` | `dzjudgment.cpp` 发布 |
| 车 → 我方 | `/enemy_Material_Number`、`/self_Material_Number`、`/all_Material_Number` | `UInt8MultiArray` | 物资队列 | 同上 |
| 车 → 我方 | `/shoot_count` | `std_msgs/Int32` | 已发射次数（`dzrknn_dataprocess` 发） | 用于判断打击是否打完 |
| 车 → 我方 | `/odom/localization` | `nav_msgs/Odometry` | 位置（**block 单位**）+ 朝向 | `serial_reader.py` |
| 车 → 我方 | `/amcl_pose`、`/odom/filtered`、`/scan`、`/image_raw` | 标准类型 | 定位/雷达/图像 | — |
| 我方 → 车 | `/LaserShot_Command` | `std_msgs/UInt8` | **开火**：发 `1` 再发 `0` | `dzrknn_dataprocess` / `dzjudgment` 订阅 |
| 我方 → 车 | `/CameMo_Conl` | `Int32MultiArray` | 云台 `[pos0, pos1, speed0, speed1]`（一般不用我们发） | `dzactuator` 订阅 |
| 我方 → 车 | `/cmd_vel`、`/pursuitAngle`、`/logicontrol` | `geometry_msgs/Twist` | 底盘速度/模式（**交给 path_executor**） | `dzactuator` 订阅 |

### 2.2 各个包干什么（别重写）

| 包 | 角色 | 关键接口 |
|---|---|---|
| `dzactuator` | 底盘底层：串口 ↔ 轮速/舵机/云台/IMU | 收 `cmd_vel`/`pursuitAngle`/`logicontrol`/`CameMo_Conl`/`StopCmd`；发 `odom`/`imu_data`/`Battery_Percentage`/`wakeup_signal`/`camemo_feedback` |
| `dzjudgment` | 裁判串口解析 + 开火下发 | 收 `LaserShot_Command`；发 `HpAndHitmsg` 等 |
| `det_node`（包名 `rknn_pt`） | RKNN 目标检测 | 收 `/image_raw`；发 `offset_center` |
| `dzrknn_dataprocess` | **瞄准 + 开火决策**（滤波/死区/PD/动态开火框/冷却/弹药/扫描） | 收 `offset_center`+`camemo_feedback`；发 `CameMo_Conl`/`LaserShot_Command`/`/shoot_count` |
| `car_localization` | 里程计读取 + **任务执行器** | `path_executor.py` 订阅 `/nav/waypoint`；`send_waypoint.py` 是发命令的小工具 |
| `dztrack` | 路径跟踪/巡线（另一套导航） | 发 `goal_pose`；收 `passenger_waypoints`/`amcl_pose`/`scan` |
| `navigation2`、`robot_localization`、`rplidar_ros-ros2`、`slam_gmapping` | 标准第三方包 | 建图/定位 |

> **结论：车端的"底盘驱动、云台控制、瞄准、开火、裁判解析"全部已经存在且经过调参。**
> 我们唯一需要产出的是**决策**：去哪、按什么顺序、在哪停靠打击。

## 4. `/nav/waypoint` 命令语法

订阅者：`car_localization` 的 `path_executor.py`（一个话题，四种命令）。

| 命令 | 例子 | 含义 |
|---|---|---|
| 复位 | `reset:N10,y` | 把里程计锚定到 N10、朝 Y+。**车是被人搬到起点的，每局必须先发**，否则整条路线整体偏移 |
| 路线 | `G8 A10 D2* E2,y` | 依次经过各格（直线连接、可对角）；`*` = **在该格停靠射击**，射满（默认 5 发）后继续；末尾 `,x` / `,y` 强制终点朝向 |
| 单点 | `M10,y` | 只去一个格（单点与路线的判别：恰有一个逗号且逗号前无空格） |
| 文件 | `load:/path/file.txt` | 从文件加载路线 |

要点（都来自源码，踩错就白跑一局）：
1. **合法格号 = 字母 A~N + 数字 1~11**。出现一个非法 token，车端会**丢弃整条命令**。
2. 逗号必须**紧贴**最后一个格号（车端用 `rsplit(',', 1)`）；写成 `E2 ,y` 会被判成"单点/非法"。
3. 连续重复的格号会被去重，`D2 D2*` 等价于 `D2*`。
4. 命令发出后**车会立即开始执行**，中途再发一条会覆盖当前路线（所以本项目的
   `car_node` 只在路线真的变化时才发）。
5. 节点启动后前 3 秒不接受命令（等模式切换），车端会打 warning。

`ag_car/route_builder.py` 已把这套语法实现+校验；`ag_car/car_node.py` 负责
「情报 → 规划 → 路线」并在 `dry_run=true` 时只算不发。

## 5. 裁判系统

### 5.1 推荐路径：用官方的 `dzjudgment`

```bash
ros2 launch dzactuator judgment.launch.py      # 参数 mcuserialport=/dev/dzjudgment, 115200
```

它自己做串口解析，发布：

| 话题 | 内容 |
|---|---|
| `/HpAndHitmsg` | `[targethp, self_hp, Bing_hit, Shooting_Count, ammo]` |
| `/all_Material_Number` / `/enemy_Material_Number` / `/self_Material_Number` | 物资队列 |

`Bing_hit`：`0x01` 左、`0x02` 前、`0x03` 右、`0x04` 后、`0x10` 未被击打。
**开火**：向 `/LaserShot_Command` 发 `1`，再发 `0`（一发脉冲）。

本项目的 `referee_node` 支持 `source=dz`：订阅上述话题、转发成
`/referee/state`，开火时在 `/LaserShot_Command` 上发 `1`/`0` 脉冲，
**完全不碰串口**（避免和官方节点抢 `/dev/dzjudgment`）。

### 5.2 原始针格式（`ag_core/dz_referee.py`，照抄 `judgment.cpp`）

```
B5 5B <len> <cmd> <data...>
  cmd  0x02 全部物资 | 0x03 对方物资 | 0x04 己方物资
  cmd  0x07 data = [targethp, self_hp, Bing_hit, Shooting_Count, ammo]
开火帧（源码写死 6 字节）： B5 5B 03 21 01 25
```

> `ag_core/referee_protocol.py` 里的 `0xAA55 + crc8` 是**自研兜底**，
> 实机不要用；两者关系已在文件头注明。

## 6. 云台 / 瞄准（既有链路，不用我们做）

`dzrknn_dataprocess` 已经实现了：EMA 滤波 → 跟踪死区 → PD 速度 → 动态开火框（按框宽估距）
→ 弹药/冷却 → 连续 N 帧确认 → 开火；没有目标时按 8 个方位点横扫搜索。

云台指令 `/CameMo_Conl`（`Int32MultiArray`，长度 ≥4）：
`[Position_0(俯仰刻度), Position_1(水平刻度), Speed_0, Speed_1]`
- 零位刻度 **2047**，`11.378 刻度/度`（4096/360）
- 水平轴限位 100~3995；俯仰轴限位 950~2400（下位机钳制）
- 反馈 `/camemo_feedback`：`[pos0, pos1, speed0, speed1, load0, load1]`

检测输出 `/offset_center`（`Int32MultiArray`，8 项）：
`[框中心x偏移, 框中心y偏移, 类别(1=蓝靶 2=红靶 0=无), 框宽, 框高, 关键点x偏移, 关键点y偏移, 关键点置信度×100]`

> ⚠️ **类别号是 1/2 而不是 0/1**：`det_node` 发的是 `res.cls + 1`。
> 训练时的类别顺序仍要锁定为 `0=蓝(敌) 1=红(友)`，映射见 `ag_core/target_policy.py`
> 的 `CLASS_BLUE/CLASS_RED` 与 `target_node` 的 `class_blue/class_red` 参数。

### 6.1 打击停靠的硬约束（决定路线怎么排）

`path_executor.py` 里和打击有关的常量（源码实测）：

| 常量 | 值 | 含义 |
|---|---|---|
| `SHOOT_COUNT_TARGET` | **10** | 到 `*` 格停车，等 `/shoot_count` 累计到 10 才继续 |
| `SHOOT_WAIT_TIMEOUT` | **150 s** | 等不到就放弃继续走（会吃掉大半局时间） |
| `SHOOT_STOP_RADIUS` | 0.17 m | 判定"已到停靠点"的半径 |
| `dzrknn_dataprocess.max_shots` | 10（`AIM_MAX_SHOTS`） | 全程弹药上限 = **10 发** |

推出三条**必须遵守**的结论：

1. **一条路线里只能有一个 `*` 停靠点**。两个的话第二个会等满 150 s 超时，
   而且此时弹药已经打光，一分都拿不到。
2. **靶是友方（红面）时绝不能标 `*`**，而且**不能因为"没有打击点"就不发车** ——
   那会白丢排雷 40 + 桥洞 20 + 终点 5 分。
3. 停靠等待是纯消耗（最长 150 s）：`car_node` 会先算
   「行驶时间 + 等待预算 ≤ 总预算 − 回终点余量」，不满足就**放弃打击保终点**。

这些都实现在 `ag_car/car_node.py`，由参数控制：

```yaml
min_mines: 1                # 至少确认几颗雷才出发
require_target_face: true   # 敌我未判决前不发车
max_shoot_stops: 1          # 弹药只够一个停靠点
shoot_wait_budget_s: 60.0   # 愿意为打击等待多久
car_shoot_wait_timeout_s: 150.0   # 与车端常量保持一致
fire_only_on_enemy: true    # 红面绝不标 '*'
```

现场若要调整打击等待，**改车端 `path_executor` 的 `SHOOT_COUNT_TARGET` 即可**
（例如按"2 次命中=1 计数、3 计数满"改成 6，能少烧 4 发弹、少等时间），
改完把 `car_shoot_wait_timeout_s` 一起同步。

## 8. 距离「丝滑」还有多远

### 8.0 四档定义（用能否复现来判定，而不是"感觉能跑"）

| 档 | 判定标准 |
|---|---|
| **L0 接口摸清** | 知道每个话题/串口/常量是什么 |
| **L1 能编译能跑** | 真机 `colcon build` 通过、节点起得来、决策链算出正确路线 |
| **L2 能跑完整一局** | 车按路线动、排雷、过桥洞、回终点，全程无人工干预 |
| **L3 能拿分** | L2 + 打击链打满 15 分、排雷精准、桥洞选对 |
| **L4 丝滑** | L3 + 现场 **2 分钟准备 + 3 分钟比赛**内稳定复现，两次机会都能跑出来 |

### 8.1 当前位置：**L1 完成，正在跨 L2**

| 证据 | 在哪 |
|---|---|

| 真机 `colcon build` 9 包零错误 + 9 入口可发现 + 4 launch 可解析 | `car_build.txt` / `car_verify.txt` |
| 契约校验 18 项与车端源码常量一致 | `car_xcheck.txt` |

## 9. 断联排查（车在 DHCP，IP 会变）

车是 `wlan0` + DHCP（实测 `10.15.166.188/24`），**IP 不固定**。

> ⚠️ 第一次遇到"车连不上了"，先看**自己这台笔记本**：
> 2026-09-27 就发生过一次"车断联"，实际是笔记本的 Wi-Fi 自动切到了另一个网络
> （`10.15.166.186` → `172.23.116.186`，SSID 还是叫 `win`），车其实一直好好的。

按顺序查三步：

```powershell
# ① 我这边在哪个网段？（关键：和车的网段是否一致）
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.IPAddress -notlike "169.254*" }
arp -a | Select-String "10.15.166"          # ARP 里没有车 = 二层都不通

# ② 车是否在线：端口探测
Test-NetConnection 10.15.166.188 -Port 22
```

```bash
# ③ 车的当前 IP（在车上的终端 / VNC 里执行）
hostname -I
ip -4 addr show wlan0
```

常见原因与对策：

| 现象 | 原因 | 对策 |
|---|---|---|
| 本机 IP 变成别的网段（如 `172.23.x`） | 笔记本自动连了别的 Wi-Fi | 手动切回比赛用的那个 SSID |
| ARP 里查不到车 | 车不在线/不在同一广播域 | 看车指示灯、VNC 是否还在 |
| 车 IP 变了 | DHCP 重新分配 | 给车做 **DHCP 保留** 或配静态 IP；或直接用 mDNS `duzhong.local` |
| 车在但 SSH 拒连 | 用户名/密码错 | 见 `docs/raw_txt/05_VNC远程桌面使用方法.txt`（车端默认用户名 `duzhong`） |

**建议现场做一次**：把车的 IP 固定下来（`nmcli` 改静态或路由器 DHCP 保留），
比赛现场才不用每次重新找 IP。

#### 找不到车时的最快做法：扫本网段的 22 端口

```powershell
# 同时发起 254 个连接，1 秒出结果（比逐个 Test-NetConnection 快得多）
$ips = 1..254 | ForEach-Object { "172.23.116.$_" }
$tasks = foreach ($ip in $ips) {
  $c = New-Object System.Net.Sockets.TcpClient
  [void]$c.BeginConnect($ip, 22, $null, $null)
  [pscustomobject]@{ IP = $ip; C = $c }
}
Start-Sleep -Milliseconds 1200
$tasks | Where-Object { $_.C.Connected } | ForEach-Object { $_.IP; $_.C.Close() }
```

2026-09-27 实测：**同一台路由器换了网段**（`10.15.166.x` → `172.23.116.x`），
SSID 仍叫 `win` 且只有一个 BSSID、信号 100%，所以"同名不同网"的坑这次是
**路由器发的网段变了**，不是笔记本连错。车仍是 DHCP 保留的最后一位：
`10.15.166.188` → `172.23.116.188`（MAC `28:2d:06:23:d0:6e`）。

> 所以"连不上车"的排查顺序应该是：
> ① 本机在哪个网段 → ② 扫本网段 22 端口 → ③ 看 ARP 里有没有车的 MAC
> （车的 MAC 后 12 位是固定的，换网段也能认出来）。
