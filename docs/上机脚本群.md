# 上机脚本群：分级、凭据与「什么输出证明什么」

> 配套 `docs/无人机工作流程.md` §7（那里只列命令，这里讲**每级证明了什么、没证明什么**）。
> 最后校准：2026-10-21，对齐分支 `agents/qoder/uav-onboard-review-20261020`。

## 0. 为什么要有这份文档

现场只有一次机会：180 s 硬时限、10 发弹、4 m × 5 m 场地。而这套系统此前反复出现的
不是「跑不起来」，是**假绿**——脚本报了通过，人照此起飞，问题在空中才暴露：

| 事故形态 | 日期 | 根因 |
|---|---|---|
| 一键启动拉起 9 月的 7 类老二进制 + 7 类引擎 | 2026-10-20 | `orin_run_dzuav.sh` 默认值指向 `$HOME/ag_test/dzuav` + `hbb_detector_fp16.engine`。类别索引与 13 类协议错位（障碍被当蓝靶），**界面上看不出任何异常** |
| `fix_live_hud.py --deploy` 静默退回修复 | 2026-10-20 | 该脚本在 `Trae-CN\default` 工作区（非 git 管理）、不在 `tools/`、不走提交、不留记录，却把硬编码的 kimi 树 `main.cpp` 覆盖到机上 |
| `orin_deploy.py --verify` 报 `L2_OK` 而编译其实失败 | 2026-10-16 | `&&` 短路后 `PIPESTATUS` 取到 2，恰好等于 usage 的期望退出码 |
| L3 用模糊匹配到的引擎出了「通过」 | 2026-10-20 | 字典序下 `cell_classifier_fp16`（7 类）排在 `cell_classifier_v4d_fp16` 前面，`find \| sort \| head -1` 选错 |

四条共性：**验证脚本证明的东西，和起飞需要的东西不是一回事**。所以本文档的核心口径是——

> **每一级只证明它实际走过的那条代码路径。改动落在哪条路径，就必须跑到哪一级，才允许把它从「已写待验」标成「已修」。**

C++ 改动在无 Orin 环境一律只算「已写待验」（见 `AGENTS.md`）。

## 2. 分级阶梯：什么输出证明什么

| 级 | 命令 | 走到的代码路径 | **证明** | **不证明** |
|---|---|---|---|---|
| **L0** | `orin_build_verify.sh` | 无（环境） | 这台机器是 arm64、有 TensorRT/CUDA、编译依赖齐 | dzuav 的任何行为 |
| **L1** | 同上 | cmake Release | 语法与链接通过，产物 `onboard/dzuav/build/dzuav` 存在 | 逻辑对不对 |
| **L2** | 同上 | `main()` 参数检查 | 二进制能起来，`usage:` + `rc=2` 这条分支活着 | 推理、相机、协议 |
| **L3** | `orin_build_verify.sh --run <engines> <图>` | **离线图片分支**（`runOffline`） | TRT 引擎能反序列化；检测→格号→PnP→UDP 全链走通；车上**同一个** `intel_protocol.parse` 能过 magic/version/CRC16/后缀校验 | **`runCamera()` 里的任何东西**：spec 解析、pipeline 三级回退、协商尺寸、断流重开、SIGINT 停机——一次都没进 |
| **L4** | `orin_camera_smoke.sh` | `runCamera()` | 相机路径的退出码语义、spec 严格性、协商尺寸对账、真出帧计数与 fps 预算、优雅停机、断流有界重开 | 检测精度、识别率（那是 L3 + 数据集的事） |

### 2.1 L3 的两个易误读点

1. **`localized=0` 不算 L3 失败。** 脚本会打 `[警告] 本图定位失败（localized=0，未发 UDP 属预期行为）`，
   L3a（推理管线完整）算过，L3b（协议闭环）没验到。要补 L3b 就换一张**含 4 个以上清晰格号**的图。
   报进度时别把「L3a 通过」写成「L3 通过」。
2. **回退到模糊匹配引擎 = 结论作废。** canonical 名不在位时脚本默认**直接判失败**，
   因为「L3 绿而下一秒 `orin_run_dzuav.sh` 报找不到引擎」比红更贵。
   确认要验旧引擎才 `ALLOW_ENGINE_FALLBACK=1`，且那个绿**不代表能上场**。

### 2.2 L4 的内部分级（A~C 不需要相机，D~E 需要）

| 级 | 验什么 | 现场要看到的那行 |
|---|---|---|
| **A** | 二进制在位且是 13 类（`grep -a uav_end` / `paper`）；canonical 引擎在位 | `[通过] 二进制为 13 类（含 uav_end / paper 类别名）` |
| **B** | 退出码语义表：坏端口 → `rc=2`，且**报错文案点名** `invalid udp port:` | `[通过] 报错点名 invalid udp port` |
| **C** | spec 严格性：9 个坏 spec 必须 `rc=2` 拒绝；7 个好 spec 必须**逐字回显** | `[通过] 回显逐字一致: camera spec: 1280x720@60` |
| **D** | 真相机：D1 spec 回显 / D2 打开 / D3 协商尺寸对账 / D4 真出帧计数与 180 s 预算 / D5 SIGINT 优雅停机 `rc=0` / D6 无故障模式 | `[通过] D3 协商尺寸 == 请求尺寸`、`[通过] D4 真出帧 N 帧 / 25s ≈ X fps` |
| **E** | 断流重开（`--drain`，**只能靠物理拔线**触发）：E1 触发了重开 / E2 次数 ≤ 3 / E3 耗尽则 `rc=4`、恢复则重新出帧 | `[通过] E2 重开次数在上限内（N ≤ 3）` |

关于 C 级为什么值得单开一节：`parseSpec` 的判据是**回写比对**（`spec != canon`），
所以 `0x0@30` 被拒（`w <= 0`），`1920x1080@0` 被接受（fps=0 = 不约束，两处 pipeline
构造都有 `if (fps > 0)` 守卫），而省略 `@fps` 会沿用调用方默认的 30 并**回显成带 @30 的
规范形**。这条「省略 @fps 时回显会多出 @30」最容易被人当成 bug 现场改代码，
所以 C 级的好 spec 表把输入与期望回显成对写死，并由
`tests/test_tools_smoke.py::test_camera_smoke_proves_default_fps_writeback_not_initial_value`
守着（要求至少一个好 spec 的分辨率不是 `1920x1080`，否则「回显等于输入」和「回显等于
初始值」两种实现分不出来）。

关于 D3 为什么默认判失败：内参按帧分辨率缩放，**协商尺寸一变，定位就系统性偏移**，
而 L1~L3 都不碰内参，看不出来。确认可接受才 `ALLOW_RESCALE=1` 重跑，否则改 pipeline
或用 `tools/calibrate_camera.py` 按协商到的尺寸重标。

### 2.3 关于 L4 的假绿防线

`orin_camera_smoke.sh` 的 `grep_log` 只看**本次调用**的日志片段（`mark_log` 在
`run_expect` 里第一件事就是打点）。不打点的话 `tail_log` 会从头读整个日志，于是
「无参数那次打过的 `usage:`」会被后面每一次 `grep_log "usage:"` 命中——断言看着在验，
其实验的是上一轮的残留。这条在本脚本的开发过程中真踩过一次。

## 3. 「已写待验」→「已修」：改动落在哪条路径，就得跑到哪一级

`orin_deploy_gate.py` 的 11 条锚点与验证级别的对应关系：

| 修复 | 闸门锚点 id | 文件 | 最低验证级 | 凭据（现场要看到的那行） |
|---|---|---|---|---|
| 相机 spec 严格解析（回写比对） | `spec-strict` | `main.cpp` | **L4-C** | `invalid camera spec:` + `rc=2` |
| 断流有界重开（3 次 + 退避 + 试读判据） | `reopen-bounded` | `main.cpp` | **L4-E** | `camera reopen failed (attempt N/3)`；耗尽 `rc=4` |
| 重开前先 `release()` 旧管道 | `reopen-release-first` | `main.cpp` | **L4-E** | 同上，且重开后能重新出帧 |
| 协商尺寸 != 请求尺寸必须喊出来 | `negotiated-size` | `main.cpp` | **L4-D** | `negotiated frame size:` 行 + D3 结论 |
| 连续异常上限两处共用同一常量 | `frame-errors-shared` | `main.cpp` | **L4-D/E** | `too many consecutive frame errors; aborting` + `rc=5` |
| 离线 `output_dir` 可省略且不淹 CWD | `output-dir-optional` | `main.cpp` | **L3** | 不传第 6 参也能跑完，CWD 无新增图片 |
| 离线循环响应 `g_running` | `offline-interruptible` | `main.cpp` | **L3 + Ctrl-C** | Ctrl-C 后 promptly 收尾，不是把整段素材跑完 |
| 定位输出 NaN 守卫 | `map-isfinite` | `MapLocalizer.cpp` | **L3** | `localized=1` 且坐标有限 |
| letterbox 居中（与训练分布一致） | `hbb-centered-letterbox` | `HbbDetector.cpp` | **L3 + 识别率** | 同一批图的召回不低于居中前 |
| 13 类协议真源 | `classes-13` | `types.hpp` | **L3 + accept_plan ⓪** | `ObjectClass` 恰好 13 成员、值 0..12 连续 |
| 类别名表与 13 类对齐 | `classname-table` | `main.cpp` | 同上 | 二进制里 `grep -a uav_end` 命中 |

### 3.1 闸门绿 ≠ 已修

`orin_deploy_gate.py` 证明的是**源码里有那段文本**（锚点、枚举形状、行尾、无明文口令），
它一次都没运行过 dzuav。它的用途是防另一类事故——**部署了一份不带修复的树**
（§0 表里第 2 行那种静默退回）。所以：

- 闸门红 → **拒绝部署**（`orin_deploy.py` 第 0 步直接 `return 1`），除非 `ALLOW_STALE_SOURCE=1`
- 闸门绿 → 只说明「送出去的那份带着全部已知修复」，**行为对不对仍要 L3/L4 出凭据**

闸门的锚点是**语义片段而非行号**，因为它必须扛得住上游重构：行号一改就红的门，
现场第三天就没人看了。同理，`frame-errors-shared` 盯的是比较语句
`frame_errors >= kMaxFrameErrors` 出现两次，不是常量名出现三次——源文件里这个常量名
实到 4 处（声明 + 相机分支比较 + 离线分支日志 + 离线分支比较），按名字数到 3 的话，
删掉相机分支那一处比较、把字面量 30 写回去，仍剩 3 处 → 照绿。
这类「削弱了的断言」由 `tests/test_orin_deploy_gate.py` 的变异测试守着
（`PINNED_COUNTS` 把重复锚点的阈值钉死，改阈值本身会被发现）。

## 4. 现场标准作业序列

### 4.1 笔记本上（部署前）

```bash
cd <仓库根>
python tools/orin_deploy_gate.py --root .          # 先看闸门，红了别推
set AG_ORIN_PASS=******                             # 口令走环境变量，别写进任何文件
python tools/orin_deploy.py --host <Orin IP> --user <用户> --verify
```

`--verify` 会远端跑 L1 编译 + L2 usage 自检（约 1~3 分钟）。
只推代码省流量加 `--skip-models`；`--all-models` 推整个 `models/release/`（>120 MB，慢网慎用，
默认只推 current 指针指向的那两个 ONNX，约 43 MB）。

### 4.2 机上（落地后，**按序**，不要跳）

```bash
cd ~/dzuav_deploy/air_ground

# ① 落地对账：机上这份 == 笔记本送出那份（防 §0 表第 2 行的静默退回）
python3 tools/orin_deploy_gate.py --root .
#    ⚠️ 清单里的 md5 是**笔记本工作区字节**的。本仓 core.autocrlf=true，而
#    .gitattributes 只锁了 *.sh/*.py/*.md/*.txt 的行尾、**没锁 *.cpp/*.hpp**，
#    所以 Windows 检出后 .cpp 全是 CRLF（main.cpp：CRLF 版 4e2b679b… / LF 版
#    fa4e2cca…）。sftp 是逐字节拷贝，机上那份因此也是 CRLF、能对上；但只要它
#    被 Linux 侧重新生成或重新 checkout 过，同一份源码就会给出不同 md5。
#    看到"md5 不一致"先想到这里，别先怀疑部署坏了。

# ② L0~L2：环境 / 编译 / usage
tools/orin_build_verify.sh

# ③ L3：真实推理 + 协议闭环（需要引擎 + 一张含 ≥4 个清晰格号的测试图）
tools/orin_build_verify.sh --run ~/dzuav/engines ~/test/field.jpg

# ④ L4：相机路径（A~C 不需要相机，可先跑）
tools/orin_camera_smoke.sh --no-camera
tools/orin_camera_smoke.sh                    # A~D，接相机
tools/orin_camera_smoke.sh --drain            # A~E，手要在 USB 线上，拔线数到 15 再插回

# ⑤ 规划验收（只写 /tmp，不动源文件；确认产物后再 --send）
tools/orin_accept_plan.sh
tools/orin_accept_plan.sh --send

# ⑥ 全栈启动（规划默认只落盘；确认过 ⑤ 的产物再开 0x4003 实发）
tools/orin_bringup.sh up
PLAN_SEND=1 tools/orin_bringup.sh up
```

手动单跑 dzuav **优先走启动脚本**（它是引擎名的唯一真源，会先把三件套亮出来）：

```bash
tools/orin_run_dzuav.sh camera /dev/video0 1920x1080@30
tools/orin_run_dzuav.sh image ~/test/field.jpg
tools/orin_run_dzuav.sh video ~/test/run.mp4
```

非要手敲二进制时，引擎名用 canonical 的 13 类：

```bash
BIN=~/dzuav_deploy/air_ground/onboard/dzuav/build/dzuav
ENG=~/dzuav/engines
HBB=$ENG/hbb_detector_d13_fp16.engine       # 13 类 D13
CELL=$ENG/cell_classifier_v4d_fp16.engine   # v4d 格号
$BIN uvc:/dev/video0 "$HBB" "$CELL" 50000 1920x1080@30
```

⚠️ **不要**用 `hbb_detector_fp16.engine` / `cell_classifier_fp16.engine`（无 `d13` / `v4d`）——
那是 7 类旧引擎，类别索引与 13 类协议错位，**障碍会被当蓝靶，而界面上看不出任何异常**。
这正是 §0 表第 1 行的事故形态。

### 4.3 证据归档（跑完当场做，别等回酒店）

```bash
# 机上：L4 的全量日志 + 结论表落在 /tmp/ag_camera_smoke_<时间戳>/
#        规划验收产物落在 /tmp/ag_accept_<时间戳>/
# 笔记本上拉回：
python tools/remote_run.py --host <Orin IP> --user <用户> \
    --get /tmp/ag_camera_smoke_<时间戳> --to 进度/evidence/
```

`camera_smoke.log` 是全量原始输出（证据），`camera_smoke.txt` 是结论表（人看的）。
归档时两个都要，随 `进度/` 一起提交。

### 4.4 AR0234 的帧率现实

USB2 下 YUY2 实测 **200 ms/帧 ≈ 5 fps**（1920x1200 原生）。L4-D4 会把实测 fps
折算成 180 s 硬时限内的可处理帧数并打出来——**起飞前先看这个数**，
它直接决定分区扫描策略能不能跑完，而不是等到空中才发现扫不完。

## 5. 三个「不要」

### 5.1 慎用仓外的 `fix_live_hud.py --deploy`，跑完必须重新对账

它在 **`Trae-CN\default` 工作区**（非 git 管理，见 `docs/成员交接/吸收决策与待验证清单-20261018.md`
V17 项），不在本仓、`orin_deploy.py` 也不推它。`--deploy` 全流程只有**一处** `sftp.put`：
把它硬编码的 kimi 树（或 `DZUAV_SRC` 指定的）那份 `main.cpp` 覆盖到机上同名文件。

> `SRC_FILES` 那五个名字（`main.cpp` / `CellClassifier.cpp` / `MapLocalizer.cpp` /
> `HbbDetector.cpp` / `UdpBroadcaster.cpp`）**不是推送清单**，是拿去做机上齐备性
> 点数的（`ls | wc -l` 必须 == 5）。另四个文件它不写。这点核对过脚本本体，
> 别按"它会覆盖五个"来理解。

为什么仍然要慎用：它在 2026-10-21 加了「汇流硬门」，是个好改进（fail-closed，
拒已知坏 md5），但**门只查两个能力标记** `jpegdec` / `DZUAV_VIEW`
——本闸门的 11 条锚点一条都不在里面。于是：

- 「过了它的门」≠「带着修复」。一份有 MJPEG 回退 + HUD 但**没有** spec 严格解析 /
  断流有界重开 / 协商尺寸对账的 `main.cpp`，它的门会放行并打印「通过汇流硬门」。
- 被覆盖的恰好是 `main.cpp`，而 11 条锚点里 **8 条**落在 `main.cpp`。这 8 条中
  5 条在 `runCamera()` 路径上（`spec-strict` / `reopen-bounded` /
  `reopen-release-first` / `negotiated-size` / `frame-errors-shared`）——
  **回退了 L0~L3 一条都不会红**（见 §5.3），只有 L4 能发现；
  2 条在离线分支（`output-dir-optional` / `offline-interruptible`），L3 够得到；
  1 条是类别名表（`classname-table`）。

所以：**要改 HUD 就走正常提交 + `orin_deploy.py` 重推，别在机上就地打补丁。**
非要跑它，跑完立刻在机上重跑闸门对账：

```bash
python3 tools/orin_deploy_gate.py --root ~/dzuav_deploy/air_ground
```

`orin_deploy_gate.py` 的 md5 清单给这五个文件打星标，就是为了现场对账时先比这五个；
其中只有 `main.cpp` 那条标成「会被覆盖」，另四条标「修复密集，对账重点」。

#### 顺带查出的三处问题（在用户工作区，本副本不动它，仅记录）

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 1 | `deploy()` 引擎预检 | 检查的是 `cell_classifier_fp16.engine` / `hbb_detector_fp16.engine`（**7 类旧名**），却打印「引擎 v4d+D13 在位」 | 机上只有 canonical 13 类引擎时（正确状态）**预检失败**，并被指向 `fix_cell_labels.py --deploy`；反过来 7 类在位时它宣称 v4d+D13 在位，是假的 |
| 2 | `probe()` 第 3 项 | 同上，`ls` 的也是 7 类旧名 | 探针报告误导 |
| 3 | `build_and_sync()` | 注释称「`orin_run_dzuav.sh` 用 ag_test」——该脚本 2026-10-20 已改成用仓库目录；仍会把二进制 `cp` 到 `~/ag_test/dzuav/build/dzuav` | 机上留第二份**会分叉**的二进制。哪天有人照旧路径手敲，跑的就是它 |

第 1、2 条与 §5.2 是同一个坑的两个入口：7 类引擎名。

### 5.2 机上已有 13 类引擎时，不要跑 `orin_convert_engines.sh`

它按 `models/release/` 的 current 指针（7 类）重新生成 `hbb_detector_fp16` /
`cell_classifier_fp16`，**会覆盖并不可逆地降级现网 13 类引擎**
（类别索引错位 → 障碍被当蓝靶）。

判据：

```bash
ls ~/dzuav/engines/ | grep -E 'd13|v4d'
# 有 hbb_detector_d13_fp16.engine + cell_classifier_v4d_fp16.engine → 别跑
# 一个都没有（换机/刷机后）→ 才需要跑
```

`orin_deploy.py` 推的是**指针指向的当前模型**，与机上已有的 13 类引擎不是同一批。
部署完成后它会把这个降级风险显式打出来；看到那行 ⚠️ 就别顺手跑引擎转换。

### 5.3 不要把「绿」直接当「能上场」

已知的三种假绿形态，以及各自的收口：

| 假绿 | 收口 |
|---|---|
| L3 用模糊匹配到的引擎出了「通过」 | canonical 名不在位时**默认判失败**；`ALLOW_ENGINE_FALLBACK=1` 才继续，且那个绿不代表能上场 |
| bringup 起了 tmux 窗口 ≠ 进程活着 | `ALLOW_STRAY` 同一套口径：异常必须显式确认，不默默放过 |
| 闸门绿 = 逻辑对 | 见 §3.1。闸门只证明源码里有那段文本 |
| `L2_OK` 而编译其实失败 | `orin_deploy.py --verify` 的命令串已改成显式 `[ $build_rc -ne 0 ] && echo BUILD_FAIL && exit 1`，不再靠 `&&` 短路 + `PIPESTATUS` |

还有一类**结构性的**假绿，值得单说：L0~L3 全都不碰相机，所以
「2026-10-20 复查发现的四条机载缺陷」即便一条都没修，L0~L3 也照样全绿。
L4 就是为这个缺口开的。**在 L4 出凭据之前，任何 `runCamera()` 里的改动都只能写「已写待验」。**

## 7. dzuav 退出码语义表

现场按这张表读 `rc`，不用翻源码。**认文案不认行号**（行号会随重构漂，文案是操作手
真正 grep 的东西）：

| rc | 含义 | stderr / stdout 文案 |
|---|---|---|
| `0` | 正常结束（含 SIGINT 优雅停机） | `stopped after ...` |
| `2` | 用法错误 | `usage:`（argc < 4）／`invalid camera spec: '<spec>'`／`invalid udp port: <p> (expect 1-65535)`／`unknown camera source: <s>` |
| `3` | 打不开输入 | `cannot open camera: all pipelines failed. ...`／离线：`cv::VideoCapture` 打不开（无文案） |
| `4` | 断流重开次数耗尽 | `camera reopen failed (attempt N/3)` 之后退出 |
| `5` | 连续帧异常超上限 | `too many consecutive frame errors; aborting`／离线：`frame N failed: <what>` 累积到上限 |

两条容易误读的：

- **`rc=2` 不一定是「参数打错了」。** 相机 spec 被拒也是 2，坏端口也是 2。
  看文案，别只看数字。L4-B 之所以除了比对 rc 还额外断言「报错点名 `invalid udp port`」，
  就是因为文案一变，现场按文案搜不到会查错方向。
- **`unknown camera source:` 这条分支实际不可达**：`runCamera` 的唯一调用方已经先按
  `argus:` / `uvc:` 前缀分流过了。它是防御性守卫，保留但不作为断言目标
  （断言一条永远不会走到的分支，只会给出永远绿的假安全感）。

## 10. 一句话总结

> **闸门保证送出去的是对的代码，L0~L2 保证它能编译能起来，L3 保证离线那条链是对的，
> L4 保证相机那条链是对的，`accept_plan` 保证规划产物是对的，`bringup` 才把它拼成一架能飞的无人机。**
> 跳过任何一级，就是把那一级验的东西留给空中去验。
