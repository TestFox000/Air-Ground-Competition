# 全线升级方案 · 2026-10-18（赛中执行版）

> 执笔：trae-glm（agents/trae-glm/upgrade-plan-20261018）。调研依据：docs/成员交接/吸收决策与待验证清单-20261018.md
> 的模块对比（OR-Tools / SMAC / Pure Pursuit / BT.CPP / Zenoh / FAST-LIVO2 等，来源与引用见该清单及本次调研记录）。
> 决策：**全线升级、赛中执行、不等下赛季**；每项必须过本方案第 2 节验证管线与第 1 节规则红线。

## 1. 赛事规则红线（每个升级项的合规检查，逐项打钩才准开工）

| 规则 | 内容（出处：01_自研包_dzmission/doc/AIR_GROUND_PROTOCOL.md §1 与 README） | 升级项合规要求 |
|---|---|---|
| **R2** | 禁止自建干扰网络（手机/电脑热点、对讲机）；自建 WiFi 是否允许**必须组委会书面确认** | 所有链路升级（U5）只换软件层，不新增任何无线硬件；自建 WiFi 合规确认是**既有关办**，与升级解耦 |
| **R16** | 比赛阶段禁止遥控 | 全部升级项零人工干预点；降级路径必须自动 |
| **传感器白名单** | 车端刻意无雷达；不新增传感器 | 车端升级（U1~U4）纯软件；无人机升级（U6）只用现有 Livox+D435i |
| **车端算力 <20 TOPS、禁在线推理** | 检测全在无人机 | OR-Tools/BT.CPP/SMAC 均为 CPU 计算（求解毫秒级），不触推理红线 |
| **3 分钟窗口 / 地图延迟 ≤300ms** | 紧格式增量 + 每秒快照 | U5 换传输层后必须实测延迟回归 ≤300ms，不达标即回滚 |
| **全程不允许人工干预** | 断链自动降级 | 每项升级保留并测试现有降级兜底（终点不可达等待扫描、单目标丢弃、死路雷放弃） |
| **裁判系统独立**（ESP32-S3 串口） | 不占空地链路 | 不动裁判链路 |

## 2. 验证管线（每项必走，缺一不上机）

```
任务分支（agents/<名>/<任务>）→ 实现 → 679+ 测试固定序+随机序双轮绿（基线只升不降）
→ SIL/仿真回归 → orin_build_verify.sh 机载编译全绿 → 台架实测 → PR（CI 门禁）
→ 余秉桓审核合 main → 上机
```

回滚保障：每项独立 PR；dzbrain v3.10 血线（preserve/car）受保护；升级一律**配置开关切换**（参照 `replan_on_update` 模式：默认关、台架验证后开），不删旧路径。

## 3. 升级项总表

### P0 · 即插即用（先行，无结构性风险）

| # | 升级项 | 内容 | 规则红线 | 认领（智能体/队员） | 验收标准 |
|---|---|---|---|---|---|
| **U1** | **OR-Tools 统一求解器** | `pip install ortools`；route_time + 排雷/打靶排序迁移到 OR-Tools Routing：方向/掉头约束作 arc cost，**"分/秒弃任务"作带 penalty 的可跳过节点**（一个求解器同时解决排序+取舍，替代 V3 的手工门控设计） | ✅ CPU 计算，无网络/传感器 | trae-glm 实现 + 万涛涛仿真验证 | 同场景 A/B：得分/耗时 ≥ 现有 DP；20 种子回归均分不降；679+ 测试绿 |
| **U2** | **Pure Pursuit（regulated）对标升级** | 车端循迹对照标准 pure pursuit 前视弧长公式校验；吸收 regulated 思想：**曲率大处自动限速**（对不可原地转向的 Ackermann 尤其重要） | ✅ 纯软件 | kimi（dznav 线）+ 黄宗启 | 台架画圆/切角问题复测；SIL 轨迹误差对比报告 |

|---|---|---|---|---|---|

| **U4** | **BehaviorTree.CPP 4.x 外层编排** | **只包外层**：任务流（起飞→扫描→发车→排雷/打靶穿插→终点→返航）建模为 BT；dzbrain 内层守卫逻辑（定位可信闸/禁火/漂移门禁）**原样封装为 BT Action 节点，不重写**。Groot2 可视化调任务流 | ✅ CPU；不改变任何安全语义 | qwen（架构评审）+ 胡锦宇（车端台架） | 全任务台架回归 + 断链/异常注入测试；血线逻辑逐条对账（M1/M2 守卫、fire_guard、jump_guard） |

## 6. 风险声明

1. **U4 风险最高**（动任务编排=动大脑）：故采用"外层 BT、内层血线封装不动"策略；台架不过就砍，不影响其他项
2. **U5 可能的结论是"不换"**——自研 UDP 本就是规避 DDS-WiFi 坑的正确设计，评估本身即是产出
3. 所有项共用一条硬规则：**orin_build_verify 不过不上机**（既有血线教训）
