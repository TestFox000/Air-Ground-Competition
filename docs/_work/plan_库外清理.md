## 1. 分类判据（先定规矩，再动手）

**只有满足下列之一才允许我们直接清：**

1. **A 类**：字节哈希与 `docs/` 内某篇相同 → 信息在库里有一份，删掉不损失任何内容。删除前记录 `(原路径, sha256, 库内对应路径)`。
2. **B 类**：同组内保留 1 份（保留哪份按「路径最短/最靠上」），其余删除，记录组内映射。
3. **C2 外部快照**：属于从 gitee/他人仓库拉下来的整棵副本，且**不是任何代码仓的运行依赖** → 整体打包为 `docs/_archive/snapshots/<名字>_20261022.tar.gz`，逐个文件不再散留。

**下列一律不自行处置，进清单：**

- C1 代码仓内文件（删了会破坏仓库完整性或门禁）；
- C3 过程稿中「结论尚未进库」的任何目录；
- 属于个人域/隐私的（`.zhiyuan` 3 篇、`memory` 2 篇）；
- 会话日志（`dzrobot_v2/src/history/log` 33 篇）——留存期限是制度问题，不是清理问题；
- 任何我们**说不清它是什么**的文件。

## 3. 回滚与不可逆边界

- 所有删除**先落 CSV 映射再动文件**；P3 的 tar 内保留原始相对路径。
- 关键一条：**被删文件的内容在 `docs/` 内必有一份**（A/B 的定义），所以真回滚是「从库内或 tar 里考回」，不需要回收站。
- 不做的动作：不删任何 git 仓库内的已跟踪文件（`dzrobot_v2` 是 git 仓，`git status` 必须保持干净）；不删任何 `vendor/`、`node_modules/`、第三方包文档。

## 4. 清单格式（你只需看这一张表）

## 6. 判定「结论是否已进库」的方法（避免误杀）

对每个过程稿目录，按顺序查三件事，任一命中即算「已进库」：

1. 目录内的 `REPORT/RESULT/结论` 文件，其关键数字是否出现在 `docs/` 的正文里（grep 数字与卡号）；
2. 目录名里的卡号（如 `TRACK-R2-REVIEW-20261020`）是否出现在 `docs/30_任务卡库/归档/`；
3. 目录内是否有 `_archive` 同名文件（说明原文已归档）。

三条都不命中的，**不删**，进清单并注明「需人工判断」。
