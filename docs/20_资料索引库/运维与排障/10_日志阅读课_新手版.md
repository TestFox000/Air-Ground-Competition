# 日志阅读课（新手版）

> **读法**：这篇回答「日志里**哪一行**说明什么」。至于「碰到某个现象该去查哪一条」，去 [01_症状索引_52条.md](01_症状索引_52条.md)，本篇不重建那张表。
> **素材**：2026-10-28 16:50:41~16:51:56 一次真车冷启动的七份日志，原样在 `_tmp_session/live/car_logs/`（1_chassis / 2_camera / 3_localization / 4_det / 5_gimbal / 6_judgment / 7_path）。引用时**已去掉终端 ANSI 颜色码**，其余一字未改。
> **一个前提**：那次起栈**没有发车**——等布局 30 s 收 0 条 → 按设计不规划、不出发。所以这批日志是「起栈 + 等布局」的完整标本，不是「跑图」的标本。
> **行号写法**：日志行的定位一律写成「`路径` + 第 N 行」而**不写成 `路径:行号`**。原因是 `check_doc_policy.py` 的 Y9 把 `_tmp_session/…:行号` 整串当路径查存在性、必然判「过程区死链」；`check_anchors.py` 对过程区锚点也只算黄。`文件:行号` 的写法只留给**仓内代码**（那是真锚点，会被机器判）。

## TL;DR（给 agent 看的）

- 七份日志里**每份只有 1~3 行决定结论**，其余是刷屏（`3_localization` 351 行里 340 行是同一条位姿）。

## 0. 先记一句：日志是「那一刻车上的 build」，不是本地代码

这是新手最容易踩的坑：拿**本地** `robot.yaml` 去解释**车上**日志里的数字，然后得出「代码有 bug」的结论。真相通常只是「车上跑的是旧版」。

把这次 10-28 的日志和本地真源对一遍，**六处对不上**——每一处都是证据，不是故障：

| 日志里的值 | 出现位置 | 本地真源 | 说明 |
|---|---|---|---|
| `ticksPer2PI:2680` | `_tmp_session/live/car_logs/1_chassis.log 第25行` | `config/robot.yaml:972` = **2670.0** | 车上是调回 2670 之前的那一版 |
| `俯仰偏移 +18.9°` | `_tmp_session/live/car_logs/5_gimbal.log 第6行` | `config/robot.yaml:50` = **+10.0** | 云台扫描俯仰基准，车上不是这份 |
| `冷却 800ms` | `_tmp_session/live/car_logs/5_gimbal.log 第7行` | `config/robot.yaml:198` = **500** | 云台侧两发最小间隔 |
| `提前量施加增益 1.00` | `_tmp_session/live/car_logs/5_gimbal.log 第14行` | `config/robot.yaml:229` = **0.5** | 两键开火补丁的提前量增益 |
| `等待无人机下发场地布局…（已 5/30s）` | `_tmp_session/live/car_logs/7_path.log 第36行` | `src/dzbrain/dzbrain/core/config.py:576` 缺省 **60.0** s | 布局门旧缺省 30 s，现行 60 s（`robot.yaml` 的 `drone:` 段没覆盖该键） |
| `[v4-dr-reset-signed]` | `_tmp_session/live/car_logs/3_localization.log 第12行` | `src/car_localization/car_localization/serial_reader.py:59` = `"v4-dr-reset"` | 节点自带版本标签，车上是带 `-signed` 的那版 |

**怎么用这张表**：判读前先扫一眼横幅里的数字，与本表/本地 `robot.yaml` 对一遍。**对得上**→ 可以拿本地代码解释行为；**对不上**→ 只解释「车上那一版当时怎么表现」，别顺手改本地代码去「修」一个不存在的 bug。

**三处「版本指纹」怎么找**：

1. **横幅参数值**（最便宜）：`_tmp_session/live/car_logs/1_chassis.log` 的参数块、`_tmp_session/live/car_logs/5_gimbal.log` 的六行参数，全是**配置中心读进来的生效值**（`dzactuator.cpp:1177-1188`、`dzrknn_dataprocess.cpp:1608-1676` 逐行打印）。
2. **节点自带版本标签**：`_tmp_session/live/car_logs/3_localization.log` 每条位姿末尾的 `[v4-dr-reset-signed]` 来自 `serial_reader.py:59` 的 `NODE_VERSION`；`_tmp_session/live/car_logs/1_chassis.log 第3行` 的 `参数来源: <路径>` 说明它读的是哪份 yaml。
3. **行为常数**：布局等待窗口（`已 X/Ys` 里的 Y）、心跳 3 s、每 5 s 一行的步进节奏——都是「这一版代码的常数」，不是「理论值」。

> **纪律**：写复盘时，凡引用车上日志的数字，标清「日志里的值」还是「仓内真源的值」。两者混用是 10 月这一轮里最费时间的误判来源。

## 2. 逐份精读

### 2.1 `_tmp_session/live/car_logs/1_chassis.log` —— 底盘：串口 + 里程标定

**先看哪三行**

```text
_tmp_session/live/car_logs/1_chassis.log 第3行   [dzactuator] 参数来源: /home/duzhong/dzrobot/config/robot.yaml
_tmp_session/live/car_logs/1_chassis.log 第29行  [dzactuator_node-3] [INFO] [...] [dzactuator]: dzactuator serial port opened
_tmp_session/live/car_logs/1_chassis.log 第24行  [dzactuator_node-3] ticksPerMeter:3280
_tmp_session/live/car_logs/1_chassis.log 第25行  [dzactuator_node-3] ticksPer2PI:2680
```

**逐行精读**

- `:3` **参数来源**——底盘读的是哪份 yaml。这一行是「配置中心生效了吗」的唯一证据；没有这行就是没读到配置、走代码内置默认值（参数由 `dzactuator bringup.launch.py` 传 `--params-file`）。
- `:23` `calibrate_lineSpeed:0`——**0 = 关掉「逐拍打印左右轮/位姿/电压」那条调试行**。想标定直线速度才临时改 1，改完每秒刷几十行（`dzactuator.cpp:1317-1322`）。**它不是「标定没做」**，是「标定打印没开」，别混。
- `:24` `ticksPerMeter:3280`——直行 1 米对应编码器计数（`robot.yaml:957`）。**动它 = 必须实车复标**，不是调参项。
- `:25` `ticksPer2PI:2680`——原地转一整圈对应的计数（`robot.yaml:972` 现为 `2670.0`）。见 §0 表。
- `:29` `serial port opened`——`/dev/dzactuator` 打开成功（`dzactuator.cpp:1191-1198`）。**这一行没有 = 底盘一个字节都发不出去**，后面所有节点都白起。

**刷屏那条要会认**（1500 行，占这份日志的 98%）

```text
_tmp_session/live/car_logs/1_chassis.log 第30行   [dzactuator_node-3] moveBaseControl.VoiceSwitch = 111
…（同一句共 1500 行，:30 到 :1529）
```

- 来自回调 `callback_voice_switch`（`dzactuator.cpp:241-246`）：**每收到一条 `/voice_switch` 就打印一次**，不是定时器。
- 1500 行 / 约 75 s ≈ **20 Hz**，说明图里有发布方在 20 Hz 重复发同一个值（本次契约表里 `/voice_switch` 写的是 `pubs=2`，见 `_tmp_session/live/car_logs/7_path.log 第28行`——除了 dzbrain 还有第二个发布方）。
- `111` 不是 dzbrain 发的：dzbrain 只在完赛时发 `mission.finish_voice_id`（缺省 0 = 不播，`core/config.py:383`）。
- **要查是谁发的**（只读，不动手）：

```bash
ros2 topic info /voice_switch -v       # 看 Publisher 列表与 QoS
ros2 topic echo /voice_switch --once   # 看值
ros2 node list                          # 对上 -v 里的节点名
```

> **教学点**：刷屏本身是证据——「某话题在 N Hz 被重复发」。别急着删打印，先反查发布方。

**坏样例（本次没遇到，但要会认）**：`_tmp_session/live/car_logs/1_chassis.log` 里**没有** `serial port opened`。可能是串口被占（上一套栈没清干净，`start_all.sh:35-44` 的进程组回收就是为这个加的），也可能是 `/dev/dzactuator` 的 udev 规则没生效。

### 2.2 `_tmp_session/live/car_logs/2_camera.log` —— 相机

**先看哪三行**

```text
_tmp_session/live/car_logs/2_camera.log 第10行  [usb_cam_node_exe-1] [INFO] [...] [usb_cam_node]: Starting 'default_cam' (/dev/video0) at 640x480 via mmap (yuyv) at 30 FPS
_tmp_session/live/car_logs/2_camera.log 第90行  [usb_cam_node_exe-1] [INFO] [...] [usb_cam_node]: Timer triggering every 33 ms
_tmp_session/live/car_logs/2_camera.log 第8行   [usb_cam_node_exe-1] [ERROR] [...] [camera_calibration_parsers]: Unable to open camera calibration file [/home/duzhong/.ros/camera_info/default_cam.yaml]
```

**逐行精读**

- `:10` 决定一切：**640×480、yuyv、30 FPS**。这三个数变了，视觉那侧的框宽标定（`box_w_far`/`box_w_near`）就跟着失真。
- `:90` `Timer triggering every 33 ms` = 出图定时器在跑（1/33 ms ≈ 30 Hz）。**这行之后没有新行是正常的**——相机不刷日志；它「有没有在出图」要到 `_tmp_session/live/car_logs/4_det.log` 去看。
- `:8` 的 **ERROR 是良性的**：没找到相机标定文件，`usb_cam` 打完警告照常出图（`:9` 是它的 WARN 版）。判读时不要因为见到 ERROR 就判「相机挂了」。
- `:12`~`:79` 是设备支持格式清单（60 多行），**纯噪声**，只有怀疑「怎么不是 640×480」时才需要看。
- `:81`/`:85`/`:88` 的 `unknown control 'white_balance_temperature_auto'` / `'exposure_auto'` / `'focus_auto'` 也是噪声：这颗摄像头没有这些 V4L2 控制项，设不上就报一句，**不影响出图**。
- `:11` `No accelerated colorspace conversion found from yuv422p to rgb24`——走软件转色，ARM 板上吃一点 CPU，**不影响正确性**。

**坏样例**：如果 `_tmp_session/live/car_logs/2_camera.log` 里没有 `Starting`，或起栈时相机那步很快退出——按 `start_all.sh:35-44` 原注释，常见根因是「残留进程抢 `/dev/video0` → 相机 `abort`（exit -6）→ 视觉侧表现为『无信号』」。处置走 [01_症状索引_52条.md](01_症状索引_52条.md) 症-07 一带。

### 2.3 `_tmp_session/live/car_logs/3_localization.log` —— 定位（`/odom/localization` 的生产者）

**先看哪三行**

```text
_tmp_session/live/car_logs/3_localization.log 第6行   [serial_reader_node-1] [INFO] [...] [serial_reader_node]: Map: 14x11, block=0.35m
_tmp_session/live/car_logs/3_localization.log 第11行  [serial_reader_node-1] [INFO] [...] [serial_reader_node]: IMU yaw init at +0.1deg
_tmp_session/live/car_logs/3_localization.log 第12行  [serial_reader_node-1] [INFO] [...] [serial_reader_node]: pos: (1.50, 0.50) | block: N10 | yaw: +90deg [imu] [v4-dr-reset-signed]
```

**逐行精读**

- `:6` `Map: 14x11, block=0.35m`——图 14 列 × 11 行、格 0.35 m（`serial_reader.py:39-41`）。**车端不留地图文件**，但「图尺寸」是编译进节点的，仍然是 14×11。
- `:7` `Start: (1.5, 0.5) blocks`——起点锚在 N10 格心（`serial_reader.py:44-45`）。
- `:8` `IMU: /imu_data, fallback after 2.0s`——IMU 断流 2 s 后 yaw 自动退到 odom 航向（`serial_reader.py:62`）。
- `:11` `IMU yaw init at +0.1deg`——IMU 零位。**每次起栈都会重锚**，所以「yaw 怎么不是 90°」这个疑问不成立：地图 yaw = 相对 yaw + `dr_yaw_off`（缺省 +90°，`serial_reader.py:135`）。
- `:12` 一条位姿行拆三段：`pos: (1.50, 0.50)`（格坐标）/ `block: N10`（格名）/ `yaw: +90deg [imu]`（**方括号里是 yaw 来源**，`imu` 好、`odom` 说明 IMU 掉了）+ 末尾方括号是节点版本标签。
- **打印节流**：位姿回调 50 Hz，但每 10 帧才打一次（`serial_reader.py:246-255`），所以日志里是 **5 Hz / 0.2 s 一行**。`:12` 之后每 0.2 s 一行就是正常。

**这一份里最值得学的一处**：把 340 条位姿比首尾——

```text
_tmp_session/live/car_logs/3_localization.log 第12行   pos: (1.50, 0.50) | block: N10 | yaw: +90deg [imu] [...]
_tmp_session/live/car_logs/3_localization.log 第351行  pos: (1.50, 0.50) | block: N10 | yaw: +91deg [imu] [...]
```

车**一动没动**，67 s 里 yaw 从 +90 走到 +91，约 **0.015 °/s** 静置漂移。这不是本次故障（不影响等布局），但正是「车停一会儿车头自己歪」那条老帐的现场形状——机制与处置在 [01_症状索引_52条.md](01_症状索引_52条.md) 症-20，本篇不重复。

**坏样例**：banner 之后**一条 `pos:` 都没有**——说明 `/odom`（底盘里程计）没进来。这时 `_tmp_session/live/car_logs/7_path.log` 会以「位姿就绪门超时 / 退出码 5」报出来（`main.py:2387-2454`）。

### 2.4 `_tmp_session/live/car_logs/4_det.log` —— 视觉检测（RKNN）

**先看哪三行**

```text
_tmp_session/live/car_logs/4_det.log 第4行   [det_node-1] [INFO] [...] [det_node]: 视觉检测: 模型=/home/duzhong/dzrobot/install/det_node/share/det_node/model/light_det.rknn | 线程=2 | 推理周期=33ms(约30 fps) | 窗口=关 | 热加载=开
_tmp_session/live/car_logs/4_det.log 第5行   [det_node-1] [INFO] [...] [det_node]: 已关闭识别画面窗口（config: draw: false）
_tmp_session/live/car_logs/4_det.log 第6行   [det_node-1] [INFO] [...] [det_node]: waiting for /image_raw ... (is the camera node running?)
```

**逐行精读**

- `:4` 一行三个关键事实：**模型从哪加载**（`install/det_node/share/.../light_det.rknn`，走安装树不是源码树）、**推理周期 33 ms ≈ 30 fps**（`det_node.cc:76-79`）、**窗口关**（`draw: false`）。
- `:5` 确认窗口关。**ARM 板上是好事**：省掉 30 Hz 的 `imshow + waitKey`（`det_node.cc:80-84`）。没设 `DISPLAY` 而 `draw` 又开着，节点会直接崩（症-07）。
- `:6` 这行是**一次性**的：只在还没收到任何图像时打，且带 2 s 节流（`det_node.cc:220-222`）。**打一次正常（比相机晚起几秒），一直刷就是相机没出图**。
- `:7` 起每秒一行 `dedup: skips=… frames=…`（`det_node.cc:206-212`）：
  - `frames` = 已推理帧数；`skips` = 「时间戳与上次相同 ⇒ 整拍跳过」的次数（`det_node.cc:231-234`）。
  - 末行 `_tmp_session/live/car_logs/4_det.log 第71行  dedup: skips=288 frames=1693` → 约 **25.6 fps 推理、跳过率 17%**，健康。
  - **为什么要去重**：单线程 executor 下定时器会阻塞在 `get()`，图像回调被饿死，同一帧被反复推理——实测重复 1.95×（`det_node.cc:228-230` 原注释）。所以 `skips` 不是错误计数。
- **反推**：`frames=1693` / 66 s ≈ 25.6 fps，与 33 ms 周期吻合；明显低于这个数说明推理在掉帧（板子温度/线程数）。

**好样例对照（收到 v2 布局时会打成什么样）**：`main.py:2481-2484` 会打布局摘要（起/终/雷/障/靶/桥洞），`main.py:3038-3040` 再打 `✅ 收到布局 v2（known N 格）→ 进入运行期步进循环 …`。**看到 `✅ 收到布局 v2` = 这一趟能跑；只看到 `⚠️ 等待…超时` = 这一趟不跑。** 就这一句之差。

### 3.2 域号：118 意味着什么

```text
ROS 链路域号: ROS_DOMAIN_ID=118  ROS_LOCALHOST_ONLY=0  (车标准域 118)
```

- **118 是对的**（车标准域；`start_all.sh:123-126` 把域号钉在 `dzros.env`，不再依赖 `~/.bashrc`）。
- 两个数**不一致**时横幅会多打 `⚠️  域号偏离标准值 —— 无人机侧必须跟着改 ~/dzlink_tools/dzlink.env，否则互相看不见`（`start_all.sh:161-163`）。
- 为什么这条最要命：**非交互 SSH / systemd / cron 不读 `~/.bashrc`**，域号会掉回 0；症状是「ping 通、SSH 通、网页通，但 ROS 死活看不见对方、一个错都不报」（`start_all.sh:114-121` 原注释）。判读时不要只看「通不通」，要看**域号一不一样**。

### 3.3 布局模式 vs 文件模式（一句话分叉）

```text
# 没有 map.yaml：
地图：布局模式（/home/duzhong/dzrobot/config/map.yaml 不存在）—— 规划依据由无人机 field_layout 下发
# 有 map.yaml（危险）：
⚠️⚠️ 地图：发现残留文件 /home/duzhong/dzrobot/config/map.yaml
        → 将进入【文件模式】：按这张图静态规划，无人机 field_layout 不决定走法
```

| 你看到 | 这趟的规划依据 | 下一步动作 |
|---|---|---|
| `地图：布局模式` | 只认无人机 `field_layout` | 先确认机端在发；收不到就是 exit 3，**别指望本地兜底** |
| `⚠️⚠️ 发现残留文件 … → 将进入【文件模式】` | 这张**静态图**，机端布局不决定走法 | 若不是故意的：`rm -f ~/dzrobot/config/map.yaml` 后重起（`start_all.sh:185`） |

**为什么要显式分叉**：历史写法恒传 `--map config/map.yaml`，而文件已被删——结果仍是布局模式，但**谎报了意图**；更危险的是谁把旧 `map.yaml` 塞回车上，就会**静默**切成文件模式（`start_all.sh:168-174` 原注释）。

### 3.4 `auto_start` 三件套（三个开关，别混）

| # | 开关 | 真源 | 现役值 | 横幅原话 | 看见它要做什么 |
|---|---|---|---|---|---|
| ① | `mission.auto_start` + `mission.auto_start_delay_s` | `config/robot.yaml:713-714` | `false` / `10.0` | dzbrain 横幅 `自动出发: False（延时 10.0s）`（`main.py:2578`） | `False` = **不会自己跑**，等人发 `/nav/waypoint` |
| ② | `path_executor.auto_start` + `auto_start_delay` | `config/robot.yaml:337`、`config/robot.yaml:341` | `false` / `45.0` | `旧核自跑：auto_start=false（不会自己出发）`（`start_all.sh:221`） | 只有 `LEGACY_PATH=1` 才相关；为真则**起栈即自己出发** |
| ③ | `LEGACY_PATH` 环境变量 | `start_all.sh:273-276` | 未设 = 新核 | `[新核] dzbrain —— 8 任务线程 …` / `[回退] 旧 path_executor …` | 确认这趟跑的是**新核还是旧核**，两者日志形态完全不同 |

**最危险的组合**是 ② 为真 + ③=1：横幅会打 `⛔⛔ 旧核自跑已武装：path_executor 段 auto_start 为真（延时 45s）`，紧跟两行 `起栈后旧核会【自己出发】，没有任何确认步骤`（`start_all.sh:215-219`）。看到 `⛔⛔` 只有一件事要做：**先别靠近车，核对起点格心/车头朝向/走廊净空，要停就 `bash start_all.sh stop`。**

## 5. 现场五分钟判读流程

1. **看 `_tmp_session/live/car_logs/7_path.log` 最后 5 行** → 有没有 `退出码 N` / `已停止` / `✅ 收到布局 v2`。一句定性：**跑了 / 拒跑 / 崩了**。
2. **回 `:9` 三行话题计数** → `odom`、`drone_in`、`pursuit_angle` 的 pubs/subs。谁 0 就是谁没起。
3. **看契约表头 `:11`** → 「阻断」是不是 0。是 0 就别再查契约；不是 0 就只查 `❌` 那几行（`⚠️` 一律跳过）。
4. **对版本** → 拿 §0 那张表扫一眼横幅数字。对不上就别用本地代码解释。
5. **看配套三份** → 云台 `:14`（两键开火）、裁判 `:10`（串口成没成）、定位 `:12`（有没有位姿）。三份都健康，问题就只在「对面没发东西」。

> 顺序不能颠倒：先定性（1）、再定位（2-3）、最后才怀疑代码（4-5）。反过来做，就是把「没发」当成「算错」。
