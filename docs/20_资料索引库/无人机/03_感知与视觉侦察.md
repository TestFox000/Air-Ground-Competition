# 感知与视觉侦察

## TL;DR（给 agent 看的）

- 感知分三层：**定位**（Livox→FAST-LIO→/Odometry→EV，真机跑通）+ **相机取流**（29.2 Hz 出图，跑通）+ **视觉侦察**（dzuav 检测/格号/箭头，**从未在可用实拍帧上验证**）。
- 三个 python 定位节点（global_localization / transform_fusion / global_map_publisher）曾全部 ImportError 死亡，10-17 已修活（open3d 0.20.0 + tf_transformations 已装）。
- **最大的坑**：单测 99/99 绿 ≠ 能看见。10-18 真机 live 窗口 21.0 fps、**det=0**，5 帧历史图拉普拉斯方差 1.37~49.1 **全是糊的** ⇒ 格级感知至今没有一次「可用帧 → 正确结论」的证据。
- 第二坑：px4_odom_convert 的 launch 默认 mode=localization，而 /localization 常常不存在 ⇒ **VIO 永不出且不报错**。必须显式 mode:=odom。

## 1. 定位链（真机跑通，有日志）

| 环节 | 实测 | 证据 |
|---|---|---|
| 雷达驱动 | /livox/lidar **10.000 Hz**、19968 点/帧；/livox/imu **200.9 Hz** | dzsmartscout/docs/drone/感知链体检_20261017.md:13-16、:55-58 |
| FAST-LIO | /Odometry **43.3~44.7 Hz**，invalid_gap=0 | 同上:92 |
| 三 python 节点 | /localization **~44 Hz**（修复后） | 同上:97-113 |
| EV 到 PX4 | /fmu/in/vehicle_visual_odometry **42.4~44 Hz**，静止 dx/dy ~0.1 mm/帧 | 同上:152；docs/交接_无人机飞行分析_agent技术文档.md:39 |
| EKF 接受度 | eph **0.032 m** / epv **0.029 m**、heading_good_for_control=true、dead_reckoning=false、timesync RTT ≈ 3 ms | 交接:39（10-17） |
| 点云桥 | /livox/points 10 Hz、/dzlink/seq 50 Hz | 感知链体检:196-197 |

**FAST-LIO 关键配置（mid360_test.yaml）**：blind=0.8 m、det_range=40 m、scan_line=4、scan/map_voxel=0.18、localization_th=0.85，外参 extrinsic_T 已标定（dzsmartscout/fc-audit/notes/fastlio.md §2.3；无人机技术文档:263-274）。

**odom 桥（px4_odom_convert）三个必知**：

| 项 | 事实 | 证据 |
|---|---|---|
| 默认模式坑 | launch 默认 mode=localization（launch:35），代码默认 odom ⇒ 必须手加 mode:=odom | launch/px4_odom_convert.launch.py:35 |
| 两模式数值等值 | 无 /map_to_odom 时 transform_fusion.py 用 np.eye(4) ⇒ odom 与 localization **逐位相同**，区别只是死的/活的 | transform_fusion.py:54 |
| 输入驱动 | 来一帧发一帧，VIO 频率 = FAST-LIO 频率（非定时器） | _tmp_session/agent_overview_20261020/drone.md:71 |

**为什么必须 mode:=odom（真实事故）**：三个 python 节点因 from tf2_ros import transformations 失败全死（exit code 1），/localization 不存在 ⇒ 默认模式订阅空话题，**永远不会向 PX4 发外部视觉，而 RViz/点云一切正常**。这就是它长期没被发现的原因（dzsmartscout/fc-audit/启动手册.md:29-35）。

## 6. 想推进视觉侦察，按这个顺序

1. 先修 P1-4（断流重连 + 退避），否则断一次流就要人工重启。
2. 用**能看清场地的实拍帧**跑一遍 5 类目标（雷/障/靶/格号/箭头），把「单测绿」换成「实拍绿」。
3. 桥顶箭头是赛制支点（只有无人机能读桥顶箭头）⇒ **优先级高于雷/障**。
4. 帧率/分辨率先定口径：640x480 出图 29 Hz 但糊；1280x720 只有 13~21 fps。

## 7. 侦察落地四阶段（2026-10-20 建议稿，未执行）

> 来源：桌面 `报告/四、建议流程（分 4 阶段，每阶段有验收判据）.txt`。这是**方案**不是现状：`recon_sender.py` 至今未写，四阶段一步都没跑。

| 阶段 | 动作 | 验收判据 |
|---|---|---|
| **0 一张好图**（只依赖抬机） | 机放场地上方 **2.5~3 m**，镜头垂直朝下对准全场 → 抓帧 | sharpness **≥100**；四角可辨；`perception.cli detect` 叠加图与官方图逐格对比：**8 雷 / 8 障 / 2 靶 / 2 桥** |
| **1 单帧 → 布局** | 四角标定 → 逐格分类 → 生成 field_layout v2 `{version,start,end,known,mines,obstacles,targets,bridges,barrier_*}` → 发 `/dzlink/drone_to_car`（BEST_EFFORT，1 Hz） | 车端 StepLoop 收到后**能据此规划**；`known` 只含真判读过的格（没判读的格绝不当「没有」，沿用 coverage.complete 语义） |
| **2 分区 / 增量侦察** | 单帧看不清就切 2×2 或上下半场；每片带 `coverage{cells,complete,mode}`，逐片发、版本递增 | **154/154 覆盖**；负证据只在 `complete=true` 的片内成立 |
| **3 飞行中侦察** | 悬停稳定 + 姿态补偿；每帧更新 `known` 与要素；段边界按 D-020「首段可靠即可发车」用增量版本 | 同阶段 2，另加姿态补偿后格号不跳变 |

**与既有缺口的对应**：阶段 1 的输出正是 [01_协议v2与契约.md](../空地链路/01_协议v2与契约.md) 的 field_layout v2；阶段 2 的 `known` 空域问题正是 [02_链路联调与已知缺口.md](../空地链路/02_链路联调与已知缺口.md) §5 缺口 1（`CELL_LABEL`/`BUCKET_*` 被丢，known 只收有检出物的格）——**四阶段跑之前，这个缺口必须先补**。
