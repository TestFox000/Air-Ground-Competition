## 2. 三个根因（本篇的核心价值）

### 2.1 云台俯仰：被"扫描区间"锁死在 `[0°,12°]`

- 现象（用户原话）：昨天跑车"云台只能在水平上跟着目标"。
- 定位：跟踪分支复用了扫描用的 `clampPitchToScan`，而允许区间 = `offset ± margin`。
- **实配与注释不符**：注释写 `-26°`，实际 `scan_pitch_offset_deg = 6.0`；`scan_pitch_levels = [0.0]`（min==max）；`tracking_pitch_margin_deg = 6.0` → 区间 **`[0°, 12°]`，刻度 `[2047, 2183]`**。
- 后果：地面靶需要低头约 **40°**，下限却是 0° ⇒ **物理上低不下去**；水平轴 ±90° 很宽 ⇒ 表现就是"只能左右跟、总追着靶头顶"。
- 修复：跟踪分支改走**机械限位** `clampPitchTick`（`950~2400` ≈ **-96°~+31°**），扫描分支保持扫描区间；同时修掉那条让人误判的配置注释。
- **后续（重要）**：本次只打开了区间，**没有解决俯仰修正方向问题**——真正症状要到 **10-17** 才除净（负号问题）。今天查代码能读到的完整复盘在 `dzrknn_dataprocess.cpp:174-203`；"区间打开反而暴露下一个缺口"是这条留到今天的方法论价值。

### 2.2 规划器静默吃雷（零告警）

- 用户要求"用 TEB 思路做 C8 路线"，结论是：**TEB 的核心（障碍斥力 + 转向代价 + 阿克曼动作集）现有规划器已有**，真 bug 在别处。
- `path_to_waypoints` 做直线段压缩时会删中间格，**`force_keep` 只含射击点与桥洞，不含雷** ⇒ 8 个雷里落在直线上的 **`H1/G2/C4/B5` 被删**，输出路线只剩一半，**且不报任何错**。
- 修复后重新生成：**雷 8/8 覆盖、桥洞 2/2、射击点 `H10*`、不踩障、挡板合规**；`route_check.py` 五层校验全过（总里程 **17.85 m**，规划输出 **29 航点**不再手工维护）。
- 可迁移教训：**压缩/简化类后处理必须把"任务语义要素"列为不可删**，否则错误是静默的。

### 2.3 障碍两份真源（连锁误判）

| 来源 | 值 | 后果 |
|---|---|---|
| `robot.yaml` `obstacle_blocks` | `A1 C2 B4 G4 E6 I7 D9 H10` | 假障碍 ⇒ `shoot_planner` 按它算视线遮挡；校验器误判"路线踩了 H10/D9/G4"，而那三格其实是合法格 |
| `map.yaml`（真源） | `B1 I2 F7 C8 E8 A9 H9 D10` | 与 `mission_blocks` 才是同一套 |

- 处理：`robot.yaml` 对齐 `map.yaml`，并立铁律"**改地图只改 `map.yaml`**"（今天仍能在 `robot.yaml:430-433` 读到该注释）。
- 附带发现：`mission_blocks` 途经 `H10/D9/G4`（按旧障碍表生成），是"路线踩障"假象的根。

## 3. 三次自伤（负优化）——都被"改完立刻验证"抓住

| # | 自伤 | 怎么发现的 | 结论 |
|---|---|---|---|
| 1 | 替换 `<body>` 时以 `</body>` 为界，**把整段 `<script>` 一起覆盖**（原 660–1631 行），页面不可用 | 备份恢复 + 改到 `<script>` 之前重做；文件 1633 → **2041 行**，`<div>` 配平 74/74 | 改大块要按"结构边界"而不是"标签边界"切 |
| 2 | 引入 `parameters=[CONFIG_FILE]`：配置文件缺失时**底盘节点直接启动失败**（原 LaunchConfiguration 自带默认值） | 复盘自述"我刚引入一处潜在负优化" | 任何"从默认值改成必填"都要留兜底 |
| 3 | 新加 `console_scripts` 入口后 **`car_localization` 编译失败** | 编译报错：`install/` 里 `share/ament_index/resource_index/packages/` 目录缺失（历史安装不完整） | 删该包安装产物重建；"只增便利"也会踩到旧安装残缺 |

> 方法论一句话：**AI 自述的"微小改动"最危险**；这三条都是"改→立刻跑→立刻发现"，而不是等人肉验收。

## 4. 协作机制（今天的 AgentTeams 前身）

- **分工**：武将（写码/改配置/跑构建/修 bug）↔ 文官（代码审阅/核对真实状态/写日志与技术文档）。
- **六条铁律**（`交接协议.md`）：① 交接文件覆盖式更新，不追加；② 每次动手前先读对方交接；③ 只改自己职责内的文件；④ 结论必须带文件证据；⑤ 移交前自检"改了会不会起不来"；⑥ 冲突以协议为准。
- **交接三样**：改了什么 / 为什么 / 待确认项（与今天"证不出来=没完成"同源）。
- 与今天的映射：交接文件 → 任务卡 + `TEAM_STATUS.md`；"文官核真实状态" → 验收/回归；"覆盖式交接" → 单写者 + 写域。
