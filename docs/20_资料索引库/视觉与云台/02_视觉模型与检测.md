# 视觉模型与检测

## TL;DR（给 agent 看的）

- 车端：det_node 出 8 个整数到 `/offset_center` @~30 Hz，**无目标也发全 0 心跳帧**（云台据此判「视觉静默」）。
- 三个致命前提：① **每帧只发 1 个目标** ② 结果**滞后约 0.26 s**（流水线深度=thread_num=8）③ `draw` 必须 **false**（SSH 无 X 时 imshow 抛 GTK 异常直接崩，D-003）。
- 机端：dzuav 13 类 → UDP 50000 私有二进制帧；**`localized=0` 时 objects 恒空**（静默为空）⇒ 现场必须 `DZUAV_FORCE_UDP=1`。
- 两个模型指针 ≠ 机上现实：`current_hbb_detector` 指 D13(13 类)，机上现役引擎仍是 7 类。

## 1. 车端检测链（det_node）

| 项 | 值 | 出处 |
|---|---|---|
| 模型 | `light_det.rknn` 8.09 MB，输出 `[1,9,8400]` | air_ground_models/README.md:38 |
| 契约 | 4 bbox + 1 cls + 1×3 kpt（单类别 YOLO-pose） | 同上；`det_node.cc` 解析 |
| 频率 | 定时器 `max(33 ms, 1000/max_fps)`，`max_fps=30`、`thread_num=8` | robot.yaml:305-306 |
| 阈值 | NMS 0.45 / BOX 0.4；类别 2（blue/red）+ 1 关键点 | det/postprocess.h:20-26 |
| 发布 | `cur_img` 非空即发；无目标发全 0；**同帧多目标只有最后一个存活**、无目标 ID | det_node.cc:240-260 |
| 显示 | `draw` 默认 true（`det_node.cc:38`），`draw:true` 时每帧 `imshow+waitKey`（ARM 上可观开销） | det_node.cc:262-270 |

**滞后 0.26 s 的机制**：`put()` 每拍入队 future，`get()` 取**队首最老**结果，且前 `thread_num` 拍不取 ⇒ 队列稳定 8 帧 ⇒ 视觉结果约滞后 8×33 ms（survey §9.2）。降到 2~3 可减滞后，但会掉吞吐。

## 3. 机端检测链（dzuav）

| 项 | 值 | 出处 |
|---|---|---|
| 类别 | **13 类**：paper(0) cell_label(1) car(2) target_red(3) target_blue(4) obstacle(5) bucket_red/green/cyan(6-8) car_start/end(9-10) uav_start/end(11-12) | _tmp_session/t3/perception/README.md §1 |
| 输出 | UDP **50000** 广播；帧头 `EF EF EF EF 10`；`0x4001` 态势 / `0x4002` 车位姿；每目标 **25 B**（type+x+y+len+wid）+ CRC16 | 同上（`UdpBroadcaster.cpp:90-97`） |
| 频率 | 每处理一帧发一帧，无节流；相机上限 30 fps，带显示实测 13~14 fps | 同上 |
| 发送条件 | **`localized==true`**（或 `DZUAV_FORCE_UDP=1`） | `main.cpp:186` |
| 格名怎么来 | `cell_label` 裁 96×96 → CellClassifier 出列/行 → 当**地标**喂 PnP（需 ≥4 格号 + 凸包 ≥2% 画幅）→ 反投影成米 → 再吸附回格名 | 同上 §1 |
| 米↔格 | `x = 0.065 + col*0.35`，`y = 0.295 + (10-row)*0.35`；离格心 >0.35 格拒收 | `field_frame.py:52` |

- **类别→语义**（工程既定口径，非本工具发明）：`paper` 落 **K 列 = bridge（通行箭头）**，其余列 = mine；`obstacle`/`target_*` 同名；`car`/`cell_label`/`bucket_*`/`*_start`/`*_end` **不进 known**。
- ⚠️ 这带来一个硬规则副作用：K 列真雷会被判「可通行」，K 列外的箭头会被判「雷」——现场值得核一次。

## 4. 相机：分辨率够、光学糊（无人机侧）

| 项 | 实测 | 判据 |
|---|---|---|
| 型号 | LRCP **AR0234**（UVC 免驱，USB2） | 补丁 04 §二 |
| 传感器 | 1920×1200、3 µm、全局快门 | onsemi 规格 |
| **ROS 通路** | `v4l2_camera` **只吃 YUYV** ⇒ 实用上限 **640×480@30**（想更大只能 1280×720@10） | 比传感器差 3 倍 |
| 清晰度 | 拉普拉斯方差 **46.2 / 46.5 / 50.2**（640×480 真帧） | `<10` 极糊、`10~100` 糊、`>100` 基本清晰 ⇒ **糊** |
| 能否软件修 | AF 开/关、`focus_absolute` 0→255 全扫，方差 46.5→46.7→38.1 | **定焦镜头，no-op** |
| 高度预算 | 1920 档 2.0 m 时 GSD 2.01 mm/px、35 cm 格占 174 px；640 档 2.0 m 时格占 58 px | 分辨率不是瓶颈，**光学清晰度才是** |
| 一帧看全 K 列 | 1920 档需 ≥ **2.0 m**；640 档需 ≈6.0 m（那时只剩 39 px） | 建议 2.0~2.5 m nadir，K 列沿画幅长边 |

- 建议动作优先级：① 物理修镜头（撕膜/旋紧 M12/退到最小对焦距离外），验收 lapvar **46→>100**；② 用 `~/ag_test/dzuav` 的 `uvc:` 跑道拿 MJPG 高分辨率（`~/dzuav` 缺 `include/` 编不出来）；③ 做一次相机标定（`MapLocalizer` 的 K 是否属这颗镜头**存疑**，fx≈995@1920 ⇒ HFOV 88°，与现场观感不符）。

## 6. 检测链实测归因：61% 的帧根本没有检测（2026-10-22）

> 来源：`_archive/20261023/tmp_session/DET-20261022.zip`、`AIM-OBS-20261022.zip`（只读离线归因，未改代码、未上车）

**先纠一个包名**：检测**不在** `src/dzrknn_dataprocess/`（它是 `/offset_center` 的消费方，`cpp:1265` 订阅）。真链是：
`usb_cam /image_raw` → **`src/rknn_pt/src/det_node.cc`**（RKNN，发布 `/offset_center`，`det_node.cc:30-33/215-260`）→ `dzrknn_dataprocess`（火控）→ `dzbrain/aim.py`。

**D11 FIRE 窗口（28.9 s，逐帧统计）**

| 类别 | 占比 | 含义 |
|---|---|---|
| A 无有效检测 | **60.7%（532/876 帧）** | 画面里没有可用框 |
| C 检测到但已出框 | 39.3%（344/876） | 框在画面外，伺服够不到 |
| B/D 正常 | 0（改框后 D 仅 36 帧 = 4.1%） | — |

⇒ **"检测不到"是第一因，"已出框"是第二因；把开火框加宽只能救回那 4.1%**。这解释了 D11 为什么"门开了也打不中"——不是判据太严，是**大部分时间根本没有目标可瞄**。

**"目标丢失"的两个来源别混**：
- 云台侧阈值 **75 帧 / 2442 ms**（`5_gimbal_BCD:223`）；FIRE 窗口内 cls=0 最长仅 **0.73 s** ⇒ **云台一次都没判丢**。
- aim 侧在**首个 cls=0 帧**就置 `_lost_at`（`aim.py:723-724, 802-805`）⇒ 出现"瞄TRACK 靶none"。**"丢失 N 次"是 aim 的计数，不是云台的**。
- 同理：`7_path` 日志里 **没有任何连续区间**能复现"79/66"（最接近 L2506-L2824 = 41/39）⇒ 拿 79/66 当 FIRE 口径硬指标会误判。

**提前量不是本轮的瓶颈**：D FIRE 段 lead 非零仅 41/1445（2.8%），非零中位 7 px、最大 44（限幅）——0.3 m/s 下远小于 25 px 框。
