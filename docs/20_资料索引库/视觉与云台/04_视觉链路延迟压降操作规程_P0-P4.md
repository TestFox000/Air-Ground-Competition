# 视觉链路延迟压降操作规程（P0~P4）

> **适用范围**：车端检测链 `/image_raw` → `det_node`（RKNN）→ `/offset_center`。
> **不适用**：云台跟随律、串口执行、开火判据（那是 [01_云台瞄准与开火链路](01_云台瞄准与开火链路.md) 的地盘；本规程只在 §10 提醒它的份额）。
> **一句话**：先把尺子钉死，再测准，再按「零结构收益 → 结构改造 → 相机档 → 模型档」四阶段逐档压，**一次只改一个变量**。

## TL;DR（给 agent 看的）

- **四把尺子不许混**：A 口径（帧到达→推理完）是**唯一验收口径**；B 口径、提前量折算口径、端到端口径各自只服务各自的下游问题，**不能相加、不能互相替代验收**（§1）。
- **实测 A 口径 p50 100.3 / p95 135.2 ms**（2026-10-31 车端，3 臂 × 4 次 × 30 s，§12.1）。分段：等拍 **14 ms** + 排队 **18 ms** + 处理链 **86 ms**（其中 NPU 单帧 **43.0 ms**，余 43 ms 为前/后处理与调度，**未再细分**）。原文"2 拍 66 ms 固定滞后 ⇒ 78 ms"的推算**已被实测推翻**（§12.2）。
- **三条假设已被实测否决（别再按它们排期）**：① 「非阻塞取最新」不降延迟（100.0 vs 100.3 ms）还把输出率从 26.55 打到 11.8 Hz；② 三核只省 **1.18 ms**（43.03→41.85），"三核 35 ms"不成立；③ 843 ms 帧龄是 `header.stamp` 固定偏移，**不是积压**（§12.2）。
- **两个已被实证的坑**：① 发布消息只有 8 个整数、**无帧号无时间戳**，下游"保序"没有消费者（`det_node.cc:238-245`）；② 车端现役二进制/模型与仓库**不是同一份**（`artifacts/agc-1024/car_snapshot/README.md:33-39`）⇒ 本文全部行号指**仓库源码（8 字段栈）**，动手前必须先对拍（§6 坑7）。
- **停手线**：P1 只剩背压一项（降延迟的两项已实测无效）；P2 **三核路线已停**（实测只省 1.18 ms），改走「砍前后处理 + 降输入」；P3 任一档检出下降立即退回（§7、§12.3）。
- **收尾必做**：`vision_latency_ms` 重标为实测 p50 —— 它是**补偿量不是限速值**，压了延迟不改它 = 系统性过冲（`artifacts/agc-1024/car_snapshot/dzrobot__config_robot.yaml:232`，§6 坑8）。

## 1. 四把尺子先钉死（本规程最重要的一节）

**规则：不同口径的数不能相加、不能互相替代验收。** 任何一张延迟表都必须先写清用的是哪把尺子，否则"100 ms 还是太慢"这种结论根本不可比。

| 口径 | 起点 | 终点 | 现值（读数 + 性质） | 出处 | 只许用来干什么 |
|---|---|---|---|---|---|
| **A 口径**（**本规程验收口径**） | `/image_raw` **帧到达本节点**（回调进入 `t_cb_enter`） | **推理完成**（`t_done`） | **实测 p50 100.3 / p95 135.2 ms**（2026-10-31 车端，3 臂 × 4 次 × 30 s；打点为"帧到达→发布"，`t_done` 与 `t_pub` 同拍差 ≤1 ms） | §12.1；`_tmp_session/P0-LATENCY-20261031/` | **所有阶段判据、p50/p95、`vision_latency_ms` 标定** |
| **B 口径** | **曝光开始** | 推理完成 | **未实测**。= A 口径 + 采集/USB/驱动/DDS 段 **35~65 ms** + 曝光时长（未读 `v4l2-ctl`，**待实测**） | 同一文件 `:10`〔档〕；相机参数 `robot.yaml:251-261` | 判断"相机档值不值得改"（§2.4） |
| **提前量折算口径** | 不测时间，**折算成位移** | — | **0.267 s**（= 4 帧 × 66.7 ms）；× 0.3 m/s ≈ 0.080 m ≈ **11 px** @140 px/m | `docs/20_资料索引库/视觉与云台/00_索引.md:47`；`00_索引.md:39` | 只喂瞄准/开火判据的"提前量该给多少"，**不参与延迟验收** |
| **端到端口径** | 光子（曝光） | 出光 | **0.5~0.9 s**〔档〕；与 10-23 实测"capture→云台 ≈105~135 ms"**从未对账**（差 ~0.4~0.8 s，出处不明） | `dzrobot_v2/src/dzbrain/dzbrain/tasks/aim.py:44`；`_tmp_session/LEAD-VISION-20261023/LAT_MEASURE_20261023.md:15`〔档〕 | 只用来回答"视觉段占整条链多少"，**不许拿来当视觉验收** |

**三条硬禁令**

1. **不许把 33 ms（拍）当延迟**：33 ms 是**采样节拍**，不是帧龄。帧龄 = 拍内相位（0~33 ms）+ 排队 + 推理。混用会把"A 口径 100 ms"说成"33 ms"，直接得出假结论。
2. **不许把 A 与 B 相减当成"曝光省下来的钱"**：B 口径里 35~65 ms 这一段有一半是**帧周期等待**（相机 30 fps 时最多等一整拍），不是曝光。
3. **不许用 `t_img_stamp` 代替 `t_cb_enter` 做 A 口径**：相机 `header.stamp` 实测**恒定慢 ~0.995~1.000 s**（`_tmp_session/LEAD-VISION-20261023/LAT_MEASURE_20261023.md:21-24`〔档〕）⇒ 用它算帧龄会凭空多出 1 秒。P0 必须先确认这条 bug 是否还在（§11）。

> **为什么 A 口径选 `t_cb_enter` 而不是 `header.stamp`**：本规程要压的是**节点内部的处理延迟**（调度 + 排队 + 推理），那是我们能动的东西；相机时钟偏移是另一条 bug，混进来只会让数不可复现。

2. **单核 / 三核 bench**（口径见 §5）：**必须与探针分开跑**，不许并发采数（§7 红线）。
3. **`v4l2-ctl` 曝光/格式/帧率**：现值 `640×480 @30 fps, yuyv`（`robot.yaml:254-257`），且**明确保留自动曝光**（`robot.yaml:261`："其余相机控制项保持驱动默认（自动曝光/自动白平衡），不要随意覆盖"）⇒ 曝光时长是**未知数**，P0 必须读出来。
4. **`lsusb -t` 速率档 + `ros2 topic hz` 输出率**：把"相机给多少帧"与"节点发多少帧"分别记下来。已知：yaml 注释记 30.4 Hz（`robot.yaml:307`）、10-23 实测 2 线程**发布 26.8 Hz**（`_tmp_session/LEAD-VISION-20261023/LAT_MEASURE_20261023.md:30`〔档〕）——**输出率 26.8 < 设计 30.4**，这条差要被解释，不能当噪声。

```bash
# ① 频率现状（边跑边记 3 × 30 s，串行执行，不要与 bench 并发）
ros2 topic hz /image_raw            # 相机出帧率（物理上限 30）

v4l2-ctl -d /dev/video0 --get-ctrl=exposure_auto,exposure_absolute,gain \
        ,white_balance_temperature

# ③ USB 速率档（480M=USB2 / 5000M=USB3）
lsusb -t
```

### 2.3 P2 · 结构改造（链 ≤55 ms；原"≤45 ms"目标随三核否决作废）

三件事一起做，但**先 bench 后接线**：

1. **NPU 三核单帧推理 —— 2026-10-31 实测否决，不要做**：方法论见下（每实例只绑一核、轮转分配：`dzrobot_v2/src/rknn_pt/include/coreNum.hpp:8` `RK3588 = 3`、`:19` `core_num % RK3588`；`rkpt.cc:112-125` 三选一、`:126` `rknn_set_core_mask`），但**实测单核 43.03 ms → 三核 41.85 ms，只省 1.18 ms（−2.7%）**，p95 47.09 → 44.90 ms（§5 产出表）。⇒ 这条路不再投入；瓶颈在前后处理与 DDR，不在 NPU 核数（§12.3）。
2. **事件驱动（低优先，须单独验证）**：图像到就送推理（在 `imageCallback` 里直投，`det_node.cc:185-198`），去掉 33 ms 定时器相位（`det_node.cc:73-74`）。按 §12.1 实测，**这一项的理论上限只有 ~14 ms（等拍）**；而 2026-10-31 的 A/B 已证明"改投递/取数机制"会掉产出率（§12.2）⇒ **要做必须单独开卡、单独验 M3**，不许与前后处理优化同轮上。
3. **完成即发（低优先）**：结果一到就 `publish`，不再等下一拍（`det_node.cc:257` 的门 + `rknnPool.hpp:99` 队首取值）。实测排队 p50 **18 ms**、池内 depth 峰值 3 ⇒ 上限 ~18 ms；本轮 A/B 实测**拿到 0**（§12.2）。同上，单独验。

**判据**：A 口径 **p95 ≤75 ms** ∧ 输出率 ≥25 Hz（原 ≤45 ms 目标随三核否决作废，§12.3）。
**停手线**：三核路线**已停**（实测 1.03×）；本阶段只剩前后处理，**拆不出 ≥15 ms 可砍项就停 P2、转 P4 模型档**（§7）。

### 2.4 P3 · 相机档（一次只改一档）

顺序固定：**短曝光 → MJPG → 60 fps**，每档单独跑一轮 3×30 s，**每档都要现场光照验证不漏检**，否则退回。

| 档 | 改什么 | 现值/位置 | 收益 | 风险 |
|---|---|---|---|---|
| P3-1 **短曝光** | 关自动曝光，锁 `exposure_absolute`（8~10 ms 量级，现场定） | `robot.yaml:261` 明确"自动曝光不要随意覆盖"；`brightness: 0`（`:259`，曾被设 50 导致过曝） | 曝光段可省（**量未知，先读 v4l2 再定**） | 现场灯光暗 ⇒ 直接掉检出 |
| P3-2 **MJPG** | `pixel_format: mjpeg` | `robot.yaml:257` 已支持 `yuyv \| mjpeg` | 换更高分辨率/帧率的带宽余量 | MJPG **解码吃 CPU**（RK3588 软件解不一定划算），必须看 CPU |

| `t_cb_enter` | 回调**进入**时刻 | `det_node.cc:185-189`（`imageCallback` 入口） | `steady_clock` / ns | 每帧 1 点 | `t_cb_enter_ns` |
| `t_submit` | **送推理**时刻 | `det_node.cc:251`（`detectPool_->put(...)` 之前） | `steady_clock` / ns | 每帧 1 点 | `t_submit_ns` |
| `t_done` | **推理完成**时刻 | **必须在 worker 内**打点（`rkpt.cc:259-260` `rknn_run`/`rknn_outputs_get` 之后、`:292` 之前） | `steady_clock` / ns | 每帧 1 点 | `t_done_ns` |
| `t_pub` | **发布完成**时刻 | `det_node.cc:283`（`det_pub_->publish(msg)` 之后） | `steady_clock` / ns | 每帧 1 点 | `t_pub_ns` |

**两个精度提醒（不写清就会测错）**

1. **`t_done` 不许在 `get()` 之后打**：`det_node.cc:257` 的 `get()` 是**阻塞取队首**（`rknnPool.hpp:99`），在它之后打点 = 推理完成 + 排队年龄，会把 33 ms 级的定时器等待算进"推理耗时"。真值只能在 worker 内打。
2. **建议补一个 `t_pick`（`get()` 返回时刻）**：`t_pick − t_submit` = 排队，`t_done − t_submit` = 纯计算，两者一减就知道该不该动 `thread_num`（对应 §6 坑1/坑3/坑4）。

**采样点数**：单窗 30 s × 30 Hz ≈ **900 帧**；3 窗 ≈2700 行；**单字段缺失率 >5% 的窗整窗作废**（插桩丢点会系统性偏快）。

## 6. 已知陷阱（本文档最有价值的部分）

> 每条都给了证据位置。**动手前逐条读一遍**，这些坑全都真实发生过。

**坑1 · 33 ms 定时器 + `put/get` 队首最老 + 前 `thread_num` 拍不取 ⇒ `thread_num=2` 固定滞后 2 帧。**
定时器周期固定 33 ms（`dzrobot_v2/src/rknn_pt/src/det_node.cc:67-71` 夹在 33.0，`:73-74` 建定时器）；每拍 `put` 一帧（`:251`），但 `get` 前面有个门 `frames_ >= thread_num_`（`:257`）⇒ **前 2 拍根本不去取**；取的时候 `rknnPool.hpp:99` 取的是 `futs.front()`，即**队首最老**那个。两者叠加 ⇒ 稳定滞后 `thread_num` 帧（`robot.yaml:306-308` 记 2 线程 ≈2 帧 66 ms）。
**后果**：任何"提高 `thread_num` 换吞吐"的想法都会**线性加大滞后**。

**坑2 · 发布出去的 `Int32MultiArray` 只有 8 个像素量，没有帧号也没有时间戳。**
`det_node.cc:238-245` 建 8 个字段（`layout.dim[0].size = 8`、`data` 全 0），`:273-283` 只写 8 个像素量就发。消息类型 `std_msgs/Int32MultiArray` 本身**没有 header**（`:30`）。而帧号其实**有**——`DetectResultsGroup` 里带着 `int cur_frame_id;`（`dzrobot_v2/src/rknn_pt/include/common.h:36`），`rkpt.cc:291` 也赋了值，但**从未上行**。
**后果**：下游无法判断"这是第几帧"，所谓"保序"没有消费者；去重、对齐、丢帧统计都做不了（P1-4 要补的就是这条）。

**坑3 · 2 路 worker 吞吐 ≈ 2/59 ms ≈ 33.9 Hz，对 30 Hz 提交率只有 13% 余量。**
`59 ms` 是**推算值**：由 `robot.yaml:308` 的"1 线程……掉到 17Hz"反推 1000/17 ≈ 58.8 ms。**同一份 yaml 注释又记"8 线程 264 ms"**（`:307`），二者不是同一个量。而 10-23 实测单线程约 **90 ms**、只有 **9.4 Hz**，并明确写"yaml 注释里记的是 17 Hz，已过时"（`_tmp_session/LEAD-VISION-20261023/LAT_MEASURE_20261023.md:32`〔档〕）。
**后果**：按 59 ms 算余量 13%，按 90 ms 算是 **2/90 ≈ 22 Hz < 30 Hz 提交 ⇒ 负余量**。**所以这条必须在 P0 重测**，不许拿 59 ms 当结论。

**坑4 · `thread_num=1` 不是"掉到 17 Hz"这么简单：消费 17 Hz < 提交 30 Hz ⇒ 池内任务队列无界增长、延迟发散。**
任务队列是裸 `std::queue<Task> tasks_`（`dzrobot_v2/src/rknn_pt/include/ThreadPool.hpp:159`），`submit` 里**无条件** `tasks_.emplace(...)`（`:73-74`），`put` 也**无条件** push future（`rknnPool.hpp:88`）——**没有任何拒绝/丢帧/背压**。所以提交快于消费时积压只增不减，帧龄随时间线性恶化，而"输出率"看起来还是 17~22 Hz（**假象**）。
**后果**：判"1 线程行不行"只能看**帧龄 p95 的稳定性（M4）**，不能看 Hz。

**坑5 · 预热的真实作用是避免启动拿到半成品，可用"首个结果到达前不发布"替代。**
现有机制是"按拍数跳过"：`frames_ >= thread_num_` 才 `get`（`det_node.cc:257`）；池初始化在建池时就建好模型（`rknnPool.hpp:53-55`、`:65` `models[i]->init(...)`；`rkpt.cc:96-105` `rknn_init`/`rknn_dup_context`）。
**后果**：它是**计数门**不是**结果门**——只要前 N 拍恰好慢，仍可能发布半成品；反过来改成"第一个真实结果到达前不发布"语义更准，P2 一并做掉。

**坑6 · 去重（`cur_stamp` 相同整拍跳过）是单线程 executor 被阻塞时的补丁，实测有 1.95× 重复推理。**
`det_node.cc:228-236` 注释写得很清楚："单线程 executor 下定时器会阻塞在 `get()`，图像回调被饿死，同一帧被反复推理；实测重复 1.95x、唯一帧率只有 14.3 Hz（相机 27 Hz）"。根因是 `:331` 的 `rclcpp::spin(node)` 为**单线程**，而 `get()` 阻塞（`rknnPool.hpp:99`）。
**后果**：去重是**症状**补丁；P1-3 把"取最新"改成非阻塞后，去重可以保留（防重发）但**不该再被当成主力**。**动 `thread_num` 前**先确认去重是不是还在替你扛频率。

**坑7 · 车端现役二进制/模型与本地仓库不是同一份（历史遗留）⇒ 动手前必须先对拍。**
字节级证据（`artifacts/agc-1024/car_snapshot/README.md:33-39`）：
- **实跑栈**：`dzrobot2__det_node` = `9b449ba2…`（3,855,872 B，10-20）+ 模型 `dzrobot2__light_det.rknn` = `59aaad60…`（9,899,901 B）；
- **仓库源码栈**：`dzrobot__det_node` = `1d0ae071…`（776,112 B，10-24，8 字段）+ 模型 `dzrobot__light_det.rknn` = `8b17ec17…`（8,125,813 B）。

**后果**：**本文所有 `路径:行号` 指的都是仓库源码（8 字段栈）**。上车前必须先确认 ① 现在跑的是哪套（10-24 快照≠现状）；② 那套的流水线形状是否与本文一致（尤其"8 字段契约"`det_node.cc:238-245`）。对不上就先对拍，别照着本文改另一套的代码。

**坑8 · `vision_latency_ms` 是补偿量不是限速值：延迟压缩后不改它 = 系统性过冲，比不压缩更糟。**
现值**两处口径不同**：车端 yaml 是 `100.0`（`artifacts/agc-1024/car_snapshot/dzrobot__config_robot.yaml:232`），C++ 默认是 `267.0` 且注释写"标定后再改"（`_tmp_session/agc-1024/e1/car/src_dzrknn_dataprocess_include_dzrknn_dataprocess.h:128`〔档〕）。
**注意：这个键不在 `dzrobot_v2/config/robot.yaml` 里**（本仓全量检索无命中）——它属于 `dzrknn_dataprocess` 的 yaml 段，不在 `det_node` 段。
**后果**：它表示"把预测向前推多少 ms"。真实延迟压到 60 而参数仍写 100 ⇒ 过度补偿 ⇒ 过冲；**正确顺序是先测准、再压缩、再同步改它**（§9）。

**坑9 · 单线程 executor 里在定时器回调阻塞等待推理结果会饿死图像回调 ⇒ "取最新"必须非阻塞。**
`det_node.cc:331` `rclcpp::spin(node)`（单线程）+ `:257` 阻塞 `get()` + `rknnPool.hpp:99` `front().get()` ⇒ 定时器回调一阻塞，`/image_raw` 回调就进不来（这正是坑6 的成因）。
**正确写法**：`wait_for(0)` 非阻塞查一次；有结果就 `while (futs.size() > 1) futs.pop();` 把旧的丢掉，只留最新。
**为什么"丢弃安全"**：池里存的是 `std::packaged_task` 的 future（`ThreadPool.hpp:65-67` `make_shared<PackagedTask>` + `get_future`）——**`packaged_task` 的 future 析构不等待**，pop 掉未取的结果不会阻塞、也不会丢任务执行（任务已在线程里跑完或正在跑）。另注意池析构时会 drain（`rknnPool.hpp:107-111`），那是**关停路径**，别和运行期的"丢旧结果"混为一谈。

**坑10 · 相机 `header.stamp` 实测恒定慢 ~1 s（独立 bug，但会毒化所有以 stamp 为准的口径）。**
`_tmp_session/LEAD-VISION-20261023/LAT_MEASURE_20261023.md:21-24`〔档〕：新订阅者 delay 中位 995.3 ms；亮度阶跃实验证明"**图像内容是新的，时间戳是慢的**"。
**后果**：任何用图像 stamp 做对齐的环节（bag 回放、`message_filters`、多传感器融合）会差整整 1 秒。**本规程 A 口径用 `t_cb_enter` 就是为了绕开它**；但要长期用 stamp 必须先修（单独开卡，别夹在延迟卡里）。

## 7. 红线与停手条件

**红线（违一条，本轮数据作废）**

1. **一回合只改一个变量**（`AGENTS.md` 铁律 6）。同时改 `draw` + 三核 + 曝光 ⇒ 收益无法归因。
2. **并发跑 bench/探针时不采数**：bench、探针、云台、视觉窗口互相抢 CPU/NPU，混跑出的 p95 一律不可用。
3. **不改冻结区默认值**：`config/**` 与 `src/dzrknn_dataprocess/**` 属冻结区（`dzrobot_v2/AGENTS.md`）⇒ 实验走 `-p` 参数或 feature flag，**默认值不动**。
4. **均值不许代替 p95**：均值会掩盖"卡一下再连发"（10-23 帧间隔 p10=0.8 / p90=71.5 ms 就是例子）。
5. **离线绿 ≠ 实车过**：113 帧离线一致只是入场券，还要真车 3×30 s。
6. **相机档一次只改一档**（P3），改两档则无法判断是哪档掉的检出。

**停手条件（到了就停，写清停因）**

| 阶段 | 停手条件 | 之后做什么 |
|---|---|---|
| P1 | p95 降幅 **<5 ms** | 停 P1，判"瓶颈不在调度"⇒ 直接进 P2 |

## 10. 前提提醒：视觉段只是端到端的一小段

- 10-23 实测：capture→发布 ≈ **105~135 ms**；发布→云台执行"未单独测，估 5~10 ms"（`_tmp_session/LEAD-VISION-20261023/LAT_MEASURE_20261023.md:15,13`〔档〕）。
- 而端到端口径是 **0.5~0.9 s**（`dzrobot_v2/src/dzbrain/dzbrain/tasks/aim.py:44`）⇒ **发布之后还有 ~0.4~0.8 s 没被解释**。这段不在 `det_node` 里，只可能在云台跟随律、EMA、串口/伺服、开火判据。
- **结论**：视觉段实测 **100 ms**（§12.1），在调度层能榨的只有 ~14 ms 等拍 + ~18 ms 排队；把链从 86 ms 压到 ~55 ms 才能到 75 ms 量级。端到端 0.5~0.9 s 里它只占一两成 ⇒ **若压完命中率没变化，瓶颈在云台跟随或串口执行**，不是这次没压够。

**所以 P0 探针顺手多打两个时间戳**（几乎零成本，收益很大）：

| 建议字段 | 起点 | 终点 |
|---|---|---|
| `t_gimbal_recv` | `t_pub` | `dzrknn_dataprocess` 收到 `/offset_center` 并完成一帧控制计算 |
| `t_motor_cmd` | `t_gimbal_recv` | 云台/电机指令真正发出（串口写/`pursuitAngle` 发出） |

拿到这两点，才能把"看不见的 0.4~0.8 s"切成可归因的段；拿不到，就永远在猜。

## 12. 2026-10-31 车端 P0 实测（回填节）

> 环境：`/home/duzhong/dzrobot`，`ROS_DOMAIN_ID=118`，相机 `usb_cam` + `det_node`（现役 install），RKNN api 2.3.2 / drv 0.9.8，模型 `light_det.rknn` 输入 `[1,640,640,3]` UINT8 NHWC。
> 证据归档：`_tmp_session/P0-LATENCY-20261031/`（探针、A/B 原始 CSV、bench 源码与输出、结论 md）。

### 12.1 实测值（A 口径 p50 100.3 / p95 135.2 ms）

| 指标 | 实测 | 采样 |
|---|---|---|
| **A 口径**：帧到达 → 发布 | **p50 100.3 / p95 135.2 ms** | 3 臂 × 4 次 × 30 s，输出 **26.55 Hz**，输入 24.9~25.2 Hz |
| 处理链：送推理 → 发布 | p50 **86.3** / p95 **124.0 ms** | 同上 |
| 排队：到达 → 送推理（扣最小） | p50 **18** / p95 **32** / max **45 ms** | 同上，池内 depth 峰值 **3** |
| 等拍：发布年龄 − 链 | **14 ms** | 推算 |
| NPU 单帧 | 单核 **43.03** / 三核 **41.85 ms** | bench 各 50 次（§5） |
| 相机节拍 | p50 **32.04** / p95 68.0 / max 136.0 ms；**≈18% 间隔被拉长到 2~4 拍** | tap 721 帧 `header.stamp` |

**分段结论**：`100.3 = 14（等拍）+ 86.3（链）`；`86.3 = 43.0（NPU）+ ≈43.3（前/后处理 + 调度，未拆）`。

### 12.2 三条原假设被实测推翻

1. **"相位 16.5 + 两帧 66 = 82.5 ms" 不成立**。实测排队只有 p50 18 ms、等拍 14 ms，`depth` 峰值 3；链里**不存在**一个独立的 66 ms 项——原推算把"链的时长"误计成了"排队"。
2. **"非阻塞取最新能省 66 ms" 不成立（A/B 实测）**：同车同窗口 3 臂——A0 基线 `100.3 / 135.2 @ 26.55 Hz`；B1 取最新+BE+准入2 → `100.0 / 126.9 @ 11.8 Hz`；B2 同上准入3 → `116.5 / 153.2 @ 16.6 Hz`。**延迟没降、吞吐腰斩**。原因：链 75 ms > 2 拍，准入在"两 worker 全忙"时丢帧，把本该完成的推理扔掉。⇒ 这条路作废；保留的只有"背压"（防队列无界增长）。
3. **"三核能把单帧压到 35 ms" 不成立**：1.03×，−1.18 ms。NPU 侧没有可压空间。

### 12.3 现在的真实瓶颈排序（下一轮就按这个排）

| 序 | 项 | 量 | 可动性 |
|---|---|---|---|
| 1 | **前/后处理 + 调度** | ≈43 ms（未拆） | 高：letterbox 640×480→640×640、8400 解码/NMS 都有现成优化空间 |
| 2 | **NPU** | 43.0 ms | 低：只能降输入（640→512 ≈ −12 ms，→416 ≈ −20 ms，须重验精度） |
| 3 | 等拍 + 排队 | 14 + 18 ms | 低：结构收益上限 ~25 ms，本轮实测**拿到 0** |

**结论**：50 ms 只能靠 1+2 同时动；调度层已经到底。

### 12.4 843 ms "帧龄"的定性：是 `header.stamp` 偏移，不是积压

四条独立证据：

1. 停掉 `det_node`、只留我自己的读者，仍读 **741 ms**（RELIABLE 与 BEST_EFFORT 相同）⇒ 与 QoS/流控无关；
2. `v4l2-ctl` 直采驱动，末帧 ts `9293.555` vs 系统 uptime `9293.62` ⇒ **驱动是实时的**；
3. 新起相机实例的**第一帧**就已 791~822 ms ⇒ 积压不可能存在于第一帧；
4. 每次重启偏移不同但固定（741 / 900 / 753 / 790 ms）⇒ 典型时钟基偏移（同 §6 坑10，10-23 记的 ~1 s 仍在）。

⇒ **A 口径必须用 `t_cb_enter`，禁止用 `header.stamp`**（这条从"待复核"升为"实测确认"）。
