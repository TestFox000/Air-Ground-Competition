# 外部实现借鉴：air_ground（2026-10-18 评估）

## TL;DR（给 agent 看的）

- **云端 air_ground 与本地 dzrobot_v2 不是同一项目**：云端是「无人机侦察 + 助航主机 + 官方 dzbrain 消费」，本地是「车端自治 + 自研 dzbrain + 云台开火」。**借鉴 ≠ 搬代码**。
- 结论：**2 个模块建议直接抄**（log-odds 证据格地图、结构化黑匣子），**2 个先评估**（曲率前馈循迹、预算内联合最优）。本地**协议层反而更新一代**（field_layout v2 + coverage），方向是我们输出给云端。
- **截至 2026-10-23，本评估的 P0/P1 一项都未开卡落地 ⇒ 本篇 status 仍是「计划」**，不是现状。引用时必须带「计划」二字。
- 最值钱的三个「坑提醒」：① 移植 pursuit 前必须先理清**到点半径 / 漂移阈值 / 排雷半径**三者关系；② PIVOT 两边**都别互换**；③ CP-SAT 在部分 Windows 上「导入成功但求解段错误」，必须子进程探针 + 降级契约。

## 1. 两边定性（先看这张，避免误判「整包搬」）

| | 云端 air_ground | 本地 dzrobot_v2 |
|---|---|---|
| 定位 | 无人机侦察 + 空地主机 + 官方 dzbrain 消费 | 车端自治 + 自研 dzbrain + 云台开火 |
| 规模 | 2677 文件 / 244 MB（225 MB 是模型权重） | 452 文件 / 18 MB |
| 决策核心 | ag_integrate（旧栈 859 行）+ dznav（新执行器）+ dzbrain_bridge | src/dzbrain/dzbrain 多线程（tracker/aim/mission/safety/localization/drone） |
| 唯一同名文件 | dzbrain_bridge.py | 同（它是**为我们 dzbrain 写**的桥） |

判定：云端 ag_integrate 是被我们取代的旧栈；dznav 是与我们平行的另一套循迹。

## 2. P0-1 证据格地图 evidential_map.py（建议直接抄）

云端：src/ag_integrate/ag_integrate/evidential_map.py（223 行 / 10408 B，纯 Python、零 ROS 依赖、自带测试）。

| 维度 | 本地现况 | 云端做法（行号） |
|---|---|---|
| 正证据 | 无人机报文格名列表 | log-odds 累加 + 置信度夹挤（防 logit 爆炸）（:52-57） |
| 负证据 | complete=True 片内未出现即 ABSENT（布尔） | log-odds 递减，且**画质不足不产生负证据**（:10,:143） |
| 红靶/友方 | aim.fire_only_blue 布尔闸 + red_early_leave_s 早退 | **粘性否决**：确认后负证据与衰减永不击穿（:58,:62,:111-121） |
| 雷 | 布尔 | 负证据**权重减半**（mine R≈98%，没看到≠没有）（:11,:67） |
| 移动靶 | 会拖影污染 | 靶证据写在轨道级 TrackSpot，瞬时落格不进静态地图（:12,:41,:193,:216） |
| 衰减 | 无 | logit 指数半衰，读取时惰性计算，无后台定时器（:14,:64,:157） |
| 快照 | 无 | confirm/drop 双门限滞后，单次负证据不让已确认目标闪断（:20,:90,:120） |

**为什么直接治病**：本地 aim.py:1294 的红面判定是 `in_stop_fire and red and run_s >= 3.0s`——**只在射击停站内有效**，离开停站即清零；云端「一旦见过，TTL 内持续以红靶身份参与否决，只增不减」允许**在路径规划阶段就排除红靶邻格**，而不是开到停站才发现。

移植成本：低（无依赖、约 260 行、自带 test_evidential_map.py）。

## 3. P0-2 结构化黑匣子 blackbox.py + log_report.py（建议直接抄）

云端：ag_core/blackbox.py（696 行 / 27107 B）+ tools/log_report.py（367 行 / 16089 B）+ log_diagnosis.py（638 行）。本地 core/events.py 已有事件总线（21 个 EV 常量），**缺落盘与复盘工具**。

| # | 设计点 | 行号 | 为什么重要 |
|---|---|---|---|
| 1 | 逐条 flush（flush_every=1） | :22-26,:221-231 | SSH 跑节点时 stdout 是管道 → C 层全缓冲 → 进程被 kill 时缓冲整体丢失（「现场日志像没打一样」）。**我们同样中招** |
| 2 | 绝不拖垮主流程 | :20,:228,:270,:655 | 写盘失败只累计 errors 并关掉自己，不抛异常 |

| 4 | 事件名纪律 | :369,:424,:485 | EV 常量集中定义；节点里手写字符串拼错一个字母，报告静悄悄少一块且不报错 |
| 5 | 保留键保护 | :155,:349-351,:572 | RESERVED={ts,mono,seq,node,ev,lvl,session,src,data}，payload 同名键自动挪进 data，否则整条记录报废 |

## 4. P1-1 曲率前馈 + Stanley + 自救（先评估，有硬前置）

云端 src/dznav/dznav/pursuit.py（402 行 / 19519 B）：转向律 `ff(κ)+k_h·e_θ−k_c·atan(...)`；**REBUILD**（cte 超阈或 3 s 无进度 → 直连重建）；**ALIGN_ARC**（首段在身后 → 原地弧转向对齐）；曲率限速含指令曲率；`track_mode` 可切 stanley/pure_pursuit。

**硬前置（不先做就移植 = 引入新 bug）**：云端自曝 `stop_radius` 默认 12 cm，且「原版 15.7 cm 大于排雷触发半径 6 cm 是实锤缺陷」（:10-11,:53-56）；本地 localization.py:889 也写着 `arrival_m(0.12) << drift_warn_m(0.30)` 的矛盾。**先把到点半径 / 漂移阈值 / 排雷半径三者关系理清**（本地自己的 bug，不依赖云端），再谈移植。

**PIVOT 别互换**：云端没有独立 PIVOT 状态机，用 ARC 机动替代；我们有完整三段 PIVOT（tracker.py:757-856，SETTLE/TURN/DONE、硬超时、abandon 防循环）+ 10-18 实车 H8 卡死的「倒车入口闭环推车」。两边都是真车验证过的方案，只吸收 ARC 出口的「软锚点 + 行程/时间双保险」。

## 5. P1-2 预算内联合最优 ortools_solver.py（先评估）

云端 src/ag_integrate/ag_integrate/ortools_solver.py（347 行）：把「两步启发式（Held-Karp 排序 → 超预算整砍）」升级为**在总耗时 ≤165 s 约束下最大化得分**的联合最优。本地 test_autoplan 23 条红里有一条正是「超软预算整砍射击位」。

| 坑 | 云端解法 | 行号 |
|---|---|---|
| CP-SAT 在部分 Windows 机「导入成功但求解段错误」（进程级崩溃，try/except 抓不住） | 独立子进程跑平凡模型探测 cp_sat_healthy()，崩溃只死探针 | :12,:30,:73,:89,:120 |
| 求解器挂 = 整局瘫痪 | 降级契约：不可用/不可行 → 返回 status，order/dropped 为空，调用方退回现行启发式 | :19,:25,:65,:124,:237,:344 |

DP 后端零原生依赖，`_TSP_EXACT_MAX_NODES=14` 内毫秒级精确解（:39,:112-157）——我们必经点通常 ≤8，**可以不引 OR-Tools，只抄 DP 后端 + 降级契约**。
