# 工作法与经验总集

> 这篇不列命令清单（那些在 [05_配置与部署](05_配置与部署.md)、[无人机/05_现场操作与脚本](../无人机/05_现场操作与脚本.md)）。
> 它只回答一个问题：**在这套车上，怎么观测、怎么改、怎么采数据、怎么收口，才不会被假象骗**。
> 每条都来自一次具体的翻车；出处写在句尾，查不到出处的一律标〔未核实〕。

## TL;DR

1. **只信三样**：启动横幅、话题的 publisher/subscriber 计数、实车数据。文件、"我改好了"、"应该生效了"都不算证据。
2. **一次只改一个变量**；连续 2 轮无提升就停，写清停因（铁律 §6）。
3. **只读观测也有副作用**：`ros2 topic echo` 会让对方的订阅计数从 0 变 1，可能改变对方的行为与日志（§2.1 实例）。
4. **采数据先定字段与口径**，复算脚本和数据同存；只存 CSV 不存算法 = 数据作废。
5. **收口 = 门禁六连 + 双远端 + 结论进库**；卡里只写过程，结论必须落到本库（§7）。
6. **归档前必写「经验总结」**：现象→机制→位置→处置→证据等级→落点，六要素缺一不算写完；落点坑库/百科/台账，见 [06_工作完结经验总结规范](../../10_agent提示词/06_工作完结经验总结规范_20261024.md)（2026-10-24 起）。

## 1. 五个循环

| 循环 | 一句话 | 判据（做完看什么） |
|---|---|---|
| ① 观测 | 先把"现在是什么"钉死，再谈改 | 横幅 / 计数 / hz / 实车数据四者能互相印证 |
| ② 改动 | 本地真源改 → 部署 → 重启 → 读横幅 | 横幅里出现新值；车端文件哈希与本地一致 |
| ③ 采集 | 一次跑车只回答一个问题 | 事前写清"这一趟要量哪个数"，跑完当场复算 |
| ④ 判定 | 同一份数据三种切法互证 | 中位数 / 占比 / 时序三者不矛盾 |
| ⑤ 收口 | 门禁六连 + 结论进库 | 六条命令退出码 + 双远端哈希一致 |

> 反例（本轮真实）：`/aim/fire_ready` 全程 0 条消息，第一反应是"判据太严"。其实是**发布它的进程根本没在车上跑**——观测结论错，后面所有调参都是拟合噪声。

## 2. 观测：四个会骗你的东西

### 2.1 只读观测会改变对方状态

- 现象：机上 `dzlink_supervisor` 日志里突然出现 `subs count:1`，而车上并没有 dzbrain 在跑。
- 原因：我在本机（域 118）执行了一次 `ros2 topic echo /dzlink/drone_to_car`，它就多了一个订阅者。
- 推论：**echo / hz / 录包都会造订阅者**；排查"对方有没有收到"时，别把自己算进订阅数。
- 出处：2026-10-24 16:2x 空转心跳期实测。

### 2.2 话题存在 ≠ 有数据

`ros2 topic list` 列得出，可能只是某个看门狗订阅着；判活永远看 `Publisher count ≥ 1` + `hz` 稳定（无人机/02 同款结论）。

### 2.3 文件 ≠ 运行值

- 车端启动横幅打的是**运行时真实加载值**；本地 yaml 只是"打算加载的值"。
- 实例：车端横幅出现「视觉延迟 267ms、k_sp 5.00、ff 1.00」，本地全树 grep 不到 ⇒ 车端跑的不是本地这份源码（交接_20261024 §1.5）。
- 做法：任何"已生效"的宣称，必须先读到横幅或 `ros2 param get`。

### 2.4 `pkill -f` 会漏杀

- 实例：现场出现 `det_node ×2` + 云台节点 ×2 并存抢 CPU（10-23 夜）。
- 做法：杀完用 `pgrep -af <名字>` 核对；pkill 的返回码不能当证据。**杀前先看清模式串会不会匹配到自己**。

## 3. 改动：三条铁规

1. **一次一个变量**（铁律 §6）。改了两个键、结果变好，也说不清是谁起的作用。
2. **四步法**：本地真源改 → `deploy_to_car.py` 推 → 重启**那个**节点（不是整栈）→ 读横幅。
   - 只改车端文件、不重启 = 没改（大多数"改了没反应"是这句）。
   - 只改本地、不部署 = 没改。
3. **冻结区不碰**：`config/**`、`src/dzbrain/**`、`src/dzrknn_dataprocess/**`、`tools/deploy_to_car.py` 改动必须登记 `tools/wf/frozen.json`（owner/卡号/解冻日）。

补充：**能热改的先热改**。云台 PID、开火框这类键改完重启单节点即可，不要为它重启整栈——整栈重启会重置信念到 N10，等于把车挪了位置。

## 4. 采集：一张数据表的五个字段组

采一次打靶/循迹，字段至少覆盖这五组（本轮 `artifacts/aim-mv-20261024/mvrec.py` 是范本）：

| 组 | 字段 | 为什么要 |
|---|---|---|
| 时间 | 相对秒 + 墙钟 | 对齐两端日志；相对秒算频率，墙钟对裁判/回放 |
| 目标 | dx, dy, cls, w, h | 误差、类别、框大小（框宽决定开火框插值） |
| 云台 | yaw/pitch 指令 + 反馈 | 分清"想动"和"动了"；速度顶格 = 饱和 |
| 判据 | status, ready, shot, hp | 状态机、开火许可、实际开火、裁判账 |
| 补偿 | lead_x | 提前量通道有没有值（0 条消息 ≠ 值恒 0，要分开记） |

三条纪律：

1. **频率要写进报告**。同一个数按帧算和按秒算差 25 倍（例：5.0 px/帧 × 25.3 Hz = 126.5 px/s）。
2. **录制期间不改任何参数**。否则数据里混了两个工况。
3. **数据 + 复算脚本 + 清单**三件一起存（见 `artifacts/aim-mv-20261024/MANIFEST.txt`）；`/tmp` 会被清空，脚本不要放那儿。

## 5. 关键数值：三把尺子与十个常量

### 5.1 延迟是五把尺子，不要混用

| 口径 | 值 | 是什么 | 出处 |
|---|---|---|---|
| 视觉流水线（**10-24 打靶所用的口径**） | **0.26 s** | 曝光+推理+传输；`cpp:295` 注释与车端横幅都写这个数。⚠️ **与 10-22 的 A/B 实测冲突**：8 线程滞后 8 帧 264 ms ⇒ 2 线程滞后约 2 帧 66 ms（`技术全景_C §…`）。两者**未定案**——若真值是 0.066 s，下面 33 px 的推导要降到 8.4 px | `dzrknn_dataprocess.cpp:295`；`技术全景_C_车端硬件与配置.md` |
| 车端横幅 | 0.267 s | 同上，实测口径 | 车端启动横幅（10-24 实录） |
| 配置键 | 0.27 s | `lead_time_s`，10-18 回标值 | `dzrobot_v2/config/robot.yaml:837` |
| 排帧延迟 | 0.0667 s | **只算 thread_num×33 ms**，不含推理 | `check_numbers` 的 `vision_pipeline_latency_s` |
| 全链路 | 0.5~0.9 s | 含点火/裁判回传，**不是瞄准要补的量** | 文档口径，待实测定案 |

> 记法：**瞄准补 0.26~0.27；排帧那个 0.0667 是另一个量；0.5~0.9 是全链路。** 三者混用会让提前量差 3 倍。
> **口径告警（2026-10-27）**：0.26 s 与 `thread_num=2` 的实测 0.066 s 到底哪个是现役，**至今没有定案**（判据见 `视觉与云台/03 §3`：靶突然停住、量云台停下的滞后）。在这之前，凡用 0.26 s 算出的提前量都只能当「上限估计」，不能当实测结论。

### 5.2 打靶：六个实测值（2026-10-24，1897 帧 / 74.9 s / 25.3 Hz）

| 项 | 值 | 出处 |
|---|---|---|
| 目标单帧速度 | 中位 **5.0 px/帧**，p90 12 ⇒ **126.5 px/s** | `artifacts/aim-mv-20261024/mvlog.csv` |
| 速度 ≤1.5 px/帧 的帧占比 | **13.77%**（开火稳定性门槛） | 同上 |
| 画面偏差 \|dx\| | 中位 **41 px**，p90 76 | 同上 |
| 落后（**按 0.26 s 口径**）= 0.26 × 126.5 | **33 px** | 计算；若按排帧 0.0667 s 则仅 **8.4 px**（口径未定案，见 §5.1） |
| 开火框 | **25~26 px**（随框宽插值） | `dzrobot_v2/config/robot.yaml:179,184` |
| 进框占比 | **30.0%**（\|dx\| ≤ 26） | mvlog 复算 |

- 33 px > 26 px ⇒ **匀速段结构上打不中**，只有换向拐点（13.77% 的帧）能中。
- 而 \|dx\| 中位 41 px > 33 px：差额来自云台是**纯 P 控制**，想输出角速度就必须留稳态误差（量级 = 靶速/增益）。**调 PID 消不掉这 41 px，只有提前量能。**

### 5.3 车体与里程：轮距有两把尺子

| 口径 | 值 | 怎么来的 |
|---|---|---|
| 实测 | **0.157 m** | 卷尺 + 3236/(2π×3280) 交叉验算 |
| 配置 A（现行） | **0.1300 m** | 3280 ticks/m ÷ 2680 ticks/2π |
| 配置 B（另一会话） | 0.1565 m | 3290 / 3236 |

- 用 0.1300 算里程会比物理短 **17.2%**；用 0.1565 只差 **0.3%**。
- 结论：`ticksPerMeter` 与 `ticksPer2PI` 必须**同时**改，只改一个 = 航向与平移各说各话（05 §6 的量测表就是为此）。

### 5.4 链路与部署

| 项 | 值 | 备注 |
|---|---|---|
| ROS 域号 | **118** | 非交互 SSH 默认 0，必须 `source dzros.env` |
| 判"通"的硬证据 | 对端 **ack**（带 seq 回执） | Publisher/Subscriber 计数对不上 = 静默 0 条 |
| QoS 方向 | 发用 BEST_EFFORT、收用 RELIABLE 会**静默收不到** | 两端必须对齐 |
| 机端二进制帧 | 352 B / 13 对象；57 B / 4 航点 | 类型表 13 类 vs 车端 7 类，**错标不报错** |
| 检测仪表频率 | 实测 **6.4 Hz**（193 行/30 s），宣称 10 Hz | `_tmp_session/sqc-20261024` |

## 6. 十个反复踩的坑

| # | 坑 | 机制 | 做法 |
|---|---|---|---|
| 1 | "改了没反应" | 只改文件没重启 / 只改本地没部署 | 四步法 + 读横幅（§3） |
| 2 | 静默 0 条 | QoS 反了、域号不同、订阅者没起 | 先看 count 与 ack，再查内容 |
| 3 | 杀不干净 | `pkill -f` 漏杀，出现双实例 | `pgrep -af` 核对 |
| 4 | 脚本不见了 | `/tmp` 被清空 | 脚本放 `~/robot_logs` 或仓库 |
| 5 | 相机"假死" | 节点在、`/image_raw` 停发，检测空转 5 min | 判活看 hz 不看进程 |
| 6 | 假目标 | 青色水桶被判成蓝靶 conf 99，云台顶到限位 | 现场先确认画面里有几个"靶" |
| 7 | 开火数为 0 | `max_shots` 是**进程生命周期累计** | `/shoot_reset` 清零，不必重启 |
| 8 | 数据作废 | 录制中途改了参数 | 一跑一变量，录前录后都记参数 |
| 9 | 假绿 | `check.py` GREEN 只代表工作流合规 | 发车另需全量回归 |
| 10 | 索引漂移 | 文档改了没重跑 gen_index | 收口六连固定顺序（§7） |

## 9. 还没证实的（别当结论用）

1. 车端实际加载的 `use_external_fire_gate` / PID 三值 —— 本地文件已知，**车端未逐项读**。
2. 0.1300 与 0.157 谁是里程真值 —— 需一次 2.10 m 推车 + 逐拍读数。
3. `check_numbers` 里 `vision_pipeline_latency_s` 的 0.0667 是否该改口径 —— 列为"需人核"。
4. 类型表以 13 类为准后，车端 `ag_ws` 的 7 类解码是否跟着改 —— 未动。
5. 「发 lead 之后能不能开火」—— 唯一硬判据是实车看到开火，目前没做过。

## 9. 三大优化方案的采纳顺序（D-028）

- 执行基线 = `_tmp_session/paper50/三大优化方案.md`（2026-10-21 用户指令转正，**不推翻 D-001~D-027**）。
- 采纳顺序：**方案一（规划/循迹）→ 方案二（云台，先 T-A0 只测不改）→ 方案三（空地，先 T-C0 链路复活）**。
- 明确不混入本轮集成：研究型 ε-anytime / 学习残差 / IMM / 熵图。
- 为什么按这个序：规划与循迹是「车能不能跑完」的地基，云台是「跑完能不能得分」，空地链路是「有没有布局可跑」；先修地基再谈得分，否则归因失效（一次只改一个变量）。
