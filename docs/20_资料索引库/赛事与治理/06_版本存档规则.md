## 2. 版本号规则

| 规则 | 内容 |
|---|---|
| 格式 | `vN.M.P` 三段短名（如 v4.0.3），**不带中文后缀**；中文主题写进 tag message 与 git_save README |
| 递进 | **两仓全部正式版本标签取版本序最大值、末位 +1**（现 v4.0.2 ⇒ 下一版 **v4.0.3**）。执行前两仓各跑一遍 `git tag -l` 核对 |
| 升位 | 小修补丁走末位（先例 v3.9.0→v3.9.1→v3.9.2）；时代级重构升中位（先例 v3.9.2→v4.0.0 air-ground 基线）。升位须有台账裁决记录 |
| 打在哪仓 | 里程碑主体产物所在仓：车端代码里程碑→dzrobot_v2；工作区/文档四库/跨仓协同里程碑→V1 根仓。两仓同里程碑都有实质产物时**只打一个号**（主体仓），另一仓对应提交哈希记进 git_save README 备注，不打第二标签 |
| 岔线标签 | `backup-*`、`pre-*-merge-*` 等备份/前置点**永不参与递进**；新增岔线须在 git_save README 备注说明 |
| tag 类型 | 一律 **annotated**（`git tag -a`）。历史遗留 lightweight（v2.2.0、v2.3.0）不补改，表中标注即可 |
| tag message 四要素 | ① 主题一句话 ② 关键数字（token 数/测试结论/文件数）③ 执行成员 ④ 改名/改号注明原号与依据（如 D-032） |
| 无 tag 的维护提交 | 纯台账/文档维护可不打 tag（先例 v3.8.1=`e40b9a1`〔档〕），**不占版本号、不进 git_save**，只在会话日志留痕 |

## 3. 存档标准流程（六步，每次照此执行）

```powershell
cd D:\User\Desktop\比赛存档\v1\dzrobot_v2      # 根仓存档则 cd v1

# ① 核对工作区——只提交属于本里程碑的文件；并发写入者的改动不得卷入
git status --porcelain
git diff --stat                                # 改动文件数须与提交信息一致

# ② 精确 add + commit（用文件路径；严禁 git add -A / git commit -a）
git add <本里程碑的文件...>
git commit -F <消息文件>                        # 中文消息一律 -F UTF-8 文件

# ③ 打 annotated 标签（中文消息同样走 -F）
git tag -a vN.M.P -F <tag消息文件>

# ④ 同步远程/镜像（矩阵见 §4）
git push origin main                            # gitee：推分支
git push origin vN.M.P                          # 标签必须显式推（默认不带）

# ⑤ bundle 备份 + verify（dzrobot_v2 传统）
git bundle create backup\dzrobot_v2-vN.M.P.bundle --all
git bundle verify backup\dzrobot_v2-vN.M.P.bundle

# ⑥ git_save 快照 + 三处登记
mkdir ..\git_save\vN.M.P                        # 根仓版本：在 v1 下 mkdir git_save\vN.M.P
git archive vN.M.P | tar -x -C ..\git_save\vN.M.P
#   完整性核对比照 git_save/README.md 的验证口径（tar -d / 树比对）
#   登记：git_save\README.md 清单表追加一行；本篇 §1 现状快照更新；会话日志照常
```

## 5. 铁律与坑（全部实际踩过，代价在案）

1. **严禁 `git add -A` / `git commit -a`**。长期存在并发写入者；`e906e6c` 曾混入他人暂存的删除（−3248 行）导致提交信息不实。提交前逐条核对 `git status --porcelain`。
2. **中文消息必须 `-F` 文件（UTF-8）**。命令行内联在 Windows 控制台编码下损坏：v3.6.0 的 tag message 至今 GBK 乱码（已裁决不 amend）；2026-10-23 改号再次复证。
3. **保留署名/日期用 raw 格式**：`GIT_COMMITTER_DATE` 给「epoch +0800」——只给 epoch 会丢时区。
4. **改号/重命名顺序：先建新号、再删旧号**。任何时刻每个提交至少一个标签指着，无撞名中间态；删掉的旧 tag 对象在对象库 dangling，**是回滚保险，不要清理**。
5. **动既有标签 = 翻案级动作**。先出方案经用户批准再执行（先例：2026-10-23 改号，方案先审后行）；执行后把回滚命令与旧对象号写进会话日志。
6. **git_save 是工作区快照，不是 git 仓**。每夹无 `.git`；恢复=直接复制文件夹；git 历史仍在两源仓。**不要在 git_save 里建 `.git`**（3 GB 副本债，D-032 已裁决）。
7. **根仓版本快照体积大**（v4.0.1=500 MB、v4.0.2=1.6 GB；dzrobot_v2 版本 24~67 MB）——根仓版本进 git_save 前留意磁盘余量。
8. **`git archive` 语义**：不导子模块内容（gitlink）；symlink 在 Windows 物化成目录副本。比对口径见 git_save/README.md 的完整性验证记录。

## 7. 远端硬约束：全史推送不可行（2026-10-23 实测）

> 来源：`_archive/20261023/tmp_session/GIT-SYNC-20261023.zip`（只读审计，未推送、未改远端）+ 2026-10-23 19:49–20:05 实测复现。

**三条硬事实**

1. **GitHub 单文件 100 MB 硬限**：本地 `main` 可达 blob 中有 **6 个 >100 MB**（320 / 287 / 252 / 208 / 207 / 118 MB，全在 `docs/history_cache/` 与 `_tmp_session/archive/`）⇒ **任何携带该历史的推送都会被拒**——包括"新建分支后推""merge 后推 main""整体搬去新仓"。本地整仓 **2.24 GiB**。
2. **Gitee 的失败点不在认证、不在协议**：`git fetch --filter=blob:none` **成功（EXIT=0）**；而 `--depth=1` / protocol v0 / HTTP/1.1 三种组合全部在 index-pack 启动后**静默卡死 150 s**，随后 `invalid index-pack output`。
3. **GitHub 与 origin 是同一个仓**：`TestFox000/v2.0` 301 重定向到 `Air-Ground-Competition`（repo id 1429839966）；远端 main = `9d8e486` = 本地 `chunk-push` 的头，"分块重建"历史已占用 main。

**当下所以推不动（2026-10-23 19:49 复现）**：GitHub 直接 `Connection was reset`（网络侧）；Gitee 用新分支推 7 分钟无进展（要上传本地独占历史，非增量）。

**可行路径（待裁决，未做）**
- 只推"瘦分支"：从远端已有提交切出，**只 cherry-pick 文档类小提交**，不带大 blob；
- 大文件（模型/录像/历史归档 zip）走外部交付（桌面包 / 网盘），**不进 Git**；
- 真要全史同步 → 必须先做**历史瘦身**（filter-repo/bfg 去掉 >100 MB blob），这属于重写历史，按 §11.4 **必须用户批准**，不许自行执行。
