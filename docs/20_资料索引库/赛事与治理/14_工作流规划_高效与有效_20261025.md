# 14 · 工作流规划：怎么排才高效、怎么验才有效

> 本篇回答两个问题：一轮工作怎么排（效率），一件活怎么算做完（有效性）。

> 依据：Claude Code / OpenAI Codex / Google Antigravity 官方实践 + AgentLens「假通过」论文（10.7%）+ 本项目 10-03 至 10-25 的实测。

## 14.1 一轮工作的固定序列

已固化在根 @B@AGENTS.md@B@ §0「每轮开工六步」，不在本篇重复。要点：先查账 → 再查库 → 再动手 → 跑门禁 → 落盘 → 提炼。

## 14.2 什么时候派子智能体

| 情形 | 判据 |
|---|---|
| 该派 | 多条互不依赖的线（多目录审计、多模块改造）；单线超过 ~30 分钟且步骤可拆 |
| 不该派 | 改一行、查一个值、读一个文件；需要全局上下文做裁决的收口 |
| 派谁 | 免费/flash 路由优先；需要长上下文分析用更强的 |
| 上限 | 3–5 个并行；超过 5–6 张卡才设协调员 |

## 14.3 怎么排才高效

1. **先做「解锁」动作**：阻塞所有人的（车没摆好、相机被占、门禁红）优先，不管它看起来多小。
2. **按目录/文件切，不按功能切**：功能切会产生共享文件抢写。
3. **串行依赖链不派发**：A 出结果 B 才能做 → 串行更省（派发只增加协调开销）。
4. **危险动作先停再报告**：发车、部署、改默认值 → 做完预检停一下，等人确认。
5. **一次只改一个变量**：否则说不清哪条起作用（§1.6）。

## 14.4 怎么验才有效（对应根 §11 验收纪律）

1. **验收命令必须机器可判**：退出码 / 结构化输出 / 指标表。不接受「看起来对了」。
2. **独立验证**：干活的 agent 不自己给自己打分。
3. **端到端分级**：
   - 算法/控制 → 仿真闭环（sim_cli 退出码 + 指标表）
   - 实车链路 → 实车闭环（bench 日志 + 视频）
   - 文档/配置 → §4 对应守卫
4. **验收清单结构化**：领卡时填全（全 false），收口时逐项勾。事后补的不算。
5. **门禁 GREEN ≠ 回归绿 ≠ 实车通过**：三件事三套判据，别混。
6. **证据绑定当时字节，跨 epoch 不重绑**（2026-10-31 增）：验收证据（哈希清单 / 快照成员 / 绑定关系）只在生成它的那一版字节上成立。上游再改后只有两条合法路径——**重跑（新 attempt）**或**如实标「未重绑」**；拿旧证据的结论去证新状态 = 假通过。实例：`trim-1029 I0` 终轮重跑 8 门禁通过，但 1860 文件绑定 / 61 恢复案例**不按新 epoch 重绑**，卡上明写。

## 14.4.1 量尺先证再用（2026-10-31 检索评测的三条教训）

> 背景：资料库痛点是「查一次拿不到答案」；先冻结量尺（`retrieval_eval.py`）再改检索。实测证明**错量尺比没量尺更危险**——它会把正确的实现判成失败，也会把没修好的状态判成绿。

| # | 教训 | 实测证据（2026-10-31） | 处置 |
|---|---|---|---|
| 1 | **单口径会系统性把正确答案判错** | 初版主口径 M1「top-1 文件本身是权威篇」= **0.0%**。但 top-1 是症状索引时，其命中行已含「机制 + `路径:行` + 处置」，用户一次查询已拿到答案。M1 把这类全判未命中 ⇒ 基线假 0% | 主口径改 **M4 = top-1 直指权威篇 ∪ 经索引中转让出去向 ∪ 权威篇在 top-5**；M1 降为辅助 |
| 2 | **阈值要分「本轮验收线」与「下一阶段目标线」** | GATES 写 m4≥90 / row≥85 / top1≥40，而交付实测 **82.4 / 58.8 / 9.8**；拿它当卡验收器 ⇒ 实现正确也被判 failed（t15 即此）。独立复核实测：这组是下一阶段目标线 | `--check` 定位为**路线图进度表**；卡验收用卡面自己的门槛（M4 ≥ 基线 78.4 即过）。**不许改阈值去凑** |
| 3 | **基线只减不增；覆盖式 `--record` 等于洗白** | 曾一次 `--record` 把旧口径（top1=0.0 / hub=56.9）覆盖成新口径（row=52.9 / hub=0.0），被独立验收判「基线被改写而非被修复」 | 基线保留口径变更史；重建基线须用「HEAD 版 + 改前快照」swap，并 sha256 校验 swap 前后逐字节一致 |

> 三条合起来一句话：**先证量尺（对手工抽样、能解释每一分），再用量尺；量尺自测与抽样矛盾时先怀疑量尺。**
>
> 交付结论（同批实测，供查）：M4 68.6% → **82.4%**（+13.8pt，超过基线 78.4）；M2 52.9% → 58.8%；hub 抢位 56.9% → **0.0%**；症状索引 top-1 时命中行给出向 29/29。三 NEXT-GATE 指标（40/85/90）未达，已记「下一阶段目标线」并转下一阶段（达成路径是语料侧「常见问法」别名映射，不是排序层）。

## 14.4.2 三层「形式完成 ≠ 事实完成」（2026-10-31 四类同型错误）

> 背景：同一天的四个事故，表面互不相关（检索、门禁、验收、部署），内核是同一个：**我用了「能确认的最小事实」，替代了「该确认的事实」**。四轮都是被独立复核或真跑推翻的，都不是自查发现的。

| 层 | 我拿来判「完成了」的 | 真正该判的 | 实例 | 后果 |
|---|---|---|---|---|
| ① 格式 | 文件存在、结构对、字段齐 | **内容会不会被读成别的意思** | `check_archive_ready` 首版只看「有无段落/有无指针」 | 8 条判据里 3 条假阳性，50% 通过率是假的 |
| ② 自测 | 我写的用例全绿 | **用例能不能骗过判据** | 10 条自测全过，但全是「按我的理解写的」 | 需 5 个对抗夹具才打出缺陷（C1/C4/D5 全漏） |
| ③ 部署 | 配置文件里有那一行 | **它挂载的那个 bundle 还活着吗；工具真能调通吗** | dzdoc MCP 挂在 `dzhairground-ssh` bundle 上，该 bundle 早已 `enabled:false` | 文档声称「已注册」，实际从未生效；只有真跑 `tools/call` 才暴露 |
| ④ 因果 | 两个数字对得上 | **这两个数字是不是同一个对象** | 我把两命令计数相减，得出「`_work/` 有 15 篇在语料里」 | 判别实验证明它本来就不在（490 vs 505）；我据此改了 1 行「修」一个不存在的缺陷 |

**统一修法（四条，按层对应）**：

1. **格式关**：写完判据先问「这段话/这个字段有没有第二种读法」，再问「谁会用它来反证我」。
2. **自测关**：**造一个该失败但可能被误放行的样本**，看它会不会通过。对抗夹具测的是判据本身，不是实现。
3. **部署关**：任何「配好了」的结论，必须**真调用一次**才算成立。可见态（`enabled:true` / `fiberPhase:loading`）不等于可用态。
4. **因果关**：差两个数之前先确认**分母是同一个对象**；能跑一个判别实验（改/不改对照）就不要靠减法推因果。

> **这四关的共同点**：我确认的都是「世界应该是什么样」，而不是「世界现在是什么样」。前者的成本是零（读一眼），后者要花钱（跑一次）。**每次想省这一步，都有人在后面替我省不了。**

## 14.6 什么时候停

- 连续 2 轮无提升 → 停，写清停因（§1.6）。
- 需要现场/需要用户动作 → 挂 @B@⏸@B@，写清下一步和阻塞项。
- 证不出来 → 不算完成（§1.5），如实标「未验证」。

## 14.7 规则的升级路径

- 新规则先按**黄线**跑满一轮零告警，再转**红线**（2026-10-23 Y6~Y8 → R7~R9 即此路径）。
- 理由：新规则一上线就判红，会把存量噪音混进真实问题（Y10 对 10-22~10-24 归档卡误报 12 条即此教训）。
