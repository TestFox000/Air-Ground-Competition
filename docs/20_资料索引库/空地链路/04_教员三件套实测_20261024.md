# 教员三件套实测：能不能用 / 与现役是否一致 / 要不要入仓

## TL;DR（给 agent 看的）

- **三件都能跑，但没有一件能直接当生产组件**：udp_bridge 只打印、不产出我们 schema 的 JSON；motor_monitor 默认参数已过期（轮距偏 **+20.4%**）且实际只有 **6.4 Hz**；udp_hexdump 只配当调试锥。
- **类型表裁决 = 两套并存**：机端发送端已 **13 类**（2026-10-16 起，模型 `hbb_detector_d13_20261016.onnx`），车端 `ag_ws` 部署层仍是 **7 类**，我们仓库 `types.hpp` 也是旧 7 类。教员那张表 **= 机端现行**，写适配器要照它。
- **最贵的坑不是"用不了"，是坐标口径**：机端米制是 MapLocalizer 帧（X0=0.065 / Y0=0.295 / 格 0.35 m），车端 `core/geometry.py:28-30` 是另一套原点+轴向；拿车端公式反解机端坐标会整场错位（§7-2）。
- 关键数字：机端真帧 **352 B / 13 对象**、0x4003 **57 B / 4 航点**；轮距 **0.1300 m**（默认参数 0.1565）；回环正向 **3/3 字段一致**、坏帧 **5/5 全拒**。

### 2.2 负向五连：全部被拒（贴原文）

| 坏帧 | 构造 | udp_bridge 输出 | 判 |
|---|---|---|---|
| CRC 错 | 翻 body 一个字节、不重算 CRC | `intel PARSE FAIL: crc mismatch` | ✅ |
| declen 改大 | 长度 +25 并重算 CRC | `intel PARSE FAIL: len 77 != 2+25*2` | ✅ |
| declen 改小 | 长度 −25 并重算 CRC | `intel PARSE FAIL: len 27 != 2+25*2` | ✅ |
| 坐标 NaN | x=NaN | `intel PARSE FAIL: NaN/Inf in object` | ✅ |
| msg_id 错 | 0x4004 | `unknown msg_id 0x4004 len=27` | ✅ |

> "改小"那条是**先按偏移 15 改 declen 并重算 CRC** 才成立的：我第一版把偏移写成 13（那是 msg_id 的位置），结果两条长度用例其实测的是 msg_id——**这一条记在这里，是因为它证明"看起来像通过"的测试可能是假的**。

### 3.3 三个缺陷（都会误导现场）

1. **频率不实**：文档说 10 Hz，实测 **193 行 / 30.00 s = 6.40 Hz**（CSV `dt` 中位 0.199 s）。根因是节流阈值 == 定时器周期（第 91 行 `< 0.1` vs 第 77 行 0.1 s），抖动就丢拍。
2. **退出不干净**：`timeout` 杀进程时 `rclpy.shutdown()` 被调两次，抛 `RCLError: failed to shutdown: rcl_shutdown already called`（第 156~166 行）。
3. **数据为 0 时说明不了问题**：`age cmd=-1.0s` 全程——车端没有 `/pursuitAngle` 发布者（dzbrain 没起），所以 PWM/duty/左右轮恒 0。**这是环境，不是脚本错**，但也意味着"有速度/转弯时的数值对不对"本轮没验（§8）。

## 4 udp_hexdump（25 行）

可用：3 帧回环输出 `#1 len=77 msg=0x4001 declen=52` + HEX 77 字节 + TXT 可读。局限：**只按 magic 计数**（第 18 行），不过 CRC、不校验长度，坏帧照样算一帧——所以它只能证明"线上有字节"，不能证明"帧合法"。

## 5 类型表裁决：**两套并存**

四条独立证据（都不是推断）：

| # | 证据 | 结论 |
|---|---|---|
| 1 | 机端部署的 `types.hpp`：`Paper=0, CellLabel=1, Car=2, TargetRed=3, TargetBlue=4, Obstacle=5, BucketRed=6, BucketGreen=7…`，注释写 **"2026-10-16 起切换 D 方案 13 类统一模型"** | 机端 **13 类** |
| 2 | 机端 `intel_protocol.py` 的 `ObjectType` 13 项，顺序与教员 `TYPE_NAMES` **逐项相同** | 教员表 = 机端现行 |
| 3 | 机端部署二进制 `build/dzuav`（10-22 16:56）`strings` 里是 `bucket_cyan/bucket_green/bucket_red/car_start/car_end/uav_start/uav_end`；`current_hbb_detector` = `hbb_detector_d13_20261016.onnx` | 跑的是 13 类 |
| 4 | 机端真帧 352 B 进 udp_bridge，13 个对象名全对（§2.3） | 线上字节与教员表一致 |

而"我们"这一侧：

| 位置 | 类别表 | 状态 |
|---|---|---|
| 仓库 `dzsmartscout/.../types.hpp:11-20` | 7 类（Mine/Car/Arrow/TargetRed/CellLabel/TargetBlue/Obstacle） | **旧** |
| 车端 `ag_ws/.../intel_protocol.py` | 7 类（MINE/CAR/ARROW/TARGET_RED/CELL_LABEL/TARGET_BLUE/OBSTACLE），且 `ObjectType(type_index)` 是**硬转换** | **旧、且会炸** |

**所以结论是"两套并存"**：发送端已 13 类，车端部署层与仓库副本仍 7 类。对"适配器该照哪张表"这个问题只有一个答案：**照教员那张（= 机端现行）**。

## 6 若照旧 7 类解新帧，会发生什么

| 线上 type | 实际含义（13 类） | 旧表会认成 | 后果 |
|---|---|---|---|
| 0 | 场地纸片（普通格=雷，K 列=通行箭头） | MINE 雷 | 普通格**碰巧对**；K 列纸片被当雷 ⇒ 封闭可穿桥洞 |
| 1 | 地面格号 | CAR 车 | 格号被当车位姿 |
| 2 | 行驶车辆 | ARROW 箭头 | 车被当桥洞箭头 |
| 4 | 蓝靶（敌方，该打） | CELL_LABEL 格号 | **敌方靶被打成格号 ⇒ 不开火** |
| 5 | 障碍物 | TARGET_BLUE 蓝靶 | **把障碍当敌靶 ⇒ 可能对着桶开枪** |
| 6 | 红桶（禁火） | OBSTACLE 障碍 | 桶被当障碍 |
| 7~12 | 红/绿/青桶、起终点 | **不存在该枚举值** | `ObjectType(7)` 抛 ValueError ⇒ **整帧丢弃** |

最后一行是车端现役代码的真实行为（`ObjectType(type_index)` 硬转换，无回退）。**只要机端一帧里出现桶或起终点，车端那条链路就整帧丢**——不报错到上层，只表现为"情报变少"。

## 7 接法方案（只出方案，不写实现）

### 7-1 转换层放哪、读哪个口、写哪个口

- **放车端（192.168.0.4）一个独立 Python 进程**，不要塞进 dzbrain（是冻结区），也不要在机上加第二写者。
- **读**：UDP `:50000`（机端广播，`UdpBroadcaster.cpp:93-100` 发 `INADDR_BROADCAST`）。
- **写**：`std_msgs/String` → `/dzlink/drone_to_car`（`contract.py:94`，BEST_EFFORT·depth 10），内容就是 `tasks/drone.py` 现在吃的五种 JSON。
- 为什么不是 `--publish`：那条路写 `/nav/waypoint`，会变成任务模块的第二个写者。

### 7-2 米制 → 格名：要哪几个参数、从哪个文件读

机端帧的坐标是 **MapLocalizer 帧**：`world_x = 0.065 + col·0.35`、`world_y = 0.295 + (10 − row0)·0.35`（机端 `ag_integrate/field_frame.py`，注明对应 `MapLocalizer.cpp`）。反解只要三个常数 + 两条轴：

```
col = round((x − 0.065) / 0.35)        # 0=A … 13=N
row0 = round(10 − (y − 0.295) / 0.35)  # 0=第1行 … 10=第11行
残差 > 0.35 格就拒收（原实现 MAX_CELL_RESIDUAL）
```

**不能用**车端 `core/geometry.py` 的 `block_to_meters` 反解：它是 `x=(10.5−row)·0.35, y=(13.5−col)·0.35`（x 由**行**决定），与机端**轴向都不同**。用错的表现是"整场错位一格到几格"，而不是报错。

### 7-3 我们那五种报文够不够装

**不够，缺三样、多两类。**

| 机端给的东西 | 我们 JSON 能装吗 | 说明 |
|---|---|---|
| 雷 / 障碍 / 靶（格名） | ✅ `field_verify{mines,obstacles}`、`target_zone{blocks}` | 需要 §7-2 换算 |
| 桥洞通行（K 列纸片） | ✅ `bridge_passable{half,block,confidence}` | `confidence` **帧里没有**，只能给常数（建议 0.9 并注明合成） |
| 车位姿 0x4002 | ❌ **无对应报文** | 我们只有车→机 `car_state`，没有机→车 "car_pose"；要用得新增 type 或只做交叉校验 |
| 桶（红/绿/青）、起终点 | ❌ 无字段 | 丢弃（桶禁火语义可作保险，但要新字段） |
| 每目标置信度 / 格号 / scan_id / 覆盖 | ❌ 帧里没有 | 所以 **不要**给 binary 来的 `field_verify` 加 `coverage`——空表会被读成负证据 |
| `field_layout`（规划真源） | ⚠️ 拼不出 | 缺 start/end/known/版本，只能由机端规划侧发（JSON），不能从 0x4001 反推 |

### 7-4 三份文件：复用还是重写

| 文件 | 建议 | 行数 |
|---|---|---|
| `udp_bridge.py` | **只复用解析核**（`crc16`/`parse_intel`/`parse_pose`/`parse_route`，约 120 行）；sniff 循环与 `--publish` 丢掉 | 新适配器约 **180~220 行** |
| `motor_monitor.py` | **复用 + 三处小修**（默认值跟仓库、节流阈值 0.09、退出只 shutdown 一次） | 改 **~8 行** |
| `udp_hexdump.py` | **原样复用**（现场调试锥），可选加 CRC 校验 + 落盘 | 26 行，或 +10 |

## 8 三档价值 / 风险 / 未验证

**价值**：①（高）udp_bridge 的解析核 = 现在缺的"二进制→JSON"那层的现成地基，且已用机端真帧验过；②（中）motor_monitor 补上"左右轮速/PWM 可见性"这个空白，是 C1/C2 标定的现场仪表；③（低）hexdump 只用于"到底有没有包"。

**风险**（按代价排）：① 类型表用错 ⇒ **静默错标**（§6，含"对着桶开枪"）；② 坐标口径用错 ⇒ 整场错位且不报错；③ `--publish` 打开 ⇒ 制造第二个 `/nav/waypoint` 写者；④ 机端 `ag_integrate` 与适配器同时发 `/dzlink/drone_to_car` ⇒ 两个生产者打架（**必须单写者**）。

**未验证（本轮明确没做）**：
- 真实相机→检测→广播的**实时帧**（机上感知未启动；本轮用机上同一编码器的工具帧 + 部署二进制 strings 验枚举）。
- 0x4002 车位的**真实数值**（本轮没触发；工具未主动发）。
- motor_monitor 在**有速度/转弯**时的数值正确性（车静止、`/pursuitAngle` 无发布者）。
- 机端 `ag_integrate` JSON 链路与二进制链路的**同时在线**行为。

## 9 三个文件收不收进仓库

**建议：本轮都不收。** 理由：它们是**现场参考工具**，不是生产件；入仓要登记复用清单 + 过 §8 三步，而现在真正要写的是适配器（§7），把三个 demo 搬进来只会变成第二份要维护的代码。真要收，落点应是 `dzrobot_v2/tools/field/`（与 `tools/` 现有约定一致）**且只收 udp_hexdump + 解析核**，不收两个 CLI 壳。**本轮没有搬任何文件进仓库。**
