### 2.2 车端状态机（`main.py` `StepLoop`）

```
WAIT_LAYOUT ──首份布局──▶ PLANNING ──规划成功──▶ DRIVING ──任务线程完成单──▶ SEGMENT_DONE
      ▲                        │ 失败/无目标/布局过期                                        │
      └────────────────────────┴──▶ WAIT_INFO（无超时，等下一份布局） ◀──────────────────┘
```

三条硬语义（代码注释 + 实测都对上）：
1. **换段只发生在段边界**：DRIVING 期间到达的新布局只记版本（`7_path` 日志 L185-186：v3 在段 2 执行中到达 → 「本段执行中 → 段边界再重规划」）。
2. **WAIT_INFO 无超时**：`step.wait_timeout_s=0`；段完成后等新版本布局（`7_path` 日志 L513-551 停 I7 等了两轮）。
3. **完成单闩锁 + 1 Hz 重发**（D1b 修法，`main.py:646-657`、`1048-1066`）：`done_seq` 单调、WAIT_INFO 期间每秒重发一次，实测 L519 出现 `↻ 段完成单重发 ×1 ... done_seq=3`。

### 2.3 机端发射器（`emit_step.py`）

- 真值图内置（第六张地图）；`known` 按 10 个批次**定时**增长（不依赖车的位置）；
- 每 **0.5 s** 心跳重发当前版本（抗丢包）；**收到车端 `car_state.done` 且 `seq` 递增**时：记 `covered_mines`/`done_stops` → `version+1` → `choose_mission_target()` 重算目标 → 立即下发；

## 5. 问题清单（按对「一次通」的杀伤力排序）

### P1 · 布局 TTL 与心跳语义错位（中，但每次都吃 11 s）

- **现象**：段 2 完成后 `WAIT_INFO` **11.2 s**，原因 `layout_stale`（L344）。
- **机制**：`_poll_layout()` 对 `version <= seen` 直接 return（`main.py:844`），只有**版本递增**才刷新 `_layout_rx_at`（`main.py:854`）；而发射器每 0.5 s 发的**同版心跳被完全忽略**。`step.layout_ttl_s=10 s`，发射器默认周期 12 s ⇒ 每个段边界**必然**先吃一次「布局过期」。
- **影响**：每个段边界固定损耗 ≈ 周期−TTL ≈ 2～12 s；再叠加机端 0.5 s 心跳，实际每次 ~11 s。四段就是 20 s 量级的白等。
- **建议**：① 新鲜度改用「**收到同版心跳**」刷新（`_poll_layout` 里版本相同且内容相同也要更新 `rx_at`）；或 ② 发射器周期压到 TTL 的 1/2（5 s/版）；或 ③ `step.layout_ttl_s` 调到 > 发射器周期。**三者选一即可，推荐①**（语义最正：心跳就是「我还活着、布局还作数」）。

### P2 · 同格空段死循环（高——会把版本和完成单推爆）

- **现象**：段 6、段 7 连续 **「同格停站（0 token）」**（L511、L543），`done_seq` 3、4 递增，车**一步没动**，版本 v6→v7 空转。
- **机制**：车端对「目标==当前格」按 D1b 口径**也记一段并回报**（`main.py:888-899`）；机端收到 done 就 `version+1` 并重算目标；`frontier_target()` 的候选是「可达前沿」，**没有排除当前格**（`scout/layout.py:401-429`）⇒ 车停在 I7 且 I7 仍是前沿 ⇒ 目标还是 I7 ⇒ 无限循环。
- **影响**：不前进但持续推版本；若机端是真实无人机，还会白耗链路与算力；若比赛限时，直接烧预算。
- **建议**：① **机端**：目标决策排除 `car_block`（`frontier_target` 结果 == car 时取次优）；② **车端**：`skipped=True` 的完成单**不推进** `done_seq`，或带 `empty=true` 让机端不推版本；③ 加「连续 N 次空段 ⇒ 上报 STUCK 事件」而不是静默循环。

### P3 · 桥洞情报与默认格没有和布局对齐（高——安全语义混用）

- **现象**：段 2 在 L7 进入 `HOLD`，等「洞口 6」的情报，上限 12 s；日志写明 `lower → K10（missing：该半场从未收到 bridge_passable → 用默认格）`、`upper → K4（missing…）`（L170、L236）。**而这一段实际规划的穿洞格是 K7**（L100）。
- **机制**：Mission 的桥洞候选来自 **v1 情报 + 配置默认格**（`tasks/mission.py:101`、`2186`），**不读布局的 `bridges`**；本次布局是 K5/K7，配置默认是 K10/K4，两套口径并存。
- **影响**：① 白等 12 s；② 若窗口内有情报把路线改成 K10/K4，而布局真值是 K5/K7，会**换到错误的洞**（本次靠「到点必发车」保持了原路线才没出事）。
- **建议**：桥洞候选**以布局 `bridges` 为唯一真源**（v1 情报只在布局给的洞里选）；`bridge_passable` 的 block 不在布局 bridges 内 → 拒收并记日志。验收：`bridge_passable=K10` 而布局 bridges=K5/K7 时，路线不变、日志出现拒收原因。

### P4 · 拐角绕圈兜底（中——两次强跳点）

- **现象**：K7 停滞 **12.2 s / 累计转 14°** 被跳（L239）；G8 停滞 **12.1 s / 累计转 183°** 被跳（L431）。183° 明确是**原地转半圈**。
- **机制**：`mission.stall_timeout_s=12 s`（`core/config.py:361`）到点强跳；触发条件是「弧长 s 不前进」——纯追踪在顶点航向误差大、前视点回摆时 s 会长期不增。段规划给出的 2 处「策略性转弯」（M7、I7）本身就被 tracker-safe 降级，等于**规划器明知这两个弯不好转仍然发**。
- **影响**：漏点（本次 K7、G8 均为路径上的必经点），虽然后续规划绕过去了，但到点率与定位一致性都被破坏。
- **建议**：① 段规划对 >90° 的转弯显式标 `PIVOT`（或限制每段最多 1 个策略性转弯）；② 兜底触发前先给一次「**倒车/原地复位**」机会（本次倒车入口 0 次使用）；③ 把 `stall_timeout_s` 与巡航速度解耦（低速时 12 s 太短）。

### P5 · 里程尺度 27%（高——步进精度的天花板）

- **现象**：吸附被拒 11 次，隐含尺度 +8.2%～+44.8%（L145/157/167/257/274/283/290/322/417/425/442）；结束时估计器给 **scale=1.26871 → 1.015**（L567）；期间判「段位移不可信」丢弃 **23 拍 / 2.736 m**（L567）。
- **机制**：`_scale_suspected()` 用「连续同向吸附 + 幅度≥半个到位半径 + 隐含尺度≥8%」判「尺度误差冒充到位噪声」（`tasks/localization.py:1056-1095`），拒绝吸附；`_settle_ds()` 用位姿位移×2 兜住 s 跳变（`tasks/fix.py:350-412`）。两者都是**护栏**，不是修复：真正的修法是标定 `ticksPerMeter`（底盘 3280 ticks/m）或按格距 0.35 m 实测。
- **影响**：s 与真距不一致 → 到点判定偏早/偏晚、段长估计偏、姿态吸附拒绝后误差累积。**步进协同越准，这个误差越致命**（目标是「某一格」）。
- **建议**：跑一次「直行 3.5 m（10 格）+ 卷尺」标定；把标定后的系数写进 `robot.yaml`，再用 `check_numbers.py` 固化；估计器的 1.015 只能当**诊断值**，不要回写。

### P6 · 静止段 yaw 漂移与位置跳变（中——等待越久越危险）

- **现象**：车停在 I7 后（21:52:11），12 分钟内 yaw 从 **+10° → -242°**（净 -252°）；期间 21:57:15 前后出现一次 **~1 m 位置跳**（(4.48,5.32) → (5.41,4.95)，block I7→J6）并伴随 yaw 大跳。
- **候选解释（未判定）**：① IMU 零偏漂移（换算 ≈21°/min，且与位移无关）；② 有人/外力挪车；③ 定位节点内部重锚（`serial_reader` 监听 `reset:` 命令会重定 DR，`serial_reader.py:100-157`）。
- **影响**：段边界等待期间航向不可信；下一段起步的 `heading_dir` 若用了漂移后的 yaw，首步就可能反向。
- **建议**：① 做一次「静止 10 分钟录 yaw」实验区分①②；② 车端在 WAIT_INFO > 5 s 时冻结 yaw 或强制要求重锚（`reset:`）后再规划；③ 航向守卫的阈值与「静止」状态解耦（R2 的 SAFE_STOP 就是静止 yaw 误判/真漂的混合）。

| 布局 TTL | 10 s（见 P1） |

### 6.2 流量账（`7_path` 日志 L579）

| 消息 | 条数 | 说明 |
|---|---|---|
| 总收包 | **208**（坏 0） | 平均 3.2 Hz |
| 布局帧 | ≈129 | 6 个版本 + 0.5 s 心跳（同版同内容被忽略，但计入消息数） |
| 心跳帧 | ≈79 | 与 ack 数一一对应（推断：208−129=79，见下） |
| `car_state` | 105 | 含 `done_seq`、`target_cell`、`stop_kind` |
| ack | 78 | **只对带 `seq` 的报文**；布局报文无 `seq` ⇒ ack **不证明布局送达** |
| 桥洞情报 | **0** | `bridge_passable` 一条未达 |
| 覆盖/核对事件 | 0 | `coverage`、`field_verify` 未使用 |

**关键推断（有算术支撑，非直读）**：208 ≈ 129（布局）+ 79（心跳）；ack=78 ≈ 心跳数 ⇒ **同一话题上至少有两个发布者**（发射器发 `field_layout`、另一个进程发带 `seq` 的 `heartbeat`）。这解释了「online=是 但桥洞情报 0」：心跳维持了在线状态，而情报通道其实没内容。

**由此得出一条现场纪律**：**不要把「online」当「情报在流」**。判布局断没断，看车端 `第 N 份布局` 与 `layout_stale`；判情报断没断，看 `桥洞情报` 计数。

### 6.3 三条通信侧发现

1. **「假在线」风险**：只要心跳还在，`online=True` 会一直保持；布局/情报停了车也不会因此下线，只会 `WAIT_INFO(layout_stale)` 无限等（`step.wait_timeout_s=0`）。建议：在线状态拆成 **心跳在线** 与 **情报新鲜** 两个指标上报（遥测已有 `layout_age_s`，把它推到 car_state 即可）。
2. **同版心跳被丢弃但计入计数**：车端日志会打 `field_layout vN 心跳重发（同版同内容，忽略）`，但**消息计数照加**，所以「208 条」里一半以上是不可用于规划的心跳。做链路健康度时要用「有效布局数」而不是总包数。
3. **整条链路会掉**：21:51–22:03 车机可 ping（8–13 ms），22:04 车 SSH 仍可通；22:19 再测 **车（192.168.0.4）与机（192.168.0.5）同时 100% 丢包**，SSH 超时。这是 **Wi-Fi/热点层**的问题，不是 DDS——两端同时掉说明是 AP 侧。现场纪律：起跑前确认「车 SSH + 机 SSH 都通」，别只看车端日志的 online。

### 6.4 与 v1 情报通道的合流缺口

- 本次只起了 `field_layout` 通道：`bridge_passable`、`target_zone`、`field_verify` 全 0（L579）。
- 车的桥洞决策（P3）因此只能走「默认格」，而默认格是**另一张图**的桥洞（K10/K4）——两套真源并存是当前最大的语义风险。
- 验收判据：一次跑动里 `桥洞情报` ≥ 1 且 `bridge_passable.block ∈ layout.bridges`；否则视为情报链路未接入。

### 6.5 车内侧 QoS 噪声（记录，不构成故障）

启动时出现 2 条：

```
New subscription discovered on topic 'pursuitAngle', requesting incompatible QoS.
No messages will be sent to it. Last incompatible policy: RELIABILITY
```

底盘对 `pursuitAngle` 的契约是 **BEST_EFFORT / depth 1**（`io/contract.py:35`），且本趟控制实际生效（段 2/段 5 都走到了），所以这条警告来自**一次性的诊断订阅**（默认 RELIABLE 的 `ros2 topic echo` 之类），不是控制链路。现场做诊断时对大话题加 `--qos-reliability best_effort`，避免刷这条警告。

## 7. 规律与教训（跨四趟）

1. **定位尺度是所有问题的共同分母**：R1 17 次拒吸附、S2 11 次 + 27% 尺度、20:14 的 SAFE_STOP 也发生在 s 与真距不一致的路径上。**先标定，再谈速度**。
2. **速度不是主因，0.30 m/s 只是放大器**：R1 在 330 s 里完成了 34/53；16:49 用 0.10 m/s 完赛。把 0.30 m/s 的问题归因于「太快」会掩盖 P5。
3. **步进协议的「正确性」已经证了**：版本单调、同版同内容拒收、段中不重规划、完成单闩锁，都在真车上跑出来了；现在缺的是**节奏**（P1）与**目标推进**（P2）。
4. **兜底机制在保护系统，也在掩盖问题**：绕圈兜底跳 2 点、吸附拒绝 11 次、不可信 ds 丢弃 2.7 m——这些都不是 bug，但每一条都在提醒底层估计有问题。
5. **起栈期的 DDS 发现要等**：`启动契约 18 项 / 失败 7 / 阻断 0`（L11-22），失败的 6 条全是 `pubs=0` 的 advisory（imu/offset_center/aim_status/shoot_count/manual_override/referee），另有 1 条是真问题——`manual_gimbal` **本节点未创建订阅**（L20，代码/装配缺口）。判「节点没起」前先等 2～3 s。
