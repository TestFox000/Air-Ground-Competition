# 步进循环协议 v2（无人机侦察 → 小车步进执行）

> 状态：设计稿（Lead 定稿，2026-10-18）。三张实现卡（T27 车端 / T28 机端 / T29 仿真台）以本文为准。
> 原则：**无人机负责"知道什么 + 下一步去哪"，小车负责"这一段怎么走 + 走得安全"。**

## 1. 循环

```
PC: START（唯一指令）
  ↓
无人机：起飞 → 按侦察路线拍帧 → 每帧把视场内格标 known → 下发布局(v2) + 目标格
  ↓
小车：等布局 → 段规划（只走 known 格）→ 执行本段 → 到目标格 → 回报
  ↑                                                      ↓
  └────────────── 等待下一段布局（无上限） ←───────────────┘
  ↓
到终点 N5 → FINISH；无人机降落
```

## 2. 报文：`field_layout` v2（无人机 → 小车，DDS/JSON）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `type` | str | ✅ | `field_layout` |
| `version` | int | ✅ | 单调递增；车端只接受 >= 当前版本 |
| `ts` | float | ✅ | 机侧时间 |
| `start` / `end` | 格名 | ✅ | 车起点/终点（不变） |
| `known` | [格名] | ✅ | **已观测格**（至少看过一次；可含空格） |
| `mines` / `obstacles` / `targets` | [格名] | ✅ | 已发现特征（⊆ known） |
| `bridges` | [格名] | ✅ | 可通行桥洞（非空） |
| `barrier_col_from` / `barrier_row_hi` / `barrier_row_lo` | 列/行 | ✅ | 隔板三键 |
| `target_cell` | 格名 | ⭕ | **本段目标格**（空 ⇒ 车只等不做） |
| `segment_id` | int | ⭕ | 段序号；车回报时原样带回 |

校验不过 → 整份拒收，保留上一份；车端日志节流。

## 3. 车端行为（T27）

1. **知识合并**：收到 v2 → 校验（known 只含合法格名；特征 ⊆ known；bridges 非空）→ 存最新布局（version 大者胜，同版本不重启）。
2. **段规划**：`MapSpec{未知格=障碍, mines, obstacles, targets, bridges}`，`from_cell=当前格`，`target=target_cell`；A*/tracker-safe 引擎；**规划失败 → 进入 WAIT_INFO，不退出**。
3. **执行**：MissionTask 执行该段（复位航向按段首格朝向）；**目标格是射击停站时**（判据与 T21 同源：到靶板中心 ∈ shoot 窗口、同侧、视线不挡），段规划器把末 token 标 `*`，MissionTask 走 SETTLE→ACQUIRE→FIRE→DONE 停站（30s 硬死线），打完才回报；到 target_cell → 发 `P_CAR_STATE`（phase=SEGMENT_DONE, segment_id, block, stop_kind）。
4. **等待**：WAIT_INFO 停车保持位姿；**无超时上限**（配置 `step.wait_timeout_s: 0 = 无限`）；每 5s 日志警示；收到新布局立即回 PLANNING。
5. **安全**：路线绝不进未知格（规划器保证）；实际投影落入未知格 → SAFE_STOP；等待期间静止闸**不得**触发假完赛。
6. **回报**：`P_CAR_STATE` 增 `phase / segment_id / known_count / stop_kind(shoot|mine|path|end)` / target_cell`。

## 4. 机端行为（T28，仿真模型先行）

1. **侦察帧位**：视场 **2×4 格**，随航向旋转 90° 变 **4×2 格**；相邻帧位 ≥30% 重叠；帧频 1~2 Hz。
2. **知识更新**：每帧把视场内格标 known；特征从真值图取出写入 mines/obstacles/targets（只写 known 内）。
3. **目标格决策**（v2 简化规则）：目标 = 车从当前格出发、在 known 图里可到达的最远"侦察前沿点"；若终点已在 known 内且可达 → target = end。
4. **下发节奏**：布局有变化就发；**另每秒心跳重发最新版**（含 segment_id 不变），防止"2 分钟停发"类问题；车端按版本去重。
5. **重发循环**：以车端 ack/最新 receipt 为准持续重发，不因过期计时器停发。

## 5. 仿真台验证场景（T29）

- 无人机按用户手画侦察路线飞（起点 N8，先扫下半场；视场 2×4 随 yaw 旋转）
- 小车从 N10 出发，按第 3 节步进循环执行
- **通过判据**：
  1. 到终点 N5 并 FINISH；
  2. 全程 **0 次进入未知格**（plan 与 truth 双查）；
  3. 每次 WAIT_INFO 前后无运动（停车等待）；
  4. 总时长、等待总时长、重规划次数有台账；
  5. 段路线全部过 route_check（0 error）。
- 对照：单次全局规划（现有 T21 路线 64 token）的时长作为下界参考。

## 7. 扫描顺序预实验（2026-10-18，骨架阶段）

同一骨架场景只改"上半场开扫时刻"：

| 上半场开扫 | 总时长 | 等待 |
|---|---|---|
| t=0 s | 94.38 s | 2.10 s |
| **t=20 s** | **93.52 s** | **1.24 s** |
| t=30 s | 103.52 s | 11.24 s |
| t=40 s | 113.52 s | 21.24 s |
| t=45 s | 118.52 s | 26.24 s |

结论：帧位排序应优先覆盖车接下来的**信息边界点**（当前路线下为 C6 / A2 / C5），而不是整体扫完上半场再发；t=20 s 开扫即可把等待压到 1.24 s，总时长 93.5 s < 单次规划基线 104.16 s。
