## 4. 与文档第 2 步（整定）的口径换算

文档的 `px_per_tick = 2.0 → 0.94` **在本车不存在这个键**——它是 v1 参考实现（`src_v1`）里的变量；本车对应两个位置：

- v1 模式：`v1_inc_gain 0.5`（注释：上游 `eff/2.0`）——即 `1/px_per_tick`，同样存在"每帧只修 47%"的问题。
- **现役 pid 模式**：每帧位置增量 = `pid_kp · e / 30`（tick），而"修正 e 像素"需要 `e / 0.94` tick ⇒
  **每帧修正比例 = pid_kp / 31.9**

| pid_kp | 每帧修正比例 | 性质 |
|---|---|---|
| 10（现值） | 31% | 稳态滞后 ≈ v_frame/0.31 ≈ 13.8px（远大于开火框 14px 的一半） |
| 32 | 100%（死拍） | 但视觉链路有 ≈267ms 纯延迟 ⇒ 死拍必震荡 |

**结论（重要）**：pid 模式**不该**追死拍增益——增益顶到 20~32 会因 267ms 延迟自激（这正是"PID 还是晃"的机制）。正确路线是 **增益压在 10~12，用 `lead_apply_gain` 的提前量去消滞后**，也就是文档第 3 步里的"提前量"必须排在"调 kp"前面。

## 7. 补充：一个**状态型**的坑（参数 dump 看不出来）

```cpp
// dzrknn_dataprocess.cpp:355
const bool ammo_ok = (max_shots_ > 0) && (shots_fired_ < max_shots_) && ...;
```

`max_shots` 是**进程生命周期内的累计上限**，打满即**永久不再开火，只能重启节点**。源码注释自己写着：
> 「一旦打满 max_shots_(10) 就永远不再开火，只能重启节点 —— 调试时极难受。」(cpp:1257)

**实证**：`~/robot_logs/5_gimbal.log`（17:06 那轮）末尾是
```
pub_LaserShot_Command  [10/10]  dz=19  v=0.000209878/-0.614785  realV=0/0
```
即**那轮把 10 发全部打满**，之后该进程再也不会开火 —— 与"发10/中0"的现场口径完全对上。

⇒ **体检规程必须加一条**：每次改参/换靶后**重启 `5_gimbal`**，否则可能继承"已打满"状态；
本次体检在 17:38 已重启，`shots_fired_ = 0`（新进程），当前 `/aim/status = 0`（IDLE）、**未开火**。

同一份日志还给出两条旁证：
- `==> 类别已锁定 locked_cls=2（红）` + `诊断(不放行开火)：类别不允许(fire_only_blue)` ⇒ **蓝靶门控确实在工作**；
- 开火时 `realV=0/0`、`dz=18~19` ⇒ 旧判据要求"画面/电机静止"，**移动靶下必然打不出去**（与 §3 #1 互相印证）。
