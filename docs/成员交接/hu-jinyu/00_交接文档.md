# 一、工程总览

## 1.1 赛题背景

空地协同侦排挑战赛，**单局 180 秒**，赛前有 **2 分钟**准备阶段。

- **无人机**负责 4 类侦察：地雷准确位置 / 敌我识别打击区位置 / 障碍物 / 桥洞可通行通道
- **地面车**负责：接收无人机信息 → 路径规划 → 运动控制 → 排雷 → 穿桥洞 → 识别标靶 → 激光打击 → 回终点

## 1.2 得分构成

| 项目 | 分值 | 说明 |
|---|---|---|
| 驶离起点 | 5 | |
| 回到终点 | 5 | |
| 无人机起飞 | 5 | |
| 无人机降落 | 10 | |
| 排雷（每颗） | 5 | 共 8 颗 = 40 分 |
| 穿桥洞（每区域） | 10 | 共 2 个区域 = 20 分 |
| **基础合计** | **65** | |
| 敌方受击计数器（每 +1） | +5 | 满 3 次 = +15 分 |
| **满分** | **80** | |
| 友方受击计数器（每 +1） | **−5** | ★ 打友方扣分 |

**关键规则**：
- **每累计 2 次有效命中 → 计数器 +1**；计数器到 3 判定击毁
- 靶标正反**共用同一靶标实体**（红面=友方，蓝面=敌方）
- 因此打满 15 分需要 **6 次有效命中**（3 计数器 × 2 命中）

## 1.3 场地规格

```
网格：14 列 A–N × 11 行 1–11，格边长 35 cm
坐标：col 0=A … 10=K(桥洞列) … 13=N
      row 0=最北 … 5 … 6 … 10=最南
场边：4.0 m × 3.85 m（无四周围挡，但不得驶出）

★ 隔离线：row6 与 row7 之间的**边**（不是格！），覆盖 D..N (col 3..13)
★ 桥洞：K 列整列隔板，两个门
        区段一 K1..K6（row 0..5）每局随机 1 格可通行
        区段二 K7..K11（row 6..10）每局随机 1 格可通行
        ★★ 两个门缺一不可（起点与终点分居线两侧）

智能车起点：M11 (col 12, row 10)，起始航向 -90°（朝北）
智能车终点：N6  (col 13, row 5)
无人机起点：N8  (col 13, row 7) —— 禁入格
无人机终点：N2  (col 13, row 1) —— 禁入格
```

## 1.4 传感器白名单与红线

| 允许 | 禁止 |
|---|---|
| 二维云台、单目 RGB 相机、激光发射、主控、IMU | **激光雷达 / UWB / 深度相机 / 双目** |

**红线条款**：
- R2：禁止自建网络
- R12：禁止穿红蓝衣物（会干扰视觉）
- R16：比赛阶段禁止遥控
- 碰撞：撞固定场地持续超 **10 s** → 裁判切手动（云台仍自动）

> ⚠️ **本工程包含 `rplidar_ros-ros2`，但雷达在本赛题是禁止的**，实际不参与比赛逻辑。

# 三、系统架构与数据流

## 3.1 进程模型

`dzmission_node` 是**单进程双节点**：

```cpp
// mission_main.cpp
auto loc = std::make_shared<LocalizationCompensator>(options);  // 定位
auto mgr = std::make_shared<MissionManager>(options);            // 任务
rclcpp::executors::MultiThreadedExecutor executor(options, 2);
executor.add_node(loc);
executor.add_node(mgr);
```

**为什么用多线程执行器**：`LocalizationCompensator` 要在 100 Hz IMU 上做预测，
不能与 50 Hz 的 `MissionManager` 定时器互相阻塞。

**为什么两个节点必须同时运行**：`LocalizationCompensator` 产生 `/odometry/filtered` 与
`/localization/healthy`，是任务层判断"定位是否可信"的**唯一依据**。缺了它 →
`pose_valid_` 永远 false → 任务层一直处于定位故障急停。

## 3.2 MissionManager 内部模块

```cpp
std::unique_ptr<CmdLink>       cmd_link_;   // 串口/UDP 指令接收（双协议）
std::unique_ptr<MotionArbiter> arbiter_;    // 运动仲裁（多源速度选择 + 限幅）
std::unique_ptr<SafetyMonitor> safety_;     // 安全监控（堵转/姿态/近场/急停）
std::unique_ptr<TargetAimer>   aimer_;      // 云台瞄准 + 激光打击（含红蓝联锁）
std::unique_ptr<RefereeBoard>  referee_;    // 裁判板交互（血量/弹量/受击）
std::unique_ptr<BridgeTracker> bridge_;     // 桥洞门位追踪
std::unique_ptr<FieldGrid>     grid_;       // 场地栅格 + 路径规划
```

## 4.2 模块详述

### 4.2.1 FieldGrid —— 地图与规划

**核心职责**：栅格地图、可通行性、方向感知 A\*、转弯几何可行性、原地转向可行性。

**★ 最关键的设计：隔离线是"边"，不是"格"**

```cpp
// field_grid.cpp::buildFixedEdges()
// 水平隔离线：row(barrier_up_row) 与 row(barrier_up_row+1) 之间的**纵向边**
// ★ 格子本身可通行，只是这条边不可跨越。
blocked_up_[idx(c, barrier_up_row)] = 1;   // 存的是"边"
```

**反面教材**：若把隔离线建模成"整排阻断格"，因 `barrier_col_hi=13`，
会把**终点 N6 自己**变成阻断格 → 终点不可达。（开发中真实踩过）

**可通行性**：

```cpp
bool cellPassable(c, r) { return v == kFree || v == kMine; }   // 只有这两个可走
```

| 占用码 | 值 | 可通行 |
|---|---|---|
| `kUnknown` | 0 | ❌ 未观测 |
| `kFree` | 1 | ✅ |
| `kBlocked` | 2 | ❌ 障碍桶/无人机禁入/隔板 |
| `kMine` | 3 | ✅ 地雷（可通行，需排） |
| `kTarget` | 4 | ❌ 靶标 |

**方向感知 A\***：状态 = `(格, 进入方向)`。为什么必须带方向？
因为"在该格能否拐弯"取决于**从哪来、往哪去**。只用格做状态、事后查转角，
会得到"格级最短但实车走不了"的路径。

**五级回退阶梯**：

```cpp
const Level ladder[5] = {
  {true,  true,  true,  false},  // 1 最严格：转弯感知 + 起始航向 + 禁折返
  {true,  true,  false, false},  // 2 放开 heading
  {true,  true,  false, true},   // 3 允许原地转向
  {false, true,  true,  false},  // 4 放开 turn_aware，保留禁折返
  {false, false, false, false},  // 5 全放开
};
```

**★ `used_level` 是必须看的诊断信号**：

```
1~3  → 路径几何可执行，可直接下发给执行层
4~5  → 路径含不可执行的转角，必须人工核验
0    → 完全无路径
```

**转弯可行性判据**（`checkTurn`）：

```
1) a->b->c 必须四连通相邻
2) 转弯中心 = 入向车道中心线 ∩ 出向车道中心线
3) 沿 90° 圆弧采样 60 点（每 1.5°）
4) 每点取 4 个车体角点 + 4 个轮位，算到最近阻挡的净空
5) feasible = (最小净空 >= turn_min_clearance_cm)
```

**原地转向判据**（`checkPivot`）：绕后轴中心纯转动，
扫掠半径 = 车体对角半径 = `hypot(17.2, 7.0) ≈ 18.6 cm`。

**为什么必须有原地转向**：单圆弧扫掠半径 = `R(26) + 对角(18.6) = 44.6 cm`
（圆直径 89.2 cm），而单格走廊只有 35 cm —— **窄条内单圆弧几何上不可行**，
原地转向是唯一方案（扫掠半径只有 1/2.4）。

**车体几何参数**：

```
车长 27.8 / 车宽 14.0 cm
轴距 15.0 / 轮距 11.0 cm       ⚠️ 学员工程用轴距 17.0
最小转弯半径 R = 26.0 cm
前悬 17.2 / 后悬 10.6 cm（0.62/0.38 × 车长）
```

### 4.2.2 MinePlanner —— 排雷覆盖规划

近似 TSP：给定若干雷点，找一条访问全部雷点的最短闭合路径。

| 配置 | 默认 | 说明 |
|---|---|---|
| `cruise_speed` | 0.5 | 巡航速度 m/s |
| `approach_cells` | 1 | 接近雷点的格数（不压雷） |
| `enforce_turns` | true | 强制转弯可行性检查 |
| `two_opt_rounds` | 64 | 2-opt 局部搜索轮数 |

输出 `PlanStats` 里 **`infeasible_turns` 与 `illegal_steps` 必须为 0**。

辅助：`verifyWheelInCircle()` —— 轮心进圆校验（排雷时车不能压雷）。

### 4.2.3 LocalizationCompensator —— 定位补偿

**核心问题**：底盘积分位姿**不可用**（编码器偏航系与物理世界不一致，
实测同一次 90° 右转两次运行轨迹偏向相反两侧）。

**解决方案**：

```
位置 = 相邻采样行驶距离（旋转不变量）沿 IMU 地图偏航积分
```

不用 `msg->pose`，只取**采样间距离**（旋转不变量且实测准确），
沿 IMU 偏航积分得到世界坐标。

**锚点标定**：`/nav/anchor` 格式 `"anchor:COL,ROW,HEADING_DEG"`
→ 把航位推算位置吸附到格心，并把 IMU 偏航重新标定为地图偏航。

**启动锚定**：构造时 `anchor_at_startup` 把位置设为初始格心、偏航设为 `start_heading_deg`。

**健康判据**（`evaluateHealth`）：

```cpp
imu_ok   = IMU 未超时
odom_ok  = 里程未超时
state_ok = 位置/偏航有限 && have_imu_yaw_ && yaw_offset_valid_
return imu_ok && odom_ok && state_ok
```

**★ 位移门槛陷阱**：`pose_valid_` 只在**检测到有效位移**时才置 true：

```cpp
if (step >= dr_min_step_m(0.5mm) && step <= dr_max_step_m(0.5m) && yaw_offset_valid_)
    pose_valid_ = true;
```

→ **车完全静止时 step=0 → pose_valid_ 永远 false → 一直 ESTOP**。
离线测试时假传感器必须制造微小位移（本项目用 `--idle-v 0.05`，每 tick 1.0 mm）。

### 4.2.4 SafetyMonitor —— 安全监控（无雷达版）

**没有雷达**，靠四路冗余信号：

| 判据 | 来源 | 动作 |
|---|---|---|
| **堵转** | `cmd>=0.05` 且 `actual<0.02` 持续 1200 ms | 急停 + 脱困建议 |
| **姿态** | IMU 横滚/俯仰超限 | 急停 |
| **视觉近场** | `offset_center` 检测框占画面比例 | 降速/急停 |
| **地图新鲜度** | 视觉数据超时 | 按急停处理（**失明即停**） |

**堵转判据用的是 `arbiter_speed`（仲裁后速度），不是 `/cmd_vel`** ——
因为任务层想给的速度可能已被裁减，拿裁减后的值做对比才准确。

### 4.2.5 TargetAimer —— 云台瞄准 + 激光打击

**状态机**：`IDLE → SCANNING → TRACKING → ALIGNED → FIRING → COOLDOWN`

**★★ 红蓝面联锁（本赛题最关键的安全约束）★★**

规则：靶标双面，**红=友方（打了扣分）、蓝=敌方**，朝向随机。
车端相机只能看到朝向自己的那一面。

```
可见面 == 蓝(2)   -> 允许开火
可见面 == 红(1)   -> ★ 绝对禁止（那是友方，扣 5 分/次）
可见面 == 不确定  -> 由 face_unknown_policy 决定，默认 0 = 禁火
```

**为什么默认禁火**：误打友方扣 5 分，比漏打（少得分）更贵。

**其他联锁**：

| 联锁 | 说明 |
|---|---|
| 靶标击毁 | HP ≥ 3 停火（正反共用同一实体，任一侧到 3 即整体失效） |
| 弹量纪律 | 裁判板 + 本地记账；链路断时按 `ammo_link_lost_policy` (0保守/1乐观/2折中) |
| 激光红点 | 首发后要求红点确实落在靶上（比"靶在画面中心"更可靠） |
| 射程 | `max_engage_range_m` |
| 被击停火 | `being_hit` |
| 开火冷却 | `fire_cooldown_ms` 默认 **3000 ms** |

**移动靶预判（β 方案）**：
`T_total = 380 ms`（33 采集 + 267 流水线 + 60 控制 + 20 执行）。
未补偿位移 11.7 cm > 靶标直径 8–10 cm → **必须补偿**。
补偿后残余 3.0 cm < 靶半径 → 可命中。

**关键数值**：
- 视觉流水线 4 帧 @15fps = 267 ms
- 云台限速 70.3 °/s（standoff=1 时 72.0 °/s）
- 全局限 10 发

### 4.2.6 RefereeBoard —— 裁判板

- 串口 `/dev/dzjudgment`（115200，`direct_serial: false` 时由 dzactuator 转发）
- 输入 `HpAndHitmsg`：靶标血量 / 受击 / 弹量 / 击毁标志
- 链路超时 1000 ms，命中保持 1500 ms

### 4.2.7 MotionArbiter —— 运动仲裁

多源速度（任务规划 / dztrack / nav2 / 遥控）→ 仲裁 → 限幅 → 发布。

```
max_v=0.60 m/s, max_steer=30.0° (hw 35°), max_w=1.20 rad/s, ttl=0.40s
输出：cmd_vel + pursuitAngle + arbiter_speed
```

### 4.2.8 BridgeTracker —— 桥洞门位

- 门位来自无人机的 `BRIDGE_GATE` 消息
- **row 是权威**（`bridge_id` 可能错）
- 进入 + 退出必须配对
- 门位行变化会重置两个 passed 标志
- **信息不完整 → 拒绝规划 + 每 2 s 发 `EVENT(NEED_GATE)`**

### 4.2.9 PivotController —— 原地转向执行

执行 `checkPivot` 判定可行的原地转向（窄条内唯一的转向方案）。

### 4.2.10 ⚠️ AirLink —— **未被实例化的死代码**

`air_link.cpp`（21 KB）实现了 `AirLink` 类，负责把空中的原始帧解析后
`publishMulti(topic, payload)` 分发到 `field`/`gate`/`mine`/`obs`/`tgt`/`map` 等话题。

**但 `MissionManager` 从未实例化它** —— 其功能已被 `CmdLink::dispatchAirFrame()`
（v2 协议支持）取代。保留文件仅为历史参考，**可直接删除**。

# 七、通信协议（两套）

## 7.1 空地协同协议 v2（无人机 ↔ 车）

```
帧头：A5 C3
字段：VER(1) TYP(1) SEQ(4) LEN(2) PAYLOAD CRC(2)
头部：10 字节
CRC ：CRC-16/CCITT (poly 0x1021)
最大：1036 字节
```

**消息类型**：

| 码 | 名称 | 方向 | 必需 |
|---|---|---|---|
| `0x01` | HEARTBEAT | 双向 | |
| `0x10` | TEAM_INFO | 无人机→车 | |
| `0x11` | **FIELD_FIXED** | 无人机→车 | 可选（车端已固化） |
| `0x12` | MAP_FULL | 无人机→车 | ★ |
| `0x13` | MAP_DELTA | 无人机→车 | |
| `0x14` | **MINE_LIST** | 无人机→车 | ★ 排雷必需 |
| `0x15` | **BRIDGE_GATE** | 无人机→车 | ★★ 最关键 |
| `0x16` | TARGET_LIST | 无人机→车 | 建议 |
| `0x17` | **OBSTACLE_LIST** | 无人机→车 | ★ |
| `0x20` | TASK_CMD | 无人机→车 | |
| `0x30` | VEH_STATUS | 车→无人机 | |
| `0x31` | EVENT | 车→无人机 | |

**★ FIELD_FIXED v2.1（12 字节，v2.0 是 8 字节，追加式向后兼容）**：

| 偏移 | 字段 |
|---|---|
| 0 | `barrier_up_row`（=5） |
| 1–2 | `barrier_col_lo/hi`（=3 / **13**，D..N） |
| 3 | `bridge_col`（=10，K） |
| 4–5 | `bridge_a_lo/hi`（=0 / 5） |
| 6–7 | `bridge_b_lo/hi`（=6 / 10） |
| **8–9** | **`drone_start_col/row`**（无人机起点） |
| **10–11** | **`drone_end_col/row`**（无人机终点） |

**★ MAP_FULL 单格编码（11 位）**：

```
occ  = v & 0x07          # 0未知 1自由 2阻挡 3地雷 4靶标 5洞未知 6洞开
conf = (v >> 3) & 0x0F   # 置信度 0..15
age  = (v >> 7) & 0x0F   # 陈旧度 0..15
```

常用值：`121=自由` `122=阻挡` `124=靶标` `125=洞未知` `126=洞开`

**★ 车端只应用 `occ==2 && conf>=50`（确认阻挡）的格**，其余忽略。

## 7.2 串口任务指令 v1（兼容旧链路）

```
帧头：AA 55
字段：LEN/CMD + PAYLOAD + CRC
CRC ：CRC-16/MODBUS (poly 0xA001)
头部：2 字节
最大：96 字节
```

**两套协议共存**：`CmdLink::feedBytes()` 同时识别 `A5 C3`（v2）与 `AA 55`（v1），
分别派发到 `dispatchAirFrame()` 与 `dispatchFrame()`。

## 7.3 操作码命名空间（★ 易错点）

`MissionCommand` 的 `kCmd*` 操作码有**两个来源**：

| 来源 | 常量 | 值 |
|---|---|---|
| 外部串口指令 | `kCmdNavTo` `kCmdOpStop` `kCmdOpEngage` `kCmdCeaseFire` … | 0x01/0x02/0x10/0x11 |
| **镜像 air 类型码** | `kCmdMapFull` `kCmdMineList` `kCmdBridgeGate` `kCmdTargetList` `kCmdObstacleList` | 0x12/0x14/0x15/0x16/0x17 |
| 自定 | `kCmdFieldFixed` | **0x18** |

**★ 血泪教训**：`kCmdFieldFixed` 最初误用 `0x11`（那是 air 的 `kFieldFixed`），
与 `kCmdCeaseFire = 0x11` 撞车 → C++ `switch` 报 `duplicate case value` 编译失败。
现用 `0x18`。**`test/opcode_check.py` 专门查这类冲突**。

# 十、★ 已知缺陷与踩坑记录（必读）

> 这一节是**最有价值的部分** —— 全部是实际调试中撞过的墙，避免重复踩。

## 10.1 时间源混用（运行时崩溃）

**现象**：`terminate called after throwing 'std::runtime_error' what(): can't subtract times with different time sources [1 != 2]`

**根因**：`rclcpp::Time` 默认构造是 `RCL_SYSTEM_TIME(1)`，而 `node->now()` 是
`RCL_ROS_TIME(2)`；两者相减抛异常。`MissionManager` 构造时 12 个 `Time` 成员未初始化，
`tick()` 里在 `pose_valid_` 守卫**之前**就做了减法。

**解法**：构造函数里用 `this->now()` 统一初始化全部 12 个 `Time` 成员。

**防回归**：`test/time_source_check.py` 扫描所有组件，报"36 个 Time 成员，高风险 0"。

## 10.2 日志文案误导（排查效率杀手）

**原写法**：

```cpp
setState(State::kEstop, safety_stop ? "safety e-stop (obstacle)"
                                    : "localization unhealthy");
```

`!pose_fresh` 时也打印 "localization unhealthy"，但它真实含义可能是：
- `pose_valid_` 为 false（没收到 `/odometry/filtered`）
- `pose_age >= 0.5`（收到了但太旧）
- `loc_healthy_` 为 false（定位节点自评不健康）

**已改为可区分**：

```
"localization: never received /odometry/filtered"
"localization: /odometry/filtered stale (X.XXXs)"
"localization: loc_healthy=false (sensor unhealthy)"
```

**教训**：急停原因日志必须能区分根因，否则会浪费大量排查时间。

## 10.3 空间尺度矛盾（规划的根本约束）

```
最小转弯半径 R        = 26.0 cm
车体对角半径          = hypot(17.2, 7.0) = 18.6 cm
单圆弧扫掠半径        = R + 对角 = 44.6 cm  → 圆直径 89.2 cm
原地转向扫掠半径      = 对角   = 18.6 cm  → 圆直径 37.2 cm
格边长 / 单格走廊宽   = 35 cm
```

| 冲突 | 需要 | 场地给 | 结论 |
|---|---|---|---|
| 单圆弧 90° 转弯 | 89.2 cm | 35 cm | 除空旷区外基本不可行 |
| 原地转向 | 37.2 cm | 35 cm | **只差 2.2 cm** |

**实测**：在某张真实比赛图上，9 个转角里 **5 个物理不可行**，
`findPathStaged` 只能用第 4 级出路径；最接近通过的转角净空 **+0.02 cm**（要求 ≥0.5）。

**待核实**：**隔离线确切行号**。代码 `barrier_up_row=5`（row5↔row6），
但现场图逐格核对显示 K7 的正上方是 K6、正下方是 K8，
即被挡边更像在 **row6↔row7**。而 `openCrossing()` 只认 `row == barrier_up_row` 或 `+1`。
→ **若被挡边在 K7↔K8，则穿门不需要 90° 转弯，整张图可达性完全改变。**

## 10.4 浮点 epsilon 缺失

几何**恰好相切**时（净空 = 容差），浮点累计误差让 `min_gap` 变成 `-1e-15`，
把**本来可行**的转角判死。实测直穿桥洞门 `L7->K7->J7` 净空恰好 0.00 被判不可行。

**Python 侧已修**（`plan_route.py` 加 `1e-9`）；**C++ 侧建议同步**：

```cpp
const bool feasible = info.min_gap_cm >= spec_.turn_min_clearance_cm - 1e-9;
```

## 10.5 仓库内部不一致

| 项 | 各处写法 | 现场证据 | 应统一为 |
|---|---|---|---|
| **隔离线列范围** | `corridor_check.py`: **D..M**<br>`field_grid.hpp`: **D..N**<br>`obstacleGapCm` 注释: **D..M** | 绿线明确画到 **N** | **D..N** |

> 列范围不一致**会直接影响可达性结论** —— 它决定"能否绕开桥洞从旁边越过隔离线"。

## 10.6 QoS 匹配（静默丢包）

**所有车端订阅都用 `best_effort`**。若发布端用 `reliable` → 兼容；
但若**发布端用 `best_effort` 而订阅端要 `reliable`** → **静默丢弃全部消息**。

**实测**：`/odometry/filtered` 曾因 QoS 不匹配而完全收不到，表现为定位永远不健康。
**离线测试脚本的假传感器必须也用 `best_effort`**。

## 10.7 CRLF 与编码坑（Windows ↔ Linux）

| 坑 | 现象 | 解法 |
|---|---|---|
| YAML 是 CRLF | `tr -d '"'` 后变量是 `udp\r`，与 `udp` 比较失败 | `tr -d '"\r'`，或把 YAML 规范为 LF |
| `grep -E '^\s*transport:'` | GNU grep 的 `\s` 不表示空白，一行都匹配不到 | 改用 `[[:space:]]` |
| PowerShell 写文件 | 中文注释变乱码（U+20AC） | **不要**用 `Get-Content -Raw \| Set-Content`；用 Python 或 write 工具 |
| 注释行干扰 | `# transport: serial \| udp \| loopback` 被 `grep` 先命中 | 先 `grep -v '^[[:space:]]*#'` |

## 10.8 其他

| 坑 | 说明 |
|---|---|
| **`ros-humble-serial` 不存在** | 必须用本工程自研 `serial/` 包 |
| **`ROS_DISTRO` 未 source** | `ros2: command not found`；`.bashrc` 要 source `/opt/ros/humble` 和 `~/ws/install` |

# 十三、术语表

| 术语 | 含义 |
|---|---|
| **隔离线** | 场地中间的水平挡板（黄线），把场地分南北；**建模为"边"不是"格"** |
| **桥洞 / 门位** | K 列的两个可通行开口；**必须两个都开**才能从起点到终点 |
| **格内转弯** | 转弯中心落在格角上，几何余量天然只有 0.1–3.5 cm |
| **原地转向（pivot）** | 绕后轴中心纯转动，扫掠半径 = 车体对角半径 |
| **方向感知** | A\* 状态含"进入方向"，才能把"该格能否拐弯"纳入搜索 |
| **used_level** | 规划成功所用回退级别；1–3=几何可执行，4–5=需人工核验 |
| **anchor** | 定位锚点，把航位推算位置吸附到格心并重标定偏航 |
| **失明即停** | 视觉近场数据超时 → 按急停处理 |
| **β 方案** | 移动靶预判：按 T_total=380ms 提前量补偿 |
| **红蓝联锁** | 红面=友方禁火，蓝面=敌方允许，未知默认禁火 |
| **双协议** | 空地 v2（A5 C3 + CCITT）与串口 v1（AA 55 + MODBUS）共存 |
