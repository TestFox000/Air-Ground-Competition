## 1. 规则重读：必须更正的事实

### 1.1 ★★★ 计分机制与我原先的理解不同

| 项 | 我原先的假设 | **规则实际**（image2） |
|---|---|---|
| 计数器增长 | 每 1 次有效命中 +1 | **每 2 次有效命中 +1** |
| 击毁所需 | 3 次命中 | **3 次计数 = 6 次有效命中** |
| 分数 | 每命中 +5 | **每计数 +1 得 5 分**（即每 2 次有效命中 +5） |
| 倾覆 | 命中即倾倒 1s | 同，**且倾倒后继续移动** |

**这意味着**：
- 全灭敌方需 **6 次有效命中**，而弹量只有 **10 发** → 容错只有 4 发
- 每 2 次有效命中才得 5 分 → **不能乱打，打空就是纯浪费**
- 「有效命中」的判据是**命中感应区**（image1 红圈标注的圆形区域），
  不是"打中靶体即可"

### 1.2 ★★★ 计数器**正反独立**，且是共享实体

image2 原文：

> 只有激光命中有效命中感应区才计为一次有效命中；**正反两侧各设独立计数器**
> 任一侧面计数器到 3，靶标向受击面反方向倾倒、**灯灭、保持倾倒不再恢复**
> **共用实体：正反两面共用同一靶标，任一侧到 3 即整体失效，后续命中均不计分、不扣分**

**推论（对我方极其不利的一条）**：
- 我方**误打友方（红面）** 会让**友方计数器**增长
- 友方计数器一旦到 3（**6 次误击**），整个靶标失效
- 而**敌方计数器还没满** → **我们再也不能得分**，且已扣了 30 分

**结论**：红面必须**严格禁止开火**，没有任何"少打一点"的余地。
我上一轮实现的红蓝联锁方向正确，但**参数需要改**（见 §1.3）。

## 2. 由规则推出的三条核心策略

### 2.1 ★ 车应该停在「轨道中点的法向正对面」，而不是去追靶

靶标沿轨道**匀速往返**（Q10），轨道是**固定的**两格。因此：

```
轨道中点 M（固定）
蓝面法向 n（垂直于轨道轴线，固定方向）
射击位 = M 沿 n 方向偏移 standoff 格
```

**停在 M 的对面时**：
- 靶标全程在视野内**横向扫动**，只需**云台跟瞄**，车体不用动
- 横向摆幅 = 轨道长度的一半（约 1 格 = 35cm）
- 若 standoff = 2 格（70cm），云台只需扫 **±26.6°** → 完全在云台能力内

**如果我方去追靶**，反而会因为车体频繁移动导致：
- 里程计漂移累积（位置=IMU 偏航积分，移动越多误差越大）
- 瞄准窗口被打断

**结论：车一次到位，云台负责跟瞄。**

### 2.2 ★ 必须做「提前量射击」

靶标**匀速**（Q10），这是最有利的条件：

```
可观测：靶标在画面中的位置 px(t) 随时间变化
可推导：靶标速度（像素/秒）→ 角速度
可预判：靶标何时经过瞄准点
```

**射击时机**：在靶标**经过预测瞄准点的那一刻**开火，而不是"等它到中心再开火"。

理由：
- 视觉流水线有 **4 帧延迟 ≈ 267ms**（15fps）
- 靶标若以 0.2 m/s 移动，267ms 内移动 **5.3cm**
- 靶标直径仅 **8–10cm**，感应区更小 → **不补偿必然打偏**

**实现**：在现有 PD 视觉伺服前加一级**运动预测**（线性外推 + 穿越时刻预测）。

### 2.3 ★ 「红点反馈」在移动靶上的用法要变

上一轮我把激光红点做成"确认落点在靶上才继续打"。但靶标在动：

- 红点会**落后于靶标**（激光飞行 ~ns 级可忽略，滞后来自视觉流水线）
- 所以红点位置**不能直接当命中判据**，要**结合靶标运动做补偿后再判**

**新用法**：
1. 红点**在感应区内**（补偿后）→ 确认有效命中 → 计数器应 +1（可交叉验证裁判板）
2. 连续 N 发**看不到红点** → 说明瞄准系统性偏差 → 触发微调/重定位
3. 红点是**唯一能自查命中**的手段（裁判板只给累计值，不告诉你是哪一发中的）

## 3. blue_dir（蓝面朝向）问题：赛前不可能标定

### 3.1 为什么赛前标定不可行

结合 §1.4：
- **打击区是比赛阶段工作人员才布置的** → 赛前场地是空的
- 准备阶段 2 分钟**不允许换硬件**，也没法把靶子摆出来测
- 因此 **blue_dir 无法在赛前通过"摆靶子测"得到**

### 3.2 方案：三级获取，优先级从高到低

| 级别 | 来源 | 是否需要人工 | 说明 |
|---|---|---|---|
| **L1** | **无人机下发轨道轴线方向** | 否 | 已有协议字段；轨道 2 格 → 轴线确定 |
| **L2** | **车端运行时自测**（推荐主用） | 否 | 车到轨道附近后，云台左右扫，判可见面 |
| **L3** | 参数写死 `aim.blue_dir` | 是（赛前） | 兜底/调试用，比赛不用 |

### 3.3 L2 的具体做法（**这是核心创新点，且能自动完成**）

关键洞察：**车不需要先知道 blue_dir 才能动**。

```
步骤 1  车开到"轨道中点、垂直于轨道轴线"的两个候选位之一
        （候选位 = 沿轨道法向的两个方向各一个）
步骤 2  云台对准轨道中点，判可见面
步骤 3  分支：
          ├─ 看到蓝面 → 就是这里，直接进入跟瞄射击
          ├─ 看到红面 → 蓝面在对面 → 横移到轨道另一侧的候选位
          └─ 看不到   → 云台左右扫 ±60°（靶标在动，扫一遍约 2s）
```

**为什么能成立**：候选位只有**两个**（轨道法向的 + 与 −），
所以最坏情况是"试一次错，再换一边"，代价约 **3~5 秒**。

**不需要参数、不需要人工、不需要赛前标定** —— 正好满足你"减少参数、自动化"的要求。

### 3.4 仍然保留的参数（仅为调试便利）

| 参数 | 默认 | 作用 |
|---|---|---|
| `aim.blue_dir` | `"auto"` | `auto` = 用 L2 自测；也可写 `+x/-x/+y/-y` 强制 |
| `aim.blue_dir_hint` | `0` | 0=无提示；1=蓝在轨道轴线左侧；2=右侧（无人机若知道可下发） |
| `aim.engage_standoff_cells` | `2` | 射击位距轨道中点的格数（**FOV 未知，现场调**） |
| `aim.target_period_s` | `3.0` | 靶标往返周期（**用于提前量；可从单片机程序取真值**） |

★ **`target_period_s` 建议你去查单片机的靶标驱动程序** —— 你提到"或许可以知道速度"。
  若知道确切周期/速度，提前量射击的命中率会显著提升（这是 10 发里省弹量的关键）。

## 4.5 ★ 移动靶固件分析（`移动靶hex文件.zip`）

### 4.5.1 结论：9 个文件只差**一个参数**

| 项 | 数值 |
|---|---|
| 文件数 | 9（`stm32移动靶140.hex` ~ `180.hex`） |
| 每个文件大小 | **完全相同** 15,388 字节 / 344 条 Intel HEX 记录 |
| Intel HEX 校验和 | **全部正确**（0 个错误） |
| Flash 有效范围 | `0x08000000 .. 0x0800154B`（**仅 5,452 字节**） |
| 程序入口 | `0x08000131` |
| **唯一差异** | `0x08001518` 处的 **32 位字**：`140,145,150,155,160,165,170,175,180` |

**文件名的数字 = 该地址的值**，一一对应（步进 5）。
`0x08001518` 位于 `.data` 段，是启动时从 flash 复制到 RAM 的**初值**。

### 4.5.2 固件特征

- **只有 5.4KB 代码** —— 裸机程序，无 RTOS、无文件系统、无字符串表
- 除该参数外，另外 2~3 个字节的差异经查是 `.data` 的**拷贝长度/边界**字段
  （随参数值变化的副产物，不是独立参数）
- 相邻的 `0x080014E8 = 1636` 可能是另一个参数（用途未知）

### 4.5.3 ⚠ 单位无法从固件确定（需要硬件验证）

这个数值可能是**单程耗时(ms)**、**往返周期**、**步进延时**或**速度档位**。
纯静态逆向无法判定，我不做猜测。

**需要你做的验证（2 分钟，用手机秒表即可）**：

```
1. 烧录 stm32移动靶160.hex
2. 上电，用手机录一段视频（含秒表）或直接计时
3. 测"靶标从轨道一端到另一端"的耗时 t_单程
4. 对照下表判断单位：
```

| 若 t_单程 ≈ | 则该参数单位是 | 速度（取轨道 = 2 格 = 70cm） |
|---|---|---|
| **0.16 s** | 秒 | **4.4 m/s**（太快，不现实） |
| **1.6 s** | 0.1 秒 | **0.44 m/s** |
| **16 s** | 10 毫秒 | **0.044 m/s**（太慢） |
| **0.16 ms** | 毫秒 | 不现实 |

**我预判是「0.1 秒」也就是 1.6 s 单程 → 约 0.44 m/s**，
因为这对 8~10cm 的靶标是"看得清、跟得上、但必须提前量"的合理速度。
**但必须实测确认。**

### 4.5.4 拿到速度后的价值

一旦确认，`aim.target_period_s` 就是**确定值**而不是估计值，方案 β 的提前量补偿
从"估"变成"算"，这是 10 发弹量里**省弹量的关键**。

同时可算出：靶标在视觉流水线延迟（267ms）内的位移
```
位移 = v × 0.267s
```
若 v = 0.44 m/s → 位移 = **11.7 cm** —— 已经**超过靶标直径（8~10cm）**
→ **再次证明：不做提前量补偿必然打偏**（这条结论被固件参数佐证）

### 4.6.2 ★ 开发过程中被数据否定的两个设计（重要）

#### 否定 1：一阶低通滤波（alpha=0.35）**不可用**

初版用低通平滑速度，量化后发现：
```
真实速度在 t=800ms 过零，但滤波估计值仍有 66.8 px/s
→ 真换向一次都没被识别（可开火帧数 0/60）
→ 残余位移 7.1cm > 靶标半径 4.5cm
```
**改用中值滤波**（3 帧窗口）：对孤立噪声免疫，对单调趋势几乎无滞后。
残余位移 7.1 → 5.9cm。

#### 否定 2：开火窗口 250ms **太大**

窗口开得久 → 靶标已重新加速 → 残余误差回升：
```
窗口 250ms -> 残余 5.9cm > 半径 4.5cm   ✗
窗口 100ms -> 残余 3.0cm < 半径 4.5cm   ✓
```
收到 100ms 后，残余从"不补偿"的 11.7cm 降到 **3.0cm（降低 74%）**。

### 4.6.3 ★★ standoff：两个方向的约束，**最终取 1**

**约束来自两侧：**

| 方向 | 约束 | 硬度 |
|---|---|---|
| **不能太近** | 靶标横向扫动角速度 `omega = v/d` ≤ 云台上限 **70.3 °/s** | 软（α 可缓解） |
| **不能太远** | **轨道可能贴边界，车与轨道之间只有一格空间** | **硬（物理限制）** |
| 不能太远 | 太远则靶标画面里太小（4 格时检测框仅约 36px 宽） | 软 |

**数据**（靶速 0.44 m/s、靶标直径 9cm、FOV 65°）：

| standoff | 距离 | 运动段角速度 | 云台 | 画面检测框 | 评价 |
|---|---|---|---|---|---|
| **1 格** | 35cm | 72.0 °/s | ★ 略超（仅高 **2%**） | 144 px 宽 | **采用** |
| 2 格 | 70cm | 36.0 °/s | ✓ 余量 2.0x | 72 px 宽 | 空间不够时无合法位置 |
| 3 格 | 105cm | 24.0 °/s | ✓ 余量 2.9x | 48 px 宽 | 备选 |
| 4 格 | 140cm | 18.0 °/s | ✓ 余量 3.9x | 36 px 宽 | ★ 检测框过小 |

**为什么取 1，而不是更"安全"的 2：**

1. **近距约束是硬的** —— 场地空间是物理限制，无法协商
2. **远距约束是软的** —— FOV / 检测框大小可现场调
3. ★ **方案 α 天然缓解了近距约束**：α 只在"换向点"开火，
   换向瞬间靶速趋 0 → 角速度趋 0 → 云台不需要追。
   所以即使运动段跟上吃力，**开火窗口内仍能打中**
4. 1 格时靶速上限 = 35cm × tan(70.3°) = **0.98 m/s**，
   远高于 0.44 m/s —— 真正卡住的不是云台速度，而是几何空间

**⇒ `engage_standoff_cells` 默认 = 1**

> ⚠ 注意：1 格时运动段角速度 72.0 °/s 略超上限 70.3 °/s（高 2%），
> **运动段可能跟丢**（这是预期行为 —— α 本就只在换向点开火）。
> 但云台**必须在靶标到达换向点前把方向指对**，哪怕跟得慢；
> 靶标停下时误差会收敛。**这一点只能实车验证。**

现场调整：检测框 < 40px 宽 → 加大到 2；连换向点都跟不到 → 加大 standoff。

### 4.6.4 部署后的实测结果

```
残余位移 3.0cm < 靶标半径 4.5cm   ✓
相比不补偿（11.7cm）降低 74%
静止靶场景 80/90 帧判定可开火（→ 静止靶不受影响）
真换向场景识别成功（0/60 -> 4/90）
```

### 4.6.5 ⚠ α 的残余风险（只能实车验证）

1. **`turn_around_v_thresh_px_s` 需现场标定** —— 默认 25 是按 FOV 65° 估的
2. **换向点的可用时间窗可能只有 2 帧**（133ms）—— 云台必须已预先指向，
   否则来不及。这依赖 PD 跟瞄的稳态精度
3. **α 不含提前量** —— 射速受 `fire_cooldown_ms`(3.0s) 主导，
   6 次有效命中约需 **18s** 净射击时间
4. **`engage_standoff_cells` 未实测** —— FOV 未知，2 格是运动学下限推导值

## 5. 方案选择（请你选）

### 方案 α：最小可用（保守打击）

| 内容 | 说明 |
|---|---|
| 车停在轨道中点对面（standoff 参数化） | 一次到位，不追靶 |
| 若可见面为红 → **横移到另一侧**，最多试 2 次 | §3.3 的 L2 |
| 云台用现有 PD 跟瞄 | 不加预测 |
| **只在靶标"经过画面中心"且速度为零（换向点）时开火** | 换向瞬间速度≈0，无滞后误差 |
| 不中则等下一个换向点 | 规避 267ms 延迟问题 |

**优点**：改动最小（约 1 个模块），逻辑简单可靠，不怕打偏
**缺点**：换向点每周期只有 2 个，若周期 3s，则每 1.5s 才有一次机会
→ 6 次有效命中约需 **9~15s 净射击时间**，加瞄准约 **25~40s**

### 方案 β：**推荐** —— 匀速预判打击

| 内容 | 在 α 基础上增加 |
|---|---|
| **运动预测**：由视觉帧序列估计靶标角速度 | 新增 `target_motion_estimator` |
| **穿越时刻预测**：算靶标何时经过瞄准点 | |
| **提前量补偿**：云台按预测位置提前偏置 | |
| **红点补偿判据**：红点位置按预测位移补偿后再判 | |
| 换向点策略保留为兜底 | |

**优点**：全程可打，射速高（每 `fire_cooldown` 3s 一发，瞄准窗口充足）
**缺点**：多一个估计器模块，需现场调 2 个参数（周期、增益）

**估时**：6 次有效命中约 **20~30s**（含瞄准）

### 方案 γ：全功能 —— β + 感应区精瞄 + 自适应

| 内容 | 在 β 基础上增加 |
|---|---|
| **感应区精瞄**：把"画面中心容差"升级为"感应区圆判据" | 需知道感应区在靶面上的相对位置/大小 |
| **自适应**：连续脱靶 → 自动微调 standoff 与提前量增益 | |
| **裁判板交叉验证**：`shoot_count` 变化 vs 红点判据，不一致则告警 | |

**优点**：命中率最高
**缺点**：感应区几何（直径、在靶面上的位置）**规则里没给**，需现场测量/试打标定

## 6. 我的推荐与理由

**推荐：先做 α，再做 β；γ 暂缓。**

理由：

1. **α 能立刻把"打不中移动靶"变成"能打中"** —— 这是当前最大的风险缺口
2. **α 不依赖任何未知参数**（换向点策略不需要知道周期）
3. **β 的收益取决于 `target_period_s` 的准确性** —— 你说"或许可以从单片机程序知道"，
   若拿不到真值，β 的提前量会不准，收益打折
4. **γ 依赖感应区几何**，而规则里没有 → 现在做等于猜
5. 赛时预算：基础分 65 分里，敌我识别只占 15 分；40 分的排雷 + 20 分桥洞**更值钱**
   → 打击模块**不应占用过多开发时间**，α 的性价比最高

**如果时间充裕**，我建议顺序：`α → 验证能在实车打中 → β → 拿到周期真值后调优`。
