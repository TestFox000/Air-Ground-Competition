## 6. 防冲突规则

1. **一个任务同时只能有一个人领**。看到 🟡 就别重复动手，去领 🔵 的。
2. **`src/ag_core/` 两边都可能动**：改前先 `git pull`，改完立刻 push。
3. **`config/params.yaml` 是高频冲突点**，按参数归属分治：
   - 现场量出来的（终点格号、朝向、单应 H、激光偏置）→ **A 机填**
   - 模型解码参数（`cls_activation` / `kpt_unit` / `input_layout`）→ **B 机标定后告诉 A 机填**
   - 谁改了都在群里/看板说一声，别闷头改
4. **测试基线 508 项**：push 前必须本地全绿。把红的推上去，对面一 pull 就跟着红，还以为是自己改坏的。
5. **`.sh` 脚本一律 LF**（`.gitattributes` 已锁死）。Windows 上千万别开 `core.autocrlf=true` 覆盖它，
   否则 shebang 变成 `#!/bin/bash\r`，车端直接 `bad interpreter`。

## 9. 实时同步（两台机器各配一次）

### 9.1 一条命令搞定一轮同步

```bash
python tools/sync_progress.py          # 拉对方进展 → 提交自己的改动 → 推给对方
python tools/sync_progress.py --status # 只看两边差多少，不碰任何东西
python tools/sync_progress.py --pull-only   # 只看对方进展，不动自己的改动
python tools/sync_progress.py --no-commit   # 拉取后不自动提交（改到一半时用）
```

冲突时它会**停下来把冲突文件列清楚**，并告诉你怎么处理，绝不自动猜、绝不覆盖对方的工作。

### 9.2 让它自动跑（这就是「实时」的实现方式）

**① 提交即推送**（最干脆的一层）

```bash
python tools/sync_progress.py --install-hook
```
装完以后每次 `git commit` 都会自动 push 给对方。不想要了就直接删 `.git/hooks/post-commit`。

**② 定时轮询**（兜住「对方提交了我这边还不知道」）

```powershell
schtasks /create /tn air_ground_sync /sc minute /mo 3 /f /tr '"C:\Users\a\AppData\Local\Programs\Python\Python310\pythonw.exe" "E:\CodeBuddy\20260927120106\air_ground\tools\sync_progress.py" --machine A --log "C:\Users\a\air_ground_sync.log"'
```

两个细节**别漏**，漏了就会踩坑：

- 用 **`pythonw.exe`**，不要用 `python.exe` —— 后者每次都会弹一个黑窗（每 3 分钟闪一次）
- 带上 **`--log`** —— `pythonw` 没有任何输出，不留日志的话出了问题无从查起

`--machine` 填 `A` / `B` 区分机器，提交信息里就能看出是谁推的。

**③ 定时任务该用哪种模式？（A 机 2026-09-28 定下的规矩）**

上面那条命令是**全自动**（拉 → 自动提交 → 推）。但它每 3 分钟跑一次，
会把**你还没写完的代码**自动提交并推出去 —— 这跟 §6 第 4 条「push 前必须本地全绿」直接冲突。
所以定时轮询统一加 **`--pull-only`**：

```powershell
schtasks /create /tn air_ground_sync /sc minute /mo 3 /f /tr '"<pythonw路径>" "<项目路径>\tools\sync_progress.py" --pull-only --machine A --log "<日志路径>"'
```

于是两个方向各由一条路负责，互不干扰：

| 方向 | 谁负责 | 效果 |
|---|---|---|
| 我 → 对方 | `--install-hook`（提交即推送） | 一提交就推出去；只在你自己认可的时点推 |
| 对方 → 我 | 定时任务 `--pull-only` | 最多 3 分钟对方的进展就自动进来；**工作区有未提交改动时它会拒绝合并**（绝不乱动你的东西） |

想要全自动（自动提交 + 推送）就把 `--pull-only` 去掉 —— 但请确认你随时处于"可提交"状态。

**日常管理定时任务：**

```powershell
schtasks /query  /tn air_ground_sync /fo LIST     # 看状态、下次运行时间
schtasks /run    /tn air_ground_sync              # 立刻跑一次
schtasks /change /tn air_ground_sync /disable     # 临时停用（保留配置，随时开回来）
schtasks /change /tn air_ground_sync /enable      # 再开回来
schtasks /delete /tn air_ground_sync /f           # 彻底删掉
```

**改间隔**（schtasks 不支持原地改，删了重建，把 `/mo 3` 换成想要的分钟数）：

```powershell
schtasks /delete /tn air_ground_sync /f
schtasks /create /tn air_ground_sync /sc minute /mo 5 /f /tr '"<pythonw路径>" "<项目路径>\tools\sync_progress.py" --machine A --log "<日志路径>"'
```

**日志在这儿看**（每一轮都记了「拉取 / 提交 / 推送」三步的结果，失败会写清原因）：

```
C:\Users\a\air_ground_sync.log
```

```powershell
Get-Content "C:\Users\a\air_ground_sync.log" -Encoding UTF8 | Select-Object -Last 20
```

两层叠加的效果：**自己一提交就推出去，对方最多 3 分钟就收到** —— 对两个人的协作来说，这已经是实际意义上的实时。

### 9.3 为什么不让网盘直接同步项目目录

看着最省事，实际最容易把仓库搞坏：

| 问题 | 后果 |
|---|---|
| 网盘会同时改写 `.git/index`、`refs/`、`objects/` 等内部文件 | 两机并发时**静默损坏仓库**，某天突然 `git` 命令全报错，且无法定位是哪次同步搞坏的 |
| 冲突处理 = 生成「xxx(2).md」副本 | 没有任何合并语义，得人工比对，比 Git 冲突难处理得多 |
| 提交历史 | 网盘没有，谁改了什么、为什么改，全丢了 |

Git 的冲突是**显式的、可解决的、可回退的**——这是它值得多一层的原因。
网盘只承担一件事：传那些**不进 Git 的大文件**（见第 5 节）。

### 9.5 本机凭据是怎么配的（换令牌时看这里）

令牌存在 **`~/.git-credentials`**（A 机为 `C:\Users\29212\.git-credentials`），明文，只有本机当前用户能读。

``` 
https://circle-of-joy:<令牌>@gitee.com
```

⚠️ 这里有个**踩过的坑**，B 机配置时不要重蹈：

本机系统级装了 Git Credential Manager（`credential.helper=manager`），它会**反复送出一个错误的旧用户名 `yubinghuan`**，
导致每次 push 都报 `yubinghuan: Incorrect username or password` —— 而且在我这种非交互环境里它**连弹窗都不弹**，
直接空密码提交，所以怎么试都过不了。

解决办法是在仓库级把 helper 链清掉、只留 `store`：

```bash
git config --local credential.helper ""        # 空值 = 重置整个 helper 链，把系统级的 manager 踢掉
git config --local --add credential.helper store
```

**换令牌 / 吊销令牌**：直接改 `.git-credentials` 里那一行，或者用
`cmdkey /delete` 清掉残留的旧凭据。文件名里的令牌建议在比赛结束后就去 Gitee 重置一次。

### 9.6 踩过的坑②：屏幕每 3 分钟闪一下 cmd / git.exe

**现象**：配好定时任务后，屏幕上每隔几分钟闪一个黑框。

**根因**：`pythonw.exe` 自己不创建窗口，但它调用的 **`git.exe` 是控制台程序**。
`pythonw` 没有控制台，Windows 就会给这个子进程**自动分配一个新的控制台窗口** → 一闪而过。

**修复**：给子进程加"不要创建窗口"的标记（`tools/sync_progress.py` 已包含）：

```python
_NO_WINDOW = subprocess.CREATE_NO_WINDOW if os.name == "nt" else 0

subprocess.run([...], creationflags=_NO_WINDOW)
```

`CREATE_NO_WINDOW` 只在 Windows 上存在，所以必须写成 `if os.name == "nt" else 0`，
否则 Linux 上（B 机）一导入就报 `AttributeError`。

**排查这类问题的通用套路**：数一下闪烁的节奏 → 去日志里比对时间戳
（`Select-String "同步开始"`），节奏对上了就是它。

## 11. 两边 AI 之间怎么协作

### 11.1 先说实话：没有直连通道

两台机器上的 CodeBuddy **之间没有任何连接**。我们都是"用户说话才醒"的东西 ——
没有后台进程、没有互相调用的接口。所谓"AI 协作"只能靠**文件**。

### 11.2 邮箱：`docs/AI信箱.md`

约定（完整规则写在文件开头）：

- 每条消息 `## [A→B] 时间 · 待回复`
- 回复**追加在那条消息下面**，并把标记改成「已回复」
- ⚠️ **没有新消息时不要提交** —— 否则一堆"没有新消息"的提交会把真正有用的淹掉

传递靠已经搭好的同步：

| 方向 | 靠什么 | 延迟 |
|---|---|---|
| 我 → 对方 | post-commit 钩子（提交即推） | 秒级 |
| 对方 → 我 | 定时任务每 3 分钟拉一次 | 最多 3 分钟 |

### 11.3 让 AI 定时自己看信箱（可选，两边各设一次）

CodeBuddy 自带**定时自动化**（周期最快是**每小时**，没有分钟级）。
给"信箱巡检"建一个任务，prompt 建议这么写（**限制它只读信箱、不许碰代码**）：

```
读 docs/AI信箱.md，只处理信箱里的往来：

## 11. 两套历史是怎么合成一条的（2026-09-28）

**背景**：到 09-28 晚上，两台机器各有一条**互不相干**的 `main`：

| 机器 | 基线提交 | 怎么来的 |
|---|---|---|
| B 机（发布到 Gitee 的那条） | `6abf5b1 chore: 重建仓库基线（迁移自旧电脑，原 a1ea04b 的 .git 未随拷贝带出）` | 项目目录拷到 B 机时**没带出 `.git`**，B 机重建了基线 |
| A 机（现场机） | `b944ee4 chore: 重建仓库基线（原 .git 被网盘同步损坏）` | A 机的 `.git` 被网盘同步**静默损坏**（pack 文件丢失），也重建了基线 |

两边根提交不同 → `git merge-base` 为空 → **直接 merge 会拉出一个"两个根"的乱账**
（§10.3 那句"别自己 merge"说的就是这个）。

**处理**：以**远端那条为准**（它带着看板、`setup_sync.py`、训练文档等完整协作记录），
把 A 机当天的工作作为**一次普通提交**叠在 `6abf5b1` 之上：

- 逐文件比对两棵树，**只有 3 个文件需要人工融合**：`tools/sync_progress.py`、`docs/协作看板.md`、`README.md`
- 1 个文件是 B 机独有的：`tools/setup_sync.py` —— **原样保留，未动**
- 其余差异要么是 A 机当天的新工作（官方栈修复、`car.py`、车端脚本、黑匣子取证），
  要么是纯换行符差异（`.gitattributes`、`src/ag_interfaces/msg/*.msg` 等 7 个文件）
- 融合时顺手把一边的漏洞补掉了：B 机的冲突提示写着"解决完再跑一次脚本"，
  但脚本开头的冲突守卫会再报一次冲突、**原地打转**；现在会在"冲突文件已全部解决"后自动收尾

**教训（还是同一条，只是换了形式）**：**不要用网盘同步含 `.git` 的目录**。
B 机那次是"拷贝时漏了 `.git`"，A 机这次是"`.git` 被改坏"，两次都逼着重做基线。
搬项目只用 `git clone` / `git pull`。

## 12. 车端也会"两边同时用"（2026-09-28 实测）

仓库有防冲突规则，**车也是共享资源** —— 两台机器都可能上车改东西，冲突起来更难查，
因为没有 `git` 帮你留下痕迹。当天就踩到了。

### 12.1 `~/dzrobot` 从 2.8G 缩到 476M 的完整台账

| 时段 | 变化 | 原因 | 证据 |
|---|---|---|---|
| 09-27 18:55 → 09-28 18:23 | 2.8G/28367 → 888M/9101（**−1.9G**） | 有人在车上跑 `rm -rf build/ install/ log/` + `colcon build --base-paths src --symlink-install`。**这 1.9G 全是构建产物**，不是源码 | 车端 `~/.bash_history` 第 1980/1998 行；`~/board_current_0928.tar.gz`（16:52） |
| 09-28 19:13 → 19:28 | 955M/9345 → 476M/3572（**−479M**） | 有人在**车上的桌面**把 `src_1`、`src_4` 拖进了回收站 | `~/.local/share/Trash/info/src_*.trashinfo`：`DeletionDate=2026-09-28T19:18:24` |

**结论：没有数据丢失。**

- 那 1.9G 是 `build/` + `install/` + `log/`，**可重建**（重编 4 个包只需 35 秒）
- `src_1`/`src_4`（538M）**还在回收站里**，且是 `src` 的重复副本
  （`src_1` 1768 文件 ≈ `src` 1764；`src_4` 多出的 2345 个文件是它自带的 `build/install/log`）
- 副作用是好的：删掉它们**正好解开** "Duplicate package names not supported" 那个死结，
  以后在 `~/dzrobot` 直接 `colcon build` 就行，不用再加 `--base-paths src`

> `*.trashinfo` 只在**图形界面删除**时生成，`rm -rf` 不会 —— 查"谁删的、什么时候删的"就靠它，
> 比翻 shell 历史可靠得多。完整取证见 `docs/probe/car_why_smaller_0928.txt`。

### 12.2 上车前先花 10 秒判断"有没有人正在用"

```

**`~/dzrobot` 的产物 mtime 比自己的作业时间新 = 别人刚动过**，先问一句再动手。
