### 1.3 为什么只打 2 发（判据链，逐条可查）

开火是 7 条 AND（`dzrknn_dataprocess.cpp:360`）：

| 条件 | 判据 | 今天实测 |
|---|---|---|
| 进框 `in_fire_zone` | \|dx+lead−laser_x\| ≤ fire_dz 且 \|dy−laser_y\| ≤ fire_dz | lead = 0（无发布者）；fire_dz = **25~26 px**（`config/robot.yaml:179,184` 随框宽插值） |
| 稳 `aim_ready` | \|vx\|、\|vy\| ≤ `fire_stable_px_per_frame` = **1.5**（`:279-281`） | 只有 **13.77%** 的帧能过 |
| 类别 `cls_fire_ok` | `locked_cls==1`（蓝） | 通过（1892/1897 是蓝） |
| 弹药 `ammo_ok` | `shots_fired < max_shots(10)` 且单目标 < 10 | 通过 |
| 冷却 `cooldown_ok` | 距上一发 ≥ `shot_cooldown_ms` = **500 ms** | 通过 |
| 目标确认 `target_confirmed` | 类别连续确认帧数 | 通过 |
| 连续保持 | `fire_hold_count >= fire_hold_frames` = **5**（`:363`） | **真正卡住的地方** |

**关键推理**：要开火得**连续 5 帧**同时满足「进框 + \|vx\|≤1.5」。而靶子在走，\|vx\| 中位就是 5.0，单帧过门槛的概率 13.8%，连续 5 帧在匀速段几乎不可能；只有靶子**换向那一瞬间**速度趋零才成段满足 —— 这就是那 2 发都落在拐点的原因。**不是运气，是结构性必然。**

## 3 天花板在哪（含延迟口径冲突，必读）

### 3.1 算式

```
落后 = 靶速 126.5 px/s × 延迟 T
开火框 = 25 ~ 26 px（config/robot.yaml:179,184，随框宽插值）
```

| T 取值 | 落后 | 和 25~26 px 框比 | 出处 |
|---|---|---|---|
| **0.26 s** | **33 px** | **超框 27%** ⇒ 匀速段必偏 | `dzrknn_dataprocess.cpp:295` 注释「视觉流水线 0.26s」 |
| **0.267 s** | **34 px** | 同上 | 车端启动横幅「视觉延迟 267ms」（T1 实录） |
| **0.27 s** | **34 px** | 同上 | `robot.yaml:837` `lead_time_s: 0.27`（注释：2026-10-18 实车回标） |
| 0.0667 s | 8.4 px | 在框内 | `check_numbers` 里 `vision_pipeline_latency_s` 的代码现值 = thread_num 2 × 33 ms，**只算流水线排帧，不含推理/传输** |
| 0.5~0.9 s | 63~114 px | 远超框 | `total_latency_ms`（全链路含点火，文档口径，待实测定案） |

> **口径纪律**：①视觉流水线延迟 ≈ **0.26~0.27 s**（三源一致），提前量用这个；②`vision_pipeline_latency_s=0.0667` 是**另一个量**（只算排帧）；③0.5~0.9 s 是**全链路**（含点火与裁判回传），不是瞄准要补的量。三者不要混用——`check_numbers.py` 已经把这条列为"需人核"。

### 3.2 但是：光有提前量不一定能开火，必须实测验证

开火的稳定性判据 `aim_stable` 用的是 **vx = 滤波后 dx 的单帧变化量**（`dzrknn_dataprocess.cpp:279`），而提前量只进 `aim_err_x`（`:300`）。设计意图是：云台物理上瞄向未来位置后，目标在画面里**停在一个恒定偏移上**，于是 vx→0、稳定性自然满足。

**这是推论，不是实测结论**。所以 P0 的验收必须是"发 lead 之后 `/aim/status` 与开火实际发生"，而不是"看到 lead 有数了就算完"。若发 lead 后 vx 仍不下降，说明控制环没吃进这个偏置（T4 说的"两条补偿互相抵消"），那时要回头改控制环，**不是继续加大 gain**。

### 3.3 另一个与结论无关、但确实在卡的事实

不加提前量时，`aim_err_x` 大概率在框外；但**即使恰好在框内**，还要连续 5 帧 `|vx|≤1.5`（§1.3）。实测只有 **13.77%** 的帧满足，所以即便框内也常常凑不满 5 帧。**两条一起卡**，别只归因于一条。

另外解释 `|dx|` 中位 41 px：云台是纯 P 控制（`Speed_1 = trackSpeedFor(eff_x)`），想输出角速度就必须留一个稳态误差，量级 = 靶速/增益。速度指令**几乎从不顶格**（yaw 0/7141）证明瓶颈在控制律的稳态偏差，不在电机。
