**M 档数据为什么作废（三个现场故障，都值得记住）**：

1. **相机节点假死**：`/image_raw` 停发（进程在、话题没了，典型 USB 挂死），det_node 空转 5 分钟。修法：重启 `ros2 launch dzactuator camera.launch.py` + det_node（det 必须 `DISPLAY=:1`，否则 GTK 初始化失败 abort -6）。
2. **检测器把青色水桶当靶**：画面右上角的水桶被识别成 `cls=1（蓝）`、conf 99，并打出「扫描确认目标，允许射击」；真靶只剩画面最左边缘。后果：云台一路追桶，45 s 内 `/CameMo_Conl` 恒定 `[2400, 340, 800, 800]`（位置顶限位、速度顶 800 上限），dx 恒 271 px、框内率 0.2%。**这是真实的误击风险，必须单独立卡。**
3. **`/camemo_feedback` 发布者掉线**（Pub 0 / Sub 1）：云台开环，不知道自己转到哪。当时底盘节点活着但不再发反馈，重启底盘可恢复（会有一声电机响）。

另外发现：`pkill -f` 重启会**漏杀**，现场出现 `det_node ×2` + `dzrknn_dataprocess ×2` 并存（8 线程的旧进程把 CPU 吃到 99%）。**改参数后必须核对进程数与 topic 发布者数各为 1**：

```bash
ps -ef | grep -E 'det_node|dzrknn_dataprocess' | grep -v grep | wc -l   # 期望 2（launch + node 各一对则 4 行）
ros2 topic info /offset_center    # Publisher count: 1
ros2 topic info /CameMo_Conl      # Publisher count: 1
ros2 topic info /camemo_feedback  # Publisher count: 1（0 = 底盘反馈断了）
```

**10-22 夜的定性结论（不是定量）**：降线程后云台**确实更跟得上**，但靶一进入大幅横向扫动就跟不住，速度指令长时间贴 800 上限；**开火死区（≤14 px）几乎不可达**。要证明「降延迟帮了多少」，必须用受控匀速扫靶做 A/B——这一步**还没做**。
