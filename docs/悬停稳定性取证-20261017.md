# 悬停/稳定性取证报告（2026-10-17）

**对象**：dzpx4 栈（Livox MID360 → FAST-LIO → px4_odom_convert → PX4 EKF2 VIO → px4_control）
**数据源**：`logs/uav/drone_logs_pull/drone_logs/`（4 会话 + 4 个 odom 单变量实验）、`logs/uav/flight2/`（2 会话）、`logs/uav/log_1_2026-10-15-17-10-50.ulg`
**分析工具**：新增 `tools/hover_drift_forensics.py`（control 状态窗 × odom delta 序列）、`tools/ulog_salvage.py`（ULog 容错打捞），均带 pytest。
**方法学说明**：odom.log 的 `position delta NED` 行无时间戳，本文用同文件内带 ROS 时间戳的 INFO/WARN 行做锚点、按行号线性插值重建时间轴（锚点间实测 43~44Hz，与标称 50Hz 的差距来自 stdout 刷新抖动；窗口统计按实测速率换算速度）。

## 1. 结论摘要（根因排序）

| # | 根因 | 严重度 | 状态 |
|---|---|---|---|
| R1 | **global_localization 自动初始化错配（yaw 偏 ~180°）**：上电点不满足"SLAM 原点≈建图原点"假设，ICP 以 fitness 0.893 收敛到对称错配位姿，/localization 整体翻转并持续被周期 ICP 拉动 | 致命（直接造成 200254 全部异常） | 建议并行会话改（§6.1） |
| R2 | **SLAM 跳变无防护直通 EKF**：10-16 晚实飞的是"直通+reset_counter bump 一次"中间版，无 jump guard；/localization 单步 15→920m 乱跳直接打崩 EKF | 致命 | 我们侧补丁已有 jump guard，本次又补了候选一致性（§5.1），**待部署实飞** |
| R3 | **EKF 以 1.00Hz 节拍式 xy reset（VIO 静止时也照复）**：间隔中位 1.01s、min 0.98、max 1.04，节拍与 GPS 1Hz epoch 一致，疑似 GPS 融合在室内反复 reset | 高（悬停抖动的持续激励源） | 建议查 PX4 参数（§6.2） |
| R4 | **px4_control 的 ARMING 无超时**：PX4 拒绝解锁时状态机永久卡 ARMING，操作员重按只得到 `ARM refused: state=ARMING` | 中（操作卡壳，非坠机风险） | 建议官方改（§6.3） |
| R5 | **10-16 下午场 px4_odom_convert launch 文件损坏**（缺 `generate_launch_description()`），164517/165851 两场飞行全程无 VIO 馈入 | 高（那次"悬停不稳"是在无 VIO 下飞的） | 建议官方加部署校验（§6.4） |

一句话：**用户感到的"悬停不稳"不是飞控调参问题，是定位链（全局重定位错配 + SLAM 跟丢乱跳）把假位置喂给 EKF；EKF 的频繁 reset 把每次定位跳变放大成机体运动。**

## 2. 现象时间线（六个会话）

### 2.1 会话 20261015_165944（10-15 17:00，健康基线）
- odom_convert 为**无 auto-align 的原版**；全程 0 次 EKF reset。
- 地面静止 356s：净漂移 (+0.024,+0.025,+0.002)m，等效速度 RMS (0.08,0.13,0.06)m/s，单步峰值 ≤2.7cm —— **FAST-LIO 原始输出在静止时非常稳**。

- 注：odom.log 在 1792055172 后无数据（采集截断），第二次起落的 delta 未覆盖。

### 2.2 会话 20261015_173217（10-15 17:32，旧 auto-align 反馈环实锤）
- 地面静止 400s 录像（未起飞）。运行的是 **auto-align gain=0.20 旧版**（"EKF frame reset detected ..., **realigning**"）。
- **EKF reset 日志 14195 条 / 400s ≈ 35Hz**；xy_reset_counter 为 uint8，观测到全部 256 个值（绕卷 ~55 圈）——EKF 在持续复位。
- 机制：EKF reset → 旧代码把 SLAM 位姿朝 EKF 帧拉 20% → VIO 流变化 → EKF 看到 innovation → 再 reset，构成**正反馈极限环**。发布位姿 400s 净游走 (2.9,-2.9)m。
- 这就是当晚四个单变量实验（odom_restart/frozen/yawonly/bump_180141）要解决的问题；实验终点是"直通 + reset_counter bump 一次"方案（odom_bump_180141，aligned yaw_offset=-173°——注意这个**结构性 ~180° yaw 偏差**在 R1 里还会出现）。

## 5. 控制链问题归因

### 5.1 "ARM refused: state=ARMING" 死循环（R4）
- 日志现场：194955（卡 140s，1 次 refused）、200254（两次卡死 21.6s/140s，共 5 次 refused）。
- 代码定位：`reference/onboard/dzpx4/px4_control/src/px4_control_node.cpp:597-601`——ARMING 唯一的出口是 `is_armed()` 为真；**无超时、无重发、无回退**。PX4 因 EKF 不稳拒绝解锁时，状态机永久停留；操作员再按 ARM 走到 `handle_arm()` 的第一道闸门（`px4_control_node.cpp:349`：`state must be DISARMED/LANDED`）即打回 `ARM refused: state=ARMING`——**正是日志里的字样**。
- 深层触发：PX4 拒绝解锁是因为 EKF 正被垃圾 VIO 冲刷（R1/R2/R3）。状态机只是放大器。
- 建议见 §6.3。

### 5.2 HOVER→LANDING "过早"（实为外部命令）
- 代码定位：`handle_land()`（`px4_control_node.cpp:398-428`）是 TAKEOFF/HOVER→LANDING 的**唯一**入口，只能由 `/px4_control/command` 的 CMD_LAND 触发；状态机自身从不自发降落。
- 日志证据：200254 HOVER 3.9s 内 VIO 位姿单步 1.80m（t=2268.29）→ 0.36s 后 LAND 命令到达（t=2268.65）→ 0.09s 后重复 LAND 被拒（"LAND ignored: state=LANDING"，典型连击/脚本重发）。
- 结论：不是状态机 bug，是操作员/任务脚本看到机体猛晃后的主动处置。真正要修的是晃的根源（R1/R2/R3）。
- 其余场次（165944×2、194955、200254 二飞）的 TAKEOFF→LANDING 无 HOVER 也全部对应外部 LAND 命令（起飞即降的点动测试）。

### 5.3 "left OFFBOARD (nav_state=2)" 脱管
- nav_state=2 = POSCTL（遥控位置模式）。代码定位：`on_vehicle_status()`（`px4_control_node.cpp:230-246`）：检测到非 OFFBOARD 即让权并落 DISARMED 状态。
- 事件清单：164517@1792140539.7（HOVER 中）、165851@1792141292.1 与 @1792141339.5（均 HOVER 中）、194955@1792151702.6（ARMING 卡死中）、200254@1792152351.5（ARMING 卡死中）。
- 谁能把 PX4 切到 POSCTL：① 安全员遥控器拨模式/动杆（试飞标准操作）；② offboard 链路失效保护回退（控制节点 20Hz 心跳一直在发，且 `COM_OF_LOSS_T` 超时回退的模式由参数定）。**现有日志无法区分两者**——控制节点没有记录 `vehicle_status.failsafe`，两次 HOVER 中脱管前控制链路也未见异常日志。
- 值得注意的相关性：5 次脱管全部发生在定位链已坏的会话（两场无 VIO、两场 EKF 正在被冲刷），与"安全员看到飞机飘而接管"的剧本一致，但不能当作定论。
- 建议见 §6.3（加 failsafe/nav_state 遥测记录）与 §6.2（PX4 侧核实）。

### 5.4 EKF frame reset 与漂移/脱管的时间相关性
- 165944（0 reset）：飞行正常。
- 173217（35Hz 持续 reset）：旧 auto-align 与 EKF 互相追逐，位姿 400s 游走 4m（未起飞，否则必炸）。
- 194955（1.00Hz 节拍 reset ×140s）：ARMING 卡死同期；reset 停止的条件未知（日志只到 1827），第二次 ARM 即成功。
- 200254：reset 加速段（2267→2282，1Hz→2Hz）精确覆盖 HOVER 晃动→LANDING→跳变风暴全过程。
- 方向性结论：**每次漂移/脱管事件都有 reset 伴随；reset 是定位异常传导到飞控的通道**。

## 7. 已修项（代码，本仓库）

### 7.1 `onboard/dzpx4_patch/px4_odom_convert.cpp` / `.hpp`：jump guard 候选一致性
- **问题**：原 jump guard 的接受条件是"连续 8 帧位移都 >0.5m"。200254 实测表明 SLAM 跟丢后的乱跳序列（15→491→920m，方向不定）每帧都超阈，8 帧后必被误判为"真实被搬运"而接受——EKF 会被反复重锚到垃圾位姿。
- **修复**：新增候选一致性检查——当前候选与上一候选落点差 < `jump_accept_dist_m_`（新增成员，默认 1.0m）才累计确认计数，否则重新计数；正常跟踪帧清空候选序列。真实搬运（位移大且落点稳定）仍能 8 帧确认；乱跳序列永远确认不了。
- 位置：`px4_odom_convert.cpp` jump guard 段（接受判定前插入候选跟踪，正常分支重置）；`px4_odom_convert.hpp` 新增 `jump_accept_dist_m_` / `gate_has_cand_` / `gate_cand_pos_` 成员，头注释同步更新。
- 验证：无 ROS 环境无法编译，改动为纯逻辑插入、成员均在 hpp 声明；部署仍走 `tools/patch_deploy.py`。**尚未实飞，建议下次试飞优先验证"落地后搬运重锚"场景**。

## 8. 待办建议（官方/并行会话/PX4 侧）

### 8.1 global_localization（并行会话，`logs/uav/fix/global_localization.py`）
1. **auto-init 必须多假设**：现版初始猜测只有单位阵（"SLAM 原点≈建图原点"），200254 实测收敛到 yaw 偏 ~177° 的对称错配（fitness 0.893）。建议初始猜测枚举 4 个朝向（0/90/180/270°），取 fitness 最高者，且要求最高与次高有明显 margin（如 >0.05），否则不初始化继续重试。
2. **初始化也要过确认**：现版 `is_init=True` 完全绕过跳变确认（`global_localization.py:218` 的 `if not is_init:`），一次 ICP 成功就发布 T_map_to_odom。建议初始化同样要求连续 2~3 次一致（复用 `pending_jumps` 机制）。
3. **机上版本门槛低于 fix 版**：飞行日志显示 fitness 0.893 被接受（fix 版 `localization_th=0.9` 会拒绝）。确认机上部署版本与 fix 目录一致。
4. **fitness 在此场地无判别力**：落地后位姿乱跳几百米时 fitness 仍有 0.975~0.989。建议补"与当前位姿偏差"硬门（周期更新也走 jump gate，现版已有 >1.5m 确认，建议把 0.1~1.5m 段的更新也加死区/速率限制， armed 期间冻结 T_map_to_odom 更新）。

### 8.2 PX4 参数（QGC/MAVLink 在线核实，ULog 已毁无法离线取证）
1. `EKF2_GPS_CTRL`：若含 GPS 位置融合，室内/格子场建议设 `0`（关闭）。依据：194955 ARMING 段 VIO 准静态而 EKF 以 1.00±0.03Hz 节拍 reset，与 GPS 1Hz epoch 一致；165851 无 VIO 时能飞 HOVER/GOTO 也旁证 GPS 融合在场。
2. `EKF2_AID_MASK` / `EKF2_EV_CTRL`：确认 vision position fusion 开启、yaw 源明确（SLAM yaw vs 磁力计二选一，勿双源）。
3. `EKF2_EV_QMIN`、`EKF2_EV_GATE`：若 EV 质量门过严会造成融合断续→反复 reset。
4. `EKF2_HGT_REF`：配合 dzpx4_patch 的 z 换源（EV z=EKF z），高度应走 `Barometer`。
5. `COM_OF_LOSS_T`：确认 offboard 丢失超时与回退模式（解释 nav_state=2 脱管路径）。
6. ULog 落盘可靠性：本次 ULog 只有头部 6.5KB，建议查 SD 卡剩余空间与 logger 缓冲区（`SDLOG_*`），并在 `tools/preflight.py` 里加"上一场 ULog 可解析"检查。

### 8.3 px4_control 状态机（官方，`reference/onboard/dzpx4/px4_control/src/px4_control_node.cpp`）
1. **ARMING 加超时回退**：`on_timer()` 的 `FlightState::ARMING` 分支（:597）加 `arming_timeout_s`（建议 10s，参数化）——超时未 `is_armed()` 则 WARN 并回 DISARMED，让操作员可重试。依据：194955 卡 140s、200254 两次卡死均靠"left OFFBOARD"外力解锁。
2. **脱管可观测性**：`on_vehicle_status()` 记录 `m->failsafe` 与 nav_state 迁移序列；HOVER 中脱管时打印当前 `current_` 与 `target_` 偏差，便于区分"遥控接管"与"失效保护"。
3. `is_on_ground()`（:106-117）依赖 |z|<0.20m 估计值——z 链被污染时（200254 二飞 start_z=+5.15）"DISARM sent"可能在空中放行。建议 DISARM 前叠加 `landing_state`/takeoff_time 交叉确认（PX4 侧 land_detector 仍是最终闸门，但上层不应先发错误指令）。
