## 2. ★ 无人机 / 机载端（重点）★

### 2.1 只有一个真相来源：我们只做三件事

无人机侧**没有**飞控/建图/定位/自主飞行代码 —— 那些全部由官方 AR5 栈负责。
我们自研的只有 **3 个节点**：

| 节点 | 源码 | 订阅 | 发布 | 作用 |
|---|---|---|---|---|
| `vision_node` | `src/ag_perception/ag_perception/vision_node.py` | `/image_raw` | `/perception/detections` | 跑 RKNN 模型，出蓝/红靶标 + 发光中心 |
| `intel_fusion_node` | `src/ag_perception/ag_perception/intel_fusion_node.py` | `/perception/mines`、`/perception/detections`、`/perception/obstacles`(可空)、`/perception/bridges`(可空) | `/air/field_intel` | **像素 → 格号**（靠单应矩阵 H）+ 多帧投票 |
| `air_link_node` | `src/ag_bridge/ag_bridge/air_link_node.py` | `/air/field_intel` | 无 ROS 发布，走 **UDP** | 情报下发给车 |

第四个 `fake_intel_node`（`src/ag_bridge/ag_bridge/fake_intel_node.py`）是**联调用的假情报源**，不是产品的一部分。
统一由 `src/ag_bringup/launch/air.launch.py` 拉起（`with_fake_intel` 开关控制第四个）。

拆解到"我们的职责"就一句话：**把相机像素变成格号，通过 UDP 发给车。**
`mission_planner.py` 是**车端**用的（车端 `mission_node` 的规划内核），别误认为机载。

### 2.2 空地链路协议（`src/ag_core/ag_core/link_protocol.py`）

- **JSON over UDP**，一帧 = `4 字节长度前缀 + JSON + 4 字节 crc32`（网络序），`VERSION=1`
- 四种帧：`intel` / `heartbeat` / `ack` / `status`
- **端口交叉对应**：机载 `bind 9902 → peer 9901`；车端 `bind 9901 → peer 9902`
- **心跳 1 Hz**（车端据此判断链路存活）
- `FieldIntelMsg` 字段：`header / mines[] / obstacles[] / bridge_a / bridge_b / target_cells[] / target_face / seq`
- `is_complete()` = 有雷 **且** 有任一桥洞
- ⚠️ **广播地址必须改成现场网段**（`params.yaml` 现填 `192.168.1.255`）；`preflight_check.py` 会 FAIL 提醒
- ⚠️ 车端无线实测掉到过 1~6.5 Mbps（`docs/AI信箱.md`），大帧要留意

### 2.3 唯一的硬闸门：单应矩阵 H

**没标定 → `intel_fusion_node` 设计上拒发情报 → 车端一帧都收不到**，而且**不是 bug**：

- `params.yaml` 的 `homography` 现在是**全零**
- `intel_fusion_node` 启动即校验 H，全零/奇异 → `_h_ok=False`；映射时 `_cell_of` 返回空串
- 再叠加 `only_when_ready=true` → `/air/field_intel` **一帧都不发**
- 诊断已配套：日志规则 `no-homography` 会**抑制 `no-intel`**，避免把人引去查网卡

标定命令：

```bash
python tools/calib_homography.py --corners "u,v u,v u,v u,v" --cols 14 --rows 11
python tools/calib_homography.py --check "<像素u,v>"        # 验证某像素落在哪个格号
```

- 四角顺序**固定** `A1 → N1 → N11 → A11`（不是老的 `A1/K1/K14/A14`，`K14` 根本不在场上）
- 结果写进 `params.yaml` 的 `homography`；重投影残差 > 5 cm 要重标

> ⚠️ **两个"没上真机所以没暴露"的坑，接手必须先处理**：
> 1. `tools/calib_homography.py` 的**默认参数是 `--cols 11 --rows 14`，与节点相反**（节点/params 是 `cols=14 rows=11`）。
>    不显式传参 → 得到**轴颠倒的 H**。`tests/test_nodes.py` 也用的是 `(11,14)`，即测试与工具一致、与节点不一致。
> 2. 同名脚本的 docstring 里**仍写着旧四角** `A1/K1/K14/A14`，是陈旧痕迹。

## 3. 车端现状

### 3.1 定位链与坐标系（已与车端源码逐条核对）

```
[STM32 编码器+IMU] --串口 115200--> dzactuator --/odom--> serial_reader
    --/odom/localization(block 单位)--> path_executor(纯追踪) --/pursuitAngle--> dzactuator --> 底盘
```

| 项 | 定义 | 验证方式 |
|---|---|---|
| 单位 | **格（block）**，1 格 = 0.35 m | 源码常量；**官方阈值 0.157 m = 0.45 格** |
| 原点 | 场地角点 **N11 = (0.5, 0.5)** | 起点信念 `(1.50, 0.50) ↔ N10` |
| 轴向 | `x = (11 − 行号) + 0.5`，`y = (14 − 列序号) − 0.5` | N10 → (1.5,0.5) ✓；**L7 → (4.5,2.5) ✓**（两个独立来源都对上） |
| 范围 | x∈[0.5,10.5]（11 行）、y∈[0.5,13.5]（14 列） | `serial_reader` 注释 |
| 朝向 | 板载 IMU 的 yaw；raw→map 偏移 `+90°` | — |
| 位置 | **步长 × 当前朝向**逐帧累加（航位推算） | — |

⚠️ **`/odom/localization` 是格，不是米。** 历史上所有"位移 1.741 m / 路径 12.68 m"的报告都因此偏大 2.86 倍，真实值是 0.61 m / 4.44 m。

**起点 N10 朝 +y = 朝 M/L/K 方向 → 直行 3 格（1.05 m）就是 K 列桥洞。** 见 §5.7。

### 3.2 画圆根因（结论 + 一个必须知道的局限）

**结论**（`docs/朝向偏差根因-20261001.md`，实车实测）：
车"以为"的朝向与真实朝向相差**恒定 68.6°**（14 秒内 8 个采样点：72.1/69.5/68.4/68.6/68.3/68.6/68.9/69.8），
纯追踪因此把目标看偏一个固定角，**绕着目标画圆，永远到不了**。

已用实车数据逐条排除：yaw 漂移（静止 10 s 仅 +0.1°）、`angular.z` 符号接反（同向）、单位（是度）、
速度折算、转向机构/轴距（理论 vs 实测角速度吻合）。

**偏差从哪来**（按复位逻辑反推）：

```
belief = raw_map_yaw + snap_yaw_off
snap_yaw_off = tyaw − raw_map_yaw(复位时)   →   belief − true = 90° − (复位时车的真实朝向)
实测 −68.6°  →  复位时车真实朝向 158.6°，而 reset:N10,y 断言它朝 90°
```

即：**车被搬到起点时的实际朝向与 reset 断言的朝向差了 68.6°**。reset 不只断言位置，还**盲目断言朝向**。

> ⚠️ **接手必须知道这个证据的局限**：表里的"实际走的方向"是由**同一路 yaw 积分出的位置**反算的，
> 而"相信的 yaw"来自同一路 yaw 加一个常数偏移 → 两者之差**按定义就是常数**，不能自证朝向真的差 68.6°。
> **决定性实验只有一个（也是当前第一步）**：把车**原地左转约 69°（俯视逆时针）**，重跑探针。
> - 若车直线开到 N9 并停下 → 摆位说成立，问题在"人摆车"，修法是**流程 + 校验**；
> - 若仍以同样的恒定偏差绕圈 → 偏差来自 yaw 源头（serial_reader / IMU / raw→map 偏移），要改代码。
>
> 更根本的一点：**车只有航位推算、没有绝对朝向参考**，它**无法自己知道**自己在场地坐标系里朝哪。
> 人的摆车 + reset 断言**就是**那个参考。所以"让车自己反推真实朝向"（原计划的第 2 条修法）
> 在原理上并不成立，除非引入外部参考（地面格号视觉、或人工标定）。**这一点留给接手的人重新评估。**

**已确认修好的旁支**：
- 到达阈值 vs 最小转弯半径不匹配（官方 0.157 m < 最小转弯半径 0.24~0.26 m）：
  阈值放宽到 **0.70 m 时实测车能锁存到位并彻底停住**（`lin=0.000` 保持 8 s）。这条是真实的第二处缺陷，
  但**不能单独解决问题**，而且阈值放大会吃掉路线（官方路线每段只有 0.35~1.11 m）。
- 执行器启动崩溃（`ModuleNotFoundError: car_localization.map_utils`）→ 起执行器必须带 `PYTHONPATH`。
- 补丁把定位"吃"掉（少 `serial_reader.py`）→ 补丁必须复制**整个包**，并校验两个模块都能导入。
- 车端部署改为**打一个 zip 上传**（逐文件 SFTP 传几百个小文件会被 SSH 反复重置）。

### 3.3 车的能力边界（决定"该要求它什么"）

见 `docs/车独立能力边界与验收标准.md`（**建议接手必读**）。要点：

- 车是**执行器**，不是侦察器：能"按格号走 + 精确到位 + 到位后用自带相机认蓝红并打击"
- **不能**认网格/读格号（无模型）、**不能**看桥顶标识（物理上看不到）、**不能**自己规划去哪
- **车独立天花板 ≈ 10/100**（驶离起点 5 + 回终点 5）；排雷 40、桥洞 20 **必须无人机**
- 验收拆两档：**A 档（车独立，无人机未到货时唯一能推进的）**、B 档（空地协同，等无人机）
- A 档判据（还没过）：不画圆（绕路系数 ≤1.2）、到位锁存、连续多段、停靠精度 ≤0.1 m、出界自停

## 5. 现场环境坑（血泪表，按踩到顺序）

### 5.1 SSH 密码会"静默死等"（已修）
`tools/remote_run.py` 没有 `AG_CAR_PASS` 时会弹 `getpass` **死等标准输入**：不打印、不报错、看起来就是"卡死"。
**本次会话因此被误判成"车不通"，好几条命令一个字都没发到车上。** 现已改为：没有终端就**立刻报错**并告诉你该给什么。

### 5.2 命令会"空闲超时"被掐断
`remote_run.py` 要**等远端跑完才回传输出**。发车脚本要跑 90 s 且中间没有输出 → 工具判定"卡住"直接终止。
**长任务一律后台跑 + 轮询日志**：

```bash
# 后台起，立即返回
python tools/remote_run.py --host <IP> --user duzhong --cmd \
  "cd /tmp && setsid nohup bash /tmp/xx.sh > /tmp/xx.log 2>&1 < /dev/null & sleep 2; echo STARTED"
# 每 20 s 看一眼
python tools/remote_run.py --host <IP> --user duzhong --cmd "tail -20 /tmp/xx.log"
```

### 5.3 `ros2` CLI 会被搞坏
反复 kill 进程组会把 **ros2 daemon** 搞坏，之后所有 `ros2` 子命令抛 `xmlrpc.client.Fault: !rclpy.ok()` 直接崩。
**修**：`ros2 daemon stop`（下次调用自动重启）。
**更好的做法**：采样不要用 `ros2 topic echo`，用脚本里**内嵌的 rclpy 订阅器**。

### 5.4 QoS：这两个话题是 BEST_EFFORT
`/pursuitAngle`、`/odom/localization` 都是 **BEST_EFFORT**；`ros2 topic echo` 默认 RELIABLE → **一条都收不到**，
表现为"节点 50 Hz 在发、采样文件却是空的"。订阅端一律显式 `best_effort`。

### 5.5 行尾必须是 LF
车端是 Linux，`.sh` 带 CRLF 会 `bad interpreter`。本仓库有 `.gitattributes`，但新写文件在 Windows 上仍可能是 CRLF，
**提交前统一**：`python -c "p='x.sh';b=open(p,'rb').read();open(p,'wb').write(b.replace(b'\r\n',b'\n'))"`

### 5.6 Windows 控制台是 GBK
脚本里**别打印 emoji**（`⚠️` 之类）→ `UnicodeEncodeError` 让整个工具崩，而且报错只出现在子进程里。
Python 工具开头统一 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。

### 5.7 ★ 桥洞在 K 列，路线千万别往 K 列走 ★
两处桥洞占据**整个 K 列**（A 段 `K1~K5`、B 段 `K6~K11`）。
而**起点 N10 朝 +y 正对 M/L/K 方向，直行 3 格就是 K 列**。
2026-10-01 就因为"抄官方路线"把第一个路点取成 `K9`，让车往桥洞里扎（已撞翻过）。
**选路自检三条**：① 不用 K 列；② 不用 J/L 列（留一格余量）；③ 每段 ≥1.5 m（否则被到达阈值吃掉）。

### 5.8 云台接口（想拍照就用）
`/CameMo_Conl`（`Int32MultiArray`，长 ≥4）= `[俯仰刻度, 水平刻度, speed0, speed1]`
零位 **2047**、**11.378 刻度/度**；俯仰限位 950~2400（**低头是加大刻度**，2350≈+27°）、水平限位 100~3995。
官方文档明确：**只改云台，不解锁驱动** → 拍照是安全动作。

### 5.9 绝不同时起两套定位
`/odom/localization` 有两个发布者时位姿会来回跳，控制器追垃圾数据。执行器自带这条检查（>1 就报 error）。
**动手前先 `ros2 node list` 确认车上是干净的。**

### 5.10 车是公用的
`~/dzrobot` **全程只读**，改参数走 `/tmp/ag_ws/patched` 补丁机制。
另外：历史日志（2026-09-04）里 path_executor 打出过 `ARRIVED! dist=0.194m` —— **同一套代码到过终点**，
说明中间有人动过车/固件而我们不知道。`params.yaml` 按段分治（机载段归 A、车端段归 B），要动先在 `docs/AI信箱.md` 说。
