# 调试日志（黑匣子）

> 目标只有一个：**跑完一圈，能在两分钟内说清"刚才到底发生了什么、卡在哪一步"。**

---

## 0. 先用这三条命令

```bash
python run.py all                          # 本机：测试 + 全流程 demo + 自动出复盘报告
python run.py log                          # 看复盘报告（哪一步卡住、为什么、下一步做什么）
python run.py car-rehearse 172.23.116.188  # 车端：上传+编译+干跑一圈+取回日志+出报告（不动车）
```

只需要记这三条。`run.py log` 的常用变体：

```bash
python run.py log --dir logs/car           # 看指定目录（默认 $AG_LOG_DIR）
python run.py log --out report.md          # 存成 Markdown
python run.py log --json | python -m json.tool     # 机器可读
python run.py log --strict                 # 有严重结论时退出码 1（可直接进 CI）
python run.py log --list                   # 只是想知道日志都写哪了
```

**迭代循环就一圈**：改代码 → `python run.py all` → 看报告里有没有新的"注意/严重"。
真车联调同理：`python run.py car-rehearse <车IP>` → 看报告。

## 1. 为什么不是"多打点 printf"

现场真正会问的是这三个问题，而终端里滚动的文本日志一个都答不了：

| 现场之问 | 文本日志的困境 | 黑匣子的做法 |
|---|---|---|
| 为什么车没动？ | 11 个节点各自的终端，得一个个翻 | `route.blocked` 一条事件带**原因代码**，直接汇总 |
| 为什么没打中？ | 打了几发、裁判血量变化散在 20Hz 的刷屏里 | `shoot.count` / `referee.state` 只在**变化时**记一条 |
| 卡在哪一步？ | 跨节点时间对不上，事后没法统计 | 所有节点写进**同一条时间轴**，`T+xx.xs` 可直接对齐 |

所以：**结构化事件（机器可读）+ 文本日志镜像（人话）+ 一个离线的复盘工具**。

## 2. 怎么打开、日志在哪

日志**默认就是开的**（`log_enabled: true`）。每个节点多三个参数，`params.yaml` 里都有：

| 参数 | 默认 | 说明 |
|---|---|---|
| `log_enabled` | `true` | 关掉就没有结构化事件了（`ros2 param set /car_node log_enabled false` 可动态改） |
| `log_dir` | `""` | 留空 → 用环境变量 `AG_LOG_DIR` → 再退到系统临时目录下的 `ag_logs` |
| `log_level` | `"info"` | `debug` / `info` / `warn` / `error`，低于此级别的事件直接丢弃 |

**目录里不写家目录、不写工作空间**，就是为了在公用车上留痕最少：

```bash
# 车端推荐（/tmp 重启即清，不污染别人的车）
export AG_LOG_DIR=/tmp/ag_logs
export AG_LOG_SESSION=20260927-final      # 可选：给这一批日志起个名字
```

布局：`$AG_LOG_DIR/<会话>/<节点名>-<pid>.jsonl`，一行一个 JSON 事件。

```bash
/tmp/ag_logs/rehearsal/
├── car_node-37105.jsonl          # 车端决策
├── ground_link_node-37067.jsonl  # 车端链路
├── air_link_node-37068.jsonl     # 机载端链路
└── fake_intel_node-37104.jsonl   # 假情报源（联调用）
```

> 磁盘写满、目录不可写、路径其实是个文件 —— 这些情况**都不会让节点崩**：
> 写失败会把 `enabled` 置 false 并记 `errors` 计数，主流程照常跑。
> 日志不该有能力拖垮一局比赛。

## 3. 事件表

`ev` 字段就是事件名。字段名即含义，工具不认识的事件会原样列出，不会丢。

| 事件 | 谁写 | 关键字段 | 什么时候看它 |
|---|---|---|---|
| `session.begin` | `car_node`（实车路径）/ `mission_node`（自研/仿真路径） | `start_cell` `goal_cell` `dry_run` `min_mines` `require_target_face` `max_shoot_stops` … | 每局的**参数快照**，复现问题不用再问"当时参数是多少"；复盘也靠它切局 |
| `mission.task` / `mission.done` | `mission_node` | `index` `total` `type` `cell` `score` `eta_s` `path` `is_target` | 自研/仿真路径的推进节奏（实车路径看 `route.publish`） |
| `node.ready` | 所有节点 | `pid` `host` `cwd` `log_file` | 确认节点真的起来了、写到了哪个文件 |
| `node.args` / `vision.model` | `aim_guard` / `vision` | 白名单、类别号、`cls_activation` `kpt_unit` | 解码参数配错时表现为"模型在跑但什么都检测不到" |
| `intel.recv` | `car_node` / `mission_node` | `ok` `why` `seq` `mines` `bridge_a/b` `target_face` | 每一帧情报都留证据；`ok=false` 说明被投票窗口丢弃 |
| `intel.stable` | `car_node` | 同上（**内容变化时**才写） | 情报第一次收敛、以及之后每次变化 |
| `intel.accum` | `intel_fusion_node` | `mines` `target_cells` `target_face` | 机载端认定的"场地真相"，与车端收到的对比就能定位链路丢帧 |
| `plan.built` | `car_node` | `route` `tasks` `eta_s` `shoot_stops` `dry_run` | 算出路线但还没发（dry_run 下只有这条） |
| `route.blocked` | `car_node` | `reason` `detail` `face` `mines` | **为什么没发车**，原因代码见 §5 |
| `route.reject` | `car_node` | `reason` `detail` | 路线本身非法被拒 |
| `route.publish` | `car_node` | `kind`(`reset`/`route`) `cmd` `shoot_stops` | 真的发出去了什么命令（含 reset） |
| `shoot.count` | `car_node` | `value` `prev` | 车端 `/shoot_count` 的变化，打击是否真的发生 |
| `aim.block` / `aim.pass` | `aim_guard_node` | `why` `cls` `blocked_total` `passed_total` | 开火闸门拦了什么、放行了什么 |
| `referee.state` | `referee_node` | `hp` `ammo` `shots` `enemy_count` `friend_count` `target_hp` | 只在**变化时**写；血量/弹药一变就是关键转折点 |
| `fire.request` / `fire.denied` / `fire.sent` | `referee_node` | `reason` `ammo` `shots_total` | 开火链路与拒绝原因 |
| `link.tx` / `link.rx` / `link.drop` | `air_link` / `ground_link` | `kind` `seq` `bytes` `bad_crc_total` | 帧数对不上、CRC 失败、单向链路 |
| `vision.detect` | `vision_node` | `count` `cls` `scores` | 按秒采样：到底有没有检出目标 |
| `vision.stale` | `vision_node`（看门狗） | `never` `gap_s` `images` `note` | **相机断流 / 从没收到图像**；恢复时也会记一条（见下 §7） |
| `homography` | `intel_fusion_node` | `ok` `stage`(`startup`/`mapping`) `reason` | **单应矩阵没标定**：像素落不到格号 → 机载端发不出情报（跟链路无关） |
| `ros.log` | 所有节点（镜像） | `lvl` `msg` | 文本日志原文，**同一条消息 2s 内只落一条**（只影响落盘） |

## 4. 复盘怎么用

```bash
python run.py log                                # 默认读 $AG_LOG_DIR 下最后一批（推荐）
# 等价写法（想直接调底层工具时）：
python tools/log_report.py --dir logs/car        # 指定目录（递归找 *.jsonl）
python tools/log_report.py --session rehearsal   # 只看某个会话
python tools/log_report.py --out report.md       # 存成 Markdown
python tools/log_report.py --json                # 机器可读（喂给脚本/CI）
python tools/log_report.py --strict              # 有 critical 时退出码 1
python tools/log_report.py --all                 # 不切局，读全部事件
python tools/log_report.py --timeline 0          # 时间轴不限条数
```

默认**只统计最后一局**（从最后一条 `session.begin` 开始），避免把上一轮的残留算进来。
报告分三段：**结论（按严重度排序）→ 指标 → 时间轴**。每条结论都带"为什么会这样"和"下一步做什么"。

单独看某个节点：

```bash
python tools/log_report.py --dir logs/car --json | python -c "import json,sys; d=json.load(sys.stdin); print(d['summary'])"
```

## 5. 结论是怎么来的（规则表）

规则在 `src/ag_core/ag_core/log_diagnosis.py`，纯函数、可单测、不依赖 ROS。

| 代码 | 级别 | 判据 | 现场含义 |
|---|---|---|---|
| `no-events` | 严重 | 一条事件都没有 | 节点没起，或日志没写到你以为的地方 |
| `no-session-begin` | 信息 | 没有 `session.begin` | 只跑了机载端（车端才写这条） |
| `no-intel` | 严重 | 车端在跑，却一帧情报都没收到 | 链路/机载端问题 —— 查 `link.*` |
| `intel-not-stable` | 注意 | 收到帧但一直没收敛 | 投票阈值太高 / 情报一直在变（视角不稳） |
| `intel-bad-frames` | 注意 | 被判无效的帧占比高 | 乱序/重复/过期；**也可能是上游跑了两套节点**（见 §7） |
| `no-route` | 严重 | 情报收敛了却没发路线 | 原因分布直接列在报告里；`dry_run` 时不报；**只对实车路径生效**（`car_node` 在跑），自研/仿真路径不发 `/nav/waypoint`，不该报 |
| `route-repeated` | 注意 | 同一局发了多条不同路线 | 车端会**从头重跑**，白掉时间 |
| `route-reject` | 注意 | 路线非法被拒 | 格号/朝向拼错，看 `reason` |
| `hp-drop` | 注意/严重 | 己方血量下降（归零则升级为严重） | 被对方打中；看 `referee.state` 里的 `hit` 方向 |
| `no-reset` | 严重 | 发了路线却没发 reset | 里程计不知道车在哪，会按旧位姿跑飞；`publish_reset=false` 时降为信息 |
| `no-shoot-stop` | 注意 | 有打击点却没标 `*` | 红面（友方）时是**正确行为**，报告会说清 |
| `shoot-stop` | 正常 | 打击停靠点是什么 | 核对这个格是否真在敌方靶前 |
| `shots` | 信息 | `/shoot_count` 打到几发 | 与 `referee.state` 对照判断命中 |
| `out-of-ammo` | 注意 | 弹药见底 | 整车只有 10 发 |
| `aim-blocks-enemy` | 严重 | 闸门拦住了**蓝面（敌方）** | 白名单配错了，会一分打击分都拿不到 |
| `aim-blocks-friend` | 正常 | 闸门拦住了红面 | 这正是闸门存在的意义（防 −15 误击） |
| `aim-gate` | 信息 | 有拦截/放行统计 | 确认闸门在工作 |
| `no-referee` | 注意/信息 | 一局没收到裁判状态 | 节点在跑却读不到 → 注意；节点压根没起 → 信息 |
| `fire-denied` | 注意 | 开火被拒 | 弹药为 0 / 射速限制 |
| `link-drop` | 注意 | CRC 失败或发送失败 | 无线环境差，或网卡/端口不对 |
| `link-one-way` | 严重 | 只在单侧看到收发 | 广播地址/防火墙/端口配错 |
| `no-homography` | 严重 | 单应矩阵没标定 / 无效 | 像素换算不出格号 → 机载端**根本产不出情报**。此时 `no-intel` 会被抑制（根因已知，不再把人引去查链路） |
| `no-image` | 严重 | 一帧图像都没收到过 | `usb_cam` 没起/崩了，或 `input_topic` 不对。**官方节点崩了我们这边不会有任何异常** |
| `vision-stale` | 注意 | 中途有段时间没有图像 | `usb_cam` 崩了 / USB 带宽不足 / 设备被占 |
| `no-detection` | 注意 | 视觉节点在跑却零检测 | 模型没加载，或 `cls_activation` `kpt_unit` `input_layout` 配错 |
| `log-io` | 注意 | 日志自身写失败 | 磁盘满/没权限（但当时流程没受影响） |
| `stall` | 注意 | 两条事件之间静默超过 `--max-gap`（默认 30s） | 卡住的**位置**就在这条之前 |
| `dry-run` | 信息 | 本局 `dry_run=true` | 没发车是预期行为 |
| `last-event` | 信息 | 最后一条事件是什么 | 停在 `route.publish` = 命令已交给车端；停在 intel 相关 = 链路断 |

表里这些是**结论代码**（会各自成为一条结论）。另有一组**原因代码**
（`min_mines` / `face_unknown` / `no_cells` / `min_shoot_stops` / `route_error` / `bridge_reject`）——
它们不单独成结论，而是出现在 `no-route` 的「原因分布」里，并决定那条结论给出什么排查提示。
（`REASON` 常量在 `blackbox.py`，两边必须对得上，否则提示查不到。）

**误报防线**（都是真机踩出来的，见 §7）：

- `dry_run=true` 时**不报**"没发路线"——本来就一条都不发；
- `referee_node` 没在跑时，`no-referee` 降为**信息**，不刷"注意"；
- `publish_reset=false`（人工 reset 的合法配置）时，`no-reset` 降为信息；
- 空日志只给一条 `no-events`，不再顺带产出"没有裁判状态""最后一条事件…"的噪音。

> 报告的价值来自**可信**。一条误报就会让人开始忽略整份报告。

## 7. 踩过的坑（真实记录，别再踩）

**① 残留节点会制造"假故障"** —— `cleanup` 只 kill 了 `ros2 run` 的外壳 pid，
它 fork 出来的节点成了孤儿继续跑。两套节点同时收发时，日志里出现
"456 帧乱序/重复""UDP 帧数翻倍""seq 对不上"，看着像链路坏了，**其实是调试脚本自己造成的**。

> 修法：`setsid` 让每个节点自成进程组、退出时 `kill -INT -<pgid>`；启动前检测残留并清理。
> 教训：**先怀疑自己的调试工具，再怀疑系统**。

**② 报告会误报就会失去信任** —— 干跑一圈，报告第一行是"情报已收敛，但没有发出任何路线"，
其实一切正常（dry_run）。规则必须匹配现实，见 §5 的误报防线。

**③ `aim_guard_node` 里 `self.class_blue` 从未赋值** —— 白名单一旦排除蓝面，
回调里就 `AttributeError` 崩掉（闸门直接失效）。是加日志时补的测试抓出来的。

**④ 测试会污染现场复盘** —— `tests/conftest.py` 把 `AG_LOG_DIR` **强制**指到临时目录。
一开始写的是 `os.environ.setdefault`，结果现场按推荐做法设了 `AG_LOG_DIR` 之后它就失效了：
`python run.py all` 先跑测试，跑一次就往要复盘的那批日志里塞上百个 `node.ready` / `session.begin`，
报告直接读不出重点（实测：18 个文件混在一起，真正的 demo 只有 7 个）。

**⑤ 相机崩了，整条链路是"静默"的** —— `usb_cam` 以 `exit code -6`（SIGABRT）崩掉后，
`det_node` 只会无限刷 `waiting for /image_raw`，我们这边也不会有任何异常，
现场表现永远只是"什么都检测不到"，要确认得去翻节点日志（真机上慢到没法用）。
后来重跑闸门验证，就是被这个打断的 —— 白跑两分钟还得了个看不懂的结论。

> 对策（已做）：`vision_node` 加看门狗，超过 `max_image_gap_s`（默认 5 s）没图像就写
> `vision.stale` 事件并报 error，恢复时再记一条；诊断规则 `no-image`（严重）/ `vision-stale`（注意）；
> 上车前用 `tools/car_camera_check.sh` 单独验相机；
> `car_stage2b_guard_proof.sh` 开头先查 `/image_raw` 帧率，没有就**快速失败**。

**⑥ 单应没标定会被误诊成"链路断了"**（提前修掉，还没在真机上咬人）——
`homography` 仍是全零时，`intel_fusion_node._cell_of` 对每个检测都返回空串，
于是**检测在跑、情报为零**。而复盘报告看到"车端一帧情报都没有"，
会给出 `no-intel` 并让人去查网卡、端口、网段 —— 方向全错，真机上够查半天。

> 对策（已做）：启动时与"有检测却映射不出格号"时各写一条 `homography` 事件；
> 诊断规则 `no-homography`（严重）直接指向 `tools/calib_homography.py`，
> 并且**抑制** `no-intel`（根因已知就别再误导）。

## 8. 性能与体积

| 手段 | 用在哪 | 效果 |
|---|---|---|
| 只在**变化时**记 | `intel.stable` / `referee.state` / `shoot.count` | 45s 内 `intel.stable` 从 88 条降到 1 条 |
| 按周期采样 | `vision.detect`(1s) / `aim.pass` / 心跳(10s) | 30Hz 回调不会写爆磁盘 |
| 同文本去重 | `ros.log` 镜像（2s 窗口） | 每帧都喊的 warning 只留第一条 |
| 轮转 | 单文件 `max_bytes`（默认 8MB）、保留 `keep`（默认 3）份 | 跑一整周也不会写满 `/tmp` |
| 批量 flush | `flush_every`（默认每 1 条；高负载可调大） | 崩溃时最多丢最后几条，不会丢一局 |

## 9. 怎么加一个新事件 / 新规则

```python
# 1) 加事件常量（src/ag_core/ag_core/blackbox.py）
class EV:
    TARGET_LOCKED = "target.locked"

# 2) 节点里写一条（已在 __init__ 里 self.bb = BlackBox.from_params(self)）
self.bb.log(EV.TARGET_LOCKED, cell="D2", dist_px=12, conf=0.91)
if self.bb.throttled("lock", 1.0):     # 高频回调记得限流
    ...

# 3) 报告里给人话（tools/log_report.py 的 describe()，可选，不加也能显示）
# 4) 诊断规则（src/ag_core/ag_core/log_diagnosis.py）
def _rule_target(ev, m):
    ...
#   并加进 RULES 列表
# 5) 补测试（tests/test_blackbox.py）
```

新增事件**不需要**改动任何已有节点，也不需要改 `params.yaml`。
