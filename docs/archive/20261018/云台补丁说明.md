# 云台 C++ 补丁说明（两键开火 + 延迟补偿提前量）

> 生成：2026-10-07 · 目标文件：`src/dzrknn_dataprocess/`
> 状态：**已改本地源码，未编译、未上车**（本地无 ROS 工具链，编译由你在车上执行）
> 设计原则：**默认关闭、可回退、开机横幅可见** —— 参数不开，行为与旧版逐字一致。

---

## 一、为什么必须打这个补丁（旧版两个硬缺口）

| # | 缺口 | 证据 |
|---|---|---|
| ① | **放行门是死线**：`path_executor` 一直在发 `/move_base/stop_signal`，但 C++ 侧**零订阅者** —— "允许开火"从未真正生效，云台一直按自己的判据开火 | `docs/survey_gimbal_fire.md` §10 第 11 条（全文件 grep 无订阅）；我在本轮复核过 |
| ② | **移动靶几乎打不出去**：开火要求"画面静止 ≤1.5 px/帧 + 连续保持 5 帧"，且预判只有 0.5 帧（≈16 ms）而链路实际延迟 **0.5~0.9 s** | 同上 §10 第 ②④ 条；车上 `5_gimbal.log` 正是"确认→允许射击→马上脱离视野"循环 |

**靶的实测参数**（用户给定）：轨道行程 0.70 m、移速 **4 cm/s**、**匀速无停顿**来回。
→ 延迟期目标位移 2.0~3.6 cm，在 0.35 m 距离上约合**一个开火框宽** ⇒ 不补偿必打偏。

## 二、改了什么（逐处）

### 2.1 头文件 `include/dzrknn_dataprocess.h`
1. 新增 `#include "std_msgs/msg/float32.hpp"`；
2. 新增三个订阅成员 + 三个回调声明 + 五个状态字段：
   `sub_fire_gate` / `sub_fire_ready` / `sub_lead_x`、
   `use_external_fire_gate_`(bool, false) / `lead_apply_gain_`(double, 0.0) /
   `external_gate_` / `external_ready_` / `lead_px_`。

### 2.2 实现 `src/dzrknn_dataprocess.cpp`
| 位置 | 改动 |
|---|---|
| 构造函数订阅区 | 三个订阅，**队列深度 1 + BEST_EFFORT**（放行门是"当前状态"不是事件流；积压旧值=按过期许可开火） |
| 新增三个回调 | 只更新状态，**不做决策**；`lead_x` 带范围守卫（非有限值或 \|v\|>400 px 直接归零，防现场标定发出离谱数污染伺服） |
| 开火判定（原 `aim_ready` 处） | 新增 `external_fire_ok = use_external_fire_gate_ && external_gate_ && external_ready_`；`aim_ready_effective = 两键模式 ? external_fire_ok : aim_ready` |
| 开火零点误差 | `aim_err_x = |dx_filt_ + lead_apply_gain_·lead_px_ − laser_offset_x_|` |
| 开火条件 | `in_fire_zone && aim_ready_effective && ammo_ok && cooldown_ok && target_confirmed` |
| 参数声明/读取 | `use_external_fire_gate`(false)、`lead_apply_gain`(0.0，夹到 [0,2]) |
| 开机横幅 | 新增一行"开火权限(★补丁): 两键开火 已启用/已关闭 \| 提前量施加增益 x.xx"（**静默失败是本项目最大的坑**，所以必须一眼可见） |

### 2.3 没有改的部分（刻意保留）
- 扫描/跟踪状态机、PD 伺服、`clampPitchTick`/`clampYawToScan`、类别迟滞、弹药上限、
  冷却、`/aim/status` 上报、手动接管 —— **一律未动**。
- 旧判据（画面静止 / 电机静止）完整保留：`use_external_fire_gate=false` 时就是旧行为。

## 三、两把钥匙怎么分工（避免两个线程抢同一个话题）

| 话题 | 谁发布 | 含义 |
|---|---|---|
| `/aim/fire_gate` | **MissionTask**（新版决策层） | 任务级：车已到站、已停稳、进入 FIRE 阶段 |
| `/aim/fire_ready` | **AimTask**（新版决策层） | 瞄准级：目标确认、**预测落点**在开火框内、冷却与弹药预算允许 |
| `/aim/lead_x` | AimTask | 提前量（px，正 = 目标向右） |

云台补丁：**两者都为 1** 才开火。任一任务误判都不会误开火（这是旧版"单一放行门还是死线"的直接对照）。

## 四、现场整定流程（重要：分步开，别一次全开）

```powershell
# 0) 编译（车上，约 30~40 s）
cd ~/dzrobot && colcon build --packages-select dzrknn_dataprocess && source install/setup.bash
python tools\dzrobot.py --dry-run      # 本地先过门禁（配置+路线），再起栈
```

| 步 | 配置 | 观察 |
|---|---|---|
| 1 | `use_external_fire_gate: false`、`lead_apply_gain: 0.0` | 开机横幅显示"两键开火 **已关闭**" ⇒ 行为与旧版一致（**回退验证**） |
| 2 | `use_external_fire_gate: true`、`lead_apply_gain: 0.0` | 横幅显示"已启用"。到站后看 `5_gimbal.log` 是否出现"★ 收到【开火放行】/【瞄准合格】"；能开火即两键链路通 |
| 3 | `lead_apply_gain: 0.3 → 0.6 → 1.0` | 每次只加一档，记录命中分布（靶在轨道哪个位置、打中/打偏的规律） |
| 4 | 调 `aim.lead_time_s`（新版决策层配置） | `lead_px = v_dx × lead_time_s`。默认 0.35 s 覆盖"视觉流水线 0.26 s + 伺服滞后" |

⚠️ **别同时乱调两个旋钮**：`lead_apply_gain`（云台施加多少）与 `aim.lead_time_s`（提前量算多大）
是两个独立环节 —— 一次只动一个，否则分不清是谁起的作用。

## 六、风险与已知边界

1. **本地无法编译验证**（本机无 ROS 工具链）—— 改动集中在上述清单内，若编译报错，很可能就在这几处；
   报错请把 `colcon build` 输出贴回来，我按行修。
2. **提前量的两个施加点**（云台伺服 vs AimTask 判据）存在耦合：`lead_apply_gain=1.0` 且
   `aim.lead_time_s` 也取全延迟时，会出现"过头"（等效双倍补偿）。所以第 4 步的建议是：
   先固定 `lead_time_s=0.35`，只用 `lead_apply_gain` 从 0 往上找最佳点。
3. `use_external_fire_gate=true` 时**不再要求画面静止** —— 这是有意的（否则移动靶打不出去），
   代价是"云台还在摆"时也可能开火。若现场发现命中率差，把 `aim.fire_box_near/far_px` 收窄
   （例如 14/26 → 10/18）比退回旧判据更有效。
4. 本补丁**不**改弹药/命中闭环，且**不需要**动 `dzjudgment`：新版 `AimTask` 直接消费车端
   已经在发的 `/HpAndHitmsg`（`UInt8MultiArray`，5 字节），在纯 Python 侧解析
   —— 命中判据是 `data[0]`（对方血量）**下降**、弹药取 `data[4]`、硬件发数取 `data[3]`。
   解析器见 [src/dzbrain/dzbrain/io/referee.py](../src/dzbrain/dzbrain/io/referee.py) 的长注释。
   ⚠️ 两个坑：`data[2]`（`Bing_hit`）是**我方被打方位**、不是命中确认，拿它当命中会"挨一发就停火"；
   该话题带 1 Hz 心跳且值与实帧相同，**必须按状态变化计数**，按"收到帧"计数会把命中刷成天文数字。
   契约里登记的 `/referee/hit`、`/referee/ammo`（`Int32`）车端**无生产者**，仅作未来桥接兜底，
   且只在从未收到合法 `/HpAndHitmsg` 帧时才认（防双计）。
