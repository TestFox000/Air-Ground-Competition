【一】场地与地图
--------------------------------------------------------------------------------
1. 场地尺寸：4m × 5m
2. 单元格：35 × 35 cm
3. 网格：14 列（A~N）× 11 行（1~11）
   坐标换算（与 path_executor.block_to_meters 一致）：
       米制：x = (10.5 - (row-1)) * 0.35      y = (13.5 - col) * 0.35
       格制：x = 11.5 - row                   y = 13.5 - col
   ★ 注意：/odom/localization 发布的位置是【格】不是米，别搞混（踩过坑）
4. 地图中间通过【黄色挡板】和【可自粘的白色长条】进行隔离
5. ★ 每局比赛由裁判系统【随机生成】：地雷位置、敌我人员与打击区域位置、
   障碍物位置、桥洞可通行通道 —— 所以每局都要重新填 config/map.yaml


【二】挡板（恒定约束）
--------------------------------------------------------------------------------
6. ★ 无论哪张地图，挡板【必定】位于：
       第 6 行 与 第 7 行 之间，横跨 D ~ N 列
7. 因此上下半场之间【只有 A / B / C 三列】可以穿行，D 列及以东全部封死
   （规划器已把这条写成硬约束；桥洞与靶标不受此限）


【三】地图元素
--------------------------------------------------------------------------------
8. 雷 × 8 ：必须全部压过（踩过才算）
9. 障 × 8 ：不可通行，且【遮挡视线】（射击点规划要查 LOS）
10. 靶     ：★ 始终【只有一个】，固定在名为"靶"的位置
             不需要"单目标上限 / 多目标弹药分配"这类逻辑
11. 通 × 2 ：两个桥洞通道


【四】桥洞规则（★ 最容易做错，重点）
--------------------------------------------------------------------------------
12. ★ 整个 K 列都是桥洞，【每一格都被侧壁隔开】
13. ★ 小车在 K 列【不能撞到壁上】—— 必须【严格水平直穿】，
    任何斜切进 K 列相邻格都会撞壁
    → 保护点必须覆盖【整列 K1~K11】，不能只标两个"通"格
14. ★ 两个通口的穿越顺序（硬要求）：
        第一个（下半场，行 7~11）：L* -> K* -> J*   向西穿
        第二个（上半场，行 1~6 ）：J* -> K* -> L*   向东穿
    （* 为符合条件的任意行号）


【五】射击与云台
--------------------------------------------------------------------------------
15. 定点狙击模式：停车 → 云台扫描 → 锁定 → 底盘静止 → 开火
16. 装备：IMU + 轮速计，【无激光雷达】；脉冲激光云台
17. ★ 全局仅【10 发】弹药
18. ★ 云台扫描：【取消多层俯仰扫描，仅保留水平扫描】
19. ★ 到达最佳射击点时，必须【连续执行两次水平扫描】
    （一轮 = 左一趟 + 右一趟；两轮由循迹主动发两次扫描请求实现）
20. 射击点候选距离：0.60 ~ 0.80 m（理想 0.70 m）
    —— 太近时所需俯角超出云台行程，靶会掉出画面


【六】★ 位姿与扫描范围约束（重要）
--------------------------------------------------------------------------------
21. ★ 云台扫描范围【仅左 90° ~ 右 90°】（相对车头）
22. ★★ 若小车【开过头】，目标会落到扫描范围之外，【将永远扫不到】
    → 规划与循迹都必须避免过冲：
        · 射击点要留出足够减速距离
        · 巡航速度不宜过高（当前 0.15 m/s）
        · 接近射击点/桥洞时提前减速


【七】定位与视觉的分工
--------------------------------------------------------------------------------
23. 地图坐标只用于【粗定位】（0.35m 粒度）
24. 视觉负责【30cm ± 10cm】内的精瞄
25. 里程计是纯轮式死推算 + IMU 航向（serial_reader），会漂移
26. 越界急停：MAP_SAFETY_MARGIN = 0.60 m（信念位姿出界即刹车）


【八】战术原则
--------------------------------------------------------------------------------
27. ★ 宁可漏打，不可卡死 —— 任何等待都必须有超时兜底，绝不堵死路线

【九】★ 射击点选择规则（第五次测试后补充）
--------------------------------------------------------------------------------
28. ★ 射击点必须选在【与靶同行或同列】的格子，优先【同列】（车头正对靶）
    —— 因为云台水平扫描只有 ±90°，同行/同列时云台几乎不用转角，
       对角位置则要大幅旋转，既慢又容易超出扫描行程。
    评分权重：同列 = 0（最优） / 同行 = 0.8 / 对角 = 2.4（最差）
29. ★ 示例（Map-C）：靶区在 F11+G11，最佳射击点是 **G10**（靶的正上方），
    而不是 H11（靶的东侧同行）。G10 车头正对靶、转角最方便。
30. 射击距离放宽回 0.20 ~ 0.45 m（理想 0.35 m）
    —— 因为"正对靶"的一格距离就是 0.35m，这才是最优解；
       之前为了迁就俯角把它拉到 0.60~0.80m 是治标，俯角问题应由
       scan_pitch_offset_deg 解决。

【十】★ 云台与循迹解耦（第六次测试后补充）
--------------------------------------------------------------------------------
31. ★★ 云台【独立持续扫描】，循迹【不得干预】。
    - 任务开始即发 /nav/scan_request data=2（持续扫描），之后再也不发 0
    - 到达射击点时【绝不发 data=1】—— 那会把持续扫描降级成单次，
      扫完就停，正是"循迹限制了云台找目标"的根源
    - 循迹在射击点只负责【停车】，找靶/锁定完全交给云台自己
32. ★ 云台俯仰 scan_pitch_offset_deg：-26°（第六次再下压 12°）
33. ★ 浏览器轨迹必须【区分前进与倒车】：前进=青色实线，倒车=紫色虚线
    （教训：不分色时倒车被画成前进，看起来像车倒着长距离跑）

【十一】★ 排查"参数改了不生效"的完整流程（血泪教训）
--------------------------------------------------------------------------------
34. ★★★ 最高优先级检查：declare_parameter 与 get_parameter 必须成对！
    最隐蔽的 bug：scan_pitch_offset_deg 声明了却【从未 get】进成员变量。
    表现：配置文件改了只更新【ROS 参数服务器】-> ros2 param get 显示新值、
          体检的运行时比对也"一致" -> 但代码用的成员永远是头文件默认值。
    代价：俯仰参数改了三次（-8/-14/-26）画面毫无变化，排查了很久。
    ✅ healthcheck 已加静态检查「参数声明配对」，此类问题以后会被直接拦下。

35. ★ 排查顺序（从"最不可能"到"最可能"，因为静默失败最费时间）：
    ① declare/get 配对      -> healthcheck 静态检查
    ② 参数是否真在运行时设上 -> healthcheck 段3 运行时比对
    ③ 类型是否匹配（double 传了 int）-> 节点会 abort(exit -6)，日志有 InvalidParameterType
    ④ 代码是否被压进注释    -> 全项目扫描 `//.*declare_parameter`
    ⑤ 判据是否被过度放宽    -> 见第 36 条

36. ★★ 「收窄参数」时务必检查依赖它的判据！
    踩过的坑：为了"只做水平扫描"把 scan_pitch_levels 从 [0,-18,-32] 改成 [0.0]，
    却没注意 clampPitchToScan 是按 min/max(levels) 算允许区间的 ——
    min==max 导致区间宽度归零 -> 视觉伺服的俯仰修正全被钳掉 -> 云台僵死。
    现在已加 tracking_pitch_margin_deg（默认 12°）保证区间总有宽度。

37. ★★ 保护类逻辑（如桥洞强制直行）的判据要用【航段索引】，不能用【几何距离】。
    踩过的坑：bridge_blocks 覆盖整列 K1~K11 后，"离最近保护点<2格"这个判据
    在 K 列附近 ±2 格的任何位置都成立 -> 该拐的弯不拐 -> 循迹僵直。
    改成预先算好"保护航段索引集合"后，只有真正穿洞的航段受保护（当前 8/54 根）。

38. ★ 视觉伺服的俯仰修正方向必须与扫描路径一致（都过 pitch_deg_sign_）。
    dy>0（靶在画面下方）-> 需要低头 -> 角度增量为负。旧版写 +eff_y/2，方向相反。

39. ★ IDLE 状态要主动归位（云台回到"正前方+基准俯仰"），不能什么都不做。
    否则云台冻结在最后一次的任意姿态上，改俯仰参数完全看不出变化。

【十二】浏览器操作台（统一调参入口）
--------------------------------------------------------------------------------
40. 打开 http://<板子IP>:8080  —— 界面分三大块：
      左上 云台图传（正方形）  实时画面 + 目标/云台状态 + 弹药计数
      右上 轨迹路线（正方形）  网格地图 + 轨迹(前进青/倒车紫) + 射击点星标 + 当前位置
      下方 参数控制台（长方形）8 个分组、34 个关键参数，滑块 + 数值框直接改

41. ★★ 调参请一律走这个操作台，不要再手改 YAML 或改代码 ★★
      流程：改控件 -> 点该组的「应用改动」-> 自动写回 config/robot.yaml
            -> 自动重启受影响的节点 -> 立即生效。
      只有涉及业务逻辑/代码结构变更时才需要动代码。

42. 为什么改完要重启节点，而不是 ros2 param set 热改：
      节点只在构造函数里 get_parameter 一次，之后不会重新读取。
      （第 34 条那个 scan_pitch_offset_deg 的坑就是这个问题的极端形态）
      所以"写 YAML + 重启该节点"是唯一可靠、行为可预期的路径。

43. 操作台的安全设计（改错了也不会把车搞坏）：
      · 白名单：param_spec.py 里没列的参数网页改不了（那是指挥标定常量）
      · 范围钳制：每项都有 min/max，越界直接拒绝并说明原因
      · 全或无：只要有一项非法就【整体不落盘】，绝不出现"改了一半"
      · 双保险：落盘前备份 .bak，落盘后回读校验 YAML，写坏自动回滚
      · 注释保全：按行精确改写，333 行配置里的 137 行注释一字不动

44. 要新增可调参数：编辑 tools/param_spec.py 加一项（key/label/min/max/unit/hint），
      刷新页面即可，不用改前端也不用改后端。

【十三】浏览器遥控器（调试期手动操作）
--------------------------------------------------------------------------------
45. 打开 8080 页面 -> 下方控制台切到「遥控操作」标签页。
      小车九宫格 D-pad：▲前进 ▼后退 ◀左转 ▶右转 ■刹车，另有速度滑块
      云台九宫格 D-pad：▲上 ▼下 ◀左 ▶右 ⌂回正，实时显示俯仰/水平刻度
      射击：开火按钮（单发，间隔 0.8s）
      键盘：WASD 开车，IK/JL 云台，空格开火

46. ★★ 必须先点「接管控制」★★
      车上同时有两个自动发布者，频率都比遥控高：
        path_executor      20Hz 发 pursuitAngle
        dzrknn_dataprocess 50~100Hz 发 CameMo_Conl
      遥控直接发会与它们【互相打架】，车会抽、云台会甩。
      所以遥控先"接管"：
        接管(on)  -> 两节点收到 /nav/manual_override(1) / /nav/manual_gimbal(1)
                     停止下发，遥控独占控制权
        释放(off) -> 两边恢复，接力无缝
      这两个开关是节点里新加的：path_executor.py 的 _GatedCmdPub
      与 dzrknn_dataprocess.cpp 的 manual_override_。

47. ★★★ 四层失效保护（任何一层单独失效都不会失控）★★★
      ① 按住才动      press-and-hold，松开立刻停；不存在"点一下冲出去"
      ② 数值钳制      速度 ≤0.30m/s、转向 ≤40°、云台刻度夹在安全包络内
      ③ 接管看门狗    接管中 2 秒没收到遥控指令 -> 自动刹车并释放接管
                      （防浏览器崩溃/网络断/人走开）
      ④ 底盘看门狗    dzactuator 自身 1.0s 无指令强制停车（既有机制，最底层）

48. ★ 紧急停止是【粘性】的，只有显式「释放控制」才解除。
      踩过的坑：最初实现只做"静默+刹车"没记独立状态，
      结果 2 秒后被接管看门狗判为"失联"而释放，自动模式立刻接管、
      车按原路线继续跑 —— 那不是急停，是"停了 2 秒"。
      现在 _estopped 一旦置位：看门狗不释放、持续补发零速度。
      代价是浏览器崩了会一直停着 —— 但"停着"本来就是最安全的失败方向。

49. 转向符号约定：path_executor 里 steer_deg > 0 = 左转（下位机 TargetAngle > 60）。
      若实车实测左右反了，改 cam_viewer.html 里的 RC_STEER_LEFT_SIGN = -1 即可。

50. 遥控器实现文件：
      tools/rc_control.py   服务端：发布/仲裁/看门狗
      tools/cam_viewer.py   /api/rc* 六个接口
      tools/cam_viewer.html 遥控界面与按住即动逻辑

【十五】★★★ 开火链路：为什么"开火键没反应"（两个真 bug）★★★
--------------------------------------------------------------------------------
56. 【bug 1】射击驱动 dzjudgment 根本没被启动
      参考《案例9：云台控制与射击》：dzshooting.launch.py 必须【同时】启动两个节点
          dzrknn_dataprocess（云台控制）
          dzjudgment（上位机与车载裁判系统通讯）← 真正的射击驱动
      但 start_all.sh 只起了前者，于是
          ros2 topic info /LaserShot_Command
          → Publisher count: 3   Subscription count: 0
      云台算得好好的开火指令，全发进了【空话题】—— 激光永远不亮，且零报错。
      ✅ 已修：start_all.sh 新增第 6 步「射击驱动」→ ros2 launch dzjudgment judgment.launch.py
              串口参数也进了配置中心（/dzjudgment 段，/dev/dzjudgment -> ttyACM1）

57. 【bug 2】射击驱动卡在串口死循环里，把订阅回调全废了
      judgment.cpp 的 recvESP32Info() 旧写法是 while (true && rclcpp::ok()) 死等完整帧，
      只在 header1==0xB5 && header2==0x5B 且帧体读齐时才 break。
      串口安静时（裁判板没上电/线松/就是没数据）ser.available() 恒为 0，
      header1/header2 还是【未初始化】的栈变量，循环永不 break，于是：
          · CPU 跑满（实测 102%，状态 Rl）
          · run() 的 10Hz 循环被彻底卡死 → rclcpp::spin_some() 再不被调用
            → 所有订阅回调失效 → 开火指令收不到
      而 ros2 topic info 依然显示 Subscription count: 1，看起来完全正常，极具迷惑性。
      ✅ 已修：改成【有界 + 非阻塞】—— 没数据立刻返回，每次最多处理 8 帧。
              修后 CPU 102% → 4%，状态 Rl → Sl。

58. ★★ 排查"开火没反应"的标准动作（按顺序，30 秒定位）★★
      ① ros2 topic info /LaserShot_Command
           Subscription count = 0  → dzjudgment 没起（bug 1），
                                     ./start_all.sh start 或 tools/restart_node.sh judgment
      ② ps -o pid,stat,pcpu,cmd -C dzjudgment
           CPU 接近 100% / 状态 Rl → 卡在串口死循环（bug 2）
           （正常应是几个百分点、状态 Sl）
      ③ grep -a "开火指令已下发" ~/robot_logs/6_judgment.log
           有 → 指令链路完全 OK，问题在硬件侧（激光模块/裁判板/连线）
           没有 → 指令没发出去，查云台节点或遥控器
