## 3. 三个缺陷（按影响排序）

### D1 车端上报 phase 用的是 MissionTask，不是 StepLoop
- 证据：机上收到的 `CAR phase 'DRIVE' -> 'FINISH' -> 'IDLE'`；而车端日志打的是 `P_CAR_STATE phase=SEGMENT_DONE`。
- 根因：`tasks/drone.py::_maybe_send_car_state` 用 `P_MISSION_PHASE`（IDLE/DRIVE/FINISH），StepLoop 的 `P_CAR_STATE` 只写黑板不上链路。
- 后果：机侧 `on_segment_done` 判据（DRIVE→IDLE）永不触发 → 不推进检查点。
- 现场处置：临时把机上判据扩成 `('IDLE','','FINISH')` 才继续跑。

### D2 到达判据与信念不一致（差一格就死锁）
- 证据：`■ 段 305 完成：停在 E5（停站 path / belief E4 ...）`；机侧 `segment done at E4 (target was E5) — keep target`。
- 后果：车进入 WAIT_INFO，机侧保留旧 target 不再发新版本 → 整条循环停在原地。
- 关联：T34 也报过同类 `belief 偏 1 格`（C3→B3、E3→E4），属**定位/投影**问题而非步进逻辑。

### D3 射击停站打不出去
- 证据：F5 停站 6.10 s 内 `发0/中0 弹9`；云台日志有 `类别已锁定 locked_cls=1`，同时 `预测落点在开火框外`、`类别未确认(还没连续 N 帧)` 交替出现。
- 结论：不是"没检测到"，而是**瞄准合格判据（fire_ready）与开火框/提前量判定**没同时满足；需要单独立卡，不要在步进循环里调。
