## 0. 一句话结论

你要的「无人机固定轨迹 + 动态规划-循迹循环」，底层**已经存在 80%**：车端 `mission.py` 已经实现了

**真正缺的是两件事**：① 无人机航线没有按「桥洞优先/短程/少拐弯」优化，且情报是「一次算完」而非
「增量交付」；② 车端改道是「单次」（`bridge_reroute_max` 默认 1），不是你要的「循环」。

所以本方案 = 把「单次改道」扩成「情报批次驱动的滚动重规划」+ 把「全覆盖 U 形航线」改成「桥洞优先短程航线」。

1. **航线非「信息优先」**：现 U 形是「全覆盖」，不显式保证桥洞情报最早拿到；且情报在 `intelAt` 里**一次性算完**，没有「checkpoint 增量交付」的概念。

## 2. 需求 1：无人机固定轨迹（三原则）

### 2.1 三原则形式化

| 原则 | 你的原话 | 量化口径 |
|---|---|---|
| 最短 | 路径尽可能短 | 航线总格数 / 总飞行距离最小 |
| 拐弯最小 | 拐弯幅度尽量小 | 90° 拐弯次数最少；连续直行段尽量长 |
| 信息最快 | 获取信息速度越快越好 | **高价值信息（桥洞）的首次覆盖时间最小** |

### 2.2 关键洞察：信息价值分层

无人机三路情报的**价值不对称**：

| 情报 | 是否改路线 | 价值 |
|---|---|---|
| `bridge_passable`（桥洞） | **是**（决定穿哪个洞，改路线拓扑） | **最高，必须最早拿** |
| `target_zone` / `field_verify`（靶/雷/障） | **否**（只核对差异，地图里已有静态位置） | 低（核对层） |

→ 结论：**航线应「桥洞绝对优先」**，先以最短路径覆盖上下半场两个 K 列桥洞，再补雷/障/靶核对。
（现 `scanPlan` 恰好起飞列 N8 在东侧、西扫会先经过 K 列，但它是「顺路经过」而非「显式优先」，且没有 checkpoint 交付。）

### 2.3 优化后航线（桥洞优先 + 短程）

```
N8 起飞
  │  ① 最短下行到下半场 K 列桥洞行（K7~K11 一带）        ← 交付 checkpoint①
  │  ② 该行东扫，精确覆盖下半场桥洞格                     ← 拿 lower 桥洞
  │  ③ 直行/少拐上行到上半场 K 列桥洞行（K1~K6 一带）      ← 交付 checkpoint②
  │  ④ 该行扫，精确覆盖上半场桥洞格                       ← 拿 upper 桥洞
  │  ⑤ 剩余雷/障/靶核对扫掠（可局部、非全覆盖）           ← 交付 checkpoint③④…
  ▼
M2 降落（情报封口）
```

- 拐弯数目标：从现 6 段（6 个 90°）压到 **4 段以内**（起飞列→桥洞列→桥洞列→降落列）。
- 桥洞「首次覆盖时间」目标：**起飞后 ≤3 拍**拿到第一个桥洞（现 U 形要到第 2 段才顺路碰到 K 列）。

## 3. 需求 2：动态规划-循迹循环

### 3.1 与现状的关键差异（说清楚，避免误解）

| | 现 t32（单次改道） | 你要的循环 |
|---|---|---|
| 发车时机 | 车**先按默认出发**，途中决策点改 1 次 | 车**等第一批情报后首规划**再出发 |
| 改道次数 | ≤ 1 次 | **多批次、循环** |
| 改道类型 | 只「换桥洞」 | 桥洞（改拓扑）+ 雷障靶（核对/纠错） |
| 仿真 | 车跑默认路线，改道只出取证 | 车随情报**真的重规划再循迹** |

### 3.2 统一后的设计：情报批次驱动的滚动重规划

把「起点等待」（t20）+「决策点改道」（t32）统一成一个循环：

```
      无人机                             车端 Mission                      规划器
        │  checkpoint① 到达                │                                │
        │ ──bridge_passable{lower:K9}──▶   │  收到情报批次                   │
        │                                  │  ──首次规划(cross_lower=K9)──▶  │
        │                                  │  ◀──── tokens ───────────────  │
        │                                  │  安装路线 → 出发循迹            │
        │  checkpoint② 到达                │                                │
        │ ──bridge_passable{upper:K5}──▶   │  收到新批次                     │
        │                                  │  ──重规划(cross_upper=K5)──▶   │
        │                                  │  ◀──── tokens ───────────────  │
        │                                  │  _install_route(keep_progress)  │
        │                                  │  → 保留进度继续循迹             │
        │  checkpoint③ 雷障靶核对          │                                │
        │ ──field_verify/target_zone──▶    │  核对（差异→告警，不改路线）    │
        │  …（循环直到）                    │                                │
        │  M2 降落 = 情报封口               │  最终路线冻结，跑到 N5          │
```

### 3.3 时序流程（可执行的完整流程）

1. **预热**：无人机起飞，车端 `DroneTask` 在线、`MissionTask` 进入等待（`bridge_info_wait_s` 窗口，沿用 t20 判据：有链路 + 在线 + 已有半场新鲜情报才等）。
2. **批次①（lower 桥洞）**：无人机最短路径覆盖下半场 K 桥洞，`bridge_passable{lower}` 到达 → 车**首次规划**（`cross_lower=情报格`，`cross_upper` 暂用默认）→ 出发。
3. **批次②（upper 桥洞）**：无人机覆盖上半场 K 桥洞，`bridge_passable{upper}` 到达 → 车**重规划**（两半场桥洞都定）→ `_install_route(keep_progress=True)` 保留进度续走。
4. **批次③+（雷/障/靶核对）**：无人机补扫，`field_verify`/`target_zone` 到达 → 车**核对**：一致则静默；不一致进 `field_diff` 告警（**不改路线**，除非裁决为「地图过期需纠正」）。
5. **封口**：无人机 M2 降落、心跳停止 → 车不再改道，路线冻结，跑到 N5 完赛。
6. **全程安全闸**：任何批次缺失/过期/离线 → 走默认格；重规划上限 + 重规划窗口（见 §4）保证「到点必走、越接近终点越不改」。

## 4. 关键安全设计（重规划的最大风险）

循环重规划的**真正难点不是「能不能规划」，而是「车已经在走，改了会不会出事故」**。四道闸：

1. **进度保留**：`_install_route(keep_progress=True)` 已实现（t32）——重装路线保留 `_passed/_next_wp/_route_s/P_ROUTE_INDEX`，**绝不回车起点**。
2. **只允许「前向」改**：新路线必须与「车当前位置 + 已过航点」兼容；改道只动「未来的穿洞三连」，已过段不可变。形状不符/校验不过 → 原样保留旧路线（现有 `_apply_intel_to_tokens` 语义）。
3. **重规划窗口（价值递减）**：车越过该半场洞口（决策点已过）后，该半场情报**不再触发改道**，只进遥测（现有 `_decision_point` + `_passed` 判据）。
4. **上限 + 预算保护**：重规划次数 ≤ `bridge_reroute_max`（需从 1 放宽到 2~3）；每次 HOLD 的 `cap = min(bridge_wait_max_s, 预算余量)`，**到点必发车**（现有 t32 ④）。

## 6. 优化建议（按价值排序）

1. **桥洞情报「首次覆盖」才是真指标**：不要追求「全覆盖更快」，桥洞早 1 拍 = 车早 1 拍规划 = 早 1 拍出发，比雷障靶核对快 10 拍更值。
2. **重规划上限建议 2（不是无限）**：桥洞只有上下两个，「换洞」最多 2 次有意义；雷障靶核对不改路线。设为 2~3 即可，无限会引入「情报抖动反复改线」风险。
3. **情报过期 `info_stale_s=30s` 与循环节奏要匹配**：无人机从起飞到封口若 > 30s，早期桥洞情报会过期回落默认 → 建议按「无人机完整航线耗时」反推该值，或改为「封口前不因时间过期而降级」。
4. **先仿真台全绿再上车**：循环重规划的竞态（车正在走 vs 新路线到达）必须在仿真里跑通，别直接上车赌。
5. **保留「默认兜底」不动**：无论循环怎么改，无人机全哑/离线时车必须按 `cross_*_default` 走完——这条「宁可漏打不可卡死」的铁律不能破。

### 7.1 「全量重规划」在仿真台的语义（重要，防止误解）

雷/障/靶的 truth 与车端本地地图**同源**（都读 `config/map.yaml`），所以仿真台里只有**页面改了 field 覆盖**时雷障靶才产生差异。因此：
- 全量重规划的**触发** = 每个 checkpoint 交付的情报批次（桥洞 + 顺路覆盖的雷障靶）；
- 车端「完赛路线」= 情报到达后的**最终全量重规划路线**（不是先验默认路线）；
- 「动态过程」= 时间线 + 每个 checkpoint 的 `plan_route` 取证（展示路线如何随情报滚动更新）。

### 7.2 航线口径（T1 定稿）

桥洞优先短程航线（3 直线段 / 2 拐弯，满足「4 段以内」）：

```
N8 起飞
  └─ 段① 横飞 N8→K8（起飞行）        checkpoint lower：K8 视场已覆盖 K9
  └─ 段② 竖飞 K8→K2（K 列，途经 K5）  checkpoint upper：途经 K5 时覆盖 K5
  └─ 段③ 横飞 K2→M2（降落行）        checkpoint land：封口
```

- **桥洞绝对优先**：两个桥洞情报在段①②（起飞后最短路径）就拿到，触发车首次规划/重规划。
- **雷点拐弯区分**：段③ 是降落封口段，雷/障/靶只做「顺路覆盖」（3×3 视场扫到的才核对），**不为了扫雷点而在西半场拐弯**；扫不到的雷点 = missing，车端按 `map.yaml` 静态默认走（宁可漏核对，不可卡死）。
- 对比旧 U 形（6 段全覆盖）：本航线桥洞「首次覆盖时间」从第 2 段提前到**第 1 段**，且总拐弯 6→2。
