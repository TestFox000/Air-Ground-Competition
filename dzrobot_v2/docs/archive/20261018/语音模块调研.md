## 0. 一句话结论

**语音由底盘 STM32（DZVCU）外挂的独立**天问 ASRPRO 2M** 语音模块发声（USART6@9600 单字节指令 → 模块内 `switch(Rec)` → `play_audio(预录ID)`），播报内容固化在模块自身 flash，上位机/STM32 全链路只透传编号、无任何映射表**——所以"换播报文本/换音色"**不能靠改 ROS 代码，需重烧语音模块**；★ 二次取证已确认**免拆机可烧**（模块自带外露 USB 烧录口，天问 Block 已在车上），代价是需 Windows + 天问账号联网 + **从零新建工程**（车上无工程存档，且直接烧会覆盖厂商预置播报，须先建 ID 对照表）。"触发哪条已有语音"软件层完全可配（A 档）；RK3588 侧 ES8388 是现成的旁路 TTS 扩展点（C 档）。

## 1. 发声链路全貌（两条路，互不相干）

### 1.1 底盘侧（现役唯一在用的发声路）

```
ROS /voice_switch(UInt8)
  → dzactuator.cpp:1163 订阅（"voice_switch"，KeepLast(1) best_effort）
  → dzactuator.cpp:243  moveBaseControl.VoiceSwitch = msg->data   ← 无任何映射表
  → dzactuator.cpp:434  buf[21] = VoiceSwitch                      ← 23 字节下行帧第 21 字节
  → /dev/dzactuator(ttyACM0) @115200 → STM32F407 (DZVCU)
STM32:
  → USART3 ISR (usartx.c:872) 收帧：0xa5 0x5a 帧头 → Urxbuf[k]=payload[k] 存 21 字节（:890-897）
  → control.c:162  memcpy(rxbuf, Urxbuf, 20)  → rxbuf[19] = buf[21] = VoiceSwitch
  → control.c:254  Sync_Control(): VoiceSwitch = rxbuf[19]（20Hz 主循环持续装载）
  → usartx.c:34    数据任务 20Hz: USART6_SEND()
  → usartx.c:403   if (VoiceSwitch != lastVoiceSwitch)  ← 变化沿才发
  → usartx.c:405   usart6_send(VoiceSwitch)  ← USART6->DR 单字节裸发，无帧头无校验（:1119-1123）
  → USART6 (PC6 TX/PC7 RX) @9600bps（system.c:174: uart6_init(9600)）
  → 【外部独立语音模块】收到单字节编号 → 播放对应预录音频 → 喇叭
```

**关键判词**：STM32 固件里 voice 相关代码只有"接收转发"逻辑，**没有任何 ID→文本/音频映射**：
- 全固件 grep `voice|语音|wtv|jq8|syn6|mp3` 语义行零命中（仅变量名 VoiceSwitch/Voice_RPI/usart6_send 注释"发送数据给语音模块" usartx.c:396）。
- 语音内容必然固化在**语音模块自己的 flash**，STM32 只是"报号器"。

证据（车端=本地同一文件，MD5 见附录 A）：
- `HARDWARE/usartx.c:399-407`（USART6_SEND 变化沿发送）
- `HARDWARE/usartx.c:1119-1123`（usart6_send 单字节直写 DR）
- `DZCONTROL/system.c:174`（`uart6_init(9600)` 波特率）
- `HARDWARE/usartx.c:34` 注释原文：`USART6_SEND(); //Serial port 6 sends data //串口6发送给语音模块`（乱码为 GBK 注释）

## 2. VoiceSwitch 字段语义与串口协议位置

### 2.1 byte21 在下行帧中的位置

`dzactuator.cpp:391-440`（sendCarInfoKernel，50Hz 主循环调用）：
```cpp
unsigned char buf[23] = {0};
buf[0] = 0xa5; buf[1] = 0x5a; buf[2] = 20;   // 帧头 + len
buf[3..4] = TargetAngle*10 (int16 BE)
buf[5]    = SpeedDirection
buf[6]    = TargetSpeed
buf[7]    = LaserGunSwitch        ← rxbuf[5]
buf[8..17]= 云台 Position_0/1, Speed_0/1 (int16 BE), Time_0/1  ← rxbuf[14]=buf[16]=Time_0
buf[18]   = Fun; buf[19] = Orin_ID; buf[20] = Set_ID_Num
buf[21]   = VoiceSwitch           ★
buf[22]   = sum(buf[2..21])       // BCC 累加和（代码注释写 buf[2..18]，实算到 21）
```

STM32 侧对位验证（帧尾→数组完全咬合）：
- USART3 ISR（usartx.c:883-897）：检测 `0x5a 0xa5` 序列（注意 STM32 收到的头两字节顺序）→ `Urxbuf[count]=temp`，count==21 帧完 + XOR 校验（usartx.c:752-760 同款逻辑）
- `control.c:162`：`memcpy(rxbuf, Urxbuf, 20)` → **rxbuf[k] = Urxbuf[k] = buf[k+2]**
- `control.c:228-229`：`LaserGunSwitch = rxbuf[5]`（= buf[7] ✓）、`VoiceSwitch = rxbuf[19]`（= buf[21] ✓）
- `control.c:265`：`Time[0] = rxbuf[14]`（= buf[16] ✓）

三处独立字段全部对位无误，rxbuf[19]↔buf[21] 链路坐实。

### 2.2 字段语义

`VoiceSwitch` = **要播放的预录音频编号（u8）**。上位机直接把编号塞进帧；STM32 检测到变化就把这一个字节原样发往语音模块；模块播放对应段。
`include/dzactuator.h:174: int VoiceSwitch; // 预留位` —— 上层作者注释为"预留位"，佐证**没有人知道 ID→内容对照**（另见 §3）。

## 4. 节流闸门与 switchvoice() 抢权行为（接包前必读）

### 4.1 2 秒节流

`dzactuator.cpp:303-309` 的 2 秒窗口**只节流 switchvoice 自身的覆盖写**：它仅在 `voice_nums[0]`（vehicle_state）变化时关闭闸门（`:296-300`），而 `/voice_switch` 回调（`:243`）**不经闸门、立即写入**。
**影响（更正后）**：连续经 /voice_switch 发不同 ID 都会各自到达模块；`test_voice.sh` 的 3s 间隔主要是给人耳留分辨时间，不是在绕闸门。真正伤自定义播报的是 §4.2 的每拍覆盖。

### 4.2 抢权路径（自动跑时会顶掉自定义播报）

50Hz 主循环每拍调用 `switchvoice()`（dzactuator.cpp:1330）：
- `:296` 若 `voice_nums[0]`（话题 `vehicle_state`）变化 → `voice_numID = voice_nums[0]`
- `:313` 每 2 秒闸门到点后：**`moveBaseControl.VoiceSwitch = voice_numID` 无条件覆盖**

而 `voice_numID` 的来源（★ 队长复核更正）：
- **不是 cmd_vel**。`voice_numID` 在全文件只有两处赋值：`:209`（=1）与 `:238`（=15），二者都位于 **`callback_logi_control`**（`:188` 起、`:239` 结束）内，其订阅的话题是 **`logicontrol`（`:1162`）**。`callback_cmd_vel_angle`（`:59`–`:111`，cmd_vel `:1160` 绑定）与 `callback_movebase_angle`（`:112`–`:186`，pursuitAngle `:1161` 绑定）**都不碰 `voice_numID`**。
- `logicontrol` 现役**零发布者**（全 src grep 仅命中 dzactuator 自身的订阅与头文件声明；10-03 清理日志已记录唯一发布者 path_planner.py 为死代码并删除）→ 现网 `:209/:238` 永不执行，`voice_numID` 恒保持初始值 **0**（`dzactuator.h:304`）。
- `vehicle_state`/`vehicle_Drivestate`（`:1168-1169` → voice_nums[0/1]）同样零发布者 → `voice_nums` 恒 0（`:1114-1116` 显式初始化）。`voice_numID` 有类内初始化 `=0`（`dzactuator.h:304`），`:296-300` 锁存分支大概率不触发（`lastvoice_num_1` 无初始化器，值不确定=UB；若为 0 则不进分支），**但无论触发与否，`voice_numID` 恒为 0**，`:313` 覆盖目标不变。`can_changevoice` 类内 `=true`（`:306`），故**启动后第一次覆盖立即发生**（不等 2 秒）。

**净效果（队长二次复核修正）**：`switchvoice()` 每拍（50Hz）运行，但 `:313` 的覆盖写**受 2 秒闸门约束**（`:306` 判 `elapsed>2.0` 才置 `can_changevoice=true`，写完 `:314` 立即重置 `change_start_time`）→ **覆盖周期是 2 秒，不是每拍**。所以通过 `/voice_switch` 发 N≠0：N **立即写入并到达模块**（`:243` 不经闸门），**存活 0~2 秒**（取决于落在 2 秒周期的哪个相位），随后被写回 0，在固件 `usartx.c:403` 产生**第二个变化沿**，模块收到 **N→0 字节对（间隔 ≤2 s）**。不是"被 15 顶掉"，而是"最多 2 秒后被 0 顶掉"。
> ⚠️ 我上一版写的"≤20ms 后就被写回 0"是**我的错误**：漏看了 `:314` 每次覆盖后重置时钟。已改正。最坏情形（N 恰好落在闸门开启瞬间）才会近似立即被顶。
附带发现：dzactuator 以 **50Hz** 改写 VoiceSwitch，STM32 侧 `USART6_SEND()` 以 **20Hz** 采样（`usartx.c:34`）→ **快速翻转存在采样丢失**，中间值可能整段被跳过（如 dzrknn 30Hz 连发 111 与 0 交替时，实际到达模块的字节序列不可预测）。
`moveBaseControl.VoiceSwitch = 111` 刷屏 141397 次是 **dzrknn 每帧发布**（无边沿去重）被 `:245` 打印的计数，**不是覆盖机制的证据**；0 号覆盖因与初值相同、不产生变化沿，故日志里看不到。

> 处置方向（更正后）：① 删掉/条件化 `:313` 的无条件覆盖（例如仅在 `voice_nums[0]` 变化时才写），或让 `switchvoice` 在收到外部 `/voice_switch` 后让路一段时间；② 若要求"必响"，还需在 dzrknn 的 111 发布处加去重，或在固件侧把采样率与写入率对齐。**均属车端源码改动，超出本次只读权限，列为后续工程项、需用户决策。**
> ⚠️ 措辞纪律：「N→0 使模块**连播两条**（N + 0 对应项）」是**推断、非取证**。已证实的仅是固件侧出现 N→0 第二个变化沿、两个字节都会经 `usart6_send` 发出。0 号在模块侧播不播、播什么、会不会打断 N，全部**未核实**（ID 对照表本身几乎全空白，见 §3）。唯一途径 = 实机试音。
> 复核新增（队长补，代码可证）：`usartx.c:401` 为 `static u8 lastVoiceSwitch = 0xFF;`，而 dzactuator 启动即 `memset(&moveBaseControl, 0, …)`（`:1106`）使 `buf[21]`=0，经 `control.c` `Sync_Control()` 装载 → 首拍 `VoiceSwitch`(0) ≠ `lastVoiceSwitch`(0xFF)，**每次上电固件都会向语音模块发出一个 0x00 字节**（该变化沿与任何 ROS 节点是否发过语音无关）。若现场观察到"一开机就有一句播报"，源头在此；播什么仍取决于模块 0 号段（未核实）。
> 补充：N→0 是否打断 N 的播报，取决于语音模块行为（**未核实**，需实机试音确认）。

### 4.3 回读/ACK 通道（部分存在，无人消费）

- STM32 回传帧（USART3_SEND，usartx.c:145）`Send_Data.buffer[32] = Voice_RPI`；
- `Voice_RPI`（usartx.c:978-988 USART6_IRQHandler）：**USART6 每收到 1 字节就翻转一次**的电平标志——即"语音模块方向有数据往来"的活动指示，**不是**"某 ID 播放成功"的确认；
- dzactuator.cpp:1026-1036 `detect_toggle(rx32)` 检测变化沿 → 发布 `wakeup_signal`(Int32=1)（:1155）；
- **`wakeup_signal` 全项目零订阅者**（grep 仅 dzactuator 自己发布）→ 回读链路存在但无人使用。

**结论**：byte21 发出后，能从 rx32 感知"模块方向有动静"（若需启用需自行订阅 wakeup_signal），但**无法确认具体播放了哪条、是否播完**。验证"真的播出来了"目前只能靠人耳。

## 5. 自定义语音可行性：三档结论

### A 档【直接可改】——软件层换"触发时机/选哪条已有语音"，不能换内容

- **能做**：改 `config/robot.yaml` 的 `finish_voice_id`（当前 0=不播，robot.yaml:364）→ 循迹跑完全程时播指定 ID（`path_executor.py:1418-1423`，默认值 `:186`，配置读取 `:451-452`；dzbrain 侧对应 `mission.finish_voice_id`，`config.py:237`）；或在任意 ROS 端 `ros2 topic pub /voice_switch std_msgs/msg/UInt8 "{data: N}"`（dzbrain 契约已备好：`io/contract.py:91`、`ros_io.py:436 publish_voice()`）。
- **限制**：① 播报内容只能是模块 flash 里已预录的段；② `/voice_switch` 写入**不经 2s 闸门、可立即生效**（§4.1 更正），但会被 `switchvoice()` 在下一拍覆盖成 **0**（§4.2 更正），且 N→0 是否打断播报未核实。要稳定播"到点/射击完成/SAFE_STOP"仍需先处置该覆盖（车端源码改动）。
- **影响面**：只改配置则零代码风险；改 dzactuator 抢权需 colcon build + 上车部署。
- **代价**：几乎为零，今天就能试音选 ID。

### B 档【需刷固件】——换语音内容（文本/音色/自录）的唯一原生途径

语音内容固化在**语音模块 flash**，要换内容必须重烧模块固件。证据链表明这**可行且工具齐全**：
- 车端附件已有官方 IDE：`附加资源/3、SmartMaster相关上位机/语音模块/天问Block 2025 春季正式版.zip`（807MB）+ 使用说明视频；
- 天问系列（ASRPRO 等）经 USB 连 Windows 上的天问Block 即可：改识别词/回复文本、**替换为自己的 WAV 录音**、调整串口指令表后一键烧录（外部资料：CSDN 多篇 ASRPRO 教程，含"替换播报音文件为自录 WAV"的明确操作路径）；
- 另有 `附加资源/…/DZVCU烧录/`（FlyMcu2188.exe + 烧录配置示意图 + fly新版本duzhong.zip）——那是 **STM32 DZVCU 固件**的烧录工具链，与语音模块是两条独立的刷写线。

**两条刷写线对比**：

| | 语音模块重烧（推荐） | STM32 DZVCU 重刷（不推荐） |
|---|---|---|
| 工具 | 天问Block（已在车上） | FlyMcu2188 + 串口 ISP（已在车上） |
| 源码 | IDE 图形化生成，无需现有源码 | DZVCU 源码在（本地/车端 MD5 一致） |
| 风险 | **低**：独立模块，刷坏不影响行车，可再刷 | **高**：同一芯片管电机/云台/遥控，刷错=车瘫 |
| 收益 | 换文本/自录音频/改协议全解锁 | 对语音无额外收益（ID 已透传到位） |
| 需要 | **USB 线 + Windows + 天问账号（联网）**；★免拆机（模块自带外露 USB 烧录口，§1.4） | ST-Link/USB-TTL、Keil 工程 |

- **影响面**：语音模块重烧不碰 ROS/STM32，行车零风险；DZVCU 重刷动底盘核心，**超出软件工作区，必须由你决定并现场执行**。
- **前置条件（已较初版大幅降低）**：型号已确认为 ASRPRO 2M、烧录路径已确认免拆机 → 只剩 ①Windows 电脑 + USB 线 ②天问账号（"生成模块"步骤强制登录联网）③**从零新建工程**（车上无 `.tw/.twb` 存档，教程帧里的 `Senerity的_示例代码` 是厂商示例、非本车实际工程，不能直接改烧）。
- ~~若模块不是天问系而是 JQ8900/WT5880 类~~ → **已排除**（§1.4 确认 ASRPRO）。
- ⚠️ **重烧前必须先建好 ID→文本对照表**：现车模块的实际工程内容未知，若直接烧新工程会**覆盖掉厂商预置的全部播报**（含 111/15 这些现役在用的 ID）。稳妥做法：先用天问 Block 尝试**读回**模块现有工程，或先用试音把在用的几个 ID 记全，再决定重烧映射。

### C 档【走旁路】——RK3588 Linux 侧 TTS，零固件风险

card2（ES8388，Headphone 输出口）现成空闲，PCM 当前 `closed`：
- **预录 wav 方案**：本地 TTS 生成 wav（任意工具）→ scp 到车 → `aplay -D hw:2,0 xxx.wav`。零安装（aplay 已在）、零固件风险；缺点：每次加词要传文件，且需接喇叭到 card2 输出口（**车体是否有喇叭接在此路：未核实**）。
- **在线 TTS 方案**：`apt install espeak-ng`（秒装，机械音中文）或 piper（60MB 级中文模型，RK3588 算力可实时，音质自然）→ 脚本：文本 → wav → aplay。需用户同意 apt install（涉网，改变车端环境）。
- **成本对比**：C 档当天可用但要接喇叭+可能装包；B 档原生喇叭位置/音量最优、能换真语音，但要拆机+Windows 烧一次。
- **混合推荐**：播报类内容（到点/射击完成/SAFE_STOP）数量少且固定 → **B 档一次烧录最省事**；临时/调试播报或频繁变文案 → C 档旁路。

### 最终推荐（按顺序）

1. ~~今天试音~~ → **已于 2026-10-11 21:10 实机执行**（ID 1/5/15/111/0，见 §7）。**待人工回填**：每个 ID 实际听到了什么、0 是否打断前一条。
2. **要自定义语音内容（B 档）**：路径已确认**免拆机**——Windows + 天问 Block（车上 zip）+ USB 线接模块烧录口 + 天问账号联网。★ 但必须先做两件事：① 用 §7 试音结果建立 ID→文本对照表，② 确认能否读回模块现有工程——否则新工程会覆盖厂商预置播报（含现役 111/15）。
3. **不碰固件的备选**：card2 接小喇叭跑 piper/espeak-ng（C 档）。
4. **DZVCU 固件不要动**（无语音收益、风险最高）。
5. **若要"到点必响"**：处置 §4.2 的 0 号覆盖（本地 C++ 与车端 md5 一致，可本地改 + `colcon build` + install 树对账后上车）。
