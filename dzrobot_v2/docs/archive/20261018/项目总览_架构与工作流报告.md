## 0. 一分钟认识这个项目

一台在 **0.35 m 格距网格场地**上比赛的智能车：从 N10 出发，避雷、穿过 K 列桥洞、到靶位停站用云台激光射击、倒车调头、再穿洞、最终到 N5 终点；同时通过 ROS 话题与一架无人机交换情报（桥洞、靶区、雷障核对）。

- **硬件**：Orange Pi 5（RK3588S）· Ubuntu 22.04 · ROS Humble · Python 3.10 · RKNN 视觉加速 · 云台+激光发射器 · 裁判串口。
- **软件核心**：`src/dzbrain/`——一套**纯 Python 决策层**，本项目从旧血统（10-03 版）重构而来的主角；周边 4 个 C++ 包（底盘驱动、云台自瞄、裁判串口、检测模型）是"硬件层"，多数沿用上游代码。
- **协作模式**：Windows 本地工作区是**唯一真源**，车端 `~/dzrobot` 只读运行；改动经"测试 → 仿真 → 部署脚本"三道门禁后，由人类执行最终上车。
- **当前阶段**：v2.2。新核心已实车完整跑通过一次全程（16.45 m FINISH），同时多条尾巴未收拢：里程计复标、射击命中率、云台 C++ 补丁、PIVOT 到达修复上车验证、无人机链路。
- **工具生态**：DSH 插件（`dsh-plugin-dzrobot-ssh`）把车的 SSH 终端/文件/VNC 搬进开发 GUI；离线仿真器可在本机无车复现全程并输出指标表。

## 1. 项目背景：这个系统要赢什么

### 1.1 场地与任务语义

场地 14 列（A~N）× 11 行，每格 0.35 m。要素：**雷**（必须压过，8 个）、**障**（不可通行，8 个）、**桥洞**（K 列仅 K1/K7 通）、**靶**（F11/G11 打击区）、**隔板**（第 6/7 行之间 D→N 无缺口，不许跨越）、起点 **N10**、终点 **N5**。另有无人机起降点（M2/N8）。

这决定了几个**物理层面不可回避的约束**：

- 最小转弯半径 ~0.272 m > 格距 0.35 m 的可切角余量 ⇒ 180° 掉头**不可能**靠连续转向完成，必须有**原地转向（PIVOT）**这一级动作；
- 隔板无缺口 + 桥洞只在 K 列 ⇒ 全场拓扑被压成"必须两次穿 K 列"的环，路线不是自由的；
- 靶位射击需要**停车稳定**（画面静止才能开火），⇒ 打击是路线上的"停站"而非"边走边打"。

### 1.2 三个子系统

| 子系统 | 职责 | 代码 |
|---|---|---|
| 循迹底盘 | 沿 token 路线行驶、到达判断、安全边界 | `dzbrain`（本项目核心）|
| 云台射击 | 扫描→锁定→视觉伺服→开火 | `dzrknn_dataprocess` + `dzjudgment` + `rknn_pt`（C++，上游血统）|
| 机车链路 | 与无人机交换桥洞/靶区/雷障情报 | `dzbrain/io/drone` + `/dzlink/*` JSON 话题 |

## 3. 系统架构全景

### 3.1 分层与数据流

```
视觉层  rknn_pt(检测模型) ──/offset_center──▶ dzrknn_dataprocess(云台自瞄C++)
                                              │ /aim/status /shoot_count
决策层  dzbrain(Python, 8线程) ◀──────────────┘
        │ 订阅 /odom/localization(格) · /imu_data · /HpAndHitmsg(裁判)
        │ 发布 pursuitAngle(舵角°/速度) · /aim/fire_gate · /aim/fire_ready · /nav/scan_request ...
硬件层  dzchassis_driver(底盘C++) ◀──pursuitAngle──  serial_reader(里程计)
        dzjudgment(裁判串口) ──▶ 激光发射
```

- 所有几何量以**格**为单位（×0.35=米），换算**只在契约层**做——这是防止"单位散落"的核心纪律。
- 例外坑：`pursuitAngle.angular.z` 是**度**（ROS 惯例是弧度）、`pursuitAngle` 与 `nav/manual_gimbal` **无前导斜杠**（历史命名，勿"顺手规范化"）。

### 3.2 ROS 话题契约（唯一真源 `src/dzbrain/dzbrain/io/contract.py`）

| imu | `/imu_data` | `sensor_msgs/Imu` | rad/s, m/s² | |

| aim_status | `/aim/status` | `std_msgs/Int32` | 0=IDLE 1=SCAN 2=TRACK | 云台状态机 |
| shoot_count | `/shoot_count` | `std_msgs/Int32` | 累计发数 | |

### 3.3 dzbrain 内部（8 线程 + 事件总线）

- 线程：**localization**（50 Hz 里程积分）· **safety**（越界/停滞/冷启动宽限）· **tracker**（路径投影+到达判断+12 s 兜底超时）· **mission**（站点切换/PIVOT 检测/射击时机）+ 4 个 IO/辅助。线程间只经**事件总线**（`core/events.py`，EV_* L24-50）与**黑板**通信，禁止直接互调。
- 入口 `main.py`：门禁（validate+config 校验）→ `build_tasks`(L109) → 起跑。CLI：`--dry-run`（只做门禁）· `--plan-only` · `--bench`（FakeBridge 无车联调）· `--drive` · `--speed-factor` · `--seconds` · `--force`（应急绕过门禁）。
- **纯追踪控制器**：自适应前视 ld=clamp(k_v·v, min, max)；曲率式舵角 δ=curvature_gain·atan(2L·sinα/ld)；曲率限速 v=√(a_lat/|κ|)；舵角速率限幅 120°/s。
- **PIVOT**：换向角>135° 触发，触发距离随速度加长（lead·(v−v_ref)，钳到 0.32 m），蠕动转向到航向 ≤15°，硬超时 14 s。设计推导在 `core/config.py` L80-112 注释，`test_pivot.py` 会现算卡死错误值。
- 几何唯一真源：`core/geometry.py`——所有里程/投影/偏差从这出。

### 3.4 配置与路线语言

- **SCHEMA 注册制**（`core/config.py` L63 起，**141 键/10 组**：pursuit 49 · aim 35 · mission 18 · fix 16 · drone 9 · route 5 · safety 4 · localization 3 · telemetry 1 · logging 1）。每键 `Spec(默认,类型,单位,下限,上限,说明)`；缺键用默认并记 `default-used`，超范围/未知键告警不静默。业务代码出现第二个裸数字常量即违规。
- **路线 token 语言**（`route/parser.py`）：格名（A1~N11）+ 动作前缀（SHOOT 停站/PIVOT/REV 倒车…），兼容旧语法。校验器 `validate.py` 的 **R001~R014 编号稳定、只能追加 R015+**：

| 规则 | 级别 | 语义 | 规则 | 级别 | 语义 |
|---|---|---|---|---|---|
| R001 | error | <2 点不可循迹 | R008 | error | 段/run 级分段规则 |
| R002 | error/warn | 格名非法/起点不一致 | R009 | error | 未沿 K 列**列内**穿洞 |
| R003 | error | 跨越隔板行 | R010 | error | 相邻航点重复 |
| R004 | error | 航点踩障碍格 | R011 | error/warn | 段长过短/过长疑似漏点 |
| R005 | error | 雷覆盖不全 | R012 | error | 完全没经过掉头列 |
| R006 | error | 无射击停站点，靶打不到 | R013 | error | 停站点距靶不在窗口内 |
| R007 | error | 过洞行域规则（标定短路线必红属预期）| R014 | warn | 倒车段占比过高 |

- 场地常量（BARRIER/CROSS/U_TURN/MIN_SEGMENT）集中在 validate.py 顶部 L36-63；**换图=改 map.yaml + 这里的常量**。
- 规划器 `route/planner.py` 可从 map.yaml 自动生成 token（需带 `pivot_penalty: 5.0` 才与人工验证路线一致——史实：无惩罚时曾产出 F10* 分叉路线）。

## 4. 关键设计决策与权衡（理解项目的钥匙）

每条：**决策 → 为什么 → 代价**。

| 决策 | 理由 | 代价/局限 |
|---|---|---|
| 纯追踪（lookahead+曲率限速+速率限幅），不引入 NMPCC/优化器 | 简单可解释、可离线仿真回归、参数有推导 | 急弯必然切角，物理下限 RMS≈0.12 m；复杂避障能力为零 |
| PIVOT 作为一级动作 | 最小转弯半径 0.272 m > 格距可切角余量，180° 掉头物理上做不出来 | 到达判定与 PIVOT 交互复杂（曾致 5 航点被超时跳过）；实车偏慢（G10 用 36.4 s 超 14 s 阈值）|
| 单位换算收口在契约层（格↔米、度↔弧度） | 防止旧版"散落乘 0.35"的病 | 每个新话题必须三同步；跨包传值的人必须知道单位 |
| R 规则编号化校验 | 换图后机器可验证路线合法性 | 标定短路线"必红属预期"，不懂规则的人会误判为 bug |
| 配置 SCHEMA 注册制 | 显式默认+范围+单位，杜绝静默错值 | 加参数必须动 schema，有一定样板成本 |
| 三层验证（测试→仿真→实车） | 仿真含里程误差/延迟/噪声模型，指标基线逐位可复现；大量 bug 在"本地可测"阶段就被抓出 | 仿真**不覆盖**云台/射击/ROS 真链路——射击问题只能实车调 |
| 纯脚本测试（无 pytest） | 车端/本机零依赖一致运行 | 无标准报告框架，断言计数靠解析输出；需要纪律防"兜底吞断言"（曾发生，已改兜底必红）|
| 线程只经事件总线/黑板通信 | 防死锁/竞态（曾有 `self._stop` 遮蔽线程方法直接崩的事故）| 调试链路间接，读代码需跟事件流 |
| 本地唯一真源 + 车端只读 + 人类最终上车 | 防车上状态漂移、可追溯 | 车端 2.3 GB 非 git、无回滚；部署链路可靠性要求高 |
| DSH 插件内嵌工具条 | 开发时车端操作集中在一个 GUI | 插件有独立的坑史（Eruda 浮窗因 `style.all=initial` 破坏 React 容器 + `destroy()` 删 React 节点而下线，教训已由测试钉死）|

## 5. 验证体系与证据边界（哪些结论能信到什么程度）

这是防止"把仿真当实车、把测试当真链路"的关键一节。

### 5.1 三层证据

| 层 | 工具 | 能证明 | 不能证明 |
|---|---|---|---|
| 测试 | 29 套纯脚本（2026-10-11 当时口径；**2026-10-17 实为 33 套**：新增 `test_incremental_plan.py` 等，见 `docs/发车门禁口径.md` §G1–G4）（`src/dzbrain/tests/`，2026-10-11 起含 `test_shutdown.py`、`test_planner.py`），共享 fakes/harness | 几何、契约、R 规则、控制回路、安全逻辑的确定性行为 | ROS 真链路、时序、云台/射击 |
| 仿真 | `python -m dzbrain.tools.sim_cli` | 全程可跑完+指标基线：**135.00 s / 6750 拍 / 横向RMS 0.1168 m / 越界 0 拍 / 倒车段 16.38 s**（逐位可复现）；里程误差/延迟/噪声注入下的鲁棒性 | 射击、视觉、真实地面摩擦；实车漂移比仿真假设大（实车 K7 偏差 0.345 m vs 仿真 ≤5.8 mm）|
| 实车 | 0.7 m 短验证段 → 全长 | 一次完整 16.45 m 全程：N5 FINISH、SAFE_STOP/pose_lost/out_of_bounds 均 0 | 复现性（只跑过一次完整全程）；射击命中（实测发 3 中 0）|

### 5.2 证据不足区（提建议时应视为"未知"而非"没问题"）

1. **射击命中率**：实车 0/3，原因是目标丢失闭锁/预测落点出框——未定位到单点根因；
2. **移动靶打击**：静态靶之外的能力，代码层有 15 条已知缺口（见 `survey_gimbal_fire.md`）；
3. **PIVOT 到达修复**（`fcf09b9`）：仿真中该路径**从不触发**（门槛求值 4000 次 0 次命中顶点），仿真全绿只证明"未伤主流程"，**修复本身只有实车能验证**；
4. **无人机链路实车**：话题契约完备，但机上跑通记录不完整；
5. **bench 到点数**：必须独占 CPU 跑，并发时同版本在 9~22 之间波动，**横向比较无意义**。

### 5.3 回归守护硬判据（卡 t12 登记；**只增不改**）

> 本节把两条已经付过代价的经验固化成**可照抄的口径**。今后回归/门禁一律引用，不再临时解释。

#### 判据 1：测试不得依赖机器负载 —— 规划类调用一律**显式传预算**

> **硬判据**：任何**测试/门禁**代码调用规划类入口（`plan_route` 及其包装）时，**必须显式传 `max_seconds=`**，
> **不得**依赖 `planner.DEFAULT_MAX_SECONDS` 的默认值。默认值是**给线上跑的兜底**，不是测试预算。

- **范式（现场实例，照抄即可）**：`src/dzbrain/tests/test_planner.py:55` 定义常量
  `TEST_PLAN_BUDGET_S = 10.0`，并在**三处** `plan_route(...)` 调用显式传入
  （`test_planner.py:645`、`:647`、`:663`）。语义：预算放宽**不改变规划结果**（同一份搜索、同一份输出），
  只让"测试是否通过"取决于**规划结果**而不是机器负载。
- **代价实例（t8 门禁抓到的 flake）**：`planner.DEFAULT_MAX_SECONDS` 旧值 **0.8 s**，
  而本机单次该规划实测 **0.55~0.58 s**（8/8 次 548~569 ms）⇒ **余量只有 ~0.25 s**；
  空闲时 0.58 s 能过，**4 忙核**下 0.89 s 稳定超时。表现为"单跑 5/5 绿、全量门禁红"，
  曾被误当成真回归并阻塞验收条款。
- **双保险现状**（t7 已落地，未提交）：① `planner.py:218 DEFAULT_MAX_SECONDS = 2.0`（= `planner.max_seconds` 现场真源）；
  ② 测试侧仍**显式**传 10 s。**注意：①不能替代②** —— 只要还有调用方吃默认值，负载敏感就会回来。
- **判别法**（见到红项先做这一步）：单跑该套件连跑 5 次全绿、而全量/满核跑红 ⇒ **先怀疑负载敏感**，
  按本条加显式预算；不要在判据里加"重试"或"放宽阈值"来掩盖。

#### 判据 2：known-red 一律显式台账，不得临时口头解释

  每条带**断言位置（文件:行）**、实测值、出处日志。
- 事故来源：t8 门禁曾因"把挂账红误当本次改动引入的失败"而**阻塞验收条款**；

#### 判据 3：门禁/复核报告必须记录被复核文件的 SHA256（修订冻结）

> **硬判据**：任何**门禁/复核/验收**报告，必须在正文（建议 §1「复核对象与 revision 冻结」+ 报告附录）给出
> **被复核的每一个源码/配置/测试文件的 SHA256 与 mtime**，**一文件一条**。没有哈希清单的报告，
> 评审方**不得**据此判定 pass —— 因为"复核的到底是哪一版"不可追溯。

- **为什么需要**（事故来源，t9 报告 O1，medium/流程）：本工作区**存在并发写入者**。t9 复核期间，
  被复核的 `src/dzbrain/dzbrain/main.py` 在**复核窗口内被其它卡改了两次**（**16:56:29**、**17:04:59**，
  后者注释自称"卡 t11"，同批还改了 `mission.py` / `test_autoplan.py` / `core/config.py` / `route/physics.py`）。
  该轮最终靠**逐行 `Compare-Object`** 才确认 t8 的改动零删改（`OLD-ONLY` 只有 hunk 头与 blob 行；
  `NEW-ONLY` 全是他人新增横幅，关键锚点仍在、仅行号位移，如 `if not alive()` 455 → 458）。
  ⇒ 结论虽对，但**成本高且差点不可追溯**：哈希清单能把这个判断从"逐行考古"降为"一次比对"。
- **范例（照抄这张表的形状；来源 = t9 报告 §1，t15 已用当前工作区逐文件复核，6/6 逐位相同）**：

  `src/dzbrain/tests/test_shutdown.py` 已变（`4F372A427D9922561C82` → **`CCBF17DDADC9573CDE9F`**，mtime 16:40:29 → **17:08:11**），
  其余 5 个文件**仍然逐位一致**。该文件是**未跟踪新文件**（`?? src/dzbrain/tests/test_shutdown.py`），

  ⇒ **处置**：任何引用 t9 结论的后续复核/门禁，必须对 `test_shutdown.py` **重跑核验**（按判据 1 的显式预算口径），
  不得直接沿用 t9 的 `39/39`；`4F372A42…`/`CCBF17DD…` 两个哈希都要写进报告。
  ⚠️ 该文件此刻仍在被并发写入者改动：**17:08:27** 再算已是 **`1537FFE2B303D6EAE75F`**（mtime 17:08:27）
  ⇒ 本卡在 **16 分钟内**目睹该文件 **3 个不同修订**（`4F372A42…` 16:40:29 → `CCBF17DD…` 17:08:11 → `1537FFE2…` 17:08:27）。
  两个偏差行都保留、不改写 —— 这就是"只追加、不改写历史行"的实际用法；复查时以当场测得为准。
  该文件在本卡观察窗内继续变化（17:08:33 又变），故**不逐个追写每一次变化**；结论只有一条：
  **该文件处于写入风暴中，其任何哈希都是"时刻快照"，复核/门禁必须当场重算判定，不得引用历史值。**
- **约定**：表内 hash 写 **前 20 位十六进制**即可（t9/t15 均此格式，够用且便于肉眼比对）；
  需要机器校验时用完整 64 位。每份报告**只写自己真正复核过的那一版**，不要写"当前值"；
  若复核后文件又变，**不要改写历史行**，而是**追加一行**"复查时刻 + 新哈希 + 处置"（本卡上面那条即此写法）。
- **报告模板（最少 5 项）**：① 文件路径；② mtime；③ SHA256 前 20 位；④ 该版是否 = 交付版（若已被人改，写明"由某时刻捕获的 diff 固化"）；
  ⑤ 我的哪些测量覆盖该版（对齐运行时刻表，t9 报告 §1 下半张表即此用途）。
- **复查（不是重审）怎么用**：**哈希一致** ⇒ 直接沿用结论；**哈希不一致** ⇒ 该文件**必须重跑核验**
  （另加判据 1 的预算口径），并在报告里记录两个哈希与差异原因。
- **反面教材（同族、同本质）**：`docs/回归守护_known_reds.md` §3③ 记录 `test_sim_guard 3.5b` 的 `diverged`
  值对不上 t10 基准 —— **恰好发生在 `config/robot.yaml` 被并发改写之后**（其 mtime 16:30:24 晚于两轮日志 16:48:48 / 16:51:54）。
  两起事故同因：**先有并发写入、后缺"被复核对象指纹"**。
- **禁止的替代做法**：靠"行号"或"我记得当时看过"来锚定 revision（行号会随他人插入位移）；
  拿"当前文件哈希"冒充"复核时的哈希"（那正好抹掉并发写入的痕迹）。
- **适用边界**：哈希只解决**对象同一性**，**不替** 内容审查 —— 哈希一致 ≠ 复核通过；
  反过来，**任何**复核报告（含 kind=review/verification）缺哈希清单 = **流程缺口**，应记为 finding（低/中），不放大成"代码有问题"。

#### 判据 4：变异/临时副本可丢弃，但转录必须先导出并记哈希

- 变异测试（mutation）的**副本目录**（如 `_tmp_verify/*/mut/`）占空间且会污染文件发现（实例：t14/t16 的
  `test_calib_backfill` 100/101 假红），**允许删除**；
- 删除前必须：① 把决定性**转录输出**（`*.out`/`*.err`）导出到副本目录之外；② 每份转录记 **SHA256** 并落盘清单
  （实例：`_tmp_verify/t9/mut_清账_删除前.md`）；③ 保留可重建副本的**变异定义脚本**（实例：`mutants.ps1`）。
- 未经上述三步，**不得**删除变异副本目录。

#### 判据 5：测试文件凡把真源 `sys.path.insert(0, …)` 钉在最前，必须支持 `DZ_PKG_ROOT` 覆盖并**自证覆盖生效**

- **事故两连发（同根）**：t14 发现 `test_shutdown.py` 的 `insert(0, src/dzbrain)` 赢过 PYTHONPATH ⇒ t9 的 5 个变异体
  "全被拦住"实为**假绿**（导入的是真源）；t17 复验时又发现 `test_safety.py` 只有 `insert(0)`、**没有**覆盖通道 ⇒
  M1/M2 第一版矩阵同样假绿（exit=0、FAIL=0）。两处均已在 t14/t17 修复。
- **硬要求**：任何测试文件若用 `sys.path.insert(0, …)` 固定真源位置，必须：① 支持 `DZ_PKG_ROOT` 环境变量
  **覆盖到 `sys.path[0]`**（变异/副本场景用）；② 加一条 `⓪ 覆盖自证`断言——覆盖未生效立即红；
  （实例：`SAFETY_NO_OVERRIDE=1` 负向对照可复现假绿，见 `_tmp_verify/t17_negative_no_override.log`）。
- **审查清单**：新增/改动测试文件时，grep `sys.path.insert` 与 `PYTHONPATH` 混用的文件，按本条核对。

## 7. 风险、弱点与技术债（发展建议的靶子）

**架构级**
- 云台自瞄 C++ 的 `callback_offset_center` 是 **300 行单函数** + 130 行参数样板，状态耦合严重（重写拆分建议已在 `survey_gimbal_fire.md`）；
- 视觉链路是 FIFO 流水线，预判仅 0.5 帧而链路延迟 0.5~0.9 s（移动靶打不准的结构性原因之一）；
- 射击链路**不订阅裁判回传做闭环**（有 referee_hp 真源但云台侧闭环未建）。

**数据/参数级**
- 标定值仍是跑偏根因旧值，且实车漂移显著大于仿真假设 ⇒ 所有基于仿真的精度结论都要打折；
- 路线存在版本分叉史（自动规划 F10* vs 人工验证 G10*），靠 `pivot_penalty` 收敛——新增规划逻辑时此坑可能复现。

**工程级**
- 工作区被**多会话并发写入**，无锁；车端 2.3 GB 非 git 无回滚；
- 备份在同一块盘（`backup/` 亦被 gitignore），防误删不防磁盘坏；`.gitignore` 排除了约 2.3 GB（附加资源/模型/build），git 备份**不含**这些；
- `test_deploy.py` 的锚点断言（"7/8 循迹"、`5b_aimshim`）对路线变更脆弱，改路线常量必须同步改它；
- `healthcheck.sh` L337 遗留 `head -1`（同类问题 L363 的 `tail -1` 已修，此处未修）；
- 知识靠 `src/history/log/` 会话日志转生，文档与代码行号会漂移，存在"文档说的和代码不一致"的慢性风险。
