## 0. 一句话结论

新版本的**决策层（dzbrain）已经是一个可跑、可测、可解释的多线程系统**：纯追踪循迹 +
云台瞄准打击移动靶 + 误差修正 + 无人机通信，8 个任务线程共用单执行器，**19 套测试 1340 条断言全绿**、
离线三层仿真 **34 点全程跑完 / 横向 RMS 0.1168 m / 越界 0 拍**；
**实闭环 bench 也从"卡在第 13 点"变成"全程跑完"**（`阶段 DRIVE → FINISH`、193.7 s、8 线程零错零超时）。

本轮挖出并修掉 **5 个"看代码都正常、上车才发现"的静默缺陷**：
① **裁判命中闭环是死的**（契约声明了 `/referee/hit`，全仓库却没有生产者）；
② **PIVOT 在 180° 折返处必然卡死**（超时值比物理转弯时间还短；修完又暴露"成功后无限重入"）；
③ **自重叠折返段的投影振荡**（命令每拍翻转、车原地抖 601 次）；
④ **PIVOT 与停滞看门狗数值撞车**（正常折返被当成"绕圈"跳点）；
⑤ **倒车段折返把车头转反 180°**（用"行进方向"当"车头朝向"，折返全由倒车完成才对）。
全部靠**实闭环 bench 实跑**与**对硬件源码逐行走查**抓到，不是靠"看起来对"。

## 2. 架构：8 个任务线程（单 `MultiThreadedExecutor`）

| 线程 | 频率 | 职责 |
|---|---|---|
| `Localization` | 20 Hz | 里程计 → 地图位姿、锚定吸附、漂移告警、前向投影 |
| `SafetyTask` | 20 Hz | **唯一有权强制停车者**：越界、定位超时、任务停滞、故障刹车 |
| `TrackerTask` | 50 Hz | 纯追踪循迹（PIVOT / 切角 / ALIGN 都在这一层） |
| `MissionTask` | 10 Hz | 阶段机（IDLE→DRIVE→…）、停站点、扫描请求、开火总闸 |
| `AimTask` | 50 Hz | 目标观测 → 提前量 → 开火判据 → **命中记账/停火** |
| `FixTask` | 10 Hz | 误差修正（估计侧比例估计、漂移剔除） |
| `DroneTask` | 5 Hz | 无人机链路（心跳/情报/车状态回传） |
| `TelemetryTask` | 2 Hz | 遥测汇总（每 0.5 s 一条） |

设计上把「谁有权停车」收敛到一处（Safety），其余线程只提请求 —— 避免旧版"人人可刹车、
责任不清"的混乱。

## 3. 循迹核心：纯追踪 + 并入 10-05 核心的三处已验证修复

| 修复 | 解决的问题 | 关键参数 |
|---|---|---|
| **PIVOT 原地转向** | 大角度换向（现场 F11 的 180° 折返）纯追踪会画大弧，横向偏差 0.37~0.41 m，而那里是**压雷段** | `pivot_angle_deg=135`、`pivot_dist_m=0.25`、`pivot_speed_mps=0.08`、`pivot_timeout_s=14.0` |

是本项目自己标注的缺口）。本轮发现它的两个真 bug，见 §6。

## 4. 云台瞄准与打击移动轨道靶

- **移动靶估计**：`RailEstimator` 用**长基线端点差分**求速度（不是相邻帧差分，抗抖动）；
  提前量 `lead_px = v_dx × lead_time_s`，`aim.lead_time_s=0.35`。
- **开火策略**：`fire_policy=moving_lead`（预测落点进动态框 + 连续 N 帧），
  另有 `sweep`（等目标扫过瞄准线）可用；`turnaround` 因本靶**瞬时折返无端点停顿**不可用。
- **距离自适应开火框**：`fire_box_px` 随框宽（≈距离）插值 14~26 px。
- **折返闭锁三道闸**：防止在靶折返的瞬间把子弹打在轨道端头。
- **双钥匙开火门控**：`/aim/fire_gate`（MissionTask 给）**且** `/aim/fire_ready`（AimTask 给）
  同时为 1，C++ 云台补丁才允许开火 —— 任一侧单独失效都不会误开火。
- **命中即停火 + 单靶 3 发 / 全场 10 发**：省弹药是刚需（见 §5）。

## 6. 本轮重点 ②：PIVOT 的两个真 bug（都由实闭环 bench 抓到）

实闭环 bench：`python tools\dzbrain.py --bench --drive --seconds 240`（FakeBridge + 虚拟小车 1× 实时）。

### 6.1 超时预算与物理不符 —— 原值「触发即超时」

- **现象**：E11 的 180° 折返处 `PIVOT 触发 → 8.0s 硬超时 → 半路放行`，车带着错误航向继续跑。
- **手算**（Ackermann，最小转弯半径 `R = L/tan 舵角`）：
  `偏航率 = 0.08/0.157 × tan30° = 0.294 rad/s = 16.9°/s`
  ⇒ 135°（触发阈值）需 **8.01 s**、180°（现场折返）需 **10.68 s**，再加 0.5 s 刹车等待。
  **原 8.0 s 比触发阈值所需的 8.01 s 还短** ⇒ 只要触发就必定超时。
- **修复**：`pursuit.pivot_timeout_s` 8.0 → **14.0**（对 180° 留约 25% 余量）。
- **防回归**：`test_pivot.py` 第 5 组按配置**现算**物理转弯时间，卡住 `timeout ≥ 需求×1.15`。

### 6.2 成功后无限重入 —— 车被永久钉在顶点（更严重）

- **现象**（修完超时值**之后**仍复现 ⇒ 与超时无关的第二个 bug）：

  ```
  ★ 进入 PIVOT（顶点 s=4.20 距 0.20m / 换向 180° > 阈值 135°）
  [T] F11 DRIVE (-0.058,3.127) yaw-105.0 v0.000 st+0.0 | 段12 s4.43/34
  ✓ PIVOT 完成：航向误差 +15.0° ≤ 15°（用时 0.5s）
  ★ 进入 PIVOT（……）        ← 下一拍又来，周而复始
  ```

  整场 240 s 卡在 `s≈4.4/34 m`（几百次循环），车每拍先被刹车 0.5 s，几乎不动。
- **根因**：`_pivot_abandon_until_s`（「该顶点已处理」标记）**只有超时分支设**，成功分支漏了。
  车完成转向后**仍停在顶点邻域内**（< `pivot_dist_m`）、换向角依旧 > 阈值 ⇒
  下一拍重新满足触发条件 → 0.5 s 刹车 → 再"完成" → 无限循环。
- **修复**：成功分支与超时分支**对称地**设同一个标记（2 行）。
- **测试有牙**：`test_pivot.py` 第 6 组构造最坏情况（车停在顶点不动 + 车头已落进容差），
  要求 3 s 内只进入 1 次、只完成 1 次。**撤掉修复后本组立刻红**（3 s 内进入 6 次、完成 6 次）。
- **bench 复验（修复后）**：`进入/完成/超时 = 1/1/0`（修复前是几百次循环），车越过 F11 继续走。

### 6.3 自重叠折返段的投影振荡 —— 命令每拍翻转、车原地抖（第三个真 bug）

修完 6.1/6.2 之后 bench 仍有 12 次「拐角绕圈兜底」跳点（F8/B8/B6），日志签名完全一致：

```
[T] F11 DRIVE (0.002,2.878) yaw-50.5 v-0.080 st+30.0 | 段13 s4.55/34
[T] F11 DRIVE (0.005,2.874) yaw-49.5 v+0.120 st+30.0 | 段12 s4.55/34
[T] F11 DRIVE (0.005,2.874) yaw-49.5 v-0.080 st+30.0 | 段13 s4.55/34   ← 每拍翻转
```

- **根因（三层，缺一不可）**：
  1. **自指环**：裁决重叠段用的"行进方向"取的是**上一拍命令的速度符号**，而它又决定选哪条段、
     进而决定 `segment_is_reverse`、再决定命令符号 —— 首尾相接。仿真不中招，正是因为它用的是
     **真值速度**（`tools/sim.py:555`）：**仿真与实车代码在这一点的语义不一致，仿真绿掩盖了实车会卡。**
  2. **搜索窗口按"段"取而不是按弧长**：`i_first = seg_index_at(lo)` 之后首段被**整段**搜索，
     `t_floor` 只在 `allow_backward=False` 时生效 ⇒ 向后搜索限位形同虚设（共线折返的两条段
     正好落在同一个首段区间里）。
  3. **等距裁决顺序错了**：折返的去程段与回程段**完全共线** ⇒ 同一物理点到两条段**等距**，
     而两条候选的 s 相差整整一段。旧代码**先比行进方向**，方向又由命令决定 ⇒ 两个互相自洽的
     吸引子互锁，每拍翻转、永不收敛（实测 24 s 内 **601 次**翻转、位置毫米级抖动）。
- **修复**：
  - 等距裁决改为**先比与上拍投影的连续性（弧长）**，方向只在连续性也分不出时用
    （典型正是折返顶点：两条候选的 s 相同）。连续性给出的是**稳定不动点**，
    这也正是自重叠路段唯一有意义的语义 —— 沿路线连续推进。
  - 窗口下界 t 钳制改为**无条件按弧长生效**；新增 `pursuit.projection_rewind_m=0.15`
    （单拍最大回退量；正常运动每拍只走 2.4 mm，15 cm 绰绰有余）。
  - `travel_heading` 改用**实测位移方向**（位移小于门限时锁存上次可信值），不再用命令符号。
- **测试有牙**：`test_tracker.py` 第 8 组用 **bench 同款积分模型驱动真实 `TrackerTask`** 跑 24 s：
  修复后 s 走到 0.689/0.70、翻转 125 次、**尾 4 秒 0 次翻转**；把裁决顺序改回旧版立刻红
  （s 卡在 0.552、456 次翻转、尾段仍抖 170 次）。
- **无回归**：离线三层仿真指标**逐位不变**（135.00 s / RMS 0.1168 m / 越界 0 拍）。

### 6.4 PIVOT 与停滞看门狗"数值撞车" —— 正常折返被误判成绕圈跳点

修好 6.1/6.2/6.3 之后 bench 出现了**新的**误判（修好一个 bug 会暴露下一个）：

```
⚠️ 拐角绕圈兜底：航点 F11（#13）停滞 12.1s / 累计转 170° 仍不可达，强制跳过
⚠️ 拐角绕圈兜底：航点 A6（#18）停滞 12.0s / 累计转 192° 仍不可达，强制跳过
⚠️ 拐角绕圈兜底：航点 D6（#20）停滞 12.0s / 累计转 160° 仍不可达，强制跳过
```

- **根因**：两条停滞判据与"正常 180° 折返"**在数值上正面撞车**：
  - 180° PIVOT 实测要 **~10.8 s**（`v=0.08 m/s`、最小转弯半径 `L/tan30° = 0.272 m`）
  - 停滞判据①：`mission.stall_timeout_s = 12 s` 内 s 不前进
  - 停滞判据②：停滞期间累计转向超过 `mission.stall_yaw_deg`（PIVOT 期间转 ~180°）
  也就是说：**PIVOT 被修成"真的会转"之后，每一次正常折返都会被判成"原地绕圈"**。
  跳点 = 漏压雷 / 漏打靶，必须修。
- **修复**：`MissionTask` 读 Tracker 遥测里的 `pivot_phase`，PIVOT 非 IDLE 时**整个停滞窗口重置**
  （不是只忽略这一次判定）。PIVOT 自带 14 s 硬超时且必然自终止 —— 看门狗的本意是
  "防无界空转"，不是"防有界机动"。
- **测试**：`test_mission` 新增 10.12 / 10.13 —— PIVOT 中（4 s > 超时 2 s、累计转 600° > 阈值 60°）
  0 跳点；机动结束后停滞判定照常生效（**豁免不是永久免疫**）。

### 6.5 倒车段折返：PIVOT 把车头**转反 180°**（bench 剩余跳点的总根源）

- **根因**：PIVOT 判据与目标航向用的都是**行进方向**，而车要转的是**车头**。下一段是倒车段（`R:`）时两者差 180°：

  | 现场 `F10→F11→E11→R:F11→F10` | 行进方向 | 车头朝向 |
  |---|---|---|
  | seg1 = F11→E11（正向） | +90° | +90° |
  | seg2 = E11→R:F11（**倒车**） | −90° | **+90°** |
  | 顶点处夹角 | **180°**（旧判据 ⇒ 触发 PIVOT） | **0°**（车头一度都不用转） |

  车本来就该**保持车头、倒着原路退回**；旧代码却按行进方向把车头转到 −90°（**反了 180°**），
  之后投影还贴在前一段（换段靠实测位移，而车头已反）＋ 纯追踪又往回转 ⇒
  `v` 在 +0.150/−0.080 之间反复翻、`yaw` 一直转、每 12 s 触发一次「绕圈跳点」。
- **修复（两半，缺一不可）**：
  1. **几何层**新增 `car_heading_on(seg)`（该段的**车头**朝向）与 `corner_turn_deg(seg)`（顶点处**车头**要转的角度）；
     `corner_angle_deg` 的文档写明它只是"行进方向夹角"，别拿它判车头动作。

# §11 续报二：弧长地板（F11 交界振荡）与一个设计结论

## 11.1 本轮修复：投影加「弧长地板」

**症状**（确定性探针实测，现场 F11 簇 `F10→F11→E11→R:F11→F10`）：车倒车回到 F11
（`seg12 E11→R:F11` 倒车段结束、`seg13` 正向去 F10）后**永久振荡** ——
30 s 内 **715 次**命令符号翻转、位置冻在毫米级；bench 表现为「拐角绕圈兜底」每 12 s 跳一个点。

**根因（三重叠加，前两个是老问题的变体）**：
1. 两条候选（倒车段末端 / 正向段起点）的 s 都在顶点附近、Δs 几乎相同 ⇒ 第①顺位
   「连续性裁决」分不出来；
2. 于是落到第②顺位「行进方向」，而方向由命令符号决定、命令符号又由 `is_rev` 决定 ⇒ 自指环；
3. 此时车**真的**在抖（0.08~0.15 m/s × 0.02 s = 1.6~3 mm/拍），**大于**行进方向的锁存门限
   1 mm ⇒ 连"实测方向"也每拍跟着翻。

**修法**：`path.project(..., s_min=)` 新增**弧长地板**（已走过的顶点不允许退回去），
与仿真 `_project_with_floor` 同语义；Tracker 在投影**贴到**顶点 5 cm 内时抬升地板
（贴到就抬升，不是越过才抬升——越过的下一拍可能已被另一条共线段抢走），路线切换时复位。

**证据**：
| 指标 | 无地板 | 有地板 |
|---|---|---|
| 命令符号翻转 / 30 s | 715 | **2** |
| 段号切换次数 | 716 | **5** |
| 沿程 s | 冻在 1.067 | **推进到 3.298/3.400** |
| bench 绕圈跳点 | 11 | **8**（F11 已从清单消失） |
| bench 到点 | 17 | **22** |

`test_tracker` 新增第 9 组复现该场景：把地板关掉 4 条断言立刻红（715 次翻转）—— 测试有牙。
全量回归 **19 套 / 1380 断言全绿**；仿真指标**逐位不变**。

## 11.2 ★设计结论：PIVOT 在**现场路线上永不触发**

用真实 `config/robot.yaml` 的 34 个 token 逐段算出「**车头**实际需要转的角度」：

| 段 | 块对 | 行进° | 倒车 | 车头° | **车头转角°** |
|---|---|---|---|---|---|
| seg11 | F11→E11 | 90 | 否 | 90 | **0** |
| seg12 | E11→R:F11 | −90 | **是** | 90 | 90 |
| seg17 | B6→A6 | 90 | 否 | 90 | 0 |
| seg18 | A6→R:B6 | −90 | **是** | 90 | **0** |
| seg19 | B6→R:D6 | −90 | **是** | 90 | 0 |

**全路线车头转角 ≤ 90°**，而 `pivot_angle_deg = 135°` ⇒ PIVOT **一次都不会触发**
（bench 实测 `进入 PIVOT 0 / 完成 0`，与推导一致）。

含义：10-05 核心引入 PIVOT 的依据是"F11 那个 **180°** 折返"—— 那是**行进方向**的夹角；
按**车头**看它根本不是调头，而是"**倒着原路退回**"（`R:` 段）。也就是说：

> **PIVOT 是在解一个由「行进方向 vs 车头朝向」混淆造成的假象问题。**
> 真正的机制是「倒车段 + 投影换段」，而后者此前是缺的（本轮与上一轮补上）。

这不代表 PIVOT 无用（对**真正的**正向调头仍然需要，`test_pivot` 里用
`B6→A6→B6` 两条正向段构造的 180° 场景仍在测它），但**现场这条路线上它是死代码**。
上车后若发现某个顶点确实需要调头，那说明路线 token 该标 `R:` 或该处车头转角真的 >135°，
届时 `corner_turn_deg` 会如实算出来。

## 12.1 本轮修复：体检脚本没检查新核心

`tools/healthcheck.sh` 是出车前 30 秒体检脚本，但新版决策层上线后它**只体检旧架构**
（usb_cam / det_node / dzrknn / path_executor / serial_reader + `pursuitAngle`）。
跑一遍会拿到"全绿"，而新核心的契约一条都没查。两个最危险的"假全绿"：

| 假全绿 | 真后果 |
|---|---|
| 缺 `/aim/fire_ready` | 双钥匙开火门控不完整 ⇒ **云台永远打不出去**，而体检显示全绿 |
| `/HpAndHitmsg` 无数据 | 命中即停火 / 弹药对账**空转**，同样看不出来 |

新增 §4b（**自动降级，绝不误报失败**）：dzbrain 在线时查 `pursuitAngle` 保活速率
（底盘 1s 看门狗，零 Twist = 刹车；期望 40~60 Hz）、双钥匙两个话题是否都在、
`/HpAndHitmsg` 是否真有 ~1Hz 心跳、输入侧 4 个话题存在性；不在线时区分
`LEGACY_PATH=1`（走旧核，提示）/ 已安装但没起来（**报失败**）/ 未安装（提示回退）。

**验证方式**（本地无 ROS，用桩 `ros2` + Git Bash 做行为验证，四个场景逐行核对）：
| 场景 | 期望 | 实测 |
|---|---|---|
| A 齐全 | 9 项全绿 | ✅ 全绿 |
| B 缺 `/aim/fire_ready` + 保活 12Hz | ❌ + ⚠️ | ❌「门控不完整，云台不会开火」+ ⚠️ 保活异常 |
| C dzbrain 未安装 | ⚠️ 回退提示 | ✅ 符合 |
| C2 `LEGACY_PATH=1` | ⚠️ 符合预期提示 | ✅ 符合 |

`bash -n` 通过（`wsl` 无发行版，改用 Git Bash 检查）。
⚠️ 过程陷阱（已修）：`awk 'BEGIN{...}'` 不给输入文件会**读 stdin 卡住**，必须 `</dev/null`。
`test_deploy` 新增第 ⑤ 组 8 条**源码级**断言，把这份覆盖钉死（将来手滑删掉立刻红）。

## 12.2 上车前必须知道的三个提醒（都来自本地实测，不是猜）

1. **⚠️ `mission.auto_start: true` + 延时 10 s** —— 起栈后 10 秒车会**自行出发**。
   第一次务必架起来（轮子悬空），或先把该键改 `false`。部署工具里有 `auto_start` 归一化
   处理（`test_deploy` 有对应断言），但**默认值是自动出发**。
2. **⚠️ 倒车+转向 1 组：最长 1.05 m / 2 段**（`route_check` 报告）—— 现场路线里
   `A6 → R:B6 → R:D6` 是**两段连续倒车并且中间要打舵**，即"盲区里打舵"。
   参数侧若现场发现该处不稳，先调 `pursuit.reverse_speed_ratio`（当前 0.6）降速；
   路线侧若要拆开需要改 `config/robot.yaml` 的 token —— **这是现场决策，我不擅自改**。
3. **急转弯 17 处**（同一份报告）—— 与 `PIVOT 现场零触发`（§11.2）一致：
   全是 ≤90° 的直角/钝角，靠纯追踪 + 倒车段处理；若现场发现某处确实需要调头，
   那说明该处 token 该标 `R:`，或者 `corner_turn_deg` 会如实算出 >135° 并触发 PIVOT。

# §14 续报五：首次实车全程跑 —— 能跑，但暴露两个真车独有缺陷

## 14.1 发车：两处挡路的"实车独有"竞态都被修掉后，车真的跑起来了

本轮按用户"落地跑全程"发车（`auto_start: true` + 只重启循迹节点），**当场撞上一个
启动竞态**：车 `阶段 IDLE → SAFE_STOP`、一动不动，日志特征很怪 ——
只有一条 `启动宽限（0.02/3.0s）`、**没有**"❌ 宽限期已过"，却出现 `pose_lost`。

根因（`safety.py`，实车血证 2026-10-09 20:1x）：
- Localization 与 Safety 读**同一个桥**，但两任务**差一拍**：前者先 tick 把 `P_ODOM_AGE`
  写成 inf，后者后 tick 时桥**已经**有帧（`pose_age` 有限）⇒ 旧判据 `never_had_pose`
  为假 ⇒ 绕开宽限、落进"`elif pose_age==inf or odom_age==inf`"那条**无宽限无日志**的分支
  ⇒ 锁存 SAFE_STOP（安全刻意不自动恢复）⇒ 车不动。

修法（一条有实车依据的语义变更，已 commit `2280876`）：
- `_ever_had_pose` 以**桥的新鲜位姿**为准（`pose_age != inf`）；
- `P_ODOM_AGE=inf` 改为**持续性判据**（单拍容忍、持续 > `pose_timeout_s` 才致命）；
- `odom_age > timeout` 排除 inf（否则 `inf > 1s` 恒真，误报成 `pose_stale infs`）。
- fail-safe **未削弱**：桥失联仍立刻致命、不自动恢复（test_safety ③g/⑧/⑨/⑩ 全保留）。
- test_safety 151→**162 断言**全绿；全量回归 **20 套 / 0 失败**。

修完后**发车成功**：`复位 N10 → 阶段 DRIVE → APPROACH`，车沿 N10→M10→L10→L9→K9→J9→I9→H10
一路开（v=0.10~0.15，`安全OK 弹10 瞄TRACK`），倒车折返也进了（段12 v=-0.080）。

## 14.2 但跑到 F11 倒车折返时，车漂出界、安全刹停（两个真车独有缺陷）

**① 倒车段投影跟丢 → 漂出界**：进入段 12（`E11→R:F11` 倒车）后，**投影 s 冻在 4.20**
（E11 顶点）而车一直在倒、向西漂了 ~2 m（x 从 E11 的 1.575 漂到 **-0.439**），
越过左边界 `x_min=-0.425`（= 最左格心 0.175 − 0.60 余量）**1.4 cm** → `out_of_bounds`
→ SAFE_STOP → 锁存（刻意不自动恢复）⇒ 卡住。**这是 bench/仿真都没复现的**
（bench 的虚拟车倒车没问题）—— 第 13 轮加的"投影跟丢自愈"在倒车+地板交互下没拦住，
需专项复现与修复。

**② G10 射击停站点未完成**：`G10*` 停滞 37.8 s 后被"拐角绕圈兜底"跳过（`发0/中0`
= 一枪未发）。是"到站不停/瞄准未锁"还是"开火门控没放行"需查。

**好消息**：安全层工作完全正确（越界即刹、绝不自动恢复 = 没有失控）；裁判闭环
（`弹10` 真源）、云台瞄准（`瞄TRACK/SCAN` 切换）、循迹、倒车入口、定位锚定全部实测在线。
